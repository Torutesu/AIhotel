# AI予測とレベニュー担当予測の差異分析

対象機能: F-DP-11（担当者予測の記録と差異算出）／F-DP-12（差異の背景の明示と検証）

同じ宿泊日について、AIが出した予測とレベニュー担当が出した予測を並べ、
どこがどれだけ食い違っているかを出し、食い違っている箇所については
「どういう意図・背景でそう見ているのか」を残して、後から検証できるようにする。

価格判断の記録（F-DP-08〜10 / `docs/意向入力仕様.md`）とは別物。あちらは
「AI推奨価格に対して実際にいくらで売ったか」、こちらは「AIと担当者の見立てが
どう違うか」を扱う。

---

## 1. 何と何を比べるか

**初期予測どうしを比べる。** レベニュー担当が最初に立てた予測（`version=1`）と、
その時点のAI予測スナップショットが比較の基準になる。

理由は2つ。

- 予測は宿泊日が近づくほど実績に寄っていく。改訂後の予測どうしを比べても
  「両者とも直前に正解へ寄せた」だけで、見立ての違いが消える
- AI予測（`AiPriceRecommendation`）は再計算のたびに上書きされる。参照で持つと、
  再計算した瞬間に過去の差異が書き換わる

そのため `OperatorForecast` は記録時点のAI予測（稼働率・ADR・室数・売上・需要
レベル・確信度・モデルバージョン）をスナップショットとして焼き込む。

改訂は上書きせず `version` を増やして追記する。見立てがいつどう変わったかも
分析材料になるため、履歴を消さない。

---

## 2. 比較する4指標と、部分入力の正規化

| 指標 | AI側 | 担当者側 |
|------|------|---------|
| 稼働率 | `predictedOccupancy` | 入力 |
| ADR | `predictedAdr` | 入力 |
| 販売室数 | 稼働率 × 総室数で導出 | 入力または導出 |
| 売上 | 販売室数 × ADRで導出 | 入力または導出 |

担当者には「稼働率とADRで考える人」と「室数と売上で考える人」がいるため、
どちらの入り口でも受け付けて同じ4指標に正規化する（`deriveForecastMetrics`）。

- 稼働率 ⇄ 販売室数 は総室数（`Hotel.totalRooms`）で相互変換
- ADR ⇄ 売上 は販売室数で相互変換
- **明示的に入力された値は導出値で上書きしない**（稼働率80%でも「室数は155室」と
  言われたらそちらを残す）

AI側は稼働率とADRしか持たないので、室数・売上は同じ規則で導出したものを使う。
両者を同じ手続きで4指標に揃えてから比べる、というのがここの肝。

---

## 3. 差異の定義

```
稼働率の差 = 担当者 − AI            （pt。プラス = 担当者の方が強気）
ADRの差    = 担当者 − AI、および AI比の率
売上の差   = 担当者 − AI、および AI比の率
```

分母は常にAI予測側に置く。「AIの見立てを基準に、担当者がどちらへどれだけ
振っているか」を読む形にするため。

---

## 4. どこから「理由が要る差異」か

全件で理由を必須にすると形骸化し、全件任意にすると肝心の箇所が空欄で残る。
そこで**乖離幅の閾値を超えた日だけ意図・背景を必須**にする。

| 閾値 | 既定値 |
|------|--------|
| 稼働率 | 5pt 以上 |
| ADR | 5% 以上 |
| 売上 | 10% 以上 |

ホテルごとに `ForecastVarianceSetting` で変更できる（MANAGER以上・監査対象）。
判定はいずれか1つでも超えれば「基準超え」。どの指標で超えたかも返し、画面では
「基準超え: 稼働率・売上」のように示す。

必須チェックはzodではなくサービス層で行う。閾値がホテル別の設定に依存し、
リクエスト単体では判定できないため。1件でも理由が欠けていれば**何も保存しない**
（部分保存すると差異分析に穴が空く）。

---

## 5. 意図・背景の分類

集計可能にするため固定の10分類にしている（`ForecastVarianceReason`）。
自由記述（`varianceNote`）は分類と併記し、現場の言葉をそのまま残す。

| 値 | 画面表示 | 想定 |
|----|---------|------|
| `BOOKING_PACE` | 予約の入り方 | ブッキングカーブが前年と違う |
| `COMPETITOR_SUPPLY` | 競合の供給・価格 | 新規開業・競合の値動き |
| `EVENT_LOCAL` | 地域イベント・催事 | 影響度をAIより大きく／小さく見る |
| `GROUP_CONTRACT` | 団体・法人契約の確度 | 契約の見込みが数字に出ていない |
| `REPEAT_GUEST` | 常連・リピーター動向 | 固定客の動きが読めている |
| `MARKET_TREND` | 市況・季節性 | 過去実績では拾えない地合い |
| `OTA_CAMPAIGN` | OTA施策の効き | 施策の効き方の見立て |
| `RENOVATION_OPS` | 改装・運営制約 | 客室閉鎖・人員で受けられない |
| `DATA_DOUBT` | AI予測の前提データに疑義 | 元データがおかしいと考えている |
| `OTHER` | その他 | 上記に当てはまらない |

分類を増やすときは `schema.prisma` の `ForecastVarianceReason`、
`validators.ts` の `FORECAST_VARIANCE_REASONS`、画面の選択肢の3箇所を揃える。

## 6. 実績が出た後：どちらの見立てが当たったか

実績が入った日は、AI予測と担当者予測の**実績に対する誤差の絶対値**を比べ、
小さい方を「近い」とする。指標ごとに判定し、総合は売上（無ければ稼働率）で決める。

```
誤差 = |実績 − 予測|
近い方 = AI / 担当者 / 互角（誤差が同じ）
```

実績が無い日（将来日・未取り込み）は判定しない。画面は「実績待ち」と表示する。

この判定は価格判断側の結果判定（`docs/意向入力仕様.md` の想定RevPAR比較）と違い、
**推定を挟まない**。予測値と実績値を直接比べているだけなので、解釈の余地がない。

---

## 7. 背景別の分析 — これが本体

差異を出すだけでは「担当者はAIより強気だった」で終わる。知りたいのは
**どういう背景のときに、どちら向きにズレて、結局どちらが当たったか**なので、
意図・背景の分類ごとに次を集計する。

| 列 | 意味 |
|----|------|
| 日数 | その背景で差異が出た日数 |
| 稼働率／ADR／売上の平均ズレ | 向きと大きさ。片側に偏っていれば癖 |
| 担当者の的中率 | その背景のとき担当者予測が実績に近かった割合 |
| 母数 | 実績が判明している日数。少ないうちは的中率を信用しない |

読み方の例:

- 「団体・法人契約の確度」で担当者の的中率が高い → AIが構造的に拾えない情報。
  データ連携かモデルの入力を増やす対象
- 「市況・季節性」で的中率が低い → 感覚的な上振れ。AI予測を尊重した方がよい領域
- 母数が一桁のうちは、どちらの結論も出さない

---

## 8. 月次ロールアップの出し方

日別を積み上げて、AI予測 / 担当者予測 / 実績 の月間着地を並べる。
担当者予測が入っている日だけを母数にする（入っていない日を0で埋めない）。

```
稼働率 = 販売室数の合計 ÷ (総室数 × 日数)
ADR    = 売上合計 ÷ 販売室数合計
```

稼働率もADRも**日平均を取らない**。日平均だと満室の日と閑散日が同じ重みになり、
月間の着地としては誤った数字になるため。

| 操作 | ロール |

## 10. 未実装と限界

- 実績（`DailyData`）の自動取り込みは Phase 4。現状は seed／手入力
- 予測の入力は画面での一括入力のみ。スプレッドシート取り込みは未実装
- 部屋タイプ別・チャネル別の予測は未対応（ホテル全体の粒度）
- 「担当者予測をAIの入力に取り込む」ことはしていない。まず差異と背景を
  蓄積し、どの背景でAIが構造的に外すのかが見えてから検討する
  （継続学習の考え方は `docs/継続学習設計.md`）
- 背景別の的中率は母数が小さいうちは統計的に意味を持たない。
  画面が常に母数を併記しているのはこのため
