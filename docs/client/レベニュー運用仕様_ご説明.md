# AIレベニュー管理システム　運用仕様のご説明

貴館への導入にあたり、本システムがどのようにデータを扱い、どのように価格を推奨するかを
ご説明する資料です。**どの施設にも共通する考え方**をまとめています。

貴館固有の設定値（客室数、料金ランクの段階数、価格方針など）は、別紙
「**ホテル個別設定ヒアリングシート**」でお伺いし、施設ごとの設定書としてまとめます。

## 1. 全体の流れ

```
 ① PMSから予約データを受け取る
      ↓
 ② 1予約を宿泊日ごとに展開する（1泊 = 1行）
      ↓
 ③ 日別の実績指標を算出（稼働率・ADR・RevPAR など）
      ↓
 ④ 需要を予測し、需要レベル（A〜E の5段階）を判定
      ↓
 ⑤ 料金ランクを推奨し、根拠とあわせて画面に表示
```

**⑤は「ご提案」までです。** 本システムがサイトコントローラーやPMSの料金を
自動で書き換えることはありません。最終的な価格の決定と反映は、貴館のご担当者さまの
操作によって行われます。

## 2. 予約データの扱い方

### 2.1 いただくデータ

PMSから出力される**予約明細データ**をいただきます。集計後の数字ではなく、
明細のままお預かりするのがポイントです。理由は2つあります。

1. **集計をシステム側で自動化できる**ため、日々の集計入力が不要になります
2. **毎日いただくこと自体に価値があります。** その日時点の予約の入り具合が記録として
   残り、「宿泊日の何日前にどれくらい入っていたか」（ブッキングカーブ）が
   自動的に蓄積されます

> ブッキングカーブは**後から遡って作ることができません。** 設定内容が固まる前でも、
> データをお預かりすることだけは早めに始めさせていただけると、その分だけ
> 予測の精度が早く立ち上がります。

### 2.2 日別への展開

PMSの予約データは通常「1予約 = 1行（3泊なら3泊まとめて1行）」です。
これを**1泊ずつの行に分解**してから分析します。

| 元のデータ | → | 展開後 |
|---|---|---|
| 10/20 〜 10/23（3泊）・80名・室料 2,664,000円 | → | 10/20 … 80名・888,000円 |
| | | 10/21 … 80名・888,000円 |
| | | 10/22 … 80名・888,000円 |

展開のルールは以下のとおりです。

| 項目 | 扱い |
|---|---|
| 宿泊日 | チェックイン日から順に1日ずつ。**チェックアウト日当日は作りません** |
| 金額の割り振り | 総額を泊数で均等に割ります。1円未満の端数は最終泊に寄せます |
| 人数の割り振り | 延べ人数を泊数で均等に割ります |
| 取消（キャンセル）分 | **削除せずそのまま保持**し、集計時に予約分と分けて扱います |
| 検算 | 日別に割った金額の合計が、必ず元の総額と一致することを確認します |

**端数を最終泊に寄せる理由**: こうすると画面に出ている日別の金額をそのまま足し算すれば
総額に一致します。電卓で検算していただいても数字が合う形にしています。

### 2.3 「割り振った数字」は推定値です

上の表のとおり、日別の人数・金額は**総額を泊数で均等に割った値**です。
実際には日によって人数が変わる予約もありますので、これは実測値ではありません。

本システムでは、**こうした推定値は画面上で実測値と区別して表示**します。
推定を実績のように見せることはいたしません。

### 2.4 取消データについて

キャンセル分は捨てずに保持します。捨ててしまうと「どの時期に、どのチャネルから、
どれくらい落ちるか」が分からなくなるためです。

実際のデータでは、**取消が全レコードの半数を超えることも珍しくありません。**
そのため集計は必ず「有効な予約のみ」で行い、取消は取消として別に分析します。

## 3. 指標の定義

### 3.1 共通の計算式

| 指標 | 計算式 | 意味 |
|---|---|---|
| 稼働率（OCC） | 販売客室数 ÷ 販売可能客室数 | どれだけ埋まったか |
| ADR | 客室売上 ÷ 販売客室数 | 売れた1室あたりの平均単価 |
| RevPAR | 客室売上 ÷ 販売可能客室数（= 稼働率 × ADR） | 持っている客室1室あたりの売上 |
| DOR | 宿泊人数 ÷ 販売室数 | 1室あたり何名でお使いか |
| 客単価 | 客室売上 ÷ 宿泊人数 | お一人あたりの単価 |

### 3.2 貴館に決めていただく部分

**計算式は共通ですが、分子・分母に何を入れるかは施設さまごとに異なります。**
PMSの仕様やこれまでの考え方に合わせる必要があるため、以下はヒアリングでお伺いします。

| 項目 | 一般的な扱い | 施設さまによって異なる理由 |
|---|---|---|
| 故障部屋（OOO）を販売可能室数から外すか | 長期の工事等は外し、1泊〜1週間程度の単発は含める | 施設さまのお考えとPMSの持ち方 |
| 無料提供室の扱い | 販売室数から除外 | 施設さまのお考え |
| ADRに食事代を含めるか | 含めない（純客室料金） | 1泊2食のご提供が中心の施設さまは含める場合があります |
| 税・サービス料の扱い | 税抜・サービス料除外 | PMSの出力仕様 |
| 会計年度の開始月 | 4月 | 貴館の会計年度に合わせます |
| 「週末」の定義 | 金・土 | **「休前日（翌日が休み）」で見たいというご要望を多くいただいています** |

## 4. 需要予測と価格推奨の考え方

### 4.1 推奨が出るまで

```
過去の実績 ＋ 現在の予約の入り具合
   ↓  例年の傾向と比べてどうか
   ↓  同じ時期の例年のペースと比べて早いか遅いか
   ↓  イベント・連休・季節要因を加味
需要レベル（A〜E の5段階）
   ↓  貴館の料金ランク表に当てはめる
   ↓  貴館の方針による制約をかける（上下限・1日の変更幅・変更頻度）
推奨料金ランク ＋ 確からしさ ＋ そう判断した根拠
```

### 4.2 「なぜその価格なのか」を必ず表示します

推奨には**根拠の内訳**（稼働が効いたのか、競合が効いたのか、イベントか）を
必ず添えます。理由の分からない数字は現場で使えないためです。

また、データが不足している場合は**確からしさを下げて表示**します。
根拠が薄いまま強い推奨を出すことはありません。

### 4.3 価格方針は貴館のものです

価格の考え方は施設さまごとに大きく異なります。たとえば、

- 売上の最大化を優先される施設さま
- 稼働が下がっても単価を維持される施設さま
- 「前日より安く売らない」をお客さまとの信頼として守られている施設さま

いずれも正しい方針であり、**システムが一律の正解を押し付けることはありません。**
ヒアリングでお伺いした方針を設定として反映し、その範囲内で推奨を出します。

## 5. データのお取り扱い

| 項目 | 方針 |
|---|---|
| 個人情報 | **分析に不要なため、お名前・電話番号等は連携対象から外すことを推奨します。** PMSの出力条件で除外していただくのが最も安全です |
| アクセス制限 | 施設さまのデータは施設さま専用の領域に分離し、他施設から参照できない構造です |
| 操作の記録 | 設定変更・データ取込は、いつ誰が行ったかを記録します |
| 取込の取り消し | 取り込んだデータは取込単位で取り消せます |

## 6. データ取込の運用

取り込みは**3段階**に分かれており、**確認の段階で中止できます**。

1. **ファイルをお預かりする**
2. **内容を確認する** — 対象期間、件数、予約と取消の内訳、注意が必要な行の一覧を
   画面に表示します。ここで取り込まずに中止できます
3. **確定する** — 取り込み単位で記録され、後から取り消せます

確認の段階では、以下のような点を自動で検出してお知らせします。

- 同じファイルを二度取り込もうとしている（二重計上の防止）
- 設定にない客室タイプのコードが含まれている
- 人数や泊数の整合が取れない予約がある

**黙って読み飛ばしたり、丸めたりすることはありません。** 判断が必要なものは
必ず画面上でお知らせします。

## 7. 現時点でできること／これからのこと

誤解が生じないよう、現状を正確にお伝えします。

### 現時点でご利用いただけるもの

- 日別・月別の実績表示（稼働率・ADR・RevPAR・宿泊人数ほか）
- 予算比・前年比の進捗表示
- 日別価格カレンダーと料金ランクの管理
- 価格戦略の重み付け設定、月間着地シミュレーション
- 競合料金の比較表示、イベント・外部要因の登録
- 月次レポートの生成（PDF / Excel 出力）
- 各種設定（客室タイプ、料金ランク、競合、予算）

### 開発中のもの

- **PMS・サイトコントローラーとの自動連携**（現在は手動でのデータ受け渡し）
- **OTA料金の自動収集**（現在は手動登録）
- **機械学習による需要予測**（現在はルールベースでの算出）
- **AIによる自然言語コメントの自動生成**
- 定時実行による自動処理

現在サンプルデータで表示している画面については、**画面上にその旨を明示**しており、
実績のように見せることはいたしません。

## 8. 導入の進め方（ご提案）

| 段階 | 内容 | 前提 |
|---|---|---|
| **第1段階** | 予約データのお預かり開始、取消分析・チャネル別分析・リードタイム分析 | ヒアリングシートのご回答 |
| **第2段階** | 稼働率・ADR・RevPAR の実データ化、ダッシュボードの本格稼働 | **販売室数がPMSから出力できること** |
| **第3段階** | ブッキングカーブ・ピックアップ分析、需要予測の精度向上 | 日々のデータ蓄積 |

> **第2段階の前提について。** 販売室数（部屋数）がPMSから出力できないと、
> 稼働率・ADR・RevPAR が計算できません。ヒアリングシートの **D-01** が
> 最優先の確認事項となります。出力できない場合は、その時点で代替案をご相談させてください。
>
> 該当する指標は、データが揃うまで「未連携」と明示して表示します。
> 推定値で埋めて実績のように見せることはいたしません。

## 8.5 ご提供をお願いする資料

予約データのほかに、以下をご提供いただくことで表示できる内容が広がります。

| 資料 | 用途 | ご提供がない場合 |
|---|---|---|
| 客室タイプ一覧（室数・定員） | 稼働率の算出 | 稼働率が算出できません |
| 月次予算（売上・室数・ADR・稼働率・人数） | 予算比の進捗表示 | 進捗表示が空欄になります |
| 前年実績（月次） | 前年比の表示 | 前年比が表示できません |
| 現行の料金ランク表（各ランクの実額） | 価格推奨の基準 | ランクから価格を算出できません |
| 販売チャネルの一覧 | チャネル別実績・直販比率 | チャネル別の分析ができません |
| 各種コードの対応表 | 画面への日本語表示 | コードのままの表示になります |
| 競合他館とOTA別URL | 料金の比較 | 競合比較が表示できません |

いずれも**後からのご提供で問題ございません。** 揃っていないものは
「未連携」と明示して表示し、推定値で埋めることはいたしません。

## 9. 用語

| 用語 | 意味 |
|---|---|
| 稼働率 / OCC | 客室の埋まり具合 |
| ADR | 売れた1室あたりの平均単価 |
| RevPAR | 持っている客室1室あたりの売上。稼働率 × ADR |
| DOR | 1室あたりのご利用人数 |
| OOO | 故障・改装で販売できない客室 |
| コンプ | 無料でご提供する客室 |
| ブロック | 団体さま向けに確保した在庫枠 |
| ウォッシュ | 団体ブロックのうち、実際には使われず戻る分 |
| ブッキングカーブ | 宿泊日に向けて予約が積み上がっていく推移 |
| ピックアップ | 一定期間に新たに入った予約数 |
| リードタイム | ご予約日から宿泊日までの日数 |
| レートパリティ | 販売チャネル間で料金が揃っている状態 |
| CTA / CTD | 到着日クローズ / 出発日クローズ |
