## 2. 重大ギャップの詳細と対応

### 2.1 料金ランク（決定#1）

実データ（`■HG_販売料金表_送付用_2025.09.11.xlsx`）の構造:

- 部屋タイプ16種（SMN/DSN/DMN/GDMN/DGN/DXN/TSN/TMN/GTSN/GTMN/TGN/TPN/GTPN/HCN/GDN/GGN/GKN…通常フロア／ゴジラフロア／特別ルーム）
- レート区分4種: **自社／会員／株優／OTA**（株優が0円=設定なしのタイプあり）
- ランク列: **65→0 の66段階 ＋ ★1〜★5 の5段階**（番号が小さいほど高価格）
- 宿泊税別

現行 `PriceRank`（ホテル単位・rank 1〜40・price1P〜4P）では表現不能。`validators.ts` の
`max(40)` 制約、`AGENTS.md` の「最大40段階」確定値は**撤廃**する。

新モデル案:

```prisma
model PriceRank {
  id           String  @id @default(cuid())
  tenantId     String
  hotelId      String
  roomTypeId   String
  rateCategory RateCategory   // OWN / MEMBER / SHAREHOLDER / OTA
  rankCode     String         // "65".."0", "★1".."★5"
  sortOrder    Int            // 表示・昇降順制御（rankCodeが数値でないため）
  price        Int            // 100円単位を許容
  isActive     Boolean @default(true)
  @@unique([hotelId, roomTypeId, rateCategory, rankCode])
  @@index([tenantId])
}
enum RateCategory { OWN MEMBER SHAREHOLDER OTA }
```

- 「AI推奨ADRに最も近いランクのピックアップ」もAIが行う（機能リスト）→ recommendation側は
  `recommendedRankCode` を持つ。
- 既存の1〜40ランクseed・UI（R01形式バッジ）は移行対象。
- **要確認（蘭賀様）**: 65→0軸の運用上の意味（残室連動か、単純なランク番号か）、★1〜★5の用途。

### 2.2 承認 → サイトコントローラー書き込み（決定#2）

仕様書PDFの技術要件どおり:

- 承認済み価格ランクを、SC APIがあればAPI経由、無ければRPA型ブラウザ操作で書き込み
- 書き込み後にSCレスポンス（成功/失敗）を検知し、**失敗時は該当日程のみ再試行**、他日程は継続
- SCごとに独立した**コネクタ層**（`backend/src/connectors/sc/`）として分離

モデル案:

```prisma
model PriceChangeProposal {  // AI提案〜承認〜書込のライフサイクル
  hotelId, date, roomTypeId?, currentRankCode, proposedRankCode,
  confidence Float,          // 確信度スコア（§5.9 半自動モード判定に使用）
  status ProposalStatus,     // PENDING/APPROVED/REJECTED/WRITING/WRITTEN/FAILED
  decidedByUserId?, decidedAt?, autoApproved Boolean
}
model ScWriteJob { proposalId, connector, attempts, lastError, status, ... }
```

承認/否認ログは学習エージェントの入力（§5.9）。画面は仕様書の「③承認・SC連携管理画面」を新設。

### 2.3 オンハンド／予約データモデル（決定#3）

取得データ = **当日から180日分の予約情報＋前日1日分の実績**（仕様書Ⅲ章）。
PMS取得項目（機能リスト）: 計上日／チェックイン日／チェックアウト日／予約日／キャンセル日／室数／室料／
サービス料／予約(アサイン)タイプ／料金タイプ／利用人数／エージェント／地域／個人団体区分。

モデル案:

```prisma
model Reservation {           // PMS予約明細（個人情報なし）
  tenantId, hotelId, pmsRef?,
  bookedAt DateTime, cancelledAt DateTime?,
  checkIn DateTime, checkOut DateTime,
  roomTypeCode String, rooms Int, guests Int?,
  roomRevenue Float?, serviceFee Float?,
  assignType?, rateType?, agentCode?, regionCode?, marketCode?, isGroup Boolean
}
model ReservationNight {      // 計上日が無いPMS向けに1泊単位へシステム内で展開（機能リスト要件）
  reservationId, stayDate, rooms, roomRevenue
}
model OnHandSnapshot {        // 日次スナップショット（ブッキングカーブ・月初比較・進捗管理の基盤）
  hotelId, stayDate, capturedDate,
  rooms Int, revenue Float, guests Int?,
  segment Json?               // タイプ別/マーケット別等の内訳
  @@unique([hotelId, stayDate, capturedDate])
}
```

- KPI表は「オンハンド／本日まで／累計進捗／年度累計／オンハンドAI予測値／AI月間・年間着地予測」構成へ
  （モックアップKPI画像・機能リスト準拠）。
- ブッキングカーブは `BookingCurveData`（roomsBookedのみ）を廃し、OnHandSnapshot由来で
  **360日前〜0日前・タイプ別/カテゴリー別・前年対比**に対応（`【進捗管理】5日間・10日間(カテゴリー別).xlsx` 再現）。
- 着地予測は月間に加え**年間**を追加。

## 3. モックアップ修正内容.xlsx の反映タスク（決定#6）

ダイナミックプライシング画面:

1. 表示月数セレクタ（1/2/3ヶ月）を廃止し**1ヶ月固定＋表示月選択**に
2. 部屋タイプ選択に**部屋タイプグループ**を追加。選択肢はハードコード（スタンダード/デラックス/スイート）をやめ**RoomTypeマスタから取得**。「全タイプ」表示は廃止し、**マスタ先頭タイプをデフォルト表示**
3. **価格戦略（重み付け設定）は撤去**。理由: AIが複数要因から導く数値に対する人側の介入は「料金ランクの変更」で行い、その結果が着地予測（ADR/稼働/Rev-Per）に反映される設計とする。`PricingStrategyConfig`・重み付けUI・合計100%制約は廃止方向（`AGENTS.md` の確定値も撤回）
4. 着地予測の表示は6項目: **現在のADR/稼働率/RevPer ＋ 着地予測のADR/稼働率/RevPer**
5. 日別テーブル: 「需要予測(A-E)」→**「アラート」に名称変更**（色レベル表示）。「ステータス」列はアラートと重複のため**削除**
6. 列構成: 日付／曜日（祝日=色、**特日=別色**。特日はAIが提示しオペレーターがマスタ設定画面で修正）／アラート／現在のADR／推奨ADR(AI)／稼働率予測(AI)／現在料金ランク(SC)／推奨料金ランク(AI)／ADR結果／稼働率結果／推奨ADR差異／推奨稼働率差異（結果系は実績確定後に表示。差異はAI学習・コメント材料）
7. タイプ別人数別カレンダー: ランク表示は利用人数によらず共通、価格は人数別表示

ダッシュボード: 残室（在庫表）追加は§2.5参照。

## 5. 追加設計方針

### 5.1 キャンセル分析（決定#8）

`Reservation.cancelledAt` から導出。専用集計は日次バッチでマテリアライズ:
日別/月別 × キャンセル室数・件数・室料売上、予約:キャンセル差異（室数/件数/室料）、
期間比較(FROM-TO)・前年差異。グラフ化対応。

### 5.2 上位・下位／期間比較（決定#9）

- 上位表示(10位): タイプ別/人数別/販路別/地域別/各グループ/団体・個人 × 月合計値(実績+OH)、
  期間比較(FROM-TO)、前年差異（順位・室数・売上）。表示数はパラメータ化（既定10、要確認事項）
- 上位・下位分析: 日別ADR・日別稼働率
- 差異分析: 月初比較（差異数値）、期間比較(FROM-TO)、対予算・対前年比・AI予測差異（合計値のみ）

### 5.3 KPI追加（決定#7）

定員稼働率（宿泊人数 ÷ 総定員。総定員=Σ RoomType.capacity×count）を追加。
オンハンド軸・AI年間着地予測は§2.3参照。

### 5.4 外部要因・特日（決定#12）

`外部要因と旅行（宿泊）の関連付け.xlsx` の構造をそのままモデル化:

- **起因カテゴリ**: 天候（気温/梅雨/台風/風水害/降雪/地震）／インバウンド動向（JNTO・海外/国内SNS）／
  イベント（催事・桜・紅葉・収穫）／アクセス（高速道路・航空国内外・新幹線）／新規ホテル／経済動向／その他
- **時間軸**: a.特日 ／ b.各種要因による期間 ／ c.デイリー
- **特日マスタ**: 年末年始(12/27-1/5)・正月明け・受験・中国春節（旧暦で変動）・春休み・GW(4/28-5/6)・
  夏休み・お盆・シルバーウィーク等。**AIが提示→オペレーターがマスタ設定画面で修正**（§3-6と連動）

```prisma
model SpecialDay      { hotelId, date, name, kind(HOLIDAY/TOKUJITSU), color?, source(AI/MANUAL) }
model ExternalFactor  { hotelId?, category, timeAxis(TOKUJITSU/PERIOD/DAILY), startDate, endDate,
                        title, description?, impactScore?, source }
```

既存 `Event` はExternalFactorのイベントカテゴリに統合するか併存かを実装時に判断。

### 5.5 レポート

実装済み（PDF/Excel、`reportsService.ts`）。第2期の「レポート作成（AI）」はAIコメント組み込みの拡張として扱う。

### 5.6 AIまとめ・要因解説

仕様書のアウトプット定義（事実コメント／予測コメント／影響度分布、①〜⑤）に合わせて
`AiComment` の種別を整理。影響度分布は導入半年以降〜の継続提示。

### 5.7 団体（決定#11）

`GroupBooking` 拡張:

```prisma
groupType   GroupType   // GENERAL(一般団体) / RECRUIT(募集旅行) / EDUCATION(教育旅行)
blockRooms  Int?        // 在庫ブロック室数
consumedRooms Int?      // ブロック消化室数
closingDate DateTime?   // 手仕舞（募集期限、概ね2週間前）
releaseCheckDate DateTime? // ブロック解除判断日（概ね1ヶ月前）
executed    Boolean?    // 催行/不催行
agentCode   String?     // JTBエース、阪急交通社、クラブツーリズム等
purpose     String?     // 目的タグ（桜・季節等 — 募集旅行の傾向分析用）
```

- MICEのうち国際会議・展示会等は団体でなく**イベント（外部要因）として扱う**
- セグメント別・季節別・目的別のキャンセル率/催行率/ブロック消化率を蓄積し予測に利用
- 過去データへのフラグ付けは人力（導入時コンサルサポート、初期導入費/月額でカバー）

### 5.8 需要予測レベル

`DemandLevel(A-E)` はデータとして維持しつつ、DP画面上の表示名は「アラート」へ（§3-5）。

### 5.9 AIエージェント構成・確信度・MLOps（決定#13 — 実装前に設計レビュー必須）

仕様書の4エージェント構成を採用:

| エージェント | 役割 | 技術方針 |
|---|---|---|
| 需要予測 | 180日先の日次需要・稼働率を毎日再学習・再予測 | 勾配ブースティング系または時系列Transformer系。`services/forecast/` のforecasterインターフェースを拡張 |
| 価格決定 | 予測＋外部要因＋料金ランクマスタから最適ランク算出 | ルール＋モデルのハイブリッド。**LLMは価格決定に使わない** |
| 要因解説 | 予実乖離の要因分析、事実/予測/改善提案コメント生成 | Claude API。二次利用防止（Opt-out）設定必須 |
| 学習 | 承認/否認ログを差分蓄積し価格感応度をフィードバック | 都度ファインチューニングではなく**特徴量重みの定期バッチ更新** |

- **確信度スコア**: 全提案に付与。基準以上→自動書き込み継続、基準未満（異常値検知時等）→
  自動書き込みを保留し**半自動モード**（オペレーター確認）。閾値は稼働後キャリブレーション、当初は暫定値
- **学習状況(MLOps)モニタリング画面**: 承認率・予測誤差推移・確信度分布・思考アジャスト進捗の可視化
- 精度目標（フル稼働1年後測定）: 需要予測エラー率±10%以内／売上+15%／費用50%削減／コメント承認率90%以上
- 権限: 「誰の承認・対話を学習の正とするか」は**ADMINのみ設定可能**（F-008）
- 日次バッチは**深夜0時〜翌朝6時に完了**（PMS夜間バッチ検知後。時刻は初期設定時ヒアリング）

### 5.10 PMSデータ自動取得（決定#15）

仕様書Ⅲ章では便宜上「別アプリ」だが、**本プロジェクトで開発し、本サービスのデータ取込基盤とする**。
クローリング／Browser UseでPMS（NEHOPS等）からデータを取り続け、本サービスで利用可能にする。

- **取得**: RPA型自動ブラウジング（Playwright等）でPMSのCSV出力機能を操作。UI変更で通常操作が
  通らなくなった場合はAIエージェント（Browser Use）操作に切替
- **実行**: 施設と協議した時刻にスケジュール実行。実行前に**PMS夜間バッチ（日付更新）完了をチェック**
  （タイムサーバ実時間とPMS内日付の比較）。未完了なら中断し、オペレーター＋アコモス社サポートへ
  アラート（メール/Webhook）
- **連携**: 取得側（クローラ）には**データを一切保持しない**。ホテル→クラウド方向のHTTPS一方向通信のみ
  （ポート開放不要）で、本サービスの取込API（例: `POST /api/v1/ingest/pms`、トークン＋署名認証）へ直接送信。
  サーバ側で正規化し Reservation / OnHandSnapshot / RoomInventorySnapshot / DailyData へ展開
- **項目設定**: 初回導入時にPMSのCSV出力画面で抽出項目を指定（個人情報は取得前にPMS側出力設定で除外）。
  PMS側仕様変更に追従できるモジュール構造
- **ログ**: 成功/失敗・開始終了時刻・取得項目を記録、**最低1年保持**。管理画面で閲覧可能
- **認証情報**: PMSのID/パスワードは暗号化保管（AWS Secrets Manager想定）
- 外部要因収集（競合価格・OTA販促等）も同じクローラ基盤に載せる（F-002。サイト仕様変更の
  モニタリングを併設。OTA販促データは管理画面NGのため当面手動移行）
