# 継続学習設計 — 運営担当者の意向をAIに取り込む

対象機能: F-DP-08（意向の記録）／F-DP-09（差異の可視化）／F-DP-10（継続学習）

このドキュメントは「運営担当者の意向を、どういう手段でAIの価格推奨に反映し続けるか」の
設計方針をまとめたもの。実装済みの範囲と、まだ実装していない範囲を明示的に分けて書く。

---

## 1. 何を解こうとしているか

AI推奨価格は、現場でそのまま使われるとは限らない。実際には運営担当者が

- 競合が動いたから追随した
- 団体が入るから残室は高めに構えた
- 常連の動きが例年と違うので勘で少し上げた

といった判断で推奨価格を上書きする。この上書き自体は現場の知識であって、ノイズではない。
にもかかわらず、従来は

1. **なぜ変えたのか（意向）が残らない** — 価格だけが上書きされ、理由が消える
2. **AI推奨と実際にやった値の差が測れない** — 推奨が使われたのかどうかも分からない
3. **その差がAIに戻らない** — 同じ判断を毎月人間が繰り返す

という状態だった。この3点を、記録 → 可視化 → 学習 のループとして閉じるのが本設計。

---

## 2. 学習ループの全体像

```
 ①記録            ②差異               ③学習                ④承認            ⑤反映            ⑥再評価
運営担当者の判断 →  AI推奨との差    →  セグメント別の     →  MANAGERが     →  需要予測に    →  実績で
＋意向（理由）      ＋実績との差       意向プロファイル      反映可否を判断    ランク補正      効果を測る
PriceDecision      /pricing/variance   OperatorPreference    isEnabled        calibrated       outperformRate
                                       Profile                                Forecaster        → ③へ戻る
```

各段階の実装場所:

| 段階 | 実装 |
|------|------|
| ①記録 | `backend/src/services/operatorIntent/priceDecisionService.ts` / `POST /api/v1/pricing/decisions` |
| ②差異 | `backend/src/services/operatorIntent/varianceService.ts` / `GET /api/v1/pricing/variance` |
| ③学習 | `backend/src/services/operatorIntent/learningService.ts` / `POST /api/v1/pricing/learning/recompute` |
| ④承認 | `PATCH /api/v1/pricing/learning/profiles/:id`（MANAGER以上） |
| ⑤反映 | `backend/src/services/forecast/calibratedForecaster.ts` |
| ⑥再評価 | ②の `outperformRate` が③の入力に戻る |

UIは `frontend/components/operator-intent-panel.tsx`（プライシングタブ内）。

## 3. 記録するデータと、その形にした理由

### 3.1 PriceDecision は追記専用ログ

1日1レコードの「現在値」ではなく、判断のたびに追記する履歴にしている。
同じ日の価格を直前に上げ下げした経緯そのものが学習材料になるため。
差異レポートでは、同一日の最新の判断を「実際に適用した値」として扱う。

### 3.2 判断時点のAI推奨をスナップショットとして焼き込む

`AiPriceRecommendation` は再計算のたびに上書きされる。参照で持つと、
再計算した瞬間に過去の差異が書き換わり「あのときAIは何と言っていたか」が失われる。
そのため `aiRecommendedRank` / `aiRecommendedPrice` / `aiPredictedOccupancy` /
`aiPredictedAdr` / `aiDemandLevel` / `aiConfidence` / `aiModelVersion` を
PriceDecision 側に複製する。監査上も「その時点の推奨に対する判断」が復元できる。

### 3.3 判断種別はサーバ側で導出する

`ACCEPTED` / `RAISED` / `LOWERED` はクライアントから受け取らず、
AI推奨ランク（無ければ価格）と適用値の差から導出する。差異の正しさが
監査と学習の前提になるため、入力側の申告を信用しない。

### 3.4 意向は「分類 + 自由記述」の二段構え

学習に使うには分類（`PriceIntentReason` の9種）が必要で、現場の文脈を残すには
自由記述（`intentNote`）が必要。どちらか一方では足りないので両方持つ。

---

## 4. 差異の測り方

`GET /api/v1/pricing/variance` は2種類の差異を並べて返す。

1. **意向差異** — AI推奨ランク／価格 と 実際に適用した値の差（`rankDelta` / `priceDelta` / `priceDeltaPct`）
2. **実績差異** — AI予測（稼働率・ADR）と実績の差（`occupancyDelta` / `adrDelta`）

さらに結果の目安として `outcome` を返す:

```
想定RevPAR = 判断時点の予測稼働率 × 判断時点の予測ADR
outcome = 実績RevPAR が 想定RevPAR を ±2%(OUTCOME_TOLERANCE) 超えて上回る / 下回る / 収まる
```

### なぜ「予測ADR」を基準にするのか

想定RevPARの基準に**推奨価格（料金ランクの1名料金）を使ってはいけない**。
実績RevPARは販売ミックス込みのブレンドADRから算出されるため、
ランク表の定価と直接比べると常に定価側が高く出て、比較が成立しない
（実装初期はこれで全日「AIの勝ち」に倒れた）。予測ADRなら実績ADRと同じ土俵になる。

### この指標の限界（重要）

`outcome` は「AI推奨どおりに運用していたらどうだったか」の反実仮想ではない。
実際に取れるのは「運営担当者が動かした後の実績」だけで、動かさなかった世界線の実績は存在しない。
したがってこれは **AIの想定を実績が超えたかどうか** の推定にすぎない。
学習側では必ず母数（`evaluatedCount`）とセットで扱い、少数の観測で補正を決めない。

## 5. 学習の中身（実装済み: ルールベース補正）

### 5.1 セグメント

需要レベル（A〜E）× 曜日区分（週末／平日）でセグメントを切る。
週末定義は `Hotel.weekendDays` を参照する（ハードコード禁止）。
「週末の高需要日は強気、平日の低需要日は競合追随で弱気」といった癖はこの粒度で出る。

### 5.2 代表値は中央値

セグメント内の `適用ランク − AI推奨ランク` の**中央値**を傾向とする。
平均だと、1件の極端な判断（例: 団体貸切で+20ランク）でセグメント全体が引きずられる。

### 5.3 3つの安全弁

| 安全弁 | 値 | 目的 |
|--------|-----|------|
| 最小サンプル数 | `MIN_SAMPLE_COUNT = 5` | 数件の判断を「傾向」と誤認しない |
| 実績チェック | `outperformRate < 0.5` かつ母数 `>= 3` なら補正0 | 意向どおりに動かしても結果が伴わない癖を学習しない |
| 補正幅クランプ | `MAX_RANK_DELTA = 3` | 誤った意向が増幅して暴走するのを防ぐ |

補正が0になった場合は理由（`INSUFFICIENT_SAMPLES` / `NOT_OUTPERFORMING`）を返し、
UIで「なぜ反映されないか」を運用者に説明する。

### 5.4 human-in-the-loop（自動反映しない）

学習結果は**自動では予測に反映しない**。MANAGER が内容を見て `isEnabled` を立てた
セグメントだけが `calibratedForecaster` で適用される。切り替えは監査ログに残る。

自動反映にしない理由は自己強化ループを避けるため。AIが運営担当者の癖を取り込む
→ 推奨がその癖に寄る → 担当者はそこから更に動かす → 癖が増幅される、という
フィードバックが起きうる。人間の承認を1段挟むことでこのループを切っている。

### 5.5 反映は「後段の補正層」として実装する

`calibratedForecaster` はベース予測（現在はルールベース）を書き換えず、
出力に対してセグメント別のランク補正を重ねるデコレータ。
補正後のランクは 1〜maxRank にクランプし、価格は料金ランクマスタから引き直す。
モデルバージョンは `rule-based-v1+operator-calibration-v1` のように連結され、
どの推奨がどの経路で出たかが `AiPriceRecommendation.modelVersion` から追える。

この構造にしておくと、ベースをMLモデルに差し替えても補正層はそのまま使える。

## 6. 段階設計 — どこまで実装済みか

| 段階 | 内容 | 必要なデータ量の目安 | 状況 |
|------|------|---------------------|------|
| **L0 記録** | 意向と適用値を残す。分析はしない | — | **実装済み** |
| **L1 可視化** | 差異を日別・理由別・セグメント別に見せる | 数十件 | **実装済み** |
| **L2 ルール補正** | セグメント別中央値をランク補正として反映（承認制） | セグメントあたり5件以上 | **実装済み** |
| **L3 モデル学習** | 意向を特徴量に含めた需要予測モデル | 1ホテル1年以上（数百〜千件） | **未実装（Phase 4）** |

L2 までで止めているのは、L3 に必要なデータ量が今のシステムにまだ無いため。
運用開始からセグメントあたり数十件が貯まる前にMLへ行っても、
過学習した推奨を承認制なしで流すことになり危険度だけが上がる。

## 7. L3（ML化）への接続方法

L3 へ進むときも、既存の構造をそのまま使える。

- **差し替え点**: `DemandForecaster` インターフェース（`backend/src/services/forecast/types.ts`）。
  `ruleBasedForecaster` を ML 実装に置き換え、`createCalibratedForecaster(mlForecaster)` で包む。
- **学習データ**: `PriceDecision` が既に「特徴量 + 人間のラベル + 結果」の形になっている。
  - 特徴量: 日付属性（曜日・週末・祝日）、需要レベル、AI予測稼働率・予測ADR、競合価格、イベント、リードタイム
  - 人間のラベル: `appliedRank`（実際に選ばれた行動）、`intentReason`（その理由）
  - 結果: 同日の `DailyData`（実績稼働率・ADR・RevPAR）
- **学習の型**: まずは「AI推奨ランク → 運営担当者が選ぶランク」の補正量を予測する回帰
  （現在の中央値ルールの素直な一般化）。行動クローンから入り、
  結果（RevPAR）で重み付けする方向へ拡張する。
- **維持すべき制約**: 承認制（`isEnabled`）と補正幅クランプは L3 でも外さない。
  モデルが賢くなっても、現場が説明できない価格を無承認で出す構成にはしない。

前提となる未実装領域（Phase 4）: PMS/OTA連携による実績の自動取り込み、
スクレイピングによる競合価格の継続収集、バッチジョブによる定期再学習。
現状の再学習は API を明示的に叩く手動実行。

## 8. 運用時に見るべき指標

| 指標 | 意味 | 見方 |
|------|------|------|
| 追随率 `followRate` | AI推奨をそのまま使った割合 | 極端に低い＝推奨が現場感覚と合っていない。極端に高い＝現場が推奨を検証せず流している可能性 |
| 平均ランク乖離 `avgRankDelta` | 推奨からの平均的なズレの向き | 一方向に偏り続けるならベース予測側の見直し対象 |
| 想定超え率 `outperformRate` | 実績がAI想定を超えた割合 | セグメント別に見る。0.5 を下回るセグメントは補正を入れない |
| `evaluatedCount` | 上記の母数 | 小さいうちは指標を信じない |
| `modelVersion` | どの経路の推奨か | 補正あり／なしの推奨で実績を比較する材料 |

## 9. 既知のリスクと対応状況

| リスク | 対応 |
|--------|------|
| 自己強化ループ（AIが癖を学び、担当者が更に動かす） | 承認制 + 補正幅クランプ。承認は監査ログに残す |
| 反実仮想が測れない（AI推奨どおりの結果は存在しない） | `outcome` を推定値と明記し、母数と併記。将来的にはセグメント内でのA/B（補正あり期間／なし期間）で検証する |
| 選択バイアス（意向が記録される日が偏る） | 記録日数 `decidedDays` / 全日数 `totalDays` を常に併記し、カバレッジを見えるようにする |
| セグメントの細分化による過学習 | 現在は需要レベル×曜日区分の最大10セグメント。細分化する場合は最小サンプル数も引き上げる |
| 担当者の交代で癖が変わる | `decidedByUserId` を保持済み。将来は担当者別プロファイルへ拡張可能 |
