## 1. 設計原則

1. **内部シグナルが主、外部要因は補正**。需要の説明力の大半は「その日の予約の積み上がり方（ペース）」にある。外部要因はペースが動く前に先回りするための事前情報と位置づける。
2. **すべての推奨に理由を付ける（説明可能性）**。ランクは要因ごとの寄与の合計として計算し、UI にその分解をそのまま出す。IDeaS との最大の差別化点。
3. **推奨・採否・結果を必ず記録し、翌日には学習に使う**。上書きしない。
4. **外部データはまず「無料・キー不要・静的」から**。API 障害で価格が止まらないよう、外部シグナルは全てオプショナルで、欠損時は係数ゼロにフォールバックする（サイレントに古い値を使わない）。
5. **モデルは差し替え可能**（既存の `DemandForecaster` インターフェースを維持）。ルールベースを常に fallback として残し、チャンピオン/チャレンジャーで昇格する。

## 2. 全体アーキテクチャ（3層 + 学習ループ）

```
[シグナル取り込み]        [需要予測]                [価格決定]               [記録・学習]
 内部: PMS/OTB, 実績      Base(季節・曜日・前年)      需要→基準ランク           ForecastSnapshot
 外部: 祝日, 天候,   →    × ペース補正          →    + 戦略重み(稼働/ADR/競合) → RecommendationDecision
       イベント, 競合      × 外部要因係数(学習)        + ガードレール             → 夜間: 残差→係数更新
                                                      → 推奨ランク + 理由分解      → 信頼度校正/バックテスト
```

### 2.1 需要予測層（Demand）

出力: 宿泊日 d、基準日 t における「現行価格水準での予測稼働率」`D(d|t)` と、要因分解。

```
D = clamp( Base(d) × PaceFactor(d,t) + Σ_k β_k(hotel) × S_k(d) , 0, 1 )
```

- **Base(d)**（内部・prior）: 現行の 28日同曜日平均×0.7 + 前年同日×0.3 を継続。ただし前年側は「前年同曜日」に揃える（祝日は暦日一致を優先）。
- **PaceFactor(d,t)**（内部・最重要）: `OTB(d,t) / OTB_expected(d,t)`。`OTB_expected` は同曜日・同シーズンの過去宿泊日について「t と同じリードタイムで積み上がっていた室数」の中央値（`BookingCurveData` から算出）。リードタイムが短いほど Pace の重みを上げる：
  `D = (1−α(L))·Base + α(L)·PaceProjection`、`α(L)` = リードタイム L 日での過去のペース予測精度から決める（初期値: L≤7で0.8、L≤30で0.5、L>60で0.2）。
  **PMS 連携（Phase 4）が入るまではここが空**。それまでは `BookingCurveData` の seed/手入力で動く。
- **S_k(d)**（外部要因シグナル、§3）: 祝日・連休、学校休暇、イベント、天候、競合稼働感、インバウンド。各シグナルは 0〜1 または実数に正規化。
- **β_k(hotel)**: ホテルごとの係数。初期値はカテゴリ prior（例: イベント high = +0.12）、夜間バッチで残差から更新（§5）。

### 2.2 価格決定層（Pricing）— 重み設定をここで初めて使う

現状の「稼働率×40」を廃止し、3つの候補ランクを戦略重みで合成する。

```
r_D    = 需要 D に対応する基準ランク（ランク表の価格帯を需要レベルに割当）
r_occ  = 稼働率重視候補: ペースが遅れていれば r_D − δ(遅れ幅)、目標稼働到達に必要な最小ランク
r_adr  = ADR重視候補: 需要が強ければ r_D + δ、弱くても前年同日ランクを下回らない
r_comp = 競合追従候補: 競合価格中央値に最も近いランク ± ホテル設定のポジション（例「競合比+5%」）
rank   = round( (w_occ·r_occ + w_adr·r_adr + w_comp·r_comp) / 100 )
```

その後ガードレール: `minRank/maxRank`（ホテル設定）、1日あたり最大変動幅（±N ランク）、フロア価格、団体・キャンペーン日の固定。競合データが無い日は `r_comp = r_D` として中立扱い（欠損で価格を歪めない）。

出力する理由分解（UI にそのまま表示）:

```json

    { "key": "holiday",    "label": "3連休中日",               "delta": +2 },
```

### 2.3 期待収益の算出（ユーザーに見せる唯一の数字）

各日について `期待RevPAR(rank)` = `price(rank) × 予測稼働率(rank)` を、価格弾力性 `ε(hotel, leadTime)` で近似する（初期値 −1.2、学習で更新）。「現行ランクのまま」と「推奨ランク」の差 × 客室数 = **その日の推奨採用による期待増収**。この値でカレンダーを並べ替えるのが UX の核（§6）。

### 3.1 シグナルの共通スキーマ（新規モデル案）

```prisma
// 取り込んだ外部シグナルの正規化ストア。取得元・鮮度を必ず持つ
model ExternalSignal {
  id         String   @id @default(cuid())
  tenantId   String
  tenant     Tenant   @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  hotelId    String
  hotel      Hotel    @relation(fields: [hotelId], references: [id], onDelete: Cascade)
  date       DateTime @db.Date      // 対象宿泊日
  signalType String                 // holiday, school_break, event, weather, comp_soldout, inbound
  source     String                 // cao_csv, jma, open_meteo, venue_extract, manual, derived
  value      Json                   // 型ごとの正規化値（例 weather: {rainProb, tempMax, warning}）
  capturedAt DateTime @default(now())
  validUntil DateTime?              // 鮮度。過ぎたら係数0で扱う（古い値を黙って使わない）

  @@unique([hotelId, date, signalType, source])
  @@index([tenantId])
  @@index([hotelId, date])
}
```

祝日・学校休暇はテナント非依存の参照データなので DB モデルにせず `shared/data/jp-holidays.json` 等の静的ファイルとしてビルドに同梱する（テナント分離ルールの対象外にするため）。

会場マスタ `Venue`（hotelId, name, lat/lng, capacity, distanceKm, websiteUrl）と `Event.venueId?` の追加で、イベント影響を「会場収容人数 ÷ エリア客室数 × 距離減衰」として初期値化できる。

### 3.2 取り込みの実装方針

- `backend/src/services/signals/<source>Adapter.ts` に取得元ごとのアダプタ。外部 URL・API キーは `lib/config.ts` 経由のみ。
- 取り込みは冪等（`@@unique` に upsert）。失敗はアラート化し、予測は該当シグナル抜きで続行。
- クラウド非依存のため、スケジューラは Node 内の軽量ジョブ（例 `node-cron`）で開始し、後で外部ジョブ基盤に移せるよう `services/jobs/` に閉じ込める。

## 4. 日々の計算フロー

```
04:00 JST  PMS 同期（Phase 4）→ 実績・OTB 取り込み
04:15      外部シグナル取り込み（祝日は静的、天候/イベント/競合はアダプタ）
04:30      需要予測 365日分 → 価格決定 → ForecastSnapshot に追記（上書きしない）
04:45      前日スナップショットとの差分 → 「今日の注目日」ダイジェスト生成（AiComment へ）
04:50      前日分の実績確定 → 残差計算 → 係数更新（§5）
随時       イベント登録・ランク手動変更・大きなピックアップ検知をトリガーに対象日のみ再計算
```

既存の `POST /pricing/recompute` は手動トリガーとして残す。

### 5.2 学習ロジック（段階的）

| 段階 | 手法 | 学ぶもの | 必要データ量 |
|---|---|---|---|
| L0（初日から） | 固定 prior | イベント種別×影響度、祝日パターンの初期係数 | なし |
| L1（実績30日〜） | 残差の指数平滑（EWMA）＋ 縮小推定（prior と実績の加重、サンプル数で重み移行） | ホテル別 β_k、`α(L)`（ペース信頼度）、価格弾力性 ε | 各要因 5〜10 サンプル |
| L2（実績180日〜） | オンライン Ridge 回帰（要因ベクトル→稼働率残差） | 要因間の相関を含めた係数 | 同時期の同種イベント複数 |
| L3（Phase 4） | LightGBM（リードタイム・曜日・祝日・ペース・シグナル・価格をfeature）をホテルクラスタ単位で学習。ルールベースはチャレンジャー比較の baseline として常駐 | 非線形・交互作用 | 1年以上 ＋ OTB 履歴 |

**信頼度の校正**: リードタイム区分（0–3/4–7/8–30/31–90/91+日）ごとに実績 MAPE の分布から p10/p90 を算出し、固定値 0.85 を廃止する。UI の「信頼度 85%」を「稼働率 71〜90%（中央 82%）」に置き換える。

**オーバーライド学習**: ユーザーが推奨を修正した日は、その理由と結果を残差に含める。同じ修正が繰り返される要因（例: 毎週火曜に必ず−2ランク）は「学習した習慣」として自動反映し、UI で「あなたの過去の判断から反映済み」と明示する。

### 5.3 バックテスト（モデル昇格の門番）

`backend/src/services/forecast/backtest.ts`: 過去12か月について「基準日 t に利用可能だった情報だけ」で予測を再現し、リードタイム別 MAPE・RevPAR 差を算出。`modelVersion` の昇格は「全リードタイム区分で baseline を下回らない」ことを条件にする。テスト（vitest）で seed データに対して回帰を固定する。

## 6. ユーザー体験: レベニューが増える「毎朝5分」

IDeaS は正しい価格を出すが、ユーザーは「なぜ」「今日何をすべきか」を自分で読み解く必要がある。ここで勝つ。

1. **今日決めるべき日（優先順位付き）**: 推奨≠現行の日を「期待増収額」順に上位10件。各行に理由分解の要約（「3連休中日＋アリーナ公演、ペース+18%」）と `[採用] [据え置き] [理由を書いて修正]`。
2. **昨日からの変化**: 前日スナップショット比で推奨が動いた日と動いた理由（「イベント登録により+2」「雨予報により−1」）。変化しなかった日は出さない。
3. **昨日の答え合わせ**: 確定した実績と、その日に出していた予測の差。外れたときは要因を示し、係数を更新した旨を表示（「雨の日の影響を弱めました」）。信頼を積み上げる仕組み。
4. **カレンダー**: 既存の日別セルに理由分解ポップオーバーと期待増収を追加。需要レベル A〜E は継続。
5. **月次「AI貢献レポート」**: 推奨採用率、採用日 vs 非採用日の RevPAR 差、予測精度推移、前年同月比。経営層に契約継続の根拠を渡す。
6. **ガードレール設定**: min/max ランク、1日最大変動、フロア価格、自動採用（一定信頼度以上は自動反映）の ON/OFF。自動採用こそ最終的な省力化の到達点。

## 7. 会話フィードバック（実装済み）

### 精度の評価をどう見せるか
- **アブレーション**: 要因は clamp 前に加法的なので、保存済みの要因分解から「その要因を外したときの MAPE」を再予測なしで出す。貢献が負の要因は係数を落とす候補。
- **要因別成績表**: リードタイム 1〜14 日のサンプルで、要因が効いた日の残差の平均と正の割合。平均 +3pt 超で「過小評価」、−3pt 未満で「過大評価」、5件未満は「データ不足」。
- **競合価格**: 需要側では `comp:price_index`（ln(自社価格 ÷ 競合中央値)、初期 −0.15）として効き、価格側では競合追従候補として効く。売止めは逼迫シグナルだが、団体等は人が除外する。
- **推奨の効果**: 採用日と上書き日の RevPAR を同じ需要レベル帯で比較する。採用される日には偏りがあるため、全体行は参考値と明記する。
- **価格弾力性**: 価格を基準から動かした日の実績から σ をグリッド探索し、指数平滑で `price:sigma` に反映する（8件以上で動く）。

### 会話での往復
- **システム → 人**: ダイジェスト（今日決めるべき日・変化理由・答え合わせ）と要因評価をツールとして LLM に渡し、基礎資料（`docs/knowledge/`）の章を出典として引用させる。
- **人 → システム**: 発話をツール呼び出しに変換する。イベント登録（全ロール）、採否記録・係数調整・売止め除外（MANAGER 以上）。実行後は該当期間を再計算し、前後のランクを報告する。曖昧な依頼は実行せず確認する。
- **記録**: 実行した操作は ChatMessage.actions と監査ログ（viaChat=true）に残り、採否理由は学習材料になる。

### 原則
数字は必ずツールの値（モデルに計算させない）。資料に無いことは「基礎資料に記載なし」。書き込みは明確な指示があるときだけ。
