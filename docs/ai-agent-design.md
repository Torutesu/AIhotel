## 0. この文書の目的

仕様書は4エージェント構成を「勾配ブースティング系または時系列Transformer系」と書いている。
そのまま受け取ると Python のMLスタックを別コンテナで立てる話になり、
「クラウド非依存・コンテナ1本」という現在の方針と衝突する。

実データを見て、**その前提が本当に必要かを先に検証した**。結論は §2。

## 1. まず事実確認：学習データは想像よりはるかに小さい

日次需要予測の学習サンプルは「1日 = 1行」である。手元の実データで数えると:

| 指標 | 実測値 |
|---|---|
| ReservationNight 明細行 | 47,263行 |
| **うち独立した宿泊日** | **119日** |
| データ期間 | 2025-01-01 〜 2026-08-10（実データは2025年1〜2月、他はseed） |
| 1施設・1年で得られる日次サンプル | **約365行** |
| 部屋タイプ別に分けた場合 | 365 × 16タイプ = 約5,800行/年 |

**これは機械学習の文脈では極端に小さい。**
勾配ブースティングの実力が出るのは数万〜数百万行の領域で、
数百行に対して適用すると、ハイパーパラメータ調整のコストに対して
正則化した線形モデルとの差がほとんど出ないか、むしろ過学習で悪化する。

さらに悪いことに、ホテル需要には**構造変化**がある（コロナ、インバウンド回復、
近隣の大型施設の開業）。3年前のデータを機械的に学習させると、
むしろ精度を落とす。実質的に使えるのは直近1〜2年 = **数百行**である。

### この事実から言えること

- 「毎日再学習」は正しい。ただし再学習の対象は**巨大モデルではなく小さなモデル**
- 精度を決めるのは**モデルの複雑さではなく特徴量の質**（曜日・特日・リードタイム・
  ブッキングカーブ形状・外部要因）。ここに投資すべき
- Python サイドカーを立てる技術的必然性が、**現時点では無い**

## 2. 提案：TypeScript内製 → 必要になったらPythonへ、の2段構え

### フェーズ1（今回実装する範囲）

すべて既存のExpressバックエンド内で完結させる。

| エージェント | 実装方針 |
|---|---|
| **需要予測** | 特徴量設計 ＋ **正則化線形回帰（Ridge）と勾配ブースティング木の内製実装**の2本立て。同じ特徴量で両方を学習し、検証誤差の小さい方を自動採用する |
| **価格決定** | ルール＋モデルのハイブリッド。予測稼働率・特日・外部要因・料金ランクマスタから推奨ランクを算出。**LLMは使わない**（仕様書明記） |
| **要因解説** | Claude API。`lib/` のアダプタ層に隔離し、controllers/services からは直接叩かない |
| **学習** | 承認/否認ログから特徴量重みを**定期バッチ更新**。都度の再学習はしない（F-007明記） |

**なぜ2本立てにするか**: どちらが勝つかはデータ次第で、事前には決められない。
両方を同じインターフェースで実装して**毎日の学習時に検証誤差で選ばせる**のが、
議論せずに答えを出す唯一の方法である。実装コストは木のほうが重いが、
どちらも数百行のデータなら学習は1秒未満で終わる。

### フェーズ2（フェーズ1で精度目標に届かなかった場合のみ）

Python の学習ワーカーを別コンテナで立て、ONNX で書き出したモデルを
Node 側が `onnxruntime-node` で読む。**バックエンド本体は TypeScript のまま**で、
AGENTS.md の「FastAPIへ移行しない」に抵触しない。

移行の判断基準を先に決めておく:
> 12ヶ月分の実データで交差検証し、**予測稼働率のMAEが±10%を超え続ける**なら
> フェーズ2へ。届いているならフェーズ1のまま運用する。

## 3. 4エージェントの責務と境界

```
                    ┌─────────────────┐
   PMS実績・オンハンド → │ ① 需要予測      │ → 日次の予測稼働率・確信度
   特日・外部要因      │   Forecaster    │
                    └─────────────────┘
                              ↓
                    ┌─────────────────┐
   料金ランクマスタ  → │ ② 価格決定      │ → 推奨ランクコード・推奨価格
   競合・在庫状況     │   PriceDecider  │   ＋確信度スコア
                    └─────────────────┘
                              ↓
                    ┌─────────────────┐
                    │  価格変更提案     │ ← 4Dの承認画面がここを読む
                    │  Proposal        │ → 承認/否認ログ
                    └─────────────────┘
                         ↓          ↓
              ┌──────────────┐  ┌─────────────────┐
              │ ③ 要因解説    │  │ ④ 学習          │
              │  Claude API  │  │  重みバッチ更新  │
              └──────────────┘  └─────────────────┘
                                        ↓
                                  ①②の特徴量重みへ反映
```

### 各エージェントが「触ってよいもの」

| | 入力 | 出力 | 触らないもの |
|---|---|---|---|
| ① 需要予測 | 実績・オンハンド・特日・外部要因 | 予測稼働率・確信度 | 価格。**価格を予測に混ぜない**（価格→需要→価格の循環を避ける） |
| ② 価格決定 | ①の出力・料金ランクマスタ・在庫 | 推奨ランク・確信度 | 実績の再集計（①の結果を信じる） |
| ③ 要因解説 | 予実・①②の出力 | 日本語コメント3種 | **数値の決定**。解説専用で、提案内容を変えない |
| ④ 学習 | 承認/否認ログ | 特徴量重みの更新 | モデル構造の変更（重みのみ） |

**③が数値に触らない**のは意図的な安全設計である。LLMの出力が価格に影響する経路を作らなければ、
LLMの誤りは「説明が変」で済み、「価格が壊れる」にはならない。

## 4. 確信度スコアの定義（仕様書は「付与する」としか書いていない）

仕様書は閾値を「稼働後キャリブレーション、当初は暫定値」としている。
**何を測った数字なのかは決めておかないと運用できない**ので、ここで定義する。

確信度 = 次の4つの積（各0〜1）:

| 因子 | 意味 | 低くなる条件 |
|---|---|---|
| `dataSufficiency` | 学習データの厚み | 同条件（曜日×季節×特日）の過去サンプルが少ない |
| `modelFit` | 直近の予測精度 | 直近30日の予測誤差が大きい |
| `stability` | 予約推移の安定性 | オンハンドが前年・直近トレンドから大きく外れている（**異常値検知**） |
| `horizonDecay` | 予測地平の減衰 | 遠い日付ほど下がる（180日先は当然低い） |

- 閾値の初期値: **0.70**。これ以上→自動書き込み継続、未満→**半自動モード**（オペレーター確認）
- 閾値はホテル単位で設定可能にする（稼働後のキャリブレーション用）
- 天変地異・大規模イベントのキャンセルは `stability` が落ちることで自動的に半自動へ倒れる

**確信度は「当たる確率」ではない**ことを画面にも明記する。仕様書Ⅲ章6(3)①の免責と整合させる。

## 5. 学習エージェントと 4D の依存関係（要判断）

学習エージェントの入力は**承認/否認ログ**で、これは 4D（承認・SC連携）の成果物である。
4E を 4D より先に実施する場合、ここだけ順序が逆になる。

**提案**: 価格変更提案とその判断ログの**データモデルだけを 4E に前倒しする**。

| 4E でやる | 4D でやる |
|---|---|
| `PriceChangeProposal`（提案・確信度・根拠） | 承認画面のUI |
| `ProposalDecision`（承認/否認・理由・実行者） | サイトコントローラーへの書き込み |
| 学習バッチが読む集計クエリ | 書き込みステータスの監視 |

こうすると 4E は自己完結し、4D は UI と SC 連携に集中できる。
モデルを二度設計せずに済む。

## 6. 権限（F-008）

「誰の承認・対話を学習の正とするか」は **ADMINのみ設定可能**。

- `User.isLearningSource`（Boolean）を追加し、ADMIN だけが変更できる
- 学習バッチは `isLearningSource = true` のユーザーの承認/否認のみを教師データにする
- 変更は `writeAuditLog()` の対象（誰が学習ソースを変えたかは監査対象）

理由: 新人オペレーターの誤操作が、そのままホテルの戦略として学習されるのを防ぐため。

## 7. Claude API の扱い（要因解説エージェント）

- **配置**: `backend/src/lib/claudeClient.ts`（アダプタ層）。
  services/controllers から直接 SDK を触らない（AGENTS.md のアーキテクチャ境界）
- **二次利用防止**: 仕様書Ⅲ章6(2)② の Opt-out を適用。
  Anthropic API はデフォルトで顧客データをモデル学習に使わないが、**設定として明示的に記録**し、
  クライアントに提示できる状態にする
- **送信データの最小化**: 個人情報は取込段階で排除済みだが、
  加えて**集計済みの数値と日付のみ**を送る。予約明細は送らない
- **APIキー未設定時**: コメント生成をスキップし、画面には「AIコメントは利用できません」と表示する。
  **モック文言へのサイレントフォールバックはしない**（AGENTS.md）
- **コスト**: 1ホテル1日あたり数十件のコメント生成。プロンプトキャッシュで固定部分を再利用する

## 8. 日次バッチ（Ⅲ章6(1)）

> PMS夜間バッチ検知後、深夜0時〜翌朝6時に日次の需要予測・価格ランク再計算を完了させる

今回作った取込基盤（`docs/pms-ingest-design.md` §E）と接続する:

```
PMS取込完了（IngestLog SUCCESS）
   → ① 需要予測の再学習・再予測（180日先まで）
   → ② 価格決定・提案生成
   → ③ 要因解説コメント生成
   → ④ 学習バッチ（週次。毎日は回さない）
```

- **取込完了をトリガーにする**（時刻固定ではなく）。夜間バッチの遅延に追随できる
- 全体の所要時間は数十秒〜数分の見込み（データが小さいため）。6時間の枠に対して余裕がある
- 起動方式は取込スケジューラと同じ仕組みを再利用する

## 9. 精度目標と、その測り方

仕様書の目標（フル稼働1年後測定）:

| 目標 | 測定方法 |
|---|---|
| 需要予測エラー率 ±10%以内 | 予測稼働率と実績稼働率のMAE。**予測時点別**に測る（7日前・30日前・90日前） |
| 売上 +15% | 導入前同月比。外部要因（インバウンド等）の影響を除けないため参考値 |
| 費用 50%削減 | オペレーターの作業時間。導入前ヒアリングでベースラインを取る必要あり |
| コメント承認率 90%以上 | 要因解説コメントの採用/修正/棄却をログに残して集計 |

**測定基盤を先に作る**。目標だけあって測れない状態を避けるため、
予測は必ず `modelVersion` と予測時点を添えて保存し、後から誤差を再計算できるようにする。

## 10. MLOpsモニタリング画面（仕様書 ④）

表示するもの:

- **承認率の推移**（週次）— AIの提案がどれだけ受け入れられているか
- **予測誤差の推移** — 予測時点別（7日前/30日前/90日前）のMAE
- **確信度の分布** — 半自動モードに落ちた割合
- **思考アジャスト進捗** — 学習バッチの実行履歴と、重みが更新された特徴量

「学習が進んでいる感」を出すための飾りは置かない。
**運用判断に使える数字だけ**を出す（閾値を上げ下げすべきか、半自動が多すぎないか）。
