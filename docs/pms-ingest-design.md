# PMSデータ自動取得の設計方針

作成: 2026/8/11 ／ 更新: 2026/8/11（リサーチ反映・方針転換）
ステータス: **P0/P0.5 実装着手。P1以降はクライアント確認待ち**
関連: `docs/drive-gap-analysis.md` §5.10、アコモス社`AI_Revenue_Tool_仕様書.pdf` Ⅲ章、`機能リスト.xlsx`

> **2026/8/11 改訂の要点**
> 調査の結果、**PMSの提供形態（ブラウザ／ネイティブクライアント）は公開情報から確定できなかった**（§A-0）。
> そこで**取得手段を確定させなくても進められる設計**に変更する。
> ①ファイル投入を正式な入口にする ②サイトコントローラー連携をPMS自動化より優先する
> ③PMS操作の自動化は方式が判明してから着手する。根拠は §A。

---

## 0. この文書の目的

「PMSはツールごとに個別対応が必要になるのでは」という論点に答えるための設計方針。
結論から書くと **個別対応は避けられない。ただし個別部分を"薄い1ファイル＋設定"に閉じ込められる**。
その閉じ込め方と、導入の進め方をこの文書で決める。

## A. リサーチ結果と、そこから導いた方針転換（2026/8/11）

### A-0. 「PMSはネイティブアプリか」— 確定できなかった（重要）

公開情報を当たった結果、**断定できる根拠は得られなかった**。証拠が割れている。

| 情報源 | 記述 | 示唆 |
|---|---|---|
| NEC公式 NEHOPS製品ページ | **「SaaS型で提供」**。専用オペレーターがシステム運用を行う | ホスティング型。UIがブラウザとは限らない（国内SaaSは専用クライアント＋ホスティングの例が多い） |
| EnterpriseZine / クラウドWatch | NEHOPS+ は**「クラウド化などで刷新」「オンプレミスからの移行」**として2026年度提供 | 現行NEHOPSにオンプレ構成が存在することを示唆 |
| NEC公式 | NEHOPS+ で**画面デザインを全面刷新**（オブジェクト指向UI・ドラッグ&ドロップ・画面分割） | 現行UIが古い世代であることは読み取れるが、実装技術は不明 |

さらに根本的な問題として、**新宿ワシントンが実際に使っているPMSがNEHOPSかどうかも未確認**である。
仕様書の記述は「**NEHOPS等のPMS連携に対応**」であり、これはベンダー側の対応可能範囲の宣言であって、
当該施設の導入製品を示すものではない。

**したがって、方式（ブラウザRPA / ネイティブ自動化 / API / ファイル）を前提に置いた設計はしない。**
どの方式であっても下流が変わらない構造にし、方式の確定はヒアリング（§12-1）に委ねる。
これは消極的な判断ではなく、**確定を待たずに価値のある部分を作り切るための積極的な選択**である。

> 確認の仕方（提案）: 「PMSの画面を1枚スクリーンショットで見せてください」または
> 「今CSVを出している手順を画面共有で見せてください」が最速。製品名より**実際の出力手順**が知りたい。

### A-1. 調べたこと

| 調査対象 | 分かったこと | 出典 |
|---|---|---|
| **NEHOPS（NEC）** | 約1,000ホテル導入の基幹システム。**2026年度から順次「NEHOPS+」を提供**し、**標準APIを備え、国際標準「HTNG Express」準拠を予定**。外部システム連携の接続コスト削減が目的と明言。※現行の提供形態は§A-0のとおり確定できず | NEC / 日経 / EnterpriseZine |
| **TL-リンカーン（シーナッツ）** | 国内最大手SC。**「料金ランク」機能が標準搭載**され、ランクを切り替えるだけで日常の料金調整ができる。**業界標準「TL-リンカーンフォーマット」で予約情報を出力**しPMSへ取込可能。出力項目はコード変換・置換・連結などカスタマイズ可。**2WAY連携対応PMSならPMS側から残室・料金調整**も可能 | シーナッツ |
| **国内SC大手** | TL-リンカーン / 手間いらず / ねっぱん! の3強 | 各社・比較記事 |
| **既存RMSの連携方式** | メトロエンジン等は「PMS＋SC連携」構成で、**AIが部屋タイプ別に毎日推奨価格を出し、SCへの価格変更まで一気通貫**。価格書き戻しはSC経由が業界の定石 | メトロエンジン |

### A-2. これが設計に与える影響（重要）

**① 我々の「料金ランク」はTL-リンカーンの料金ランクとそのまま対応する**

機能リストの「現在料金ランク **TL**」はTL-リンカーンの料金ランク機能を指していると考えて整合する。
つまり **SCへの書き込みは「日付 × 部屋タイプ × ランクコード」を送るだけ**で済む可能性が高い。
価格そのものを送るのではなくランク切替なので、**書き込み処理が単純で事故りにくい**。
4Cで実装した `PriceRank`（65〜0＋★1〜★5）はこの構造と噛み合っている。

**② オンハンド（予約180日）・残室はSC側から取れる可能性がある**

SCはそもそも「他システムと繋ぐための製品」であり、予約情報の標準出力フォーマットを持つ。
一方PMSはネイティブアプリで自動化が重い。
→ **日次で必要なデータ（予約・残室）はSC、月次的な確定実績（セグメント付き）はPMS**、
という分担にすると、**日次自動化の難所がネイティブPMSからSCへ移る**。これは大きい。

**③ PMS操作の自動化は、方式が判明してから着手する（かつ重投資しない）**

NEHOPS+ が2026年度から順次API提供・HTNG Express準拠予定。
導入先がNEHOPS系でその移行に乗るなら、いま作る操作自動化は**寿命の短い「つなぎ」**になる。
→ つなぎには最小限の投資に留め、**API化を待てる構造**（取得層を差し替え可能に）にしておく。
→ 方式が未確定（§A-0）である以上、**いま自動化の作り込みを始めるのは手戻りリスクが高い**。

**④ 現実として、実績CSVは既に人手でエクスポートされている**

Driveに `HG2024年CSV.zip` / `HG2025年CSV.zip` / `accommo作成HG*.xlsb` が現に存在する。
つまり**今すでに手作業でファイルが出ている**。ならば
**「ファイルを受け取る口」を正式なAPIとして持てば、その日から本番運用できる**。
自動化はその後で、同じ口に繋ぎ込むだけになる。

### A-3. 結論：優先順位を入れ替える

| 旧案 | 新案 | 理由 |
|---|---|---|
| P1 = NEHOPSコネクタ（RPA） | **P1 = ファイル投入の正式化＋運用開始** | 今日から価値が出る。ツール非依存 |
| SC連携は4Dで後回し | **P2 = SC（TL-リンカーン）連携の調査・接続** | 日次自動化の本命。読み書き両方の可能性 |
| - | **P3 = PMSネイティブ自動化（別途検討）** | 寿命が短い。NEHOPS+ API待ちの選択肢もある |

> ユーザー指摘のとおり **ネイティブアプリのRPA / Browser Use は別トラックで検討**する。
> 本文書の残りは「それ以外で確実にできる範囲」を厚くする設計とする。

## B. 「共通基盤が成立せず、1つずつ個別対応になる」リスクの評価

率直に言うと、**取得層は個別対応になる。これは避けられない**。
争点は「個別対応がどこまで**染み出す**か」で、以下の3段階で評価した。

| 層 | 個別対応が必要か | 根拠 |
|---|---|---|
| ③送信（取込API） | **不要** | 4Aで実装済み。PMSが何であれ同じ契約 |
| ②正規化（列マッピング・型変換・検証） | **設定で吸収可能** | 列名の差はプロファイルJSONで表現できる。実CSV40列で検証する（P0.5） |
| ①取得（操作） | **必要** | ここは諦める。ただし「ファイルを1つ作る」だけの薄い層に留める |

**基盤化が崩れる条件**（＝1つずつ作り直しになるケース）と、その対処:

| 崩れる条件 | 起きる確率 | 対処 |
|---|---|---|
| PMSごとにデータの**意味**が違う（例: 「室数」が延べ室数か実室数か） | 中 | プロファイルに`transforms`を持たせ、意味の変換もデータで表現。それでも足りなければプロファイル単位の変換関数をフックできるようにする |
| 取得できる**項目自体**が足りない（セグメントが無い等） | 中 | 共通スキーマを**必須項目を最小限**にして、欠けても取り込めるようにする（分析側で「不明」に寄せる。4Bのセグメント集計は既に`不明`扱いを実装済み） |
| ファイルが**1本にまとまらない**（予約と実績が別画面・別形式） | 高 | dataset単位（nights/reservations/inventory）で独立して投入できる設計にする（4Aで既にそうなっている） |
| PMSが**そもそもエクスポートを持たない** | 低 | その場合はSC側から取る（§A-2②）。それも無ければ手動運用 |

**したがって「基盤 + 個別最適化」は成立する見込みが高い**と判断する。
ただし成立を担保するのは**②を設定データで駆動すること**で、
これはP0.5で実CSVを流して実証する（＝机上で終わらせない）。

## 2. 基本方針：3層に分けて、ツール差を最下層だけに閉じ込める

```
┌─────────────────────────────────────────────┐
│ ③ 送信層（全ツール共通・変更なし）              │
│    POST /api/v1/ingest/pms/{nights,reservations,inventory}
│    ※ 4Aで実装済み。冪等・全量置換・IngestLog記録   │
├─────────────────────────────────────────────┤
│ ② 正規化層（全ツール共通）                      │
│    生の表 → 共通スキーマへ変換                   │
│    ・列名マッピング適用（プロファイル駆動）        │
│    ・型変換／日付正規化／1泊単位展開              │
│    ・必須項目検証（zodと同じ契約）               │
├─────────────────────────────────────────────┤
│ ① 取得層（★ここだけツールごと）                  │
│    ログイン → 画面遷移 → 条件入力 → CSVダウンロード │
│    PmsConnector インターフェースを実装する          │
└─────────────────────────────────────────────┘
```

**ポイント**: ②③は一度作れば全PMS共通。新しいPMSが増えても触らない。
①も「操作手順」だけで、データの解釈は②に任せる（＝コネクタは`Buffer`を返すだけ）。

### 何が共通で、何がツールごとか

| 関心事 | 共通 | ツールごと |
|---|:---:|:---:|
| スケジュール実行・リトライ・多重起動防止 | ● | |
| 認証情報の暗号化保管・取り出し | ● | |
| バッチ完了検知の**枠組み** | ● | |
| バッチ完了検知の**判定方法**（どこに日付が出るか） | | ● |
| ログイン操作・画面遷移・CSV出力操作 | | ● |
| ダウンロードファイルの受け取り | ● | |
| 文字コード（Shift_JIS/UTF-8）・CSV/Excel判定 | ● | |
| **列名 → 共通項目のマッピング** | | ●（ただしコードではなく**設定データ**） |
| 型変換・日付正規化・1泊展開・検証 | ● | |
| 取込APIへの送信・冪等制御・ログ | ● | |
| UI変更の検知とアラート | ● | |
| AIエージェントへのフォールバック | ● | ●（起点の指示文のみ） |

→ **新しいPMSを1つ増やす作業 = コネクタ1ファイル（操作手順）＋マッピングJSON1つ**

## 3. 取得方式のフォールバック階梯

上から順に試し、無理なら下へ落ちる。**同じ`PmsConnector`インターフェースの実装違い**として扱う。

| 優先 | 方式 | 使う条件 | 安定性 | 備考 |
|---|---|---|:---:|---|
| 1 | **公式API / DB直** | PMSがAPIを提供、または連携用エクスポートがある | ◎ | 最優先で確認する。あるなら迷わずこれ |
| 2 | **定型RPA（Playwright）** | Web UIでCSV出力できる | ○ | 仕様書の想定する既定手段 |
| 3 | **AIエージェント操作（Browser Use等）** | UI変更で2が壊れた／画面構造が不定 | △ | 仕様書Ⅲ章2の「AIエージェントによる操作に切り替え」 |
| 4 | **手動アップロード** | 上記すべて不可・OTA販促データ等 | - | 管理画面からCSVを投げる導線を用意（仕様書Ⅱ章6(3)②の「手動移行への切り替え」） |

**設計上の要点**: 2で壊れたときに3へ自動フォールバックできるよう、
「何を取りたいか（＝取得したい期間・データ種別）」を宣言的に持ち、
操作手順は交換可能にする。3は毎回使うと不安定かつ高コストなので**復旧用の非常口**と位置づけ、
成功したらその操作をログに残して2の手順修正の材料にする。

## 4. コネクタのインターフェース案

```ts
// backend/src/connectors/pms/types.ts（案）
export type PmsDataset = 'nights' | 'reservations' | 'inventory'

export interface PmsFetchRequest {
  dataset: PmsDataset
  /** 実績=前日1日 / 予約=当日から180日 のように呼び出し側が期間を決める */
  from: Date
  to: Date
}

export interface PmsFetchResult {
  /** ダウンロードした生ファイル（CSV/Excel）。解釈しない */
  content: Buffer
  fileName: string
  /** 監査・UI変更検知用 */
  fetchedAt: Date
  method: 'api' | 'rpa' | 'agent' | 'manual'
}

export interface PmsConnector {
  readonly id: string          // 'nehops' / 'tl-lincoln' など
  readonly displayName: string

  /** PMSの夜間バッチ（日付更新）が完了しているか（仕様書Ⅲ章3.2） */
  isBatchReady(ctx: PmsContext): Promise<{ ready: boolean; pmsDate?: Date; reason?: string }>

  fetch(req: PmsFetchRequest, ctx: PmsContext): Promise<PmsFetchResult>
}

export interface PmsContext {
  hotelId: string
  credentials: PmsCredentials   // 復号済み。メモリ上のみ
  profile: PmsProfile           // 列マッピング等（§5）
  logger: IngestLogger
}
```

**コネクタは「取ってくる」だけ**にする。パース・変換・送信を持たせない。
これでツールごとのコード量が最小になり、テストもファイル比較で済む。

## 5. 列マッピングは「コード」ではなく「設定データ」にする

ここが個別対応コストを一番左右する。列名の差はコードで分岐せず、プロファイルで吸収する。

```jsonc
// profiles/nehops-hg.json（案）
{
  "id": "nehops-hg",
  "encoding": "shift_jis",
  "format": "csv",
  "headerRow": 1,
  "datasets": {
    "nights": {
      "map": {
        "stayDate":            "計上日",
        "roomTypeCode":        "部屋タイプ",
        "rateTypeCode":        "料金タイプ",
        "packageCode":         "パッケージコード",
        "rooms":               "室数",
        "guests":              "人数計",
        "guestsDetail.male":   "男人数",
        "guestsDetail.female": "女人数",
        "guestsDetail.child":  "子供人数",
        "roomRevenue":         "室料NET",
        "serviceFee":          "サービス",
        "agentCode":           "エージェントコード",
        "regionCode":          "地域コード",
        "marketCode":          "Market(市場)コード",
        "individualGroupType": "個人団体区分",
        "buildingCode":        "棟コード",
        "blockCode":           "ブロック",
        "checkIn":             "チェックイン日",
        "checkOut":            "チェックアウト日",
        "isDayUse":            "デイユースフラグ",
        "compHuType":          "COMP/HU区分"
      },
      "transforms": {
        "isDayUse": "flag01",        // "0"/"1" → boolean
        "stayDate": "date:YYYY-MM-DD"
      }
    }
  }
}
```

- **右辺（PMS側の列名）だけを差し替えれば新PMSに対応できる**構造にする
- 左辺は取込APIのzodスキーマと1:1（`ingestNightRowSchema` — 4Aで実装済み）
- プロファイルはリポジトリ管理（レビュー可能・差分が追える）。将来ホテルごとに変えたくなったらDB移行
- 新宿ワシントンの実CSV40列のうち、計算済み列（ADR/サ込み/泊数/件数/リードタイム）は**取り込まない**
  （システム側で再計算する。二重定義を避ける）
- 同梱の「コードマスター7」シートは**セグメントマスタ取込**（`PUT /settings/segments`）に回す

## 6. 新しいPMSを追加するときの手順とコスト目安

| # | 作業 | 担当 | 目安 |
|---|---|---|---|
| 1 | CSV出力項目のヒアリング＋出力設定（個人情報除外を含む） | 導入担当＋ホテル | 1〜2時間の打合せ |
| 2 | サンプルCSVを1本もらう | ホテル | - |
| 3 | プロファイルJSON作成（列マッピング） | 開発 | **0.5日** |
| 4 | コネクタ実装（ログイン→出力画面→条件入力→DL） | 開発 | **1〜3日**（画面数と癖に依存） |
| 5 | バッチ完了検知の判定方法を決めて実装 | 開発 | 0.5日 |
| 6 | 実データで取込→分析画面までの疎通確認 | 開発 | 0.5日 |

→ **1PMSあたり おおむね2.5〜4.5人日**（API提供ありなら1〜2人日）。
既存の②③層に手が入らないことが前提。**この前提を守るのが本設計の目的**。

> 注: 上記はPMSがWeb UIでCSV出力でき、認証にSMS/ワンタイム等の追加要素が無い場合の見積り。
> 二要素認証・VPN必須・Windowsデスクトップアプリの場合は別途見積りが必要（§8リスク）。

## 7. 実行基盤をどこに置くか

仕様書Ⅲ章2に沿って2形態を用意する。**同じコネクタが両方で動く**ようにする。

| 形態 | 条件 | 構成 |
|---|---|---|
| **A: クラウド実行** | PMSがインターネット経由でアクセス可能 | ECS Scheduled Task上のPlaywrightコンテナ。開発企業側で完結（仕様書「処理の実行主体は開発企業側」） |
| **B: ホテル端末経由** | 施設内ネットワークからのみアクセス可 | ホテル既存端末に常駐エージェント。**取得したデータは端末に保持しない**、HTTPS一方向でクラウドへ送信 |

Aを既定とし、Bは同じコードを別の起動形態で動かす（差はネットワーク到達性だけ）。
Bのときも認証情報はクラウドのSecrets Managerから取得し、端末に置かない設計を第一候補とする
（端末保管が避けられない場合はOSの資格情報ストア＋暗号化）。

## 8. UI変更への備え（仕様書Ⅱ章6(3)②のリスク項目）

1. **セレクタを1箇所に集約**：コネクタ内でCSSセレクタを定数化。画面変更時の修正点を明示化
2. **各ステップにアサーション**：期待する画面要素が無ければ即中断（誤ったファイルを掴まない）
3. **取得結果の健全性チェック**：列数・必須列の有無・行数の対前日比。異常なら取込せずアラート
4. **失敗時のスクリーンショット＋HTML保存**：原因調査用（個人情報が写り込む可能性があるため保存先と保持期間を限定）
5. **AIエージェントへのフォールバック**：2回連続失敗でエージェント方式に切替、成功操作をログ化
6. **アラート先**：運用オペレーター＋アコモス社サポート（メール/Webhook。仕様書Ⅲ章3.4）

## 9. サイトコントローラー書き込み（4D）も同じ構造にする

PMS取得と鏡写しの構造にして、コネクタ層のノウハウを流用する。

**先にPMS取得をやる価値はここにもある**（基盤が共通）。

## C. P0/P0.5 の実施結果（2026/8/11）

### C-1. 実データでの疎通結果

`HG2025年CSV.zip / CSV202501HG.xlsx`（6.9MB・2025年1月分）を実APIに投入した結果:

| 指標 | 結果 |
|---|---|
| データ行数 | **24,235行** |
| 検証で弾かれた行 | **0行** |
| プロファイルが期待して**ファイルに無かった列** | **0列** |
| ファイルにあるが**マッピングも除外指定もされていない列** | **0列** |
| 取込所要時間 | 約10秒 |
| 分析API（セグメント別）での集計 | 12セグメント・27,205室・売上6.65億を集計。**地域名がマスタから解決**（中国/オーストラリア/アメリカ/韓国/香港…） |

→ **「基盤＋プロファイル」で実データが端から端まで通ることを実証できた**（机上の設計で終わっていない）。

### C-2. 実データ投入で見つかった不具合（修正済み）

seedの小規模データでは顕在化せず、実データ量で初めて出た:

- **Prismaの対話トランザクションが既定5秒で切れる**（24,235行の処理に9.4秒かかりROLLBACK）
  → タイムアウトを明示し、`createMany`を2,000行ずつチャンク分割して修正。修正後は約10秒で完了

### C-3. 分かった運用上の注意

- **マスタに無いコードは名前解決されずコードのまま出る**（例: 市場コード `FST` `OPT` `JAR`）。
  マスタ設定.xlsxのMarketシートは30件だが、実データにはそれ以外のコードも現れる。
  → 分析は落ちない（コード表示にフォールバック）が、**導入時にマスタの棚卸しが要る**。
    §12に確認事項として追加。
- 6.9MBのファイルはbase64で9.2MBになり、現在の受信上限（10MB）にほぼ達する。
  **月次より大きい単位のファイルは分割投入が必要**。将来的には署名付きURLでの
  直接アップロードに移行する（P2の課題として記録）。

## 11. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| PMSがWebでなくデスクトップアプリ | RPA方式が根本から変わる | **未確定（§A-0）**。ヒアリング最優先（§12-1）。該当時はWindows常駐エージェント＋UI Automation（別トラックで検討）。本設計はどちらでも下流が変わらないため、判明まで待てる |
| そもそも導入PMSがNEHOPSではない | 調査前提が崩れる | 製品名でなく**実際のエクスポート手順とサンプルファイル**を起点にする設計（P0）にしてある |
| 二要素認証・IP制限 | 自動ログイン不可 | 専用アカウントの発行と認証方式の緩和をホテル側に依頼。不可なら形態B＋端末の既存セッション利用 |
| PMS側の利用規約でRPA禁止 | 方式変更 | 導入前にPMSベンダー確認。API提供の有無もここで確認 |
| 個人情報の混入 | 重大インシデント | 出力設定で除外（一次）＋取込時に既知の個人情報カラム名を**拒否**（二次防御）。両方入れる |
| PMS仕様変更 | 取得停止 | §8の検知＋アラート。プロファイルで吸収できる範囲は設定変更のみで復旧 |
| 施設ごとにPMSが異なる | コスト増 | §6の見積りが施設数分。早期に全施設のPMSを棚卸し |

## 12. クライアント確認事項（この設計の前提を固めるため）

1. **新宿ワシントンのPMS製品名と、いまCSVを出している実際の手順** ← 最優先。
   製品名だけでなく「どの画面で何を押すと `HG2025年CSV` 相当が出るか」を画面共有かスクリーンショットで。
   ブラウザかネイティブクライアントかはここで判明する（公開情報では確定できなかった — §A-0）
2. 予約（オンハンド180日）のCSV出力が実績と同じ項目で出せるか。出せない場合の代替
3. 自動化用アカウントの発行可否と、二要素認証・IP制限の有無
4. PMSベンダーのAPI提供有無、およびRPA利用の可否（規約確認）
5. 対象施設の一覧と、施設ごとのPMS製品
6. サイトコントローラー製品名（TLリンカーンで合っているか）
7. 日次実行時刻（PMS夜間バッチの完了時刻に依存。仕様書Ⅲ章3.2）
8. **マスタの棚卸し**: 実データに現れる市場コード（`FST`/`OPT`/`JAR` 等）がマスタ設定.xlsxに無い。
   最新のコードマスターをもらえるか、または同梱の「コードマスター7」シートを正とするか（§C-3）

## 13. この設計で答えていること

> 「PMSツールごとに対応しないといけないのでは？」

→ **はい、①取得層だけは必要**。ただし
- 契約（取込API・共通スキーマ）を先に固定してあるので、②③は増えない
- 列の差は**設定データ**で吸収し、コード分岐にしない
- 1ツールあたり**2.5〜4.5人日**に収まる見込み
- 同じ構造をサイトコントローラー書き込みにも流用でき、基盤が二度おいしい

→ さらに **P0.5 で実CSVを使って正規化層まで検証できる**ので、
PMS接続が確定する前に価値のある部分を作り切れる。
