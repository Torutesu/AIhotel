## 2. レイヤ構成と責務

### 2.1 バックエンドのレイヤ

```
routes/        ルーティング、ミドルウェア適用（認証・認可・検証）
  ↓
controllers/   HTTP入出力の変換、監査ログ呼び出し
  ↓
services/      業務ロジック、永続化
  ↓
lib/           config・prisma・auth・validators・storage
```

各層の制約は以下のとおり。ESLint により機械的に検証される。

| 層 | 許可されること | 禁止されること |
| --- | --- | --- |
| `routes/` | ミドルウェア適用、コントローラ呼び出し | Prisma の import |
| `controllers/` | サービス呼び出し、レスポンス生成、監査ログ記録 | Prisma の import |
| `services/` | Prisma 利用、業務ロジック | `process.env` の直接参照 |
| `lib/config.ts` | `process.env` の読み取り | — |

`process.env` の読み取りは `lib/config.ts` の1箇所に限定する。これは環境変数とシークレットの読み込み経路を単一にし、実行基盤を変更する際の影響範囲を限定するためである。

### 2.2 ディレクトリ名の注意

ミドルウェアの配置は `backend/src/middlewares/`（複数形）である。単数形 `middleware/` は存在しない。

## 4. 需要予測・価格算出ロジック

### 4.1 インタフェース

将来の機械学習モデルへの差し替えを可能にするため、予測器はインタフェース経由で呼び出す（`services/forecast/types.ts`）。

```ts
export interface DemandForecaster {
  name: string
  forecast(input: ForecastInput): Promise<DailyForecast[]>
}

export interface DailyForecast {
  date: Date
  predictedOccupancy: number
  demandLevel: ForecastDemandLevel   // 'A' | 'B' | 'C' | 'D' | 'E'
  recommendedRank: number | null
  recommendedPrice: number | null
  confidence: number
  modelVersion: string
}
```

現行実装は `ruleBasedForecaster`（`MODEL_VERSION = 'rule-based-v1'`）である。

### 4.2 定数

`services/forecast/ruleBasedForecaster.ts:9-24`

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `DEFAULT_MAX_RANK` | 40 | 料金ランク未設定時のフォールバック上限 |
| `MOVING_AVERAGE_WINDOW_DAYS` | 28 | 同曜日移動平均の窓 |
| `YEAR_OVER_YEAR_TOLERANCE_DAYS` | 3 | 前年同時期の許容ずれ |
| `FALLBACK_OCCUPANCY` | 0.6 | 実績が皆無の場合の基準稼働率 |
| `EVENT_IMPACT_PT` | high 0.15 / medium 0.08 / low 0.03 | イベント影響（稼働率への加算幅） |
| `WEEKEND_ADJUSTMENT_PT` | 0.05 | 週末補正 |

週末補正が控えめな値であるのは、同曜日移動平均が既に週末パターンを内包しており、二重計上を避けるためである。

### 4.3 算出手順

対象日ごとに以下を順に算出する。

**手順1: 同曜日移動平均**（`computeMovingAverageBySameWeekday`）
対象日から遡って28日以内、かつ対象日と同じ曜日の実績稼働率の単純平均。該当実績がなければ `null`。

**手順2: 前年同時期**（`computeYearOverYearOccupancy`）
対象日の1年前から±3日以内で最も近い実績日の稼働率。該当がなければ `null`。

**手順3: イベント影響**（`computeEventImpact`）
対象日を期間に含む `Event` の `expectedImpact` を加算する。複数該当時は合算する。

**手順4: 週末補正**（`computeWeekendAdjustment`）
対象日の曜日が `Hotel.weekendDays` に含まれる場合のみ 0.05 を加算する。週末の定義はハードコードせず、必ずホテル設定を参照する。

**手順5: 予測稼働率の合成**（`computePredictedOccupancy`）

| 手順1 | 手順2 | 基準値 |
| --- | --- | --- |
| あり | あり | `movingAverage × 0.7 + yearOverYear × 0.3` |
| あり | なし | `movingAverage` |
| なし | あり | `yearOverYear` |
| なし | なし | `0.6`（フォールバック） |

基準値に手順3・手順4を加算し、小数第3位で丸め、`[0, 1]` にクランプする。

**手順6: 需要レベル判定**（`mapOccupancyToDemandLevel`）

| 予測稼働率 | 需要レベル |
| --- | --- |
| > 0.9 | A |
| > 0.8 | B |
| > 0.65 | C |
| > 0.5 | D |
| 上記以外 | E |

**手順7: 推奨ランク**（`mapOccupancyToRank`）
`round(予測稼働率 × maxRank)` を `[1, maxRank]` にクランプする。`maxRank` はホテルの有効な `PriceRank` の最大値、未設定なら40。

**手順8: 推奨価格**
`PriceRank.price1P` を推奨ランクで引く。該当ランクがなければ `null`。

**手順9: 確信度**（`computeConfidence`）

| 利用できたデータ | 確信度 |
| --- | --- |
| 移動平均・前年比較の両方 | 0.85 |
| 移動平均のみ | 0.7 |
| 前年比較のみ | 0.6 |
| どちらもなし | 0.4 |

### 4.4 DBアクセス

`ruleBasedForecaster.forecast()` は以下を並行取得する。

- `Hotel`（`weekendDays` 取得。存在しなければ `NotFoundError`）
- `DailyData`: 開始日の400日前から開始日直前まで、`occupancy` が非NULLのもの。400日は移動平均28日と前年比較365日の双方を賄うための窓
- `Event`: 対象期間と重なるもの
- `PriceRank`: `isActive` のもの

純粋関数（手順1〜9）はDBに依存せず、単体テストの対象となる。

### 4.5 予測結果の永続化

`services/forecast/forecastService.ts` の `recomputeForecastService(hotelId, startDate?, endDate?, forecaster?)` が予測を実行し、`AiPriceRecommendation` へ保存する。既定の予測期間は90日。

`AiPriceRecommendation` は `@@unique([hotelId, date, roomTypeId])` を持つが、現在の運用では `roomTypeId` が NULL（ホテル全体の予測）である。PostgreSQL では NULL を含む複合一意キーが一意制約として機能しないため、Prisma の `upsert` は使用できない。`upsertHotelWideRecommendation` にて `findFirst` → `create` / `update` の手順で代替している。

### 4.6 価格戦略の重み付け

`PricingStrategyConfig` は以下を保持する。ホテルごとに1件（`hotelId @unique`）。

| フィールド | 既定値 | 制約 |
| --- | --- | --- |
| `weightOccupancy` | 40 | 0〜100の整数 |
| `weightAdr` | 40 | 0〜100の整数 |
| `weightCompetitor` | 20 | 0〜100の整数 |

3つの合計が100であることを `updateStrategySchema` の `refine` で強制する。

#### 4.6.1 算出方式

`services/forecast/strategyWeighting.ts` にて、3観点をそれぞれ料金ランクへ写像し、重みで加重平均する。

| 観点 | ランクへの写像 | 意味 |
| --- | --- | --- |
| 稼働率 | 手順7で得た予測稼働率由来のランク | 需要の強さに価格を追随させる |
| ADR | 直近28日の**同曜日**ADR平均に最も近い価格のランク。同曜日実績が無い場合は窓内全体の平均 | 達成ADR実績に価格を追随させる |
| 競合 | **対象日**の競合平均価格（`price1P`）に最も近い価格のランク | 競合の価格水準に追随させる |

価格からランクを引く際（`mapPriceToRank`）、距離が同着の場合は**下位ランク（安い側）**を採用する。丸めによって意図せず値上げ方向へ寄ることを防ぐためである。

#### 4.6.2 データ欠損時の重み按分

ADR実績や競合価格は日によって存在しない。欠損した観点を「ランク0」として扱うと推奨価格が不当に引き下がるため、**欠損した観点は合成から除外し、その重みを残る観点へ按分する**（`blendRanksByStrategy`）。

| 状況 | 実効重み |
| --- | --- |
| 3観点すべて利用可 | 設定値どおり（例 40 / 40 / 20） |
| 競合価格が無い日 | 稼働率 67 / ADR 33 / 競合 0 に按分 |
| 有効な観点が1つも無い | 稼働率100（最終防衛線。稼働率は常に算出可能） |

重み0の観点も合成対象から除外する。

合成結果は `[1, maxRank]` にクランプする。

#### 4.6.3 戦略設定が存在しないホテル

`PricingStrategyConfig` の行が無いホテルでは、稼働率100%（`OCCUPANCY_ONLY_WEIGHTS`）として扱い、従来どおり予測稼働率のみで推奨ランクを決定する。既存ホテルの挙動を変えないための措置である。

#### 4.6.4 需要レベルとの独立性

需要レベル（A〜E）は**需要の大きさ**を表す指標であり、価格戦略とは独立させる。重み付けの影響を受けるのは `recommendedRank` と `recommendedPrice` のみで、`demandLevel` は従来どおり予測稼働率のみから判定する。

#### 4.6.5 モデルバージョン

本変更により算出結果が変わるため、`MODEL_VERSION` を `rule-based-v1` から `rule-based-v2` へ更新した。`AiPriceRecommendation.modelVersion` に記録され、どの方式で算出された値かを判別できる。

#### 4.6.6 未確定事項

各観点をランクへ写像する方式は、要件として確定していない。現行実装は「ADRは直近実績に、競合は当日の競合平均に追随させる」という初版の解釈である。以下は確認を要する（基本設計書 Q-10）。

- ADR観点の参照窓（現行28日・同曜日優先）が妥当か
- 競合観点で `price1P`（1名料金）のみを見てよいか。人数別料金や部屋タイプを考慮すべきか
- 競合平均に単純平均を用いてよいか。`reliability` による重み付けや外れ値除外の要否
- 競合より高く/安く設定するといった相対ポジションの指定が必要か

## 5. KPI算出ロジック

`services/dashboardService.ts` の `getDashboardKpiService`。

### 5.1 実績集計

「実績のある日」を `DailyData.totalRevenue` が非NULLの行と定義し、以下を算出する。

| 指標 | 算出式 |
| --- | --- |
| 販売可能室数（roomNights） | `Hotel.totalRooms × 実績日数` |
| ADR | `総売上 ÷ 総販売室数` |
| 稼働率 | `総販売室数 ÷ roomNights` |
| RevPAR | `総売上 ÷ roomNights` |
| DOR | `総宿泊人数 ÷ 実績日数` |
| 客単価 | `総売上 ÷ 総宿泊人数` |

### 5.2 予算・前年比較

月の途中では予算・前年実績を月全体と比較すると過小評価になるため、経過日数で按分する。

```
elapsedRatio = 実績日数 ÷ 当月日数
比較対象値 = 予算（または前年実績） × elapsedRatio
```

### 5.3 日次推移

過去日は実績値、将来日は `AiPriceRecommendation` の予測値を用いて系列を構成する。

> **注記**: 上記の算出式は `dashboardService.ts`、`reportsService.ts`、`analysisService.ts` の3箇所に個別に実装されており、共通化されていない。`shared/utils/index.ts` に `calculateADR` / `calculateOccupancy` / `calculateRevPAR` が存在するが、バックエンドからは参照されていない。算出定義を変更する場合は3箇所すべてを更新する必要がある。

## 6. 認証・認可の実装詳細

### 6.1 トークン

`lib/auth.ts`

| 関数 | 仕様 |
| --- | --- |
| `hashPassword` | bcrypt、コスト12 |
| `verifyPassword` | bcrypt 比較 |
| `generateAccessToken` | JWT。ペイロードは `{userId, email, role, tenantId, hotelId}` |
| `generateRefreshToken` | ランダム文字列 |
| `hashToken` | SHA-256。DB保存用 |
| `getRefreshTokenExpiry` | 既定7日 |

`RefreshToken.tokenHash` は `@unique` であり、平文は保存しない。

### 6.2 リフレッシュのローテーション

`refreshTokenService` は、提示されたリフレッシュトークンを検証したうえで新しいトークン対を発行し、旧トークンを無効化する。

### 6.3 認可ミドルウェア

`middlewares/auth.ts`

| 関数 | 動作 |
| --- | --- |
| `authenticate` | `Authorization: Bearer` を要求。欠落・不正形式・検証失敗はすべて401。成功時 `req.user` を設定 |
| `requireRole(...roles)` | `req.user` 未設定なら401、ロール不一致なら403 |
| `requireHotelAccess(extractor)` | **ADMIN は全検証を通過する**。抽出した hotelId が空なら400、`req.user.hotelId` と不一致なら403 |

`optionalAuth` と `requireSelfOrAdmin` は定義されているが、いずれのルートからも使用されていない。

> **設計上の注意**: `requireHotelAccess` の ADMIN バイパスにより、ADMIN ロールは全テナントの全ホテルへアクセスできる。これはシステム提供側の運用を想定した仕様である。テナント間の分離を厳格に保つ必要がある場合、ADMIN の権限範囲を再定義する必要がある（基本設計書 Q-01 と関連）。

## 7. 入力検証仕様

`lib/validators.ts` に全スキーマを定義し、`middlewares/validate.ts` の `validate(schema, target)` で適用する。

### 7.1 検証の動作

`validate` は検証後の値で `req[target]` を上書きする。これにより後続処理は型変換済みの値を受け取る。検証失敗時は `ApiError(400, 'バリデーションエラー', fieldErrors)` を送出する。

コントローラおよびサービスは、生の `req.body` / `req.query` を参照してはならない。

### 7.2 主要スキーマ

| スキーマ | 制約 |
| --- | --- |
| `entityIdSchema` | `[A-Za-z0-9_-]{1,64}`。cuid 形式に限定しない（seed の `demo-hotel-001` 等を許容するため） |
| `registerSchema` | パスワード8文字以上、大文字・小文字・数字を各1文字以上含む |
| `createPriceRankSchema` | `rank` は 1〜40。上限超過時のメッセージは「料金ランクは最大40段階です」 |
| `updateStrategySchema` | 3つの重みが各0〜100、合計100 |
| `updateHotelSettingsSchema` | `weekendDays` は 0〜6 の整数配列、最大7要素 |
| `monthlyReportQuerySchema` | `format` は `pdf` / `excel` |
| `recomputeForecastSchema` | 期間指定は任意。開始日 ≤ 終了日 を検証 |

### 7.3 未使用スキーマ

以下は定義されているが、いずれのルートにも適用されていない。対応機能が未実装であることを示す。

`createRoomTypeSchema` / `updateRoomTypeSchema`、`createDailyDataSchema` / `updateDailyDataSchema` / `bulkUpdateDailyDataSchema`、`createCampaignSchema` / `updateCampaignSchema`、`dailyDataQuerySchema`、`pricingQuerySchema`、`idParamSchema`、`dateRangeSchema`

## 9. 監査ログ仕様

`services/auditService.ts` の `writeAuditLog(entry)` が `AuditLog` へ記録する。

### 9.1 記録項目

`userId`、`action`（CREATE / UPDATE / DELETE / LOGIN / LOGOUT）、`entity`、`entityId`、`oldValue`、`newValue`、`ipAddress`、`userAgent`

### 9.2 失敗時の扱い

監査ログの書き込みに失敗した場合、例外を送出せずログ出力のみを行う。監査記録の失敗が業務操作そのものを失敗させないための設計である。

> **運用上の含意**: この設計により、監査ログの欠落は呼び出し側に伝播しない。監査記録の完全性が要求される場合は、書き込み失敗の検知を別途監視で担保する必要がある。

### 9.3 記録対象

| 対象 | 記録箇所 |
| --- | --- |
| ログイン・ログアウト | `authService.ts` |
| ホテルの作成・更新・削除 | `hotelsController.ts` |
| 料金ランクの作成・更新・削除、ホテル設定変更 | `settingsController.ts` |
| 価格戦略更新、需要予測再計算 | `pricingController.ts` |
| イベントの作成・更新・削除 | `eventsController.ts` |

参照系（GET）およびレポート出力は監査対象外である。

## 10. レポート出力仕様

`services/reportsService.ts` の `getMonthlyReportService(hotelId, year, month, format)`。

| 形式 | 生成ライブラリ |
| --- | --- |
| Excel | ExcelJS |

pdfkit の既定フォントは日本語グリフを持たず文字化けするため、`backend/assets/fonts/NotoSansJP-Regular.ttf` を同梱して埋め込む。

## 11. フロントエンド詳細設計

### 11.1 ルーティング

App Router 上のルートは `/` の1件のみ（`frontend/app/page.tsx`）。`AuthProvider` の内側に `MainLayout` を配置し、以降の画面遷移はクライアント側のタブ状態で制御する。

`next.config.mjs` にて `/api/:path*` を `NEXT_PUBLIC_BACKEND_URL`（既定 `http://localhost:3001`）へリライトする。`@shared` エイリアスで `shared/` を参照する。

### 11.2 タブ構成

`shared/types` の `Tab` 型に対応する7区分。

| タブ | 表示名 | 主な呼び出しAPI |
| --- | --- | --- |
| `dashboard` | ダッシュボード | `dashboardKpi`, `alerts`, `aiSummary`, `hotels` |
| `pricing` | ダイナミックプライシング | `pricingCalendar`, `pricingStrategy`, `events` 系 |
| `daily` | 日別分析 | `bookingCurve`, `competitorPrices` |
| `analysis` | 各種分析 | `monthlyTrend`, `competitorAnalysis` |
| `reports` | レポート | **なし（静的表示）** |
| `ai-summary` | AIまとめ | **なし（静的表示）** |
| `settings` | 設定 | `hotels`, `priceRanks`, `updatePriceRank`, `updateHotelSettings` |

`chat-interface.tsx`、`campaign-participation-manager.tsx`、`segment-cross-analysis-settings.tsx` はいずれもAPIを呼ばず、ローカル状態のみで動作する。

### 11.3 API呼び出し層

`frontend/lib/api.ts`（822行）の構成。

1. **トークン保管**: localStorage キー `hrms.accessToken` / `hrms.refreshToken`
2. **`ApiClientError`**: `status` と `isBackendUnreachable` を保持
3. **開発専用デモモード**: `NODE_ENV !== 'production'` かつ `NEXT_PUBLIC_DEMO_MODE === 'true'` の場合のみ有効。`withDemoFallback()` は**バックエンドへ到達できない場合に限り**モックへ切り替える。通信できているがエラーを返した場合はフォールバックしない
4. **`rawRequest<T>`**: Bearer 付与、401 を受けたら `tryRefresh()` を1回だけ実行して再試行、`body.data` を展開して返す
5. **型定義**: レスポンス契約の型
6. **モック生成**: シード付き乱数。需要レベルの閾値と40段階ランクの写像はバックエンドと同じ値を持つ
7. **`api` オブジェクト**: 21関数

> **設計上の注意**: モックのしきい値（A〜E の境界、40段階ランク）はバックエンドのロジックを複製したものであり、共通化されていない。バックエンド側の閾値を変更した場合、`frontend/lib/api.ts` の該当箇所も更新しないと、デモモードと実環境で表示が食い違う。

### 11.4 未接続API

基本設計書 4.4 に記載のとおり、バックエンドに存在するが `lib/api.ts` に対応関数がないエンドポイントがある。画面から利用する場合は API 層への関数追加が必要である。
