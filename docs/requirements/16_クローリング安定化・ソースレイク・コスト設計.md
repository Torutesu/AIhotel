# 16. クローリング安定化・ソースレイク・コスト設計

版: 0.1（ドラフト）
本書は15の実行方式を3つの観点で深掘りする: (A) **Browser Use型エージェント vs 決定的スクレイピングの使い分けと「取れないと致命的」への安定化設計**、(B) **SNS等を係数化せずソースとして厚く貯める「ソースレイク」**、(C) **クロール・API・LLMの実費見積りとコスト最適化**。

---

## A. 取得方式の使い分けと安定化

### A-1. 結論: 「LLMエージェントに日次運用させない」

Browser Use / computer-use 型のLLMブラウザエージェントは「毎回LLMが画面を見て判断する」方式であり、次の理由で**日次の定常クロールには不適**:

- **非決定性**: 同じページでも実行ごとに挙動が揺れる。価格に直結するデータで「たまに取れない・たまに違う場所を読む」は許容できない
- **コスト**: 1ページごとにスクリーンショット+推論でLLM呼び出しが数回〜数十回走る。決定的スクリプトの100〜1000倍のコスト
- **速度**: 1ページ数十秒。巡回数が増えるとバッチ時間を圧迫
- **監査性**: 「なぜこの値を取ったか」の再現が難しい

ただしエージェントが**圧倒的に強い場面が2つ**あり、そこに限定して使う:

| 場面 | 使い方 |
| --- | --- |
| ① 新規ソースのパーサ初期構築 | エージェントに1回だけページを探索させ、「一覧のセレクタ・ページネーション・詳細ページの構造」を発見させる → 出力は**決定的スクリプト（セレクタ定義）**として保存し、以後はそれを実行 |
| ② 破損時の自己修復 | パース失敗検知（件数激減・スキーマ不一致）→ エージェントが新HTMLを解析し**修正セレクタ案+新旧の抽出結果差分**を提示 → 人間承認でパーサ更新（自動適用しない） |

つまり **「エージェントはスクリプトを書く人、日次実行はスクリプト」**。これが安定性・コスト・監査性のすべてで最良の組み合わせ。

### A-2. 取得方式の4段スタック（ソースの重要度で使い分け）

```
方式1: 公式API / 公式ファイル        … 楽天・じゃらん・気象庁・祝日CSV・e-Stat
方式2: HTTPフェッチ + 決定的パース    … 静的HTML/RSS/CSV。Playwright不要（最軽量・最安定）
方式3: Playwright + 決定的スクリプト  … JSレンダリング必須のページのみ
方式4: LLMエージェント               … ①初期構築 ②修復提案 ③ソースレイクの探索的収集(B章)のみ
```

- **判定順は必ず 1→2→3→4**。「Playwrightで全部」にしない（方式2で足りるページにヘッドレスブラウザを使うのは故障点とコストを増やすだけ）
- 商用スクレイピングSaaS（Apify / Zyte / Bright Data等）は「大量・対ボット対策サイト」向け。本システムの対象（会場カレンダー・自治体サイト）は小規模・低頻度なので**原則不要**。使う場合も対ボット回避機能でアクセス制限を突破する用途には使わない（規約・法務リスク。C2/I-6のチェックリスト対象）

### A-3. 「取れないと致命的」への多重防御（競合価格を例に）

価格に直結するデータは**取得の冗長化と縮退の設計**で守る。クローラを頑張って強くするより、**取れなかった日でもシステムが正しく振る舞う**方が重要:

```
第1防御: ソース冗長化
  競合価格 = 楽天API（主） + じゃらんAPI（副） の2系統。片方死んでも継続
  照合一致率を常時監視（乖離>10%で信頼度down・要確認キュー）

第2防御: 鮮度つき縮退（クリティカルパスを止めない）
  当日取得失敗 → 前日値を使用し reliability を日数で減衰（1日 0.9, 2日 0.7, 3日〜 0.5）
  reliability < 0.5 → C_market を 1.0 へ縮退 + 根拠表示に「競合データ3日以上未取得」を明示
  ※ 誤った古い値で強気推奨を出すより、係数を無効化して内部要因だけで推奨を出す方が安全

第3防御: 監視と復旧
  コネクタごとの canary（毎回必ず存在するはずの値を1件検証）
  連続失敗2回で管理者アラート + 修復エージェント起動（A-1②）
  最終手段: SC-11 の手動入力UI（競合3社×30日分なら人手で15分で入る粒度に設計）

第4防御: 影響の可視化
  「このデータ欠損が今日の推奨に与えた影響」をverifyジョブが算出
  （C_market有効時と1.0固定時の推奨差分件数）→ 欠損の重大度を定量表示
```

- イベント・天候など他のソースも同じ縮退パターン（係数1.0へフォールバック）。**全係数が「無くても動く」設計（15§0）だからこそ、クローラは「壊れても致命傷にならない」**——ここが安定性の本質
- 逆に唯一縮退できないのは**自社予約データ（サイトコントローラー）**。ここだけはT0手動アップロードという人間系フォールバックを持つ（12-A2）

## B. ソースレイク（係数化しない厚い収集）

### B-1. 考え方

SNS・ニュース・世界情勢などは「予測係数には入れない（ノイズが大きく因果が薄い）が、**将来の係数候補・AIコメントの文脈・事後分析の材料として原文を貯めておく**」。これを **ソースレイク** として正式なレイヤーにする:

```
収集(安く広く) → raw保存(オブジェクトストレージ) → 週次LLMダイジェスト(AIまとめ用)
                                   ↓
        係数昇格パイプライン: 候補シグナル化 → アブレーション(15§4) → 合格したら係数へ昇格
```

**「評価に加えない」と「捨てる」は別**。rawで貯めてあれば、後から「あの急伸はSNSで先に見えていたか？」を遡って検証でき、効くと分かった時点で係数に昇格できる（スナップショット同様、過去に遡って集め直せないデータのため早く貯め始める価値がある）。

### B-2. ソースレイクの収集対象（安い順）

| ソース | 取得 | 費用 | 備考 |
| --- | --- | --- | --- |
| ニュースRSS | Google News RSS (https://news.google.com/rss/search?q=...) + 地元紙RSS | 無料 | 「(地名) 観光」「(地名) ホテル」等のクエリ別フィード。方式2で毎日 |
| Googleトレンド | pytrends（非公式） | 無料 | 地名・観光キーワードの週次系列。壊れやすい前提 |
| YouTube | YouTube Data API（公式・無料枠） | 無料枠内 | 地域観光系動画の再生数トレンド |
| 自治体・観光協会のお知らせ | RSS/クロール（方式2） | 無料 | 規制・工事・キャンペーン等の一次情報 |
| X (旧Twitter) | 公式API（有料。Basicティア月額$100〜200程度・要実装時確認） | 有料 | 地名言及数・話題化検知。**費用対効果が出るまで見送り可**。代替: Yahoo!リアルタイム検索の目視運用 |
| Instagram/TikTok | 公式に取得手段が実質ない | — | 対象外（規約リスク）。ハッシュタグ数の手動定点観測なら可 |
| 世界情勢・渡航情報 | 外務省海外安全HP、各国渡航情報のRSS | 無料 | LLMダイジェストの文脈のみ |

### B-3. 処理設計

- 収集は方式2（HTTP+RSS）中心で**Playwrightすら原則使わない**。1日1回、テナント共有で取得（地域単位で1回、B-2は全テナント共用データ）
- LLM処理は**週次ダイジェスト1回だけ**: 1週間分の見出し・スニペットを安価モデルに渡し「ホテル需要に関係しうるトピック上位N件+要約」を生成 → AIまとめ(SC-07)の文脈情報・チャットのコンテキストに供給。**数値・係数には一切入れない**
- 昇格判定（四半期）: ソースレイクの系列（例: 地名検索トレンド）を候補特徴としてバックテストに追加し、WAPE改善が2四半期連続で確認できたら15§4の係数マスター表へ昇格（I-5と同じ基準）

## C. コスト設計（実費の見積りと最適化）

前提: 概算は設計時点の公開価格に基づくオーダー感。**実装時に最新の料金表で必ず再見積り**（I-7）。1テナント=1ホテル、競合5社×90日先、商圏ソース10箇所を標準構成とする。

### C-1. 費目別の月額オーダー（1テナントあたり）

| 費目 | 内訳 | 月額目安 | 備考 |
| --- | --- | --- | --- |
| クロール/API取得の計算資源 | 方式1-2が中心+Playwright数十ページ/日 → 小型VM1台（2vCPU/4GB）で**数十テナント分**を捌ける | 1テナント換算 数十円〜百円台 | サーバレスでも可。ブラウザ起動は1日数分 |
| 公式API | 楽天・じゃらん・気象庁・e-Stat・祝日・Frankfurter: すべて無料枠 | 0円 | レート制限遵守のみ |
| オブジェクトストレージ(raw+レイク) | HTML/JSON 圧縮後 1〜5GB/月/テナント | 数円〜数十円 | R2/S3クラス。無期限保存でも安い |
| PostgreSQL | 共有クラスタ（テナント数十まで1インスタンス） | 1テナント換算 数百円 | マネージド小〜中インスタンス |
| LLM | 下記C-2 | **数百円〜2千円程度** | 構成次第。ここが最大の変動費 |
| （任意）レートショッパー | Lighthouse等 | 1物件 数千円〜数万円 | 楽天/じゃらんAPIで足りる間は不要 |
| （任意）X API | Basic ティア | 全テナント共有で1〜3万円 | 効果確認まで見送り推奨 |

→ **必須分の変動費は1テナント月数百円〜2千円台**に収まる想定。SaaS原価として十分軽い。重いのは任意の商用データ（レートショッパー・X API）で、これらは**上位プランの原価**として料金設計に反映する（決済は作らないがプラン概念は持つ）。

### C-2. LLMコストの内訳と削減設計（ここを工夫する）

タスク×モデルティアの使い分け（LLM抽象化層 12-E で taskType ごとに設定）:

| taskType | 頻度/テナント | モデルティア | 1回あたり概算トークン | 月額オーダー |
| --- | --- | --- | --- | --- |
| イベント/統計の構造化抽出 | 差分があった日のみ 0〜10ページ/日 | **最安クラス（Haiku級/Flash級）** | in 3-5k / out 0.5k | 数十円 |
| 日次AIコメント（ダッシュボード+プライシング提案文） | 1日 3〜5生成 | 中位クラス | in 3k / out 1k | 百円台 |
| 週次ソースレイク・ダイジェスト | 週1 | 最安クラス | in 20k / out 2k | 数十円 |
| チャット | 利用量次第（想定 数十問/月） | 中位〜上位（設定可） | in 5k / out 1k | 百円〜千円台 |
| クローラ修復提案 | 月0〜2回 | 上位クラス | in 20k / out 2k | 数十円 |
| 月次レポート文面 | 月1 | 中位 | in 10k / out 3k | 数十円 |

**削減の構造的工夫（効き順）**:

1. **差分ゲート**: contentHash が前回と同じページはLLM抽出をスキップ（15§3.1）。イベントページの更新は週1程度なので抽出コストが1/5〜1/10になる
2. **テナント共有**: 天候・イベント・祝日・ソースレイクは**地域単位で1回だけ**処理して全テナントに配る。テナント数が増えるほど1社あたりコストが逓減（SaaSの構造的優位）
3. **バッチAPI**: 日次コメント等の非対話系はバッチエンドポイント（各社50%割引が一般的）+夜間実行
4. **プロンプトキャッシュ**: システムプロンプト・スキーマ定義・根拠JSONの共通部分をキャッシュ（入力コストが大幅減）
5. **モデルティアのデフォルトを下に**: 抽出・ダイジェストは最安クラスで品質十分（スキーマ検証で担保）。上位モデルは「チャットの設定で選んだ場合」と「修復提案」だけ
6. **サブエージェント分割は使いどころ限定**: 並列サブエージェントは「初期オンボーディング時の過去データ一括処理」「新規ソース探索」等のスポット作業でだけ使う。**日次定常処理には使わない**（定常はワークフロー固定が安・速・安定）
7. **出力の再利用**: AIコメントは根拠JSONが変わらない限り再生成しない（キャッシュキー=入力ハッシュ）

**コストガードレール**: taskType×テナント別のトークン計上（12-E-3）+ 月次上限（超過時は生成系を停止して定型文フォールバック、予測・推奨は影響なし）。原価ダッシュボードをSC-99に表示。

### C-3. どこにお金を使うべきか（優先順位の提言)

1. **払う価値が最も高い**: レートショッパー（楽天/じゃらんの2 OTAでは足りない高級帯・海外OTA比率が高いテナント向けオプション）
2. **次点**: LLMチャットの上位モデル化（ユーザー体感に直結）
3. **見送ってよい**: X API、航空券API、商用スクレイピングSaaS — いずれも係数への寄与が実証されてから
