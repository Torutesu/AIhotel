# 04. 評価設計（予測精度・プライシング効果・システム品質）

## 0. 原則

- **「予測が当たるか」と「推奨に従うと儲かるか」は別の問い**。前者はバックテストで機械的に測れるが、後者は反実仮想（従わなかった場合の結果）が観測できないため、代理指標と運用設計で担保する
- 評価はリリース後に始めるものではなく、**予測ログ（何を・いつ・どの根拠で予測したか）をフェーズ2から貯める**ことが前提。Prediction/Recommendationログテーブルが評価基盤そのもの

## 1. 需要予測の精度評価

### 1.1 指標
| 指標 | 対象 | 備考 |
| --- | --- | --- |
| WAPE / MAE（単価重み付き） | 最終稼働率・販売室数・ADRの着地予測 | **MAPE単独は禁止**（実績ゼロ近傍で発散。文献上もMAE系が金銭損失の最良近似【検証済み・20参照】）。MAPEは参考表示のみ |
| バイアス（ME） | 同上 | 系統的な上振れ/下振れの検知。プライシングでは誤差の向きが金額に直結 |
| ピンボール損失 | 予測区間（P10/P50/P90）を出す場合 | 「強気/弱気の幅」を出すなら必須 |
| ヒット率 | 需要ランクA〜E | 業務者の体感と繋がる指標。混同行列で±1ランク以内も見る |

### 1.2 評価の切り方（ここが重要）
- **リードタイム別**: 「90日前時点の予測」「30日前」「7日前」「前日」で精度は全く違う。リードタイムバケットごとにWAPEを出す。予測ログに`asOf`を持たせるのはこのため
- **セグメント別**: 平日/週末、シーズン、部屋タイプ、イベント日/非イベント日。「イベント日だけ外す」等の弱点を特定できる形に
- **バックテスト方式**: 時系列クロスバリデーション（学習期間を過去に固定し、未来をローリングで検証）。**ランダム分割は厳禁**（リークする）
- **ベースライン比較**: 「前年同日実績」「同時点前年OTB×去年の伸び率」という素朴な予測を常に併走させ、モデルはこれに勝って初めて意味がある（勝てないなら素朴な方を使う）

## 2. プライシング（推奨価格）の評価

### 2.1 直接測れないことへの対処
反実仮想が取れない中での代理評価:

| 方法 | 内容 | 限界 |
| --- | --- | --- |
| 前年同期比 RevPAR | 導入前後の同月比較 | 市況変動と交絡（コロナ回復・インフレ等） |
| 競合セット比（RGI相当） | 自社RevPAR ÷ 競合平均RevPAR の推移。市況を競合が吸収してくれる | 競合のRevPARは直接見えない → 競合「価格」×推定稼働で近似 or STRのようなデータ購入を検討 |
| 推奨採用率と採用/非採用の結果比較 | 担当者が採用した日 vs しなかった日の結果を比較 | 採用判断自体にバイアス（自信のある日だけ採用等） |
| オフポリシー評価（バックテスト） | 過去データ上で「推奨に従っていた場合」の期待収益を弾力性モデルでシミュレーション | 弾力性モデル自体の誤差に依存。参考値扱い |
| 限定A/Bテスト | 部屋タイプ or 期間を分けて推奨適用/非適用を比較 | ホテル運用上の合意が必要。同一ホテル内では干渉あり |

→ **推奨: 「競合セット比 + 採用率 + リードタイム別予測精度」の3点をメインダッシュボード化**し、限定A/Bはホテルと合意できたら実施

### 2.2 業務KPI（使われるかどうか）
- 推奨採用率（そのまま採用 / 修正して採用 / 不採用）と、不採用理由の記録UI
- 手動オーバーライド頻度の推移（下がっていけば信頼が積み上がっている証拠）
- 根拠表示の閲覧率・チャット利用率

## 3. 説明（根拠出力）の評価

- 構造化根拠（要因×寄与）と実績の整合: 「イベントで+15%」と説明した日の実績リフトを事後突合し、要因別の説明精度をレポート化
- LLM生成コメントの評価: (a)数値は層1のJSONからのみ引用しているか（自動チェック可能）、(b)ホテル担当者による定性評価（週次サンプリング）
- ハルシネーション対策の受け入れ基準: コメント内の数値・固有名詞はすべて入力JSONに存在すること（機械検証をCI/バッチに組込む）

## 4. IDeaSベンチマークの使い方

IDeaSと精度を直接比較することは（先方データが無いため）できない。ベンチマークの実用的な意味は**機能・運用水準の比較表**として使うこと:

| 観点 | IDeaS（参考水準） | 本システムの狙い |
| --- | --- | --- |
| 予測 | 滞在日×セグメント別、日次自動更新 | 同等（フェーズ3） |
| 価格決定 | 連続価格/BAR、承認レス自動反映まで可 | 65段階ランク+人間承認から開始 |
| 根拠表示 | 限定的（ブラックボックスと言われがち） | **差別化ポイント: 要因分解+自然言語の根拠を全推奨に添付** |
| 団体対応 | グループ評価機能あり | フェーズ2以降で個人/団体分離、団体評価は将来 |
| 導入データ要件 | 2年以上の履歴推奨 | 同様（履歴が浅い場合のフォールバックを用意） |

「IDeaSにあって本システムに無いもの」を要件から意図的に落とす判断（スコープ管理）にも使う。

## 5. システム品質(非機能)の受け入れ基準（初期案・要合意）

- バッチ: PMS取込〜予測〜推奨生成まで日次で完走、朝の業務開始（例: 9:00）までに前日データ反映
- 任意分析（都度計算）: 3年分×クロス集計で応答 数秒以内（事前集計テーブルの設計で担保）
- 予測ジョブの失敗時: 前回予測を保持しつつ「予測が古い」ことをUIに明示（黙って古い数字を出さない）
- 監査: 推奨・採用・価格変更はAuditLogに全件記録（スキーマ実装済みの活用）
