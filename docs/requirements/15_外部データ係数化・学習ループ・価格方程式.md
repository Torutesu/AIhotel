## 0. 価格決定の方程式（マスター式）

すべての設計はこの式に収束する。宿泊日 D、セグメント s、評価時点 t、候補価格 p について:

```
【需要式】
  q̂(D,s,p,t) = PU(D,s,t)                          … 加法的pickup推定（内部要因の核・13§3.1）
              × C_pace(D,s,t)                      … ペース係数（内部）
              × C_event(D)                         … イベント係数（外部）
              × C_dow_hol(D)                       … 祝日・連休係数（外部→ベースに内包可）
              × C_market(D,t)                      … 市場係数 = 競合満室×マクロ（外部）
              × C_weather(D,t)      [L≤14のみ]     … 天候係数（外部）
              × (p / p_ref)^ε(s)                   … 自社価格弾力性
              × (p / p_comp(D,t))^εx               … 競合相対価格（クロス弾力性）

【期待売上】
  R̂(p) = p × min( q̂(D,s,p,t) × (1 − ĉ(D,s,t)), remaining(D,s) )
    ĉ: 新規予約分の期待キャンセル率、remaining: 残室（団体ブロック控除後）

【推奨価格】
  p* = argmax_{p ∈ 65ランク∩ガードレール}
         [ w_adr·norm(R̂(p)) + w_occ·norm(occ(p)) − w_comp·pen(|p−p_comp|/p_comp) ]
       ただし score(p*) − score(p_now) < θ なら現状維持（ヒステリシス）

【根拠】
  log q̂ = log PU + Σ_k log C_k + ε·log(p/p_ref) + εx·log(p/p_comp)
  → 各項がそのまま要因寄与（足し算で厳密に一致）
```

各係数 C_k の「データ源・推定式・初期値・更新頻度」を§4のマスター表で定義する。**全係数はデータ未整備なら1.0で縮退**し、パイプラインは止まらない。

## 2. クローリング設計（APIが無いソースの取り方）

### 2.1 実行基盤

```
クローラーワーカー（Node + Playwright / 軽量ページは fetch+cheerio）
  ├─ ソース定義（DB管理・コード非依存）:
  │    CrawlSource { id, name, url(具体URL), kind(event/weather_hist/stats),
  │                  parserType(css|table|llm), schedule(cron), robotsPolicy,
  │                  rateLimit(req/min), lastSuccessAt, consecutiveFailures }
  ├─ 実行: robots.txt確認 → 取得（UA明示・1req/数秒のスロットル・リトライ3回指数バックオフ）
  ├─ raw保存: HTML/PDF/CSVをそのままオブジェクトストレージへ（§3.1）
  └─ パース: parserTypeに応じて
       css/table: 決定的パーサ（CSSセレクタ/テーブル抽出。コード管理）
       llm:       LLM構造化抽出（§5.1）— レイアウト不定・自然文のソース用
```

### 2.2 設計原則

1. **APIがあるものは絶対にクローリングしない**（楽天・じゃらん・気象庁・e-Stat・祝日は上のAPI/公式ファイルを使う）。クローリング対象は「会場イベントカレンダー・自治体サイト・統計PDF」等のAPI非提供ソースに限定
2. **robots.txt と利用規約の遵守をソース登録時のチェックリストに含める**（拒否されているソースは登録不可。判断記録を残す）。アクセス頻度は日次1回・深夜帯・1リクエスト数秒間隔を標準とする
3. **壊れる前提の監視**: パース結果件数が過去中央値の50%を下回ったら「構造変更疑い」アラート → LLMに新旧HTMLを渡して**セレクタ修正案を提案**させ、人間承認でパーサ更新（自動適用はしない）
4. **raw再処理可能性**: パーサを直したら過去rawを再パースして遡及補完できる（FR-D06）

### 2.3 ソース別パーサ方針

| ソース | パーサ | 出力 |
| --- | --- | --- |
| 会場イベントカレンダー | css/table + **LLM抽出のハイブリッド**（一覧はセレクタ、詳細文はLLM） | EventRegistry行（名称・日付・種別・想定規模） |
| 自治体イベント | LLM抽出（レイアウト多様なため） | 同上 |
| JNTO統計（PDF/Excel） | テーブル抽出 + LLM検証 | 国別月次系列 |
| 気象庁過去データ | テーブルパーサ（決定的） | 日別実績気象 |

## 3. どのDBに貯めるか（ストレージ設計）

### 3.1 3層構成

```
① raw層: オブジェクトストレージ（S3 / Cloudflare R2 / GCS — D1のインフラ選定に従う）
    パス: raw/{source}/{yyyy-mm-dd}/{fetchId}.html|json|csv|pdf
    メタ: RawDocument(id, sourceId, url, fetchedAt, httpStatus, contentHash, storagePath) → PostgreSQL
    保持: 無期限（安価）。contentHash同一ならスキップ（差分なし日を検知）

② 正規化層: PostgreSQL（本体DBと同居・スキーマ分離 `external`）
    external_factors(source, factorType, targetDate, observedAt, geoScope, value JSONB, reliability, rawDocId)
    event_registry(...), competitor_price_data(...), weather_forecast/actual(...), fx_rates(...), macro_series(...)
    ※ (targetDate, observedAt) の2軸を全テーブルで強制 — as-of結合の基盤（13§C）

③ 特徴量・係数層: PostgreSQL（`features` スキーマ）
    factor_coefficients(hotelId, factorKey, segmentKey?, coefValue, ci_low, ci_high,
                        sampleN, method, trainedAt, modelVersion, status: active|challenger|retired)
    feature_view: 予測入力のマテリアライズドビュー（observedAt ≤ asOf の制約付きSQL）
```

- 選定理由: 数百万行オーダー・JOIN中心・as-of制約のSQL表現 → **PostgreSQL一択で十分**（14§1と同一DB）。時系列DBやDWHは全テナント横断分析が重くなった時点（数十テナント〜）でDuckDB/BigQuery等をレプリカとして追加検討
- rawをDBに入れない理由: サイズとコスト。DBにはハッシュとパスのみ

### 3.2 品質評価（データをどう評価するか）

取込時に各レコードへ **reliabilityスコア** を付与し、係数推定時の重みに使う:

```
reliability = w1·ソース品質(official=1.0 / api=0.9 / crawl=0.7 / llm抽出=0.6 / manual=0.8)
            + w2·鮮度(SLA内=1.0, 超過で減衰)
            + w3·照合(2ソース一致=+, 矛盾=−)     … 例: 楽天vsじゃらん価格の乖離>10%で要確認フラグ
検証ルール（取込時に機械チェック）:
  - スキーマ/型/範囲（価格が0や10^7でないか、日付が未来すぎないか）
  - 系列の跳ね検知（前回値比±3σ）→ 保留キューへ（自動では正規化層に入れない）
  - LLM抽出は「元テキストに存在する値のみ」制約 + 抽出信頼度の自己申告 + サンプリング人手検査
```

## 4. 係数化マスター表（どの係数として、どう効かせるか）

**推定はすべて統計処理（SQL+軽量回帰）で行い、LLMは使わない**（LLMの役割は§5）。log q（補正後需要の対数）に対する乗法係数として統一。

| 係数 | 定義・推定式 | 初期値 | 更新頻度 | 主データ源 |
| --- | --- | --- | --- | --- |
| C_pace | `1 + w(L)·(Pace−1)`, w(L)=RefCurve^0.7, クリップ[0.7,1.4]（13§3.2） | 1.0 | 日次算出（推定不要） | 自社OTB |
| C_event | カテゴリc別 `lift(c) = (n·lift_raw + k·lift_global)/(n+k)`, k=5。lift_raw = 検閲補正後実績/ベースライン、同種イベント日の幾何平均 | 距離×キャパのルックアップ表（ヒアリング初期化）: 例 大規模(1万人+)×徒歩圏=1.3、電車圏=1.15、中規模=1.1 | イベント終了の都度＋月次一括 | 会場クローラ+手動登録 |
| C_dow_hol | 曜日・連休位置係数（ベースラインに内包）。`median(実績/季節調整値)` | 過去実績から即算出 | 月次 | 自社実績+祝日CSV |
| C_market | `1 + β_full·(競合満室率 − 平常値) + β_price_gap·(市場価格前年同期比 − 1)` を[0.85,1.25]にクリップ | β_full=0.3, β_price_gap=0（=無効で開始） | βは四半期に回帰再推定 | 楽天/じゃらんAPI |
| C_weather (L≤14) | 天気カテゴリ別係数（晴/雨/大雨・台風接近）。`median(直前pickup実績/期待値)` を天気別に層別 | 雨=0.97, 大雨=0.90, 台風=アラートのみ | 四半期 | 気象庁API |
| C_macro | `1 + γ·(訪日客数トレンドYoY−1)·インバウンド比率` を[0.95,1.05]にクリップ | γ=0（**表示のみで開始**、効果確認後に有効化） | 月次 | JNTO/e-Stat |
| ε（自社弾力性） | 需要シグナル統制回帰（13§7.2）: `log(実現Pickup) ~ ε·log(p/p_ref) + controls`、セグメント別+階層縮小、クリップ[−4,−0.3] | レジャー週末−1.2 / ビジネス平日−0.8（ヒアリングで調整） | 四半期（人間レビュー付き） | 自社価格履歴+決定ログ |
| εx（競合相対） | 同上の回帰に `log(p/p_comp)` を追加 | −0.3（小さく開始） | 四半期 | 楽天/じゃらんAPI |
| ĉ（キャンセル率） | リードタイムバケット×チャネル別ハザードの頻度推定（13§6） | 過去実績から即算出 | 月次 | 自社予約明細 |

**係数の採否評価（アブレーション）**: 各係数は「入れた場合/1.0固定の場合」のバックテストWAPE差で評価し、**改善が確認できない係数はstatus=retired（1.0固定）に自動降格**。係数ごとの寄与はfactor_coefficientsの履歴で追跡（「この係数は効いているのか」に常に答えられる状態を保つ）。

## 5. どのAIで何を分析するか（役割分担の確定）

| layer | 使うもの | タスク | 使わない理由/注意 |
| --- | --- | --- | --- |
| 抽出 | **LLM（抽象化層経由: Claude/Gemini/GPT差替可）** | クロールしたHTML/PDF/自然文からの構造化抽出（イベント名・日付・規模、統計表）、クローラ破損時のセレクタ修正案、ニュース・世界情勢のコンテキスト要約（係数化しない） | 出力は必ずスキーマ検証+元テキスト存在チェック。数値の創作禁止 |
| 係数推定 | **統計（SQL集計・ロバスト回帰・経験ベイズ・ハザード頻度推定）** | §4の全係数、ベースライン、リファレンスカーブ、検閲補正(DES/Holt) | LLMは使わない（再現性・監査性のため）。ライブラリ: フェーズ2はTS/SQLで可、回帰系はPython(statsmodels)へ寄せてよい |
| 需要予測コア | **加法的pickup+指数平滑（フェーズ2）→ GBDT/LightGBM（フェーズ3の挑戦者）** | 13§3.1。フェーズ3はPython(FastAPI)サービス | 深層学習・RLは現規模で不採用（20の評価表） |
| 最適化 | **決定的アルゴリズム（65ランク全探索）** | §0の argmax。1ホテル365日×65ランク×数タイプ=十数万評価/日で計算量問題なし | — |
| 言語化 | LLM | 根拠JSON→AI解説・提案文・チャット | 計算はしない（FR-L03） |

## 6. 追加学習ループ（時間とともに精度が上がる仕組み）

### 6.1 学習のトリガーとサイクル

```
毎日:   予測・推奨・根拠を全件ログ（Prediction/Recommendation） ← 学習素材が毎日貯まる
        宿泊日が確定するたび: 実績突合 → リードタイム別誤差を error_log に記録
イベント終了ごと: 当該イベントの実績リフトを算出 → C_event のカテゴリ統計に加算（nが増え縮小が解けて係数が個別化していく）
週次:   ドリフト監視（WAPE移動平均 + ブッキングウィンドウ分布シフト）→ 閾値超過で臨時再学習
月次:   ベースライン・RefCurve・ĉ・C_weather 再推定 → チャンピオン/チャレンジャー比較（§6.2）
四半期: ε・εx・β再推定 → 変化幅レポート付きで人間承認 → 反映
```

### 6.2 安全な自動更新（チャンピオン/チャレンジャー方式）

```
新係数セット(challenger) を直近13週のバックテストでchampionと比較
  勝ち（WAPE改善 かつ 高需要日バイアスが悪化しない）→ 自動昇格（係数履歴に記録）
  負け → retired。3回連続で負けたfactorは調査タスク発行
ε等の価格系パラメータのみ自動昇格禁止（人間承認必須）— 価格への影響が直接的なため
```

### 6.3 人間のフィードバックを学習に使う

- 推奨の**採用/修正/不採用ログ（PricingDecision）**: ①修正幅の系統的パターン（「AIよりいつも1ランク下げる」）を検出してガードレール/係数のズレとして提示 ②推奨と異なる価格が設定された日は自然実験として弾力性推定のサンプルに
- 手動登録イベント・手動係数オーバーライド: オーバーライド値と実績の乖離を四半期レポートで返す（人間側の学習も回す）

### 6.4 精度向上のロードマップ（何で精度が上がっていくか）

| 時期 | 精度が上がる要因 |
| --- | --- |
