# 13. アルゴリズム詳細設計（需要予測・価格最適化）

版: 0.2（文献リサーチ反映。変更点は【R】マーク、根拠は `20_リサーチ_RMS手法サーベイ.md`）
本書は `03_モデル設計方針.md`・`12_プライシングアルゴリズム・データ取得設計.md` の D 章を実装可能なレベルまで詳細化する。数式・擬似コード・数値例を含む。フェーズ2（ルール/統計ベース）を主対象とし、フェーズ3（ML化)での置き換え点を各節に付記する。

> **v0.2の主な変更（リサーチ反映）**: ①Pickup予測の主推定器を「移動平均つき加法的pickup」に変更（乗法/比率型は比較研究で一貫して劣位のため補正シグナルへ格下げ） ②検閲補正のフェーズ2実装をカーブ外挿からDES/Holtベース（Queenan 2007）に変更 ③手法をバックテストで比較選択する枠組みを追加（最良手法は施設依存という定番研究の結論） ④ドリフト監視にブッキングウィンドウ分布を追加 ⑤誤差指標からMAPE単独を排除。

## 1. 予測の全体構造（分解）

最終販売室数の予測を次の形に分解する:

```
最終室数予測(D,s) = NetOTB(D,s,t) + Pickup予測(D,s,t)

NetOTB     = 現時点の予約室数 − 今後のキャンセル予測分（§6）
Pickup予測 = 加法的pickup推定(§3.1) × ペース/イベント/市場/価格の補正(§3.2,4,5,7)
             を在庫残でクリップ(§8)。推定器はバックテストで選択(§3.1)
```

この分解の意味:
- **OTBは事実、Pickupだけが予測** — UIの3層表示（実績/予約/予測)と正確に一致する
- リードタイムが短くなるほどOTBの比重が増え、予測は自動的に「当たりやすく」なる（信頼度表示の根拠にもなる）

## 2. ベースライン需要とリファレンスカーブ

### 2.1 最終需要ベースライン `BaseFinal(D,s)`

過去2〜3年の実績から、乗法モデルで推定する:

```
BaseFinal(D,s) = 年間水準(year) × 季節係数(month/week-of-year) × 曜日係数(dow)
                 × 祝日・連休係数(holiday position)
```

- 推定方法（フェーズ2）: ロバスト集計。例: `曜日係数 = median(実績 / 季節調整値)`。外れ値（イベント日・満室日）は除外 or Winsorize
- 学習重み: 直近年ほど重く（指数減衰、半減期12ヶ月目安）。**レジーム断絶（例: 感染症・改装）期間は学習窓から明示除外**できる設定を持つ
- 祝日・連休は「連休の何日目か / 前日か」を位置特徴として係数化（3連休の中日と最終日は全く違う）
- フェーズ3: GBDTに置換（特徴量: 上記+外部要因）。ただし係数分解による説明はSHAP射影で維持

### 2.2 リファレンスカーブ（正規化ブッキングカーブ）

`RefCurve(L; cluster)` = リードタイム L 時点での「最終室数に対するOTB比率」の期待値。

- クラスタ単位で推定: 曜日グループ（平日/金/土/日祝前）× シーズン（繁忙/通常/閑散）程度の粗い粒度から始める（細かくしすぎるとノイズ）
- 推定: 過去の各宿泊日について `OTB(L)/最終室数` を計算し、クラスタ内で中央値カーブを取る
- 用途: ①ペース判定（§3） ②ブッキングカーブ画面の「基準カーブ」重ね描き（SC-03） ③Pickup配分

### 2.3 満室日の検閲補正（Unconstraining）— 重要・見落としやすい

満室（または在庫制限・売止め）だった日の「観測された予約数」は真の需要より小さい（検閲されている）。**補正せずに学習すると、需要が強い日ほど需要を過小評価する系統誤差**が入る。

【R】フェーズ2の実装 — **DES/Holt（二重指数平滑）ベースのunconstraining**（Queenan et al. 2007）を主手法とする:
```
宿泊日Dが満室閉鎖された時点 L_close を特定（在庫 or 売止めログから）
検閲前のブッキングカーブ観測点（L > L_close の累積OTB系列）に Holt の線形トレンド平滑を適用し、
L_close 以降の累積需要を外挿 → 真の最終需要の推定値
```
- 選定理由（20参照）: 比較研究で3データセット中2つでEM/PDを上回り、**履歴が少ない・検閲率が高い状況でむしろ強く、実装が軽い**【検証済み】。当初案の単純カーブ外挿（`OTB(L_close)/RefCurve`）は比較研究で劣位とされた系統のため、RefCurve未整備期間の暫定フォールバックに格下げ
- 学習（ベースライン・イベント係数・弾力性）にはこの補正後需要を使う。表示（実績）には観測値を使う
- 補正できない場合（閉鎖時点不明）: 満室日は需要学習から除外し「下限サンプル」として扱う
- フェーズ3: EM/PD（projection detruncation）への高度化は選択肢。ただし「EMが常に最良」は反証済みの俗説で、**小サンプルではEMは不安定**になりうる（20の【反証】項参照）— 移行時はDES/Holtとのバックテスト比較を必須とする
- 検閲を無視した場合の帰結は「スパイラルダウン効果」（過小予測→絞り込み→さらに過小予測の単調収益低下）として文献で確立している【検証済み】— 本工程を省略してはならない根拠

## 3. Pickup推定とペース補正（内部要因の中核）【R: v0.2で構成変更】

### 3.1 主推定器: 移動平均つき加法的pickup

**リサーチの結論（20参照）**: 定番比較研究（Weatherford & Kimes 2003）で、加法的pickupと指数平滑が最頑健の2手法である一方、**乗法（比率）型pickupは一貫して劣位で、リードタイム7日超で劣化する**【検証済み】。さらに増分を移動平均で平滑化した拡張は28日先MAPEを23.9%→4.6%に改善した実証がある【検証済み・単一シーズナルホテルでの実証という限定付き】。よって主推定器を次とする:

```
Pickup_add(D,s,t) = Σ_{l=0..L-1} avgIncrement(l; cluster, D近傍)
  avgIncrement(l) = 過去の類似日（同クラスタ: 曜日グループ×シーズン）の
                    リードタイム l における日次予約増分の移動平均（MA7〜MA14で平滑化）
着地予測 = NetOTB(D,s,t) + Pickup_add × 補正項(§3.2, §4, §5, §7)
```

- 併走ベースライン: 指数平滑（SES/Holt、完了済み宿泊日の最終値系列）— 最頑健手法としてアンサンブル/比較要員【検証済み】
- **手法選択はバックテストで行う**: 最良手法は施設・セグメント・リードタイムで異なるというのが定番研究の実務推奨【検証済み】。additive pickup / MA付きpickup / 指数平滑（+フェーズ2.5のPCA類似日参照）をホテルごとにバックテスト比較し、勝者または単純平均アンサンブルを採用する。SaaSとしては「テナントごとに勝者が違う」前提の手法レジストリ構造にする
- フェーズ2.5【R】: **類似日参照の高度化** — ブッキングカーブをPCAで低次元化し近傍過去日を距離重みでpickup平均する手法が、固定クラスタ版を全ホテル・全ホライズンで上回った実証がある（26〜47室・3〜5年データ、解釈可能性も維持）【検証済み】。RefCurveの固定クラスタ→データ駆動類似日への置換候補。ADRを補助成分に入れると精度が上がる（=価格情報を予測に入れる）示唆も採用検討

### 3.2 ペース補正（比率型は補正シグナルに限定）

```
Pace(D,s,t) = NetOTB(D,s,t) / ( BaseFinal(D,s) × RefCurve(L; cluster) )
PaceAdj(D,s,t) = 1 + w(L) × (Pace − 1),  w(L) = RefCurve(L)^γ（例: γ=0.7）
```

- 【R】比率型ペースは**主予測には使わず**、①§3.1のpickup推定への乗法補正（クリップ付き、例: 0.7〜1.4）、②根拠表示・画面のペース指標（基準カーブ比・前年同曜日比の両方）、の2用途に限定する
- 直感は従来通り: 「180日前にOTB3室で前年比2倍」を真に受けない。「14日前に前年比+20%」は強く反映する（shrinkage w(L)）

## 4. イベント補正

### 4.1 係数の適用
```
EventLift(D) = Π_e lift(e)   （同日複数イベントは乗算、上限クリップ例: 2.5）
```

### 4.2 lift の学習（データが薄い問題への対処）
- イベントカテゴリ `c`（コンサート大/中、スポーツ、展示会、花火、桜… × 会場距離帯）ごとに:
  `lift_raw(e) = 補正後実績需要 / ベースライン需要` を過去の同種イベント日で集計
- **経験ベイズ縮小**: サンプル数 n が少ないカテゴリは全体平均へ縮小
  `lift(c) = (n × lift_raw(c) + k × lift_global) / (n + k)`（k=5目安）
- 初期値（実績ゼロのカテゴリ）: 会場キャパ×距離のルックアップ表（ホテルヒアリングで初期化 → 実績で自動更新）
- 未来イベントは登録データ（B-2）から該当カテゴリの lift を引く。**根拠表示にはイベント名と過去の同種イベントの実績リフトを出す**（納得感の核）

## 5. 市場補正（競合・マクロ）

```
MarketAdj(D,t) = CompAdj(D,t) × MacroAdj(month(D))
```

- **CompAdj（競合シグナル）**: 2つの入力を使う
  1. 競合満室率: 対象日に価格非表示/満室の競合割合 → 高いほど市場需要が強い（+方向）
  2. 相対価格は§7の価格効果側で扱う（二重計上しないこと。CompAdjは「市場の総需要」、価格効果は「シェアの奪い合い」と役割分担）
  - 実装: `CompAdj = 1 + β_full × (競合満室率 − 平常値)`。β_full は過去データの回帰で推定（初期値0.3程度）
- **MacroAdj**: インバウンドトレンド（JNTO前年比）× 為替トレンドを月粒度の緩い係数に（例: ±5%以内にクリップ）。効果が不明な初期は1.0固定で開始し、根拠表示には「参考情報」として提示のみ
- **天候**: L ≤ 14 のみ `WeatherAdj` を適用（雨予報→直前予約減、台風→キャンセル増は§6へ）。それ以遠は係数1.0

## 6. キャンセル・ネットOTB

### 6.1 キャンセル率モデル
残存キャンセル率（今からD日までにキャンセルされる確率）をハザード形式で持つ:

```
survive(L→0 | channel, rateType, season) = Π_{l=1..L} (1 − h(l; channel,...))
NetOTB = Σ_予約 rooms × survive(L→0 | 予約属性)
```

- `h(l)`: リードタイムバケット別ハザード（当日/1-3/4-7/8-14/15-30/31-60/61+）× チャネル別。過去のキャンセルログから頻度推定
- OTAの無料キャンセル期限（多くは前日〜3日前）でハザードが跳ねる形状になる — バケット割りはこれを跨がないように切る
- 団体はハザード別建て（ブロックの「こなし率(wash)」として扱う。§9）
- 台風等の突発キャンセルはモデル外事象としてアラート扱い（AIまとめのシナリオ表示と連動）

### 6.2 グロス/ネットの使い分け
- 表示: ブッキングカーブはグロス/ネット切替可能に（SC-03要詰めの解: デフォルトはネット）
- 予測・最適化: 常にネット
- キャンセル率そのものも分析画面の指標として出す（FR-A01の予約期間分析にキャンセル率列が既にある)

## 7. 価格効果と弾力性推定

### 7.1 需要への価格効果

```
PriceEffect(p; D,s) = (p / p_ref)^ε(s, season, Lバンド)
p_ref = 直近の自社実勢価格（同曜日近傍の中央値）を基準とし、
        競合相対項を追加: × (p / p_comp)^ε_x   （ε_x: クロス弾力性、初期は小さく設定）
```

### 7.2 弾力性 ε の推定 — 内生性の罠（最重要注意点）

**素朴に「価格と販売数」を回帰すると符号が逆に出る**（需要が強い日に価格を上げるため、高価格×高販売の相関が生まれる）。対策:

1. **需要シグナルを統制した回帰**: 目的変数=残存期間の実現Pickup(log)、説明変数=log(価格) + ペース + 季節・曜日・イベント等の需要シグナル。需要シグナルを入れることで価格係数から需要起因の相関を除く
2. **同一宿泊日内の価格変化を使う**: 宿泊日固定効果を入れ、「同じ日への価格改定前後のペース変化」から識別する（パネル回帰）
3. **事前分布と制約**: ε ∈ [−4.0, −0.3] にクリップ。セグメント別推定は階層ベイズ的縮小（全体推定へ縮小）で暴れを防ぐ
4. データが無い初期: ホテルヒアリング+業界レンジで初期値設定（例: レジャー週末 −1.2、ビジネス平日 −0.8）。**運用開始後の価格改定ログが最良の実験データ**になるため、推奨と異なる価格を設定した記録（FR-P07の決定ログ）も学習に使う

- 再推定頻度: 四半期。推定値の変化はレポートで人間レビュー（勝手に大きく動かさない）
- フェーズ3+: 意図的な微小ランダム化（±1ランクのA/B）を提案できるが、ホテル合意が前提（04参照）

## 8. 最適化

### 8.1 基本形（フェーズ2: 宿泊日独立・貪欲）

```
for each stayDate D, roomType r:
  remaining = capacity(r) − groupBlocks(D,r) − NetOTB(D,r)
  for each rank in 許容ランク集合(ガードレール適用後):
    p = price(rank, r)
    q = Pickup_add(§3.1) × PaceAdj × EventLift × MarketAdj × PriceEffect(p)
    q_net = q × (1 − 期待キャンセル率_新規予約分)
    sales = min(q_net, remaining)
    revenue(rank) = p × sales
    occ(rank) = (NetOTB + sales) / capacity
  score(rank) = w_adr × norm(revenue) + w_occ × norm(occ) − w_comp × penalty(|p − p_comp|/p_comp)
  推奨 = argmax score、次点2件も保存
```

- `w_adr, w_occ, w_comp` はSC-02の重み設定（合計100%）。`norm()` は候補集合内でmin-max正規化（重みの直感的挙動を保つため）
- **ヒステリシス**: `score(新推奨) − score(現ランク) < θ` なら現ランク維持を推奨（毎日±1ランクのチラつき防止。θは期待売上の1%目安）
- **単調性ガード**: 同一週内で稼働予測が高い日ほどランクが低い、等の逆転が出たら警告（モデル不整合の検知）

### 8.2 既知の限界と将来拡張（フェーズ3+で判断）
- **宿泊日独立の近似**: 連泊需要（LOS）を無視している。連泊者は複数日の価格合計で判断するため、厳密にはネットワーク最適化（bid-price/DP）になる。都市型・短泊中心なら独立近似の誤差は小さい。**導入ホテルの平均泊数を確認して要否判断**（確認事項に追加: 平均LOS）
- **今売るか後で売るか**の時間構造: 残存期間の価格経路を最適化するDPは複雑化に見合わないことが多く、日次再最適化（毎日解き直す）で実用上代替する — 本設計はこの立場
- オーバーブッキングはスコープ外（キャンセル率が高いホテルでは将来検討）

## 9. 団体・部屋タイプ・粒度の整合

- **団体分離**: `capacity_available = capacity − 団体ブロック`。団体はwash率（ブロックのこなし率）だけ別途推定し、個人需要モデルには一切混ぜない。団体フラグ（A4）が無い場合の代替: 同一予約IDで大口室数のヒューリスティック（精度低下を明示）
- **部屋タイプ間の連関**: タイプ別に独立予測すると「シングル満室→ツインへの染み出し」を見逃す。フェーズ2は独立+染み出し係数（上位タイプへの転送率、ヒアリング初期値）で近似
- **粒度の整合（reconciliation）**: 予測の基本粒度は `宿泊日 × 部屋タイプ`。
  - 月別 = 日別の和（ボトムアップ。別モデルを作らない）
  - 人数別・チャネル別 = シェアモデル（過去の構成比を季節・曜日別に推定し、タイプ別予測を按分）。独立に予測して合計が合わなくなる事態を構造的に防ぐ
  - ホテル計 = タイプ別の和

## 10. 需要ランクA〜E・信頼度の定義（案 → 要合意 G-5）

```
需要ランク: 着地稼働予測のパーセンタイル（同曜日・同シーズンの過去分布に対する位置）
  A: ≥90pct（例外的に強い）  B: 70–90  C: 30–70（平常）  D: 10–30  E: <10
信頼度（confidence）:
  high:   L ≤ 14 or OTBカバー率(RefCurve) ≥ 0.7
  medium: L ≤ 60 or カバー率 ≥ 0.4
  low:    それ以外（予測区間も広く表示）
予測区間: 残差の経験分位点（リードタイムバンド別）から P10/P90 を付す
```

## 11. 根拠（factors.impact）の算出方法

乗法モデルなので log 分解で**厳密に**寄与を出せる（フェーズ2はSHAP不要）:

```
log(Pickup予測) = log(ベース) + log(PaceAdj) + log(EventLift) + log(MarketAdj) + log(PriceEffect)
factor_i.impact = 各項の log 値（=寄与率。exp すれば倍率）
```
- 表示は倍率（+15% 等）に変換。合計が総変化と一致するため「説明の分解が足し算で合う」— 監査可能性の要
- 在庫クリップが効いた場合（min で切られた）は「満室制約」を factor として明示
- フェーズ3のML化後: log需要に対するSHAP値を同じ factor 枠（ペース/イベント/市場/価格/その他）に集約して射影。**「その他」が大きくなりすぎたらモデルの説明性が劣化したとみなす**閾値監視（例: |その他| > 総変動の20%で警告）

## 12. 数値例（動作イメージの共有用）

前提: 8/15(土)、L=26日、キャパ100室、NetOTB=58室、基準カーブ比 RefCurve(26)=0.55

```
BaseFinal = 92室（土曜・お盆明け週の水準）
Pace      = 58 / (92×0.55) = 1.146 → w(26)=0.55^0.7=0.66 → PaceAdj = 1+0.66×0.146 = 1.096
ベース残存 = 92 × (1−0.55) × 1.096 = 45.4室
```

## 13. 学習・更新パイプライン

| 対象 | 更新頻度 | 窓 | 備考 |
| --- | --- | --- | --- |
| ベースライン・リファレンスカーブ | 月次 | 直近3年（指数重み） | レジーム除外設定 |
| イベントlift | 月次（イベント実績確定の都度） | 全期間 | 経験ベイズ縮小 |
| キャンセルハザード | 月次 | 直近18ヶ月 | チャネル追加時は再推定 |
| 弾力性 ε | 四半期 | 直近24ヶ月 | 人間レビュー必須 |
| 日次予測・推奨 | 日次（F章タイムライン） | — | 全宿泊日 t+1〜t+365 |

- **ドリフト検知**: リードタイムバンド別WAPEの移動平均が閾値超過（例: 直近4週が過去12週平均の1.3倍）で警告 → 再学習 or 人間調査
- 【R】**ブッキングウィンドウ分布の監視を追加**: リードタイム分布のシフト（中央値リードタイム・分位点の移動監視）はpickup系予測の主要な劣化要因であることが実証されている【検証済み・Webb 2020】。WAPE監視だけでは劣化の原因が見えないため、分布シフト検知を独立の監視項目とする
- 【R】**誤差指標**: 細粒度セグメントでは実績ゼロによりMAPEが発散するため**MAPE単独での評価・報告は禁止**。主指標はWAPE/MAE（可能なら客室単価で重み付けしたMAE=金銭損失の近似)【検証済み】。`04_評価設計.md` にも反映
- 【R】**予測バイアスの非対称性**: 高需要日では過大予測の方が収益毀損が大きいという実証がある【検証済み・航空】。高需要日（需要ランクA/B）の予測は保守側（P50でなくやや下方の分位点を意思決定に使う等）の運用オプションを持つ
- すべての学習ジョブはテナント（ホテル）単位で独立実行（NFR-10。他ホテルデータは混ぜない。将来「業界プライア」を導入する場合は匿名集約+opt-in）

## 14. コールドスタート（SaaS新規テナントの立ち上がり）

| データ状況 | 動作 |
