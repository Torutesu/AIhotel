## A. 内部要因データ取得: サイトコントローラー日次AIエージェント

### A-1. 役割
サイトコントローラー（TL-リンカーン/手間いらず/ねっぱん等・要確認B1）から**予約状況を毎日取得**し、予約明細DBを差分更新する。これが内部要因（OTB・ブッキングペース・ADR実績）の唯一の継続的供給源となる。

### A-2. ベンダー別アダプタ・アーキテクチャ（SaaS前提の中核設計）

**前提: サイトコントローラーはベンダー・プロダクトごとに接続仕様が全く異なり、都度対応が必要。さらにプロダクトによっては自動取得が不可能な場合がある。** したがって「1つの連携を作る」のではなく、**アダプタを追加していけるプラグイン構造**と、**自動化不可でもサービス提供できるフォールバック**を最初から設計に含める。

```
SiteControllerAdapter interface（全ベンダー共通契約）:
  capabilities(): { tier, supportsCancellation, supportsHistory, maxHorizonDays, ... }
  authenticate(credentials)          … テナント別認証情報（暗号化保管、NFR-11）
  fetchReservations(dateRange) → RawDocument[]
  parse(RawDocument) → ReservationRecord[]   … 共通の予約明細スキーマへ正規化
  healthcheck()

対応ティア（アダプタごとに宣言）:
  T1: 公式API/データ連携          … 最優先。安定・契約要
  T2: 定型エクスポート自動取得     … CSV DL操作の自動化 / メール添付 / FTP
  T3: ブラウザ操作エージェント     … Playwright固定シナリオ+LLM復旧支援
  T0: 手動アップロード（フォールバック）… 自動化不可 or アダプタ未開発のベンダー向け。
      CSV/Excelアップロード UI + ベンダー別フォーマット変換テンプレート
```

- **下流は方式を知らない**: T0〜T3のどれで入っても、正規化後の予約明細スキーマ以降（検証→upsert→OTB生成→予測）は完全に共通。これにより「まず T0（手動）でオンボーディングし、アダプタができ次第 T1〜T3 に切替」という営業展開が可能になる
- **テナント別設定**（FR-S07）: `(tenantId, hotelId) → adapterType, credentials, schedule, フォーマット版数`。同一ベンダーでもプロダクト版・契約プランで画面/出力が違うことがあるため、**アダプタ×版数**で管理する
- **新規ベンダー対応のコスト見積りを標準化**: アダプタ開発チェックリスト（認証方式/2FA有無、出力項目マッピング、キャンセルの表現、遡及修正の扱い、レート制限）を作り、案件ごとの都度対応を型化する
- **初期対応ベンダーの選定**（要詰めG-1）: ターゲット顧客層のシェア上位（TL-リンカーン、手間いらず、ねっぱん、らく通等）から1〜2社に絞って開始。1社目は最初の導入ホテルが使っている製品で決まる

> 方針: 「AIエージェント」といっても毎回LLMに画面を判断させるのではなく、**決定的なスクリプトを正とし、LLMは(1)アダプタ初期構築の補助、(2)画面変更時の復旧提案、(3)取得データの妥当性チェック** に限定する。日次バッチの信頼性が最優先。

### A-3. エージェントの日次フロー

```
1. ログイン（認証情報はSecrets管理。2FA有無を要確認）
2. 予約データ取得（対象範囲: 本日〜365日先の宿泊日 + 過去30日の遡及修正分）
3. 生データ保存（raw層: 取得日時・ソース・元ファイルをそのまま保管 → 再処理可能性 FR-D06）
4. 検証: 件数・必須項目・前日比の異常検知（例: 予約数が前日比±50%超なら警告して人間確認）
5. 正規化: チャネル/部屋タイプ/プランのコードマッピング（マスタ参照、未知コードは保留キューへ）
6. 差分更新: 予約IDベースでupsert。消えた予約はキャンセル扱いにせず「消失」として記録し照合
   （サイトコントローラーのエクスポートにキャンセルが含まれるかで設計が変わる → 要確認A3）
7. OTBスナップショット生成: (snapshotDate=今日, stayDate, セグメント) → 室数・売上・人数
8. 完了通知 / 失敗時リトライ（3回、指数バックオフ）→ 最終失敗で管理者アラート + UIに鮮度警告
```

### A-4. 設計上の論点（要詰め）
- **冪等性**: 同日再実行しても二重登録しない（snapshotDateキー・予約ID upsert）
- **遡及修正**: 過去宿泊日の実績修正（ノーショー・料金訂正）をどこまで取り込むか
- **取得時刻**: サイトコントローラー側の集計確定時刻に合わせる（例: 深夜2:00取得 → 9:00までに全パイプライン完走 NFR-01）
- **PMSとの二重ソース問題**: サイトコントローラー経由予約とウォークイン/電話予約（PMS直）の網羅性。**サイトコントローラーだけで全予約を捕捉できるか**が最重要確認事項（捕捉できない場合はPMSエクスポート併用）
- **初期データ投入**: 過去2〜3年分はエージェントではなく一括エクスポートで投入（A5）

## B. 外部要因データ取得基盤（クローリング/APIコネクタ）

### B-1. アーキテクチャ

すべての外部ソースを「コネクタ」として統一インターフェースで実装する:

```
Connector interface:
  fetch(targetDateRange) → RawDocument[]     … 取得（API呼出 or クロール）
  parse(RawDocument) → NormalizedRecord[]    … 正規化
  schedule: cron定義 / retryPolicy / rateLimit
  healthcheck: 最終成功時刻・連続失敗回数

保存:
  raw層（取得物そのまま+取得日時） → external_factors テーブル
  external_factors: (source, factorType, targetDate, observedAt, value(JSON), reliability)
```

- `observedAt`（いつ取得したか）と `targetDate`（どの宿泊日に効くか）を必ず分離 → as-of結合によるリーク防止（C参照）
- ジョブスケジューラ（フェーズ1: cron+ジョブテーブル、必要に応じBullMQ等）で全コネクタを一元管理・監視（FR-D05）

### B-2. ソース別設計

| ソース | 方式 | 頻度 | 正規化後のデータ | 注意点 |
| --- | --- | --- | --- | --- |
| **競合ホテル価格** | 第1候補: レートショッパーAPI（OTA Insight等）。第2候補: OTA公開ページのクローラー（Playwright、宿泊日×人数のマトリクス取得）。第3候補: 手動入力UI | 日次（宿泊日90日先まで。直近30日は日2回も検討） | (競合ID, 宿泊日, 人数, 部屋タイプ相当, 最安値, 在庫有無, observedAt) | **法務確認必須**（OTA利用規約・アクセス頻度・robots）。満室=価格非表示の扱い（在庫切れシグナルとして別途価値あり）。取得失敗率を織り込む（信頼度メタ） |
| **天候** | 気象庁API等の公式API | 日次（予報は毎日更新） | (地点, targetDate, 予報種別, 気温/降水確率/警報, observedAt) | 予報は日々変わる→ observedAt別に全部保存。台風は特別イベントとして別扱い |
| **イベント** | イベント情報API・自治体/会場サイトのクローラー + **手動登録UI（確実な運用の要）** | 週次+随時 | (イベント名, 会場, 期間, 種別, 想定規模, 距離) | 網羅は不可能と割り切り「大規模イベントの取りこぼしゼロ」を目標に手動登録と併用。会場キャパ×距離で影響度スコア化 |
| **祝日・連休** | 内閣府CSV + 訪日主要国（中国・韓国・台湾等）の祝日 | 年次 | カレンダーマスタ | 静的データ。連休の並び（飛び石等）を特徴量化 |
| **交通** | 鉄道運行情報・新幹線/航空の臨時便・高速道路情報。航空券価格はAmadeus等（有料・フェーズ3） | 日次〜週次 | (路線/空港, targetDate, 種別, 変化) | 「アクセス」要因。定量化が難しいものはイベント同様スコア化+LLM文脈情報 |
| **為替** | 公開API | 日次 | (通貨ペア, 日次レート) | 単体では弱くインバウンド補正の一部として使用 |
| **インバウンド統計** | JNTO月次（公開） | 月次 | (国, 月, 訪日客数) | 2ヶ月遅れ→トレンド項として使用 |
| **SNS/検索トレンド** | Googleトレンド（無料）から開始 | 週次 | (キーワード, 週, 指数) | フェーズ3以降。ノイズ大 |

### B-3. 運用設計
- コネクタごとの**鮮度SLA**を定義（例: 競合価格24h以内、天候24h以内）。SLA超過はUIの該当箇所に「データが古い」表示（NFR-03と同思想）
- クローラーは対象サイト構造変更で必ず壊れる前提: パース失敗率の監視 + raw保存により**後から再パース可能**にする
- 新規ソース追加はコネクタ1個の追加で済む構造（プライシング側はexternal_factorsテーブルしか見ない）

## C. 特徴量化（内部×外部の結合点）

予測サービスへの入力は「特徴量ストア」ビューに一元化する:

```
feature_view(stayDate, segment, asOf):
  内部: OTB室数/売上, リードタイム, ペース(同時点前年比/基準カーブ比), 残室数,
        現在価格ランク, 直近予約速度(7日移動), キャンセル率実績, 曜日/月/連休位置
  外部: 競合平均価格・自社との乖離率(asOf時点), 競合満室数,
        イベントスコア(会場距離×規模), 天候予報(asOf時点の予報値),
        祝日/連休特徴, 為替トレンド, インバウンドトレンド
```

- **絶対規則: asOf時点で観測済み（observedAt <= asOf）のデータのみ結合する**。学習・推論・バックテストのすべてで同じ結合ロジックを使う（リーク防止。ここが崩れると「バックテストだけ好成績」になる）
- 実装: SQLビュー or 事前計算テーブル。フェーズ2はSQL集計で十分、フェーズ3で特徴量計算をPythonサービスに移管

## D. プライシングアルゴリズム（03の詳細化）

### D-1. パイプライン（日次）

```
①需要予測: 各(stayDate, segment)について
   ベースライン需要 = 過去実績の 季節性 × 曜日 × トレンド
   × ペース補正   = f(同時点OTB / 基準カーブOTB)
   × イベント補正 = イベントスコア→リフト係数（学習 or ルックアップ表）
   × 市場補正     = f(競合価格ポジション, 競合満室状況, インバウンド/為替トレンド)
   × 天候補正     = 直前期間(〜14日)のみ適用
   → 残存需要予測(現在価格のまま販売した場合の追加販売室数) と 着地予測(OTB+残存)

②弾力性適用: 残存需要(p) = 残存需要(p_ref) × (p/p_ref)^ε
   εはセグメント×シーズン×リードタイム帯別。初期値は業界標準値+ホテルヒアリングで設定し、
   運用ログ（価格変更と需要反応）で四半期ごとに再推定

③最適化: 各候補ランク r ∈ {R01..R65} について
   期待売上(r) = price(r) × min(残存需要(price(r)) × (1-予測キャンセル率), 残室数)
   目的関数 = w_adr × ADR寄与 + w_occ × 稼働寄与 − w_comp × 競合乖離ペナルティ
   （SC-02の重み設定 weightOccupancy/weightAdr/weightCompetitor をここで反映）
   → ガードレール適用（min/maxランク、変更幅制限、固定期間、団体ブロック除外）
   → 推奨ランク + 次点候補2件（各候補の期待稼働・期待売上付き: FR-P02）

④根拠生成: 下記フォーマットで全推奨に添付・永続化
```

### D-2. 根拠出力JSON（外部契約として固定 — E4）

```json
{
  "stayDate": "2026-08-15",
  "asOf": "2026-07-20T02:00:00+09:00",
  "recommendation": { "rank": 42, "adr": 21500, "currentRank": 38,
    "alternatives": [{ "rank": 40, "expectedOccupancy": 0.94, "expectedRevenue": 2510000 }] },
  "prediction": { "occupancy": 0.92, "landingAdr": 20800, "demandLevel": "B",
    "confidence": "high", "otbOccupancy": 0.61 },
  "factors": [
    { "name": "ブッキングペース", "type": "internal", "impact": 0.08,
      "detail": "同時点前年比+12%、基準カーブ比+6%", "source": "site_controller", "observedAt": "..." },
    { "name": "イベント", "type": "external", "impact": 0.15,
      "detail": "○○夏祭り(徒歩10分・来場5万人想定)", "source": "event_registry", "observedAt": "..." },
    { "name": "競合価格", "type": "external", "impact": 0.05,
      "detail": "競合3社平均比-8%、うち1社満室", "source": "rate_shopper", "observedAt": "..." },
    { "name": "天候", "type": "external", "impact": 0.0, "detail": "14日以上先のため未適用" }
  ],
  "guardrails": [{ "rule": "maxDailyChange", "applied": false }]
}
```

- モデルがルールベース→MLに進化しても**このフォーマットは不変**（フロント・LLM・監査の全消費者を保護）
- MLモデル化後はSHAP値をfactorsの同項目に射影する

### D-3. フェーズ別のモデル実体
| フェーズ | 需要予測 | 弾力性 | 実装 |
| --- | --- | --- | --- |
| 2 | 季節性×曜日×ペースのルール/統計 | 固定値（カテゴリ別） | Node内（SQL+TS） |
| 3 | GBDT(LightGBM等)で残差学習、予測区間(P10/50/90) | セグメント別回帰 | Pythonサービス(FastAPI)追加 |

## E. LLM抽象化層（ベンダー非依存）

### E-1. 方針
- **特定ベンダーにロックインしない**。Claude / Gemini / GPT 等を設定で切替可能にする
- 実装: LiteLLM等の抽象化ライブラリ、または自前の薄いアダプタ（`generate(taskType, context) → text`）。ストリーミング(SSE)対応を含める
- 用途ごとにモデルを変えられる設計（例: 日次バッチのコメント生成は低コストモデル、チャットは高性能モデル）

### E-2. LLMの責務境界（重要）
| やる | やらない |
| --- | --- |
| 根拠JSON・KPIの自然言語化（AI解説・インサイト・提案文） | 数値計算・予測・集計（すべて予測サービス/DB側） |
| チャット応答（注入コンテキストの範囲内） | 根拠JSONに無い数値・固有名詞の生成（FR-L03で機械検証） |
| （限定）クローラーの画面変更時の復旧提案 | 日次バッチの判断そのもの |

### E-3. 共通基盤
- プロンプトはコードから分離してバージョン管理（taskTypeごとにテンプレート）
- 出力検証: 数値・固有名詞の入力照合（正規表現+突合）→ 不合格は再生成 or 定型文フォールバック
- ベンダー横断の評価: 同一入力セットでの出力品質比較ハーネスを用意し、モデル切替の判断材料にする
- コスト・レイテンシのロギング（taskType×モデル別）
- 個人情報はコンテキストに含めない（NFR-06。そもそもDBに保持しない方針: NFR-04）

## F. デイリー運用サイクル（タイムライン案）

```
02:00  サイトコントローラーエージェント実行（予約取得→検証→正規化→upsert）
03:00  外部コネクタ群実行（競合価格・天候・イベント・為替…並列）
04:00  OTBスナップショット生成 → 基本分析の事前集計バッチ
05:00  需要予測 → 価格最適化 → 推奨+根拠JSON生成（365日先まで、直近90日は必須）
06:00  LLMバッチ: ダッシュボードAI解説・プライシング提案文・アラート文の生成
07:00  完了チェック。失敗があれば前回値保持+鮮度警告+管理者通知
09:00  業務開始: 担当者が推奨確認→承認→サイトコントローラーへ反映（B1の方式による）
日中   任意分析（都度計算）、チャット、手動イベント登録は随時
```

- 将来（フェーズ4）: 直近日程のみ日中再取得+再推奨（日数回）、承認レス自動反映（FR-P10）
