## 1. 概要

### 1.1 目的
ホテルの過去実績・予約状況（内部要因）と、競合価格・天候・イベント・交通・インバウンド動向等（外部要因）を組み合わせ、需要予測とダイナミックプライシングの推奨を**根拠付きで**提供し、ホテルの収益（RevPAR）最大化と収益管理業務の効率化を実現する。

### 1.2 位置づけ・ベンチマーク
- ベンチマーク製品: IDeaS Revenue Solutions
- 差別化ポイント: すべての予測・推奨に対する**要因分解された根拠の提示**（IDeaSがブラックボックスと評されがちな点への対抗軸）

### 1.3 ユーザー
| ロール | 想定ユーザー | 主な利用機能 |
| --- | --- | --- |
| ADMIN | システム管理者 | 全機能・設定・ユーザー管理 |
| MANAGER | ホテル支配人・レベニューマネージャー | 推奨価格の承認、分析、レポート |
| STAFF | フロント・予約担当 | 閲覧、日次確認、イベント登録 |
| READONLY | 経営層・オーナー | ダッシュボード・レポート閲覧 |

### 1.4 用語定義
| 用語 | 定義 |
| --- | --- |
| ADR | 平均客室単価 = 室料売上 ÷ 販売室数（税サ扱いは要詰め: B8） |
| RevPAR | 販売可能客室1室あたり売上 = 室料売上 ÷ 販売可能室数 |
| OTB (On The Books) | ある時点で確定している予約の積み上がり |
| リードタイム | 宿泊日と予約日（または評価時点）の差 |
| ブッキングカーブ | 宿泊日に対するOTBのリードタイム推移 |
| 料金ランク | 65段階の価格テーブル（R01〜R65、人数別料金を内包） |
| 需要ランク | A〜Eの5段階需要評価 |
| サイトコントローラー | OTA・自社サイトの在庫・料金を一元管理する外部システム（TL-リンカーン、手間いらず、ねっぱん等）|

## 2. スコープ

### 2.1 対象
- 情報可視化（ダッシュボード / 日別分析 / 月次レポート / AIまとめ）
- 価格最適化（ダイナミックプライシング推奨、根拠提示、人間による承認）
- データ分析（基本分析=バッチ / 任意分析=都度 / セグメント分析=個人・団体）
- データ取得基盤（サイトコントローラー経由の予約データ日次取得、外部要因のクローリング/API取得）
- AIによる状況解説・チャット
- **SaaS提供のためのマルチテナント基盤**（テナント=ホテル運営会社。テナント別のデータ分離、接続設定、オンボーディング）

### 2.2 対象外（現時点）
- **決済・課金機能**（SaaS利用料の請求・決済はシステム外で運用。将来必要になっても外部課金サービス連携とし、本システムにカード情報等は持たない）
- PMS本体機能（チェックイン/アウト、会計）
- 推奨価格のサイトコントローラーへの**自動書き戻し**（フェーズ4で検討。初期は人間承認→手動または半自動反映）※要詰め: B1
- 団体営業の見積・ブロック管理（団体は分析上の分離のみ）
- 多言語UI（初期は日本語のみ）※要詰め

## 3. システム構成（全体像）

```
┌─────────────── 外部世界 ───────────────┐
│ サイトコントローラー   OTAサイト群      天気API/イベント/交通/為替 │
└──────┬──────────────┬──────────────────┬──────┘
        │(日次AIエージェント)  │(競合価格クローラー)      │(APIコネクタ/クローラー)
┌──────▼──────────────▼──────────────────▼──────┐
│              データ取得層（ジョブスケジューラ管理）              │
│   取込 → 検証 → 正規化 → 生データ保管(raw) → ドメインDB反映     │
└───────────────────────┬───────────────────┘
                            │
┌───────────────────────▼───────────────────┐
│ PostgreSQL: 予約明細 / OTBスナップショット / 競合価格 / 外部要因    │
│             / 料金ランク / 予算 / 予測・推奨ログ / 監査ログ         │
└──────┬───────────────────────────┬────────┘
        │                                       │
┌──────▼──────────┐          ┌──────▼──────────┐
│ 予測・最適化サービス      │          │ バックエンドAPI (Express) │
│ (需要予測/弾力性/最適化/   │◀────────▶│ 画面集約API/汎用分析API/   │
│  根拠JSON生成)            │          │ 認証/設定                 │
└──────┬──────────┘          └──────▲──────────┘
        │ 根拠JSON                              │
┌──────▼──────────┐          ┌──────┴──────────┐
│ LLM抽象化層              │          │ フロントエンド (Next.js)   │
│ (Claude/Gemini/GPT差替可) │          │ 7タブ+チャット (実装済)    │
│ コメント生成/チャット      │          └─────────────────┘
└─────────────────┘
```

- LLMは**言語化・対話のみ**を担当し、数値計算・予測はすべて予測サービス側で行う（数値捏造防止）
- LLM抽象化層によりベンダー切替（Claude / Gemini / GPT等）を設定変更で可能にする

## 5. データ要件（サマリ）

詳細は `02_データ要件.md`。骨子:
- **予約明細**（予約受付日時・宿泊日・部屋タイプ・人数・チャネル・料金・キャンセル日時・団体フラグ）が全機能の土台。サイトコントローラー経由の日次取得（FR-D01）で蓄積し、導入時に過去分をPMS/サイトコントローラーのエクスポートで初期投入する
- **OTBスナップショット**を日次生成（後から遡って作れないため、稼働開始を最優先）
- 外部要因は「宿泊日に対する特徴量」として、**予測時点で既知だった値**（as-of）で保存する（リーク防止）
- 予算マスタ（月次×指標）の新設が必要（ダッシュボード予算比の前提）
