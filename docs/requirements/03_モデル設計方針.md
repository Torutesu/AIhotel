# 03. モデル設計方針（需要予測 × 価格最適化 × 説明可能性）

## 0. 設計原則

1. **予測と最適化を分離する** — 「需要を予測するモデル」と「価格を決める最適化ロジック」を別モジュールにする。説明可能性・デバッグ・段階的高度化のすべてで有利
2. **説明可能性を後付けにしない** — 「予想の根拠を出力できる」が重要ポイントである以上、ブラックボックスモデル前提で後からSHAPを貼るのではなく、**構造的に分解可能なモデル（ベースライン＋補正項）**から始める
3. **人間の承認を挟む前提で設計する（Human-in-the-loop）** — 初期は推奨→承認→反映。全自動化はフェーズ4以降
4. **シンプルなベースラインを先に作り、常に比較対象として残す** — MLモデルは「ベースラインに勝てたら採用」

## 1. 予測対象の定義

予測の基本単位: **宿泊日 D × セグメント s（部屋タイプ/人数/チャネル…） × 評価時点 t（リードタイム）**

- 出力1: 最終稼働率・最終販売室数の予測（宿泊日Dの着地見込み）
- 出力2: 最終ADRの予測
- 出力3: 残存需要曲線 = 「今からD日までに、価格pのとき追加で何室売れるか」（価格最適化の入力）

ポイント: ブッキングカーブの可視化とモデルは同じデータ構造（OTB as-of）を共有する。**「現在のOTB + 残存需要予測 = 着地予測」という分解**にすると、ユーザーは「確定分」と「予測分」を分けて見られる（フロントの実績/予約/AI予測の3層表示と一致）。

## 2. 内部要因と外部要因の組み合わせ方

推奨アーキテクチャ: **乗法的ベースライン + 補正項の階層構成**

```
最終需要予測(D, s) =
    ベースライン需要(D, s)          … 内部要因: 季節性 × 曜日 × トレンド（過去実績から）
  × ペース補正(D, s, t)             … 内部要因: 同一リードタイム時点の前年比OTB（ブッキングペース）
  × イベント補正(D)                 … 外部要因: イベント・祝日・連休のリフト係数
  × 市場補正(D, t)                  … 外部要因: 競合価格ポジション、インバウンドトレンド、天候(直前のみ)
  × 価格効果(p / p_ref)^ε           … 自社価格の弾力性項
```

この形の利点:
- **各係数がそのまま「根拠」になる**: 「ベースライン80室 × イベント補正1.15（東京マラソン） × ペース補正1.08（前年比+8%） = 99室」という説明が直接出せる
- 外部要因のデータが未整備でも係数=1.0で動く（フェーズ1から段階導入できる）
- 将来、各補正項を個別にML化できる（例: イベント補正をルックアップ表→回帰モデルへ）

フェーズ3では、この構造を保ったまま GBDT（LightGBM等）で残差学習する、または各項を統合したモデルにSHAPを適用して同じ「要因分解」フォーマットに射影する。**根拠出力のフォーマット（要因×寄与率のリスト）を先に固定し、モデルがどう進化しても同じフォーマットを返す**のがシステム設計上のキモ。

## 3. 価格最適化

1. **弾力性推定**: 過去の自社価格変更と需要反応から価格弾力性εを推定（セグメント・シーズン・リードタイム帯別）。初期はカテゴリ別の定数、データが貯まれば回帰で
   - 注意: 過去の価格履歴が無いと推定できない（02の確認事項）。無い場合は業界標準値で開始し、運用ログから学習
2. **期待収益最大化**: 各候補価格 p（=65段階の各ランク）について `期待収益(p) = p × min(予測需要(p), 残室数)` を計算し、最大となるランクを推奨
   - 残室が少ない日: 在庫制約が効く → 自然に強気価格が出る
   - キャンセル予測を織り込むなら `ネット需要 = グロス需要 × (1 - 予測キャンセル率)`
3. **ガードレール（業務ルール）**: 最低/最高ランク制約、1日あたりの変更幅制限、手動オーバーライドと固定期間、団体ブロックの除外。これらはモデルではなく設定として持つ（設定画面の要件になる）
4. **推奨の出し方**: 単一の推奨ランクだけでなく「推奨候補＋各候補の期待稼働・期待売上」を提示（機能要件2-1の「推奨価格候補の提示」と一致）

## 4. 説明可能性（根拠出力）の設計

出力は2層構造にする:

**層1: 構造化された根拠データ（API/DBに保存）**
```json
{
  "date": "2026-08-15",
  "recommendedRank": 42,
  "currentRank": 38,
  "predictedOccupancy": 0.92,
  "confidence": "high",
  "factors": [
    {"name": "ブッキングペース", "type": "internal", "impact": +0.08, "detail": "同時点前年比+12%"},
    {"name": "イベント", "type": "external", "impact": +0.15, "detail": "夏祭り（徒歩10分・来場5万人）"},
    {"name": "競合価格", "type": "external", "impact": +0.05, "detail": "競合3社平均より8%安い"},
    {"name": "天候", "type": "external", "impact": 0.0, "detail": "影響なし（14日以上先）"}
  ]
}
```

**層2: LLMによる自然言語化（AIコメント・チャット）**
- 層1のJSONと当該期間のKPIをプロンプトに入れて、ダッシュボードの「AI状況分析コメント」やチャットの回答を生成
- LLMに数値計算をさせない（計算はすべて層1まででやる。LLMは言語化のみ）— 数字の捏造を防ぐ
- 予測ログとして層1を全件保存 → 後から「あの時なぜこの推奨だったか」を監査できる（信頼獲得に直結）

## 5. 個別論点

- **団体の扱い**: 団体は価格ロジックが別（相対・手動）なので、**需要予測の学習からは団体ブロックを分離**し、可視化では個人/団体/合計を切替表示（機能要件3-3、フロントのAnalysisSettings.individualGroupTotalと一致）。団体の入り方（ブロック→こなし）はカーブ形状を大きく歪めるため、フラグ必須
- **キャンセル**: グロス予約とネット予約を分けて保持。キャンセル率はリードタイム・チャネル別に推定（OTAの無料キャンセル期限前後で跳ねる）
- **コールドスタート**: 開業直後や新規導入ホテルは自社履歴が薄い → 類似ホテルテンプレート＋外部要因のみで開始し、実データで漸進更新
- **月別と日別**: 月別ブッキングカーブは日別の集計で導出（別モデルにしない）
- **特徴量のリーク防止**: 学習時は「予測時点tで知り得た情報」のみ使う（as-of結合）。競合価格・天気予報・OTBすべて同様。ここを間違えるとバックテストだけ好成績になる

## 6. 技術スタック案（バックエンドとの関係）

- 予測・最適化は **Pythonの別サービス**（FastAPI + pandas/LightGBM等）として切り出し、Node/Express本体とはREST/ジョブキューで連携する案を推奨
  - 理由: MLエコシステム（学習・SHAP・バックテスト）はPython一択。Node側はデータ提供とUI向けAPIに専念
  - 代替案: フェーズ2のルールベースまではNode内で実装し、フェーズ3でPythonサービスを追加（初期の運用コストを抑えられる）→ **推奨はこちら（段階導入）**
- バッチ基盤: 日次バッチ（PMS取込→OTBスナップショット→事前集計→予測→推奨生成）。cron+ジョブテーブルで開始し、必要になったらキュー（BullMQ等)へ
- LLM: **特定ベンダーに依存しない抽象化層を挟む**（Claude / Gemini / GPT を設定で差し替え可能に）。AIコメント生成（バッチ・キャッシュ）とチャット（都度）で呼び分け。詳細は `12_プライシングアルゴリズム・データ取得設計.md` の LLM抽象化層を参照
