# 02. データ要件

## 1. 自社データ（ホテル側から受領）

### 1.1 最重要: 予約明細データ（PMSエクスポート）

ブッキングカーブ・セグメント分析・モデル学習のすべての土台。**1予約=1レコード（または1泊1レコード）**で以下が必要:

| フィールド | 必須度 | 用途 | 備考 |
| --- | --- | --- | --- |
| 予約ID | ◎ | 一意識別・変更追跡 | |
| 予約受付日時 | ◎ | ブッキングカーブのas-of軸 | これが無いとカーブが描けない |
| チェックイン日/チェックアウト日（or 宿泊日） | ◎ | 宿泊日軸 | 連泊の泊数展開ルールを確認 |
| 部屋タイプ | ◎ | 部屋タイプ別分析 | マスタとのコード対応表が必要 |
| 利用人数 | ◎ | 人数別分析（可視化要件で◎） | 大人/子供の区別有無を確認 |
| 販売チャネル（OTA名/公式/電話等） | ◎ | チャネル別分析（要件で△だが取得は必須） | チャネルマスタの整備が必要 |
| 室料金額 | ◎ | ADR・売上・平均販売価格 | 税サ込/抜き、食事付きプランの室料分離可否を確認 |
| キャンセル日時・キャンセルフラグ | ◎ | ネットOTB計算、キャンセル率予測 | キャンセル済予約が出力に含まれるか要確認 |
| 団体/個人フラグ | ◎ | セグメント分析（機能要件3-3）、団体は別扱い | **要件メモに「予約データにフラグが必要」とある通り。PMS上のフラグ有無を最優先確認** |
| プラン/レートコード | 〇 | プラン別分析、キャンペーン効果測定 | |
| 地域（居住地）・国籍 | 〇 | 地域別・インバウンド分析 | 個人情報の扱いに注意（後述） |
| 泊数・リードタイム | 〇 | 導出可能だが検算用に | |
| 予約変更履歴 | △ | 精密なOTB再構成 | 無ければ最新状態+キャンセルで近似 |

**確認事項**: エクスポート形式（CSV/API/固定長）、文字コード、更新頻度（日次バッチか都度か）、**過去何年分遡れるか**（学習には最低2年、できれば3年以上）、キャンセル済み・ノーショーの扱い。

### 1.2 日別実績データ

- 日別の 販売室数 / 稼働率 / 室料売上 / ADR / RevPAR / 宿泊人数（予約明細から導出可能だが、PMS側の確定値と突合するために受領したい）
- 予算データ（月別 or 日別の予算稼働・予算ADR・予算売上）— ダッシュボードの予算比表示に必要
- 販売可能室数の変動（改装・故障によるアウトオブオーダー）— 稼働率の分母が日によって変わる点に注意

### 1.3 料金設定データ

- 料金ランク表（現状スキーマは65段階・1〜4名料金を想定済み）
- **過去に実際に設定していた価格の履歴**（宿泊日×日付ごとの設定ランク）— 価格弾力性の推定に必須。これが無いと「価格を変えたら需要がどう動いたか」が学習できない。PMS/サイトコントローラーのどちらに残っているか確認

## 2. 外部データ

優先度は「モデル寄与の見込み × 取得コスト」で整理。フェーズ1では★のみで開始可能。

| データ | 優先度 | 取得手段の候補 | 更新頻度 | 備考 |
| --- | --- | --- | --- | --- |
| 競合ホテル価格（ベンチマークホテル） | ★最高 | **第一候補: 楽天トラベル空室検索API・じゃらんWebサービス（公式・無料）**。不足分はレートショッパー（Lighthouse等・有料）/ 手動入力で補完 | 日次以上 | 最も説明力が高い外部要因。具体URL・規約確認事項・冗長化設計は `15_外部データ係数化・学習ループ・価格方程式.md` §1.1・`16` A-3参照。OTAサイトの直接スクレイピングは規約リスクが高く非推奨 |
| イベント | ★高 | 会場公式サイト・自治体観光サイトのクローリング + 手動登録 | 週次 | 現状スキーマにEventテーブルあり。会場キャパ・距離で影響度をスコア化。具体URL例は`15`§1.4 |
| 祝日・連休カレンダー | ★高 | 内閣府CSV + Nager.Date API（訪日主要国祝日） | 年次 | 中国国慶節・春節など訪日主要国の祝日も含める。URLは`15`§1.3 |
| 天候・気象予報 | 中 | 気象庁 公式JSON（無料） | 日次 | 直前需要（当日・前日予約）への影響。予報は2週間先まで、それ以遠は平年値。URLは`15`§1.2 |
| インバウンド統計 | 中 | JNTO訪日外客統計・観光庁宿泊旅行統計調査(e-Stat API) | 月次 | 国別トレンドの補正項として。月次かつ2か月遅れの点に注意 |
| 為替レート | 中 | 公開API（Frankfurter等） | 日次 | 単体では弱い。インバウンド比率が高いホテルほど効く |
| 航空券価格・座席供給 | 低〜中 | Amadeus API等（有料） | 日次 | 取得コスト高。フェーズ3以降の検討で十分 |
| SNS・ニュース・検索トレンド | 低（係数化はしない） | Google News RSS / Googleトレンド / YouTube Data API（すべて無料） | 日次〜週次 | **「ソースレイク」として係数化せずrawで厚く収集**し、週次LLMダイジェストのみ生成。効果実証（アブレーション）が取れたら係数へ昇格。X APIは有料のため事業課金開始後・テナント共有で1社あたり月5,000円以下になる場合のみ導入（判断基準確定済み）。詳細は`16_クローリング安定化・ソースレイク・コスト設計.md` |
| 世界情勢・外交 | 低 | 外務省海外安全情報等（ソースレイク扱い） | - | モデル係数にはせず「AIコメントの文脈情報」としてLLMに渡す扱い |

**設計上の注意**: 外部データは「宿泊日に対する特徴量」として使うものと「予約日時点で既知だったか」の区別（リーク防止）が重要。例えば天気の「実績」は予測時点では未知なので、学習時も「その時点の予報」を使う必要がある（少なくとも実績をそのまま特徴量にしない）。

## 3. データモデルへの示唆（現状スキーマからの拡張）

現状の `schema.prisma` に対して、少なくとも以下の拡張が必要:

1. **Reservation（予約明細）テーブルの新設** — 上記1.1のフィールド。ブッキングカーブは全てここから集計
2. **OtbSnapshot（日次スナップショット）テーブル** — `(snapshotDate, stayDate, hotelId, セグメント次元…) → rooms, revenue, guests`。予約明細から日次バッチで生成（明細が遡れない期間の手当てにも使う）
3. **Channel マスタ** — 現状チャネルはCampaign.channelの文字列のみ。マスタ化して予約明細と紐付け
4. **PriceHistory（自社設定価格履歴）** — 宿泊日×設定日×部屋タイプの設定ランク/価格。DailyRoomDataは「宿泊日につき1行」なのでas-of履歴が持てない
5. **Prediction/Recommendation ログテーブル** — 予測値・推奨ランク・根拠（特徴量寄与のJSON）・採用/不採用を保存。評価設計（04）の土台
6. **DailyData.externalFactors（String）の構造化** — 外部要因はテーブル化（factor種別・値・出典・対象日）し、根拠表示に使えるようにする

## 4. 非機能・ガバナンス面の考慮

- **個人情報**: 予約明細に氏名・連絡先は不要。受領前に除外してもらうのが最も安全（要件にも分析にも不要）。国籍・居住地はセグメント分析に使うが個人単位で識別しない設計に
- **マルチテナント**: スキーマはhotelId分離のマルチホテル前提になっている。1ホテル目はシングルテナント運用でも、データ分離・権限（既存のUserRole）を最初から効かせる
- **データ量の見積り**: 200室・年間予約3〜5万件 × 3年分 + OTBスナップショット（365日先×365日×セグメント）でも数百万行オーダー。PostgreSQLで十分。集計はマテリアライズドビュー or 事前集計テーブル（基本分析=バッチの機能要件と対応)
- **タイムゾーン・日付境界**: 予約受付日時のTZ、宿泊日の切り替わり（チェックイン日基準）を全テーブルで統一
