## 1. テスト方針

### 1.1 基本方針

マルチテナントSaaSであり、テナント分離の欠陥は他社データの漏洩に直結する。したがってテストの優先順位は以下とする。

1. **テナント分離・認可** — 最優先。欠陥が本番事故になる
2. **ドメイン計算ロジック** — 料金ランク、需要レベル、KPI算出。誤りが業務判断を誤らせる
3. **入力検証** — 不正値の混入防止
4. **画面表示** — 上記が担保された後

### 1.2 テストレベル

| レベル | 対象 | 現状 |
| --- | --- | --- |
| 単体テスト | 純粋関数、検証スキーマ、認証ユーティリティ | 実装済み |
| 結合テスト（API） | エンドポイント単位の認証・認可・応答 | **未実装** |
| E2Eテスト | 画面操作を通じた業務シナリオ | **未実装** |

### 1.3 テスト対象外

Phase 4 の未実装機能（PMS/OTA連携、スクレイピング、需要予測ML、Claude API連携、バッチ基盤）はテスト対象外とする。実装時に本書へテストケースを追加する。

## 2. テスト環境

### 2.1 単体テスト

| 項目 | 内容 |
| --- | --- |
| フレームワーク | Vitest 3 |
| 設定ファイル | `backend/vitest.config.ts` |
| 実行環境 | node |
| 対象パターン | `src/**/*.test.ts` |
| DB接続 | **不要**（純粋関数のみを対象とするため） |

`lib/config.ts` は import 時に環境変数を検証し、不備があれば例外を送出する。このためテスト設定側で `JWT_SECRET`、`JWT_EXPIRES_IN`、`JWT_REFRESH_EXPIRES_IN`、`NODE_ENV=test` を注入している。

### 2.2 実行コマンド

```bash
# 単体テスト
pnpm --filter backend test

# コミット前に必ず通すこと（AGENTS.md）
pnpm --filter './*' type-check && pnpm --filter backend test
pnpm --filter backend build && pnpm --filter frontend build
```

### 2.3 CI

`.github/workflows/ci.yml` にて、PR および `main` / `production-readiness` への push で以下を順に実行する。

1. pnpm / Node 20 セットアップ
2. `pnpm install --frozen-lockfile`
3. `pnpm --filter backend db:generate`（型チェックの前提）
4. 全パッケージの `type-check`
5. `pnpm --filter backend lint`（アーキテクチャ境界ルールを含む）
6. `pnpm --filter backend test`
7. backend ビルド → frontend ビルド

### 2.4 手動確認用アカウント

seed により投入されるデモアカウント。

| ロール | メールアドレス | パスワード |
| --- | --- | --- |
| ADMIN | `admin@demo-hotel.example.com` | `Admin1234` |
| MANAGER | `manager@demo-hotel.example.com` | `Admin1234` |
| OPERATOR | `operator@demo-hotel.example.com` | `Admin1234` |

seed は冪等（upsert / createMany）であり、繰り返し実行しても重複しない。

## 4. テストカバレッジ評価

### 4.1 担保されている領域

| 領域 | 内容 |
| --- | --- |
| パスワードハッシュ | bcrypt によるハッシュ化と照合 |
| JWT | 生成・検証の往復、改竄トークンの拒否 |
| トークンハッシュ | SHA-256 の決定性、異なる入力での相異、64桁16進 |
| リフレッシュ有効期限 | 約7日 |
| ログイン・登録の検証 | パスワード強度（長さ・大文字・数字）、氏名必須 |
| 料金ランク上限 | 40は許容、41は拒否、0は拒否（F-SET-02） |
| 価格戦略の重み | 合計100は許容、それ以外は拒否（F-DP-02） |
| 需要予測の純粋関数 | 移動平均、前年比較、イベント影響、週末補正、A〜E判定、ランク写像、稼働率合成とクランプ、確信度 |
| 価格戦略の重み付け合成 | 価格→ランク写像（同着時は安い側）、ADR観点、競合観点、重みによる加重平均、**重み変更で推奨ランクが変わること**、欠損観点の重み按分、競合欠損時に引き下がらないこと、クランプ |

週末補正のテストには既定以外の週末定義を用いたケースが含まれており、`Hotel.weekendDays` を無視したハードコードが混入すれば検出できる。

### 4.2 担保されていない領域（重大度順）

| # | 領域 | 想定される影響 | 重大度 |
| --- | --- | --- | --- |
| G-1 | テナント分離（`requireHotelAccess`） | 他テナントのホテルIDを指定した際の遮断が検証されていない。回帰時に他社データが露出しうる | **最高** |
| G-2 | ロール別認可（`requireRole`） | OPERATOR が変更系操作を実行できてしまう欠陥を検出できない | **最高** |
| G-3 | 認証ミドルウェア（`authenticate`） | トークン欠落・不正形式・期限切れの挙動が未検証 | 高 |
| G-4 | リフレッシュのローテーション | 旧トークンの再利用が拒否されるか未検証 | 高 |
| G-5 | KPI算出 | ADR・稼働率・RevPAR・按分比較の計算が未検証。3箇所に重複実装されており不整合が生じても検出できない | 高 |
| G-6 | エラー変換 | Prisma エラーコードからHTTPステータスへの変換が未検証 | 中 |
| G-7 | 監査ログ | 変更系操作で記録されること、失敗が業務を止めないことが未検証 | 中 |
| G-8 | 予測結果の永続化 | `roomTypeId` が NULL の場合の擬似 upsert（重複作成しないこと）が未検証 | 中 |
| G-9 | フロントエンド | 401 での自動リフレッシュ・再試行、デモモードのフォールバック条件が未検証 | 中 |
| G-10 | レポート生成 | PDF/Excel の生成と日本語表示が未検証 | 低 |

G-1 と G-2 は、本システムで最も事故コストが高い領域でありながらテストが存在しない。結合テスト基盤の整備を最優先の対応とする。

## 6. 受け入れ基準

### 6.1 コミット前（全開発者・全変更）

`AGENTS.md` に定める以下をすべて通過すること。

```bash
pnpm --filter './*' type-check && pnpm --filter backend test
pnpm --filter backend build && pnpm --filter frontend build
```

### 6.2 新規APIルート追加時

以下をすべて満たすこと。1つでも欠ければマージしない。

- [ ] `authenticate` が適用されている（公開可は `/auth/login`・`/auth/refresh`・ヘルスチェックのみ）
- [ ] hotelId を受け取る場合、`requireHotelAccess(...)` が適用されている
- [ ] 変更系の場合、`requireRole('ADMIN','MANAGER')` と `writeAuditLog()` が適用されている
- [ ] 入力が `validators.ts` の zod スキーマと `validate()` で検証されている
- [ ] 生の `req.body` / `req.query` を参照していない
- [ ] レスポンスが `utils/response.ts` 経由の統一形式である
- [ ] TC-T および TC-R に相当するテストケースが追加されている

### 6.3 新規Prismaモデル追加時

- [ ] `tenantId` とテナントリレーションを持つ
- [ ] `@@index([tenantId])` を付与している
- [ ] クエリが hotelId / tenantId で絞り込まれている
- [ ] `prisma migrate dev` でマイグレーションを生成しコミットしている（`db:push` を使わない）

### 6.4 ドメイン確定値の保護

以下を変更する場合、要件変更としての承認を要する。テストで固定されている値でもある。

- 料金ランクは最大40段階
- 需要レベルは A〜E の5段階
- 価格戦略の重みは合計100%
- 週末は `Hotel.weekendDays` を参照（ハードコード禁止）
- ロールは ADMIN / MANAGER / OPERATOR の3種
