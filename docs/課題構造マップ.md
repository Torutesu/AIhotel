## 1. 分類軸

2つの軸で分類する。**すべての課題は「領域」1つと「ブロッカー」1つに必ず属する**（相互排他）。

### 軸1: 領域（何に関する課題か）

| 大分類 | 領域 | 定義 |
| --- | --- | --- |
| **I. プロダクト開発** | 1. データ取込基盤 | 外部（PMS・OTA・競合サイト）からデータを取り込む |
| | 2. 収益管理ロジック | 取り込んだデータから予測・価格・分析結果を出す |
| | 3. 認証・権限・テナント | 誰が何にアクセスできるかを制御する |
| | 4. 画面・UX | 利用者に見せる・操作させる |
| | 5. インフラ・運用基盤 | 動かす環境と運用の仕組み |
| | 6. 仕様・文書管理 | 何を作るかの定義と、その記録の整合性 |
| **II. 事業・運営** | 7. 対外物 | ブランド・営業資料・LP など顧客に見せるもの |
| | 8. プロジェクト進行 | スケジュール・会議体の運営 |

領域1〜5は「作るもの」、6は「作る対象の定義」、7〜8はプロダクト外。境界は**成果物がコードかどうか／顧客に直接渡るかどうか**で切り分けている。

### 軸2: ブロッカー（今、何で止まっているか）

| 記号 | ブロッカー | 意味 |
| --- | --- | --- |
| 🔴 | クライアント回答待ち | 藤田観光・ホテル側の回答や資料提供が無いと進まない |
| 🟡 | 社内決定待ち | 自分たちで決めれば進む |
| 🟢 | 着手可能 | 決定済み。作るだけ |
| ⚪ | 他Issue待ち | 先行Issueの完了が前提 |

「決めてから作る」課題は**現時点のブロッカー**で分類する（決定待ちなら🟡、決定済みなら🟢）。

## 6. 推奨アクション

優先順位は「詰まりの解消」と「取り返しのつかなさ」で決めた。

| 順 | やること | 理由 |
| --- | --- | --- |
| 1 | **#18 のA1〜A5をクライアントへ照会** | 🔴7件のうち最上流。ここが決まらないと領域1・2が動かない |
| 2 | **E2（OTBスナップショット開始）を独立Issue化して即着手** | スナップショットは後から作れない。判断を遅らせた分だけ永久に失う |
| 3 | **🟡8件の期限を設定** | 相手待ちではないため、放置すると自責の遅延になる |
| 4 | **#20（テナント分離テスト）を着手** | 🟢かつ事故コスト最大。機能追加より先に置く |
| 5 | **未Issue化7件のうち、フロント接続とAIチャットをIssue化** | 前者は工数が小さく提供機能が増える。後者は閲覧ロールの主要価値 |
| 6 | **4章の重複・粒度を整理** | #7統合、#19/#21/#24の分割 |
