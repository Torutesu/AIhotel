# 運営担当者への入力依頼と反映の仕様

対象機能: F-DP-08（意向の記録）／F-DP-09（差異の可視化）／F-DP-10（継続学習）

「運営担当者に何を入力してもらうのか」「その入力がいつ・どこに・どう反映されるのか」を
定義する。設計思想は `docs/継続学習設計.md`、画面は プライシングタブ内の
`frontend/components/operator-intent-panel.tsx`。

---

## 1. 入力を求める場面と原則

### 1.1 いつ入力するのか

**価格を決めた（または決め直した）タイミングで記録する。**
宿泊日の当日ではなく、判断した日に入れる。1日に複数回入れてよく、履歴として全部残る
（差異レポートでは同一日の最新の判断を「実際に適用した値」として扱う）。

### 1.2 AI推奨どおりにした日も記録する

これが運用上いちばん重要なルール。
「変えたときだけ記録する」運用にすると、記録が全部「AIに従わなかった日」になり、
追随率（`followRate`）も学習も歪む（選択バイアス）。
AI推奨をそのまま採用した日は、意向＝「AI推奨に従う」で記録する。

画面では常に `意向の記録日数 21 / 31日` のようにカバレッジを併記し、
どれだけの日が記録されているかが分かるようにしている。

### 1.3 誰が入力するのか

| ロール | 意向の記録 | 学習の再実行・承認 |
|--------|-----------|------------------|
| OPERATOR（現場フロント） | ○ | × |
| MANAGER（支配人・レベニューマネージャー） | ○ | ○ |
| ADMIN | ○ | ○ |

価格判断は現場が行うため、記録は OPERATOR にも開放している
（イベント登録 F-DP-07 と同じ扱い）。ただし記録は必ず監査ログに残る。
学習結果を需要予測へ反映するかの判断は MANAGER 以上に限定する。

## 2. 入力項目の定義

画面: 「意向を記録」ボタン → ダイアログ
API: `POST /api/v1/pricing/decisions`

| 項目 | 画面ラベル | 必須 | 制約 | 何のために聞くか |
|------|-----------|------|------|-----------------|
| `date` | 対象日 | 必須 | 日付 | どの宿泊日の判断か。実績との突合キーになる |
| `appliedRank` | 実際に適用した料金ランク | 必須※ | 整数 1〜40（F-SET-02） | AI推奨との差（`rankDelta`）の算出元。学習の中心 |
| `appliedPrice` | （画面では非表示） | 任意 | 整数 0以上 | 省略時は料金ランクマスタの `price1P` から自動解決する |
| `intentReason` | 意向（判断理由） | 必須 | 下記9分類から1つ | 差異の理由別集計と、セグメントの傾向説明に使う |
| `intentNote` | 補足メモ | 任意 | 1000文字以内 | 現場の言葉をそのまま残すため。**学習には使わない** |
| `roomTypeId` | （現状UI未使用） | 任意 | — | 省略時はホテル全体の判断として扱う |

※ `appliedRank` と `appliedPrice` の少なくとも一方は必須（zodスキーマで検証）。
画面はランク入力に統一しており、対象日を選ぶとAI推奨ランクが初期値として入る。

### 2.1 意向（判断理由）の9分類

分類は学習の集計単位になるため、自由記述ではなく固定の選択肢にしている。

| 値 | 画面表示 | 想定する場面 |
|----|---------|-------------|
| `FOLLOW_AI` | AI推奨に従う | 推奨をそのまま採用した |
| `COMPETITOR_MOVE` | 競合の動きに追随 | 近隣館の価格変更に合わせた |
| `EVENT_DEMAND` | イベント・地域需要 | 周辺イベント等で引き合いが強い／弱い |
| `GROUP_BLOCK` | 団体・グループ受入 | 団体ブロックの都合で残室を調整した |
| `OTA_CAMPAIGN` | OTAキャンペーン | キャンペーン参加に合わせた |
| `BUDGET_PRESSURE` | 予算達成 | 月次予算の未達／超過を意識した |
| `FIELD_INSIGHT` | 現場の肌感覚 | 常連の動き等、数字に出ていない情報 |
| `OPERATION_LIMIT` | オペレーション制約 | 清掃・人員などで受けられる室数に制限 |
| `OTHER` | その他 | 上記に当てはまらない |

分類を増やす場合は `schema.prisma` の `PriceIntentReason`、
`backend/src/lib/validators.ts` の `PRICE_INTENT_REASONS`、
画面の選択肢とラベルの3箇所を必ず揃える。

### 2.2 入力を求めない項目（自動で埋まる）

担当者に聞かない。聞いてはいけない項目もある。

| 項目 | 埋まり方 | 理由 |
|------|---------|------|
| 判断種別（そのまま採用／上げた／下げた） | AI推奨ランクと適用ランクの差からサーバが導出 | 差異の正しさが監査と学習の前提。自己申告を信用しない |
| 判断時点のAI推奨（ランク・価格・予測稼働率・予測ADR・需要レベル・確信度・モデルバージョン） | 記録時にスナップショットとして複製 | 推奨は再計算で上書きされるため。参照で持つと過去の差異が後から書き換わる |
| 記録者 | ログイン中のユーザー | 監査。将来の担当者別プロファイル拡張の布石 |
| 実績（稼働率・ADR・RevPAR） | `DailyData`（実績の取り込み） | 判断時点では存在しない |
| 結果判定（`outcome`） | 実績確定後にサーバが算出 | 後述 |

## 3. 入力がどこに、いつ反映されるか

入力は**その場で価格を変えない**。担当者にはこの点を明示する必要がある。
記録は「実際にやったことの申告」であって、価格の適用操作ではない。

```
 入力した瞬間          実績が確定したら        再学習を実行したら      MANAGERが承認したら     次回の予測再計算で
      │                      │                       │                      │                    │
      ▼                      ▼                       ▼                      ▼                    ▼
 差異レポートに反映     結果判定が付く          セグメント傾向が更新     補正が有効化           推奨ランクに反映
 ・ランク差／価格差     ・実績RevPAR vs         ・中央値・件数           isEnabled = true       ±Nランク
 ・理由別の集計          AI想定RevPAR           ・想定超え率                                   modelVersion に
 ・追随率              ・想定超え率の母数        ・補正値（0の場合あり）                        補正層名が付く
```

### 3.1 入力項目ごとの反映先

| 入力 | 反映先 |
|------|--------|
| 対象日 | 差異レポートの日別行。曜日区分（週末／平日、`Hotel.weekendDays` 準拠）の判定。実績との突合 |
| 適用ランク | `rankDelta` → 日別の差異表示 → セグメント別の中央値 → 予測へのランク補正 |
| 適用価格（自動解決含む） | `priceDelta` / `priceDeltaPct` → 日別表示と理由別の平均価格乖離率 |
| 意向（判断理由） | 理由別サマリ（日数・平均ランク乖離・平均価格乖離率・想定超え率）。セグメントの「主な理由」 |
| 補足メモ | 日別一覧に表示するのみ。集計にも学習にも使わない |
| 記録者 | 日別一覧に表示。監査ログ |

### 3.2 結果判定（`outcome`）の出し方と限界

実績が入った日だけ、次の比較で判定する。

```
AI想定RevPAR = 判断時点の予測稼働率 × 判断時点の予測ADR
実績RevPAR が AI想定RevPAR を ±2% 超えて上回る／下回る／その範囲内
```

想定RevPARの基準に**推奨価格（料金ランクの定価）を使わない**。実績RevPARは
販売ミックス込みのブレンドADR由来なので、定価と比べると常に定価側が高く出て
比較が成立しないため（実装初期にこれで全日「AIの勝ち」に倒れた）。

**この判定は「AI推奨どおりにしていたらどうだったか」ではない。**
動かさなかった世界線の実績は存在しないため、取れるのは「AIの想定を実績が超えたか」
という推定にすぎない。画面では必ず母数（`〇日`）を併記し、少数の観測で
判断しないようにしている。

### 3.3 学習に反映されるまでの条件

記録すれば自動的に予測が賢くなるわけではない。次の関門を全部通ったものだけが効く。

| 関門 | 条件 | 通らなかったときの画面表示 |
|------|------|--------------------------|
| 件数 | セグメントあたり5件以上 | 「補正なし」＋ツールチップで理由を説明 |
| 結果 | 想定超え率が0.5以上（母数3件以上のとき） | 同上 |
| 幅 | 補正は ±3ランクにクランプ | クランプ後の値を表示 |
| 承認 | MANAGER が反映スイッチを入れる | スイッチOFF（補正0のセグメントはスイッチ自体を無効化） |

セグメントは「需要レベル（A〜E）× 曜日区分（週末／平日）」。
代表値は平均ではなく**中央値**を使う（1件の極端な判断でセグメントが引きずられないため）。

## 4. 担当者に伝えるべきこと（画面文言の意図）

| 画面上の文言 | 伝えたいこと |
|-------------|-------------|
| 「AI推奨との差は自動で算出されます」 | 差分を自分で計算・申告する必要はない |
| 「反映するかは人が判断します（自動では反映されません）」 | 記録がそのままAIに直結して暴走することはない |
| 「補正なし」＋ツールチップ | 件数不足か、結果が伴っていないため学習に使っていない |
| 「実績待ち」 | まだ結果判定ができない日（将来日・実績未取り込み） |
| 「想定超え率 0.0%（2日）」 | 率だけでなく母数を必ず見る |
