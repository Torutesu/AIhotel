# レベニュー知識ベース 作成ガイド

**対象読者**: クライアントのレベニュー担当者・社内の元レベニュー担当者（エンジニアでない方）
**目的**: これから作る「レベニュー知識ベース」が、システムの価格計算とどういう関係にあるかを理解した上で、内容の確認と執筆に参加していただくためのガイドです。

---

## 1. まず結論

- 皆さんに作っていただくのは、**レベニューマネジメントの一般知識をまとめた文書**（用語の定義、判断の考え方、現場のノウハウ）です。
- この文書は、システムが**説明したり、質問に答えたりするときの「教科書」**として使われます。
- **価格の計算そのものには使われません。** 計算はプログラムの中に別途あり、この文書を書き換えても推奨価格は1円も変わりません。
- だからこそ、安心して「正しい一般知識」を書いてください。計算を壊す心配はありません。

## 2. システムの全体像 — 2つの層

このシステムには、役割の違う2つの層があります。

```
┌─────────────────────────────────────────────┐
│ 層1: 計算エンジン（プログラム）                    │
│  過去の実績・イベント・曜日から需要を予測し、        │
│  需要レベル(A〜E)と推奨料金ランク(1〜40)を出す      │
│  → 数値・計算式はプログラム内に固定。テストで保護     │
└─────────────────────────────────────────────┘
                    ▲ 別物（お互いに干渉しない）
┌─────────────────────────────────────────────┐
│ 層2: 知識ベース（今回作る文書）                    │
│  レベニューの用語・考え方・判断の原則をまとめた教科書  │
│  → システムが「なぜこの推奨なのか」を説明する時や、   │
│    ユーザーの質問に答える時の土台になる              │
└─────────────────────────────────────────────┘
```

たとえるなら、**層1は電卓、層2はその横に置く解説書**です。解説書をどれだけ書き換えても電卓の答えは変わりませんが、良い解説書があるほど「なぜその答えなのか」を分かりやすく説明できるようになります。

## 3. 層1（計算エンジン）は今どう動いているか

確認作業の前提として、現在の計算の仕組みを平易に説明します。
**※ここに書く数値は2026年8月時点の実装値のスナップショットです。正式な値は常にプログラム側が正であり、変更されることがあります。**

### 需要予測の流れ（毎日・日別に計算）

1. **ベースの読み**: 次の2つを組み合わせて、その日の稼働率を予測します。
   - 直近4週間の「同じ曜日」の平均稼働率 …… **70%の重み**
   - 昨年の同じ時期（±3日で最も近い日）の稼働率 …… **30%の重み**
   - どちらかしかデータがなければある方だけを使い、両方なければ仮の値（稼働60%）から出発します。
2. **イベント補正**: 登録されたイベント期間中は稼働率の読みを上乗せします。
   影響度 大 = **+15pt** / 中 = **+8pt** / 小 = **+3pt**
3. **週末補正**: 週末（初期設定は金・土。ホテルごとに変更可）は **+5pt**。
   ※同じ曜日の平均を使っている時点で週末らしさはある程度織り込み済みなので、控えめな値にしてあります。
4. **需要レベル判定**: 予測稼働率を5段階に変換します。
   A: 90%超 / B: 80%超 / C: 65%超 / D: 50%超 / E: それ以下
5. **料金ランク決定**: 予測稼働率を料金ランク（1〜最大40段階）に割り当て、ランク表から推奨価格を出します。
6. **確信度**: 使えたデータが多いほど高い確信度（最大85%）を付けます。データが乏しい日の推奨は確信度が低く表示されます。

### 皆さんに確認してほしいこと（層1について）

計算式を変えるのはエンジニアの仕事ですが、**「この読み方はレベニューの現場感覚として妥当か」の判断**は皆さんにしかできません。特に:

- [ ] 直近4週:前年 = 70:30 の重みは実務感覚に合うか
- [ ] イベント補正 +15/+8/+3pt は妥当か（過大・過小はないか）
- [ ] 需要レベルの境界（90/80/65/50%）は現場の肌感に合うか
- [ ] 「こういう時はこの読みは外れる」という既知の例外があれば教えてください（例: 連休の中日、直前の団体キャンセル など）

違和感があれば、それは知識ベースに「注意事項」として書く価値のある知見です。計算式自体の変更要望は別途エンジニアに引き継ぎます。

## 4. 層2（知識ベース）に書くこと・書かないこと

### 書いてほしいこと ✍️

時間が経っても変わらない、レベニューマネジメントの一般知識です。

| 種類 | 例 |
|---|---|
| 用語の定義 | ADR、RevPAR、OCC、ピックアップ、ブッキングカーブ、レートフェンス |
| 判断の原則 | 「稼働が高くADRが低い日は値上げ余地がある」「イベント日は早めに在庫を絞る」 |
| 現場の思考手順 | 朝いちで何を見るか、どの順で判断するか、いつ値付けを見直すか |
| よくある失敗と対策 | 早売りしすぎ、直前の投げ売り、競合追従しすぎ など |
| 説明の言い回し | 支配人やオーナーに説明する時の伝え方・トーン |

### 書かないでほしいこと 🚫

- **具体的な数値ルール**（「稼働90%超はAランク」等）
  → 数値の原本はプログラム側です。文書に転記すると、将来プログラム側を調整した時に文書だけが古くなり、システムが**古い情報をもとに間違った説明をする**事故につながります。数値に触れたい場合は「需要レベルの境界値はシステム設定に従う」のような書き方にしてください。
- **このシステム固有の仕様**（ランクは40段階、週末は金土 等)
  → 別の文書で管理済みです。重複させると同じ理由でずれます。
- **特定ホテルの機密情報**(実際の料金・稼働実績・契約条件)
  → この文書は複数の関係者が読む前提です。一般化して書いてください。

## 5. 進め方

1. 叩き台（`知識ベース叩き台.md`）を用意してあります。まずは通読して、赤入れ・コメントをください。
2. 空欄のセクション（✍️マーク）に、ご自身の経験からの加筆をお願いします。箇条書き・話し言葉で構いません。整形はこちらで行います。
3. 判断に迷ったら「書かないことリスト」に当たるかだけ確認してください。当たらなければ書いてOKです。
4. いただいた内容はシステムの説明機能・AIコメント機能の土台として組み込みます。組み込み後、実際のシステムの説明文を見ていただく確認の場を設けます。

## 6. よくある質問

**Q. 私が書いた内容で推奨価格が変わってしまうことはない？**
A. ありません。価格計算はプログラム内で完結しており、この文書は読みません。

**Q. じゃあ書いた内容はどこに効くの？**
A. システムが推奨の理由を説明する文章、ユーザーからの質問への回答、将来のAIコメント機能の品質に効きます。「答えの数字」ではなく「答えの説明のうまさ」が変わります。

**Q. 計算式がおかしいと思ったら？**
A. この文書に書き込むのではなく、レビューコメントとして指摘してください。エンジニア側でプログラムとテストを修正します（その方が確実に反映されます）。
