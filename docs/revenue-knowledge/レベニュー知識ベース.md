# ホテルレベニューマネジメント知識ベース（ルールベース版）

**版**: v3.0（2026-09）｜ ルール 311 項目 ＋ 用語 50 語
**用途**: AIレベニュー管理システムの需要予測・需要レベル判定・価格推奨・アラート・AIコメント生成が参照する判断基準。また、汎用的な「レベニュー担当者の知識・判断」の原本として、説明・Q&Aの根拠に使う。
**生成元**: `tools/rules_data.py`（単一ソース）。`tools/build.py` で本MDと `レビューシート.xlsx` を生成する。手で本MDを編集せず、データ側を直す。

> **実装値との関係**: 各ルールの「推奨パラメータ」は汎用的な初期値の提案。実際の閾値・重み・補正値はシステム設定（`PricingStrategyConfig`・料金ランク・ホテル設定）およびコード（`ruleBasedForecaster.ts` 等）が正であり、本書はそれらを**説明・検証・改善する根拠**として使う。両者が食い違う場合は実装を確認し、意図的な差ならデータ側の「システム対応」欄に注記する。

## A. 指標・計算定義

関連機能・データ: F-DASH-01 / DailyData

### A-01 OCC（稼働率）
- **種別**: 計算式
- **内容**: OCC = 販売客室数 ÷ 販売可能客室数。販売可能客室数は総客室数から OOO（故障・改装で販売不能）を除いた数。無料提供（コンプ）や社用利用は販売数に含めない。
- **推奨パラメータ（初期値）**: OOO除外・コンプ除外
- **システム対応**: DailyData.occupancy / soldRooms

### A-02 ADR（平均客室単価）
- **種別**: 計算式
- **内容**: ADR = 客室売上 ÷ 販売客室数。客室売上は税・サービス料・朝食等の付帯を除いた純客室料金で統一する。混在するとチャネル別・前年比較が崩れる。
- **推奨パラメータ（初期値）**: 税抜・付帯除外で統一
- **システム対応**: DailyData.adr

### A-03 RevPAR
- **種別**: 計算式
- **内容**: RevPAR = 客室売上 ÷ 販売可能客室数 = OCC × ADR。RMの最重要指標。稼働と単価のどちらが効いたかは必ず分解して読む。
- **システム対応**: DailyData.revPar（REV-Per）

### A-04 RevPARの分解
- **種別**: 計算式
- **内容**: RevPAR変化率 ≒ OCC変化率 ＋ ADR変化率（小さい変化では加法近似）。例: OCC +5%・ADR −3% → RevPAR ≒ +2%。前年比・予算比の説明は必ずこの2要因に分ける。
- **システム対応**: F-DASH-02 予算比・前年比

### A-05 TRevPAR / GOPPAR
- **種別**: 定義
- **内容**: TRevPAR = 総売上（料飲・宴会等含む）÷ 販売可能客室数。GOPPAR = 営業総利益 ÷ 販売可能客室数。客室単価を下げて料飲で回収する判断はTRevPARで、コストを含む最終評価はGOPPARで行う。
- **システム対応**: 将来拡張

### A-06 DOR（1室あたり利用人数）
- **種別**: 計算式
- **内容**: DOR = 宿泊人数 ÷ 販売室数。人数課金（1P/2P/3P）のホテルでは DOR が上がるほど同じ室数でも売上が増える。利用人数別分析の基礎指標。
- **システム対応**: F-DASH-01 DOR / F-ANA-01

### A-07 客単価（人単価）
- **種別**: 計算式
- **内容**: 客単価 = 客室売上 ÷ 宿泊人数 = ADR ÷ DOR。ADRが上がっても客単価が下がっていれば「多人数利用が増えただけ」の可能性。両方を見る。
- **システム対応**: F-DASH-01 客単価 / F-ANA-01

### A-08 ネットADR / ネットRevPAR
- **種別**: 計算式
- **内容**: ネットADR = (客室売上 − チャネル手数料) ÷ 販売客室数。手数料はポイント原資・決済手数料・広告費を含む実効率で計算。チャネル別評価は必ずネットで行う。
- **推奨パラメータ（初期値）**: 実効手数料率をチャネル別に設定
- **システム対応**: OtaChannelData.commission

### A-09 OTB（On The Books）
- **種別**: 定義
- **内容**: ある宿泊日について現時点で確定している予約室数・売上。キャンセル済みは除く。すべてのペース分析・フォーキャストの起点。
- **システム対応**: BookingCurveData

### A-10 ピックアップ
- **種別**: 計算式
- **内容**: ピックアップ(n日) = 今日のOTB − n日前のOTB（同一宿泊日）。新規予約 − キャンセルのネット値。日次・週次の2本を標準とする。
- **推奨パラメータ（初期値）**: n = 1日, 7日
- **システム対応**: F-DAILY-01

### A-11 ペース
- **種別**: 計算式
- **内容**: ペース = 今日のOTB − 前年同等日の同リードタイム時点OTB（STLY: Same Time Last Year）。絶対差と比率の両方で見る。着地実績との比較はペースではない。
- **推奨パラメータ（初期値）**: STLY基準 = 364日前
- **システム対応**: F-DAILY-01 / BookingCurveData

### A-12 リードタイム
- **種別**: 定義
- **内容**: 予約日から宿泊日までの日数。セグメント別に分布が大きく異なる（ビジネス0〜7日、国内レジャー14〜60日、インバウンド30〜120日）。カーブは必ずリードタイム軸で描く。
- **システム対応**: BookingCurveData.daysBefore

### A-13 残需要（Remaining Demand）
- **種別**: 計算式
- **内容**: 残需要 = 予測最終需要 − 現在OTB。残在庫との比較で「売り切れる見込みか」を判断する。残需要 > 残在庫なら値上げ余地、残需要 < 残在庫なら販促余地。
- **システム対応**: F-DP-05

### A-14 制約なし需要（Unconstrained Demand）
- **種別**: 定義
- **内容**: 満室・売止め・価格制約がなかった場合に実現していたはずの需要。満室日の実績＝需要ではない。断った問い合わせ、OTAでの表示回数・クリック等から推計する。
- **推奨パラメータ（初期値）**: 満室日の需要 = 実績 × 1.1〜1.3 を初期仮定
- **システム対応**: F-DP-05

### A-15 ALOS（平均泊数）
- **種別**: 計算式
- **内容**: ALOS = 延べ販売室数 ÷ 予約件数（滞在数）。連泊比率が上がると清掃コスト・チェックイン工数が下がる。泊数制限の効果測定に使う。
- **システム対応**: 将来拡張

### A-16 MPI / ARI / RGI
- **種別**: 計算式
- **内容**: MPI = 自館OCC ÷ コンプセットOCC × 100、ARI = 自館ADR ÷ コンプセットADR × 100、RGI = 自館RevPAR ÷ コンプセットRevPAR × 100。100超は市場より優位。RGIはRMの総合成績。
- **システム対応**: F-ANA-02

### A-17 インデックスの読み
- **種別**: 判定ルール
- **内容**: MPI高・ARI低 → 安売りで稼働を買っている疑い。MPI低・ARI高 → 強気すぎて売り逃し疑い。両方低 → 商品・露出の構造課題。RGIで総合し、どちらの軸を直すか決める。
- **システム対応**: F-ANA-02

### A-18 キャンセル率 / ノーショー率
- **種別**: 計算式
- **内容**: キャンセル率 = キャンセル室数 ÷ 予約室数、ノーショー率 = ノーショー室数 ÷ 到着予定室数。曜日・リードタイム・チャネル・セグメント別に持つ。オーバーブッキング上限とウォッシュ率の根拠。
- **推奨パラメータ（初期値）**: 曜日×チャネル別に集計
- **システム対応**: 将来拡張（GroupBooking）

### A-19 ウォッシュ（Wash）
- **種別**: 定義
- **内容**: 団体・法人ブロックのうち最終的に消化されない割合。過去の同種団体の実績から推計し、ブロック室数 × (1 − ウォッシュ率) を実需とみなす。
- **推奨パラメータ（初期値）**: 初期仮定 20〜30%
- **システム対応**: F-SET-05 / GroupBooking

### A-20 予算達成率の3軸
- **種別**: 計算式
- **内容**: 本日まで（当月1日〜昨日の実績 ÷ 同期間予算）、累計進捗（実績＋OTB ÷ 月予算）、年度累計（4月起点）。同じ軸で売上・ADR・OCCを揃えて表示し、軸違いの比較をしない。
- **推奨パラメータ（初期値）**: 年度 = 4月始まり
- **システム対応**: F-DASH-02

### A-21 前年比の基準日
- **種別**: 判定ルール
- **内容**: 前年比は「前年同日付」ではなく「前年同曜日（364日前）」を基準にする。月次合計は暦日ベースでよいが、日別・曜日別比較で日付基準を使うと平日/週末が入れ替わり誤読する。
- **推奨パラメータ（初期値）**: 日別=364日シフト、月次=暦日
- **システム対応**: F-DASH-02 / F-DASH-03

### A-22 週末定義
- **種別**: 定義
- **内容**: 週末 = チェックイン日が金・土。日曜泊は平日側として扱う（日曜は需要が急落するため）。この定義はホテル設定に従い、分析・予測・説明の全てで同一定義を使う。
- **推奨パラメータ（初期値）**: デフォルト [金, 土]
- **システム対応**: Hotel.weekendDays / F-DAILY-02


## B. データ品質・前処理

関連機能・データ: DailyData / BookingCurveData / OtaChannelData

### B-01 日付の基準
- **種別**: 定義
- **内容**: 全ての日別データはチェックイン日（宿泊日）基準。予約受付日と混同しない。タイムゾーンはホテル所在地で固定し、UTC変換で日付がずれないことを確認する。
- **推奨パラメータ（初期値）**: JST固定
- **システム対応**: DailyData.date / BookingCurveData

### B-02 OOO・売止めの記録
- **種別**: 注意
- **内容**: 改装・故障で販売不能だった客室数は日別に記録し、販売可能客室数から除く。除かないと稼働率が過小になり、その日の需要を弱く誤学習する。
- **システム対応**: DailyData（拡張）

### B-03 欠損値の扱い
- **種別**: 判定ルール
- **内容**: 実績欠損日は「0」ではなく null として扱い、移動平均・前年比較の分母から除外する。0で埋めると予測が系統的に下振れする。
- **推奨パラメータ（初期値）**: null除外
- **システム対応**: ruleBasedForecaster（occupancy not null）

### B-04 外れ値の検知
- **種別**: 判定ルール
- **内容**: 同曜日の過去8週平均から ±3σ を超える稼働・ADRは外れ値候補としてフラグを立て、原因（イベント・団体・データ誤り）を確認してから学習に使う。イベント起因なら除外せずイベントとして登録する。
- **推奨パラメータ（初期値）**: ±3σ、8週
- **システム対応**: DailyData / Event

### B-05 キャンセルの反映
- **種別**: 注意
- **内容**: OTBスナップショットはキャンセル反映後のネット値で保存する。グロス（予約のみ）で保存するとピックアップが過大になり、直前の在庫戻りを見逃す。
- **推奨パラメータ（初期値）**: ネット保存
- **システム対応**: BookingCurveData

### B-06 団体ブロックの分離
- **種別**: 判定ルール
- **内容**: 団体・法人ブロック（未確定枚数）は個人OTBと分けて保存し、カーブには「確定分のみ」と「ブロック込み」の2本を描けるようにする。ブロック込みで需要を読むとウォッシュ分だけ過大になる。
- **推奨パラメータ（初期値）**: 確定/ブロックを別列
- **システム対応**: GroupBooking / BookingCurveData

### B-07 スナップショット頻度
- **種別**: 判定ルール
- **内容**: OTBスナップショットは最低1日1回（同時刻）。繁忙日・イベント日の直前7日は複数回（朝・夕）取ると当日の動きが見える。
- **推奨パラメータ（初期値）**: 日次固定時刻、直前7日は朝夕
- **システム対応**: BookingCurveData

### B-08 価格データの条件揃え
- **種別**: 注意
- **内容**: 競合価格は「部屋タイプ階級・利用人数・食事条件・キャンセル可否」を揃えて記録する。最安値だけを拾うと条件が毎日変わり比較不能になる。
- **推奨パラメータ（初期値）**: スタンダード・2名・食事なし・キャンセル可を標準条件
- **システム対応**: CompetitorPriceData.price1P/2P/3P

### B-09 価格スクレイピングの時刻
- **種別**: 注意
- **内容**: 競合価格の取得は毎日同時刻に行い、取得時刻を保存する。競合も日中に価格を動かすため、時刻がばらつくと「動き」が読めない。
- **推奨パラメータ（初期値）**: 毎日同時刻 + 取得タイムスタンプ
- **システム対応**: CompetitorPriceData / F-SET-03

### B-10 在庫切れの区別
- **種別**: 判定ルール
- **内容**: 競合の価格が取得できない日は「売止め（満室）」と「取得失敗」を区別して記録する。売止めは強い需要シグナルであり、欠損と混ぜると失われる。
- **推奨パラメータ（初期値）**: status: soldout / error
- **システム対応**: CompetitorPriceData

### B-11 祝日・連休マスタ
- **種別**: 注意
- **内容**: 日本の祝日・振替休日・連休の並び（3連休か、飛び石か）をマスタとして持ち、毎年更新する。前年比較の暦補正とイベント補正の基礎。
- **推奨パラメータ（初期値）**: 内閣府祝日データ + 自館の独自休日
- **システム対応**: DailyData.isHoliday / holidayName

### B-12 学習期間の下限
- **種別**: 判定ルール
- **内容**: 同曜日移動平均は最低4週、前年比較は最低1年分の実績があるときのみ使う。不足時は代替（全曜日平均、市場平均、手入力ベースライン）にフォールバックし、確信度を下げる。
- **推奨パラメータ（初期値）**: 移動平均 ≥4週、前年 ≥1年
- **システム対応**: ruleBasedForecaster.computeConfidence

### B-13 断絶期間の除外
- **種別**: 判定ルール
- **内容**: 休館・大規模改装・パンデミック等の異常期間は学習対象から除外できるフラグを持つ。除外せずに前年比較すると回復期の需要を過小に読む。
- **推奨パラメータ（初期値）**: excludeFromLearning フラグ
- **システム対応**: DailyData（拡張）

### B-14 単位・通貨の統一
- **種別**: 注意
- **内容**: 金額は税抜・円・1室あたりで統一する。人数課金ホテルでは「1室料金」と「1人料金」を明示し、混在させない。
- **推奨パラメータ（初期値）**: 税抜円・1室
- **システム対応**: PriceRank.price1P〜4P


## C. 需要予測

関連機能・データ: F-DP-05 / AiPriceRecommendation / ruleBasedForecaster

### C-01 予測の構造
- **種別**: 定義
- **内容**: 予測稼働 = ベースライン（同曜日移動平均と前年同曜日の加重） ＋ イベント補正 ＋ 曜日・祝日補正 ＋ ペース補正、を0〜100%にクリップ。各項を分けて保存し説明可能にする。
- **システム対応**: F-DP-05 / computePredictedOccupancy

### C-02 同曜日移動平均
- **種別**: 計算式
- **内容**: 直近N週の同曜日稼働の平均（外れ値・イベント日除外後）。直近ほど重みを大きくする指数加重が望ましい。
- **推奨パラメータ（初期値）**: N = 4〜8週、直近週の重み ≈ 0.4
- **システム対応**: computeMovingAverageBySameWeekday（現状28日単純平均）

### C-03 前年同曜日（STLY）
- **種別**: 計算式
- **内容**: 364日前（52週前）の同曜日実績を基準とし、祝日・連休は暦の位置で個別に対応付ける。365日前の同日付は曜日が1つずれるため使わない。
- **推奨パラメータ（初期値）**: 364日シフト＋祝日マッピング
- **システム対応**: computeYearOverYearOccupancy（現状365日±3日最近接）

### C-04 ベースラインの加重
- **種別**: 計算式
- **内容**: 移動平均と前年の加重は、前年データの信頼度で変える。前年が平常期なら 移動平均0.6 : 前年0.4、前年が異常期（断絶・改装）なら移動平均のみ。直近トレンドが強い（前月比±10%超）ときは移動平均の重みを上げる。
- **推奨パラメータ（初期値）**: 0.6:0.4 を初期値、トレンド強時 0.8:0.2
- **システム対応**: computePredictedOccupancy（現状0.7:0.3）

### C-05 前年トレンド補正
- **種別**: 計算式
- **内容**: 前年同曜日実績に「直近3か月の前年比（同曜日ベース）」を掛けて今年水準に補正する。市場が前年比+10%で推移していれば前年値も+10%して使う。
- **推奨パラメータ（初期値）**: 直近90日の前年比を乗算
- **システム対応**: F-DP-05

### C-06 イベント補正の加算
- **種別**: 計算式
- **内容**: イベント影響は稼働ポイントの加算（pt）で表現し、影響度クラス別の初期値を持ち、過去の同イベント実績があればそれで上書きする。複数イベント重複は単純合算せず最大値 + 副次分の半分とする。
- **推奨パラメータ（初期値）**: 高 +15pt / 中 +8pt / 低 +3pt、重複 = max + 0.5×others
- **システム対応**: computeEventImpact（現状単純合算）

### C-07 イベントの前後泊波及
- **種別**: 計算式
- **内容**: 大規模イベントは前日に主影響の50%、翌日に30%の波及を初期値として加算する。ライブ・スポーツは前日型、学会・展示会は会期中フラット型、と種別ごとに形を持つ。
- **推奨パラメータ（初期値）**: 前日0.5、翌日0.3（種別で調整）
- **システム対応**: Event.type / expectedImpact

### C-08 週末補正
- **種別**: 計算式
- **内容**: 同曜日移動平均を使う場合、週末らしさは既に含まれるため週末補正は小さく（+3〜5pt）。全曜日平均を使う場合のみ大きな補正（+10〜15pt）を入れる。二重計上しない。
- **推奨パラメータ（初期値）**: 同曜日平均時 +5pt
- **システム対応**: computeWeekendAdjustment（+5pt）/ Hotel.weekendDays

### C-09 祝日・連休の補正
- **種別**: 計算式
- **内容**: 祝前日は週末扱い、連休中日は「金土相当」、連休最終日は「日曜相当」で補正する。3連休の中日は最も強く、飛び石連休は弱い。GWは中日（平日）の谷を個別に補正する。
- **推奨パラメータ（初期値）**: 祝前日 = 土曜相当
- **システム対応**: DailyData.isHoliday

### C-10 ペース補正
- **種別**: 計算式
- **内容**: 現在OTBが同リードタイム時点のSTLYより X% 速ければ、ベースラインに X% の一部（係数k）を加える。リードタイムが短いほど k を大きく（直前のOTBは着地に近い）。
- **推奨パラメータ（初期値）**: k = 0.3（60日前）→ 0.8（7日前）
- **システム対応**: F-DAILY-01 → F-DP-05

### C-11 残ピックアップ推定
- **種別**: 計算式
- **内容**: 着地予測 = 現在OTB ＋ 残ピックアップ。残ピックアップ = 過去同等日の「同リードタイムからの平均伸び率」× 現在OTB、または平均伸び室数。伸び率方式はOTBが少ない遠い日で暴れるため、遠い日は室数方式を優先。
- **推奨パラメータ（初期値）**: 60日超は室数方式、以内は比率方式
- **システム対応**: F-DP-04 / F-DP-05

### C-12 リードタイム別の予測手法
- **種別**: 判定ルール
- **内容**: 90日超: ベースライン主体（OTBは参考）。30〜90日: ベースライン＋ペース補正。7〜30日: OTB＋残ピックアップ主体。7日以内: OTB＋直前ピックアップ＋キャンセル見込み。
- **システム対応**: F-DP-05

### C-13 キャンセル見込みの控除
- **種別**: 計算式
- **内容**: 着地予測 = (OTB × (1 − 残キャンセル率)) ＋ 残ピックアップ。残キャンセル率はリードタイム・チャネル別実績から。キャンセル期限（宿泊前日等）を跨ぐ日は期限後の戻りを見込む。
- **推奨パラメータ（初期値）**: 直前7日のキャンセル率を実績から
- **システム対応**: 将来拡張

### C-14 需要の上限クリップ
- **種別**: 計算式
- **内容**: 予測稼働は 0〜100% にクリップするが、100%に張り付いた日は「制約なし需要」を別に保存する（例: 115%）。価格判断はクリップ前の値で行う。
- **推奨パラメータ（初期値）**: unconstrainedOccupancy を別保存
- **システム対応**: F-DP-05

### C-15 確信度の算出
- **種別**: 計算式
- **内容**: 確信度 = データ充足（移動平均・前年の有無）× 予測誤差実績（同リードタイムでの過去MAPE）× 異常要因の有無（新規イベント・断絶期）。0〜1で保存し、説明文と価格変更幅の抑制に使う。
- **推奨パラメータ（初期値）**: 両データ有 0.85 / 移動平均のみ 0.7 / 前年のみ 0.6 / なし 0.4
- **システム対応**: computeConfidence / AiPriceRecommendation.confidence

### C-16 確信度と価格幅の連動
- **種別**: 判定ルール
- **内容**: 確信度が低い日は推奨ランクの変更幅を抑える（±1ランク以内）。確信度が高い日は大きく動かしてよい。低確信度で大きく動かすのは予測の過信。
- **推奨パラメータ（初期値）**: conf<0.6 → 変更幅 ±1ランク
- **システム対応**: F-DP-01 / F-DP-05

### C-17 予測の更新頻度
- **種別**: 判定ルール
- **内容**: 予測は最低日次で再計算し、イベント登録・団体確定・大量キャンセル等のトリガー時は即時再計算する。90日超先は週次でよい。
- **推奨パラメータ（初期値）**: 日次 + イベントトリガー
- **システム対応**: バッチ（Phase 4）

### C-18 予測精度の評価
- **種別**: 計算式
- **内容**: MAPE（平均絶対誤差率）と Bias（平均符号付き誤差）をリードタイム別（30日前・14日前・7日前・前日）に月次で算出。Biasが恒常的に負なら弱気癖、正なら強気癖として補正係数を見直す。
- **推奨パラメータ（初期値）**: 目標 MAPE: 30日前 ≤12%、7日前 ≤6%
- **システム対応**: F-DP-05（精度ログ）

### C-19 予測の説明可能性
- **種別**: 説明ルール
- **内容**: 各日の予測には内訳（ベースライン・前年・イベント・週末・ペースの各寄与）を保存し、「なぜこの予測か」を1文で説明できる形にする。ブラックボックス化した予測は現場に採用されない。
- **推奨パラメータ（初期値）**: 寄与を項目別に保存
- **システム対応**: AiPriceRecommendation（拡張）/ F-DASH-06

### C-20 新規開業・データ不足時
- **種別**: 判定ルール
- **内容**: 自館実績が不足する期間は、コンプセットの市場稼働 × 自館の想定シェア、または類似ホテルのパターンをベースラインに使い、確信度を0.4以下にして毎週見直す。
- **推奨パラメータ（初期値）**: conf ≤ 0.4
- **システム対応**: F-DP-05

### C-21 需要の季節指数
- **種別**: 計算式
- **内容**: 月別・週別の季節指数 = 当期平均稼働 ÷ 年平均稼働。年間ベースラインに掛けて遠い将来（90日超）の予測に使う。過去2〜3年の平均で作り、年1回更新。
- **推奨パラメータ（初期値）**: 過去3年平均
- **システム対応**: F-DP-05 / F-ANA-03

### C-22 天候の扱い
- **種別**: 判定ルール
- **内容**: 天候は7日以内の直前予測にのみ反映する（それ以前は予報精度が低い）。レジャー型は悪天候予報で直前需要 −5〜10pt、ビジネス型は影響小。台風等の交通麻痺はキャンセル急増として別途扱う。
- **推奨パラメータ（初期値）**: 7日以内のみ
- **システム対応**: DailyData.externalFactors

### C-23 インバウンド比率の考慮
- **種別**: 判定ルール
- **内容**: インバウンド比率が高いホテルは、為替・航空便・訪日者数統計・大型連休（春節・国慶節等）を需要要因に加える。国内の祝日カレンダーだけでは説明できない山ができる。
- **推奨パラメータ（初期値）**: 海外連休カレンダーをイベントとして登録
- **システム対応**: Event.type = intl_holiday

### C-24 予測の下限保護
- **種別**: 判定ルール
- **内容**: 予測稼働が過去同曜日の最低値を下回る場合、外れ値やデータ不備を疑いフラグを立てる。極端な弱気予測がそのまま値下げ推奨につながるのを防ぐ。
- **推奨パラメータ（初期値）**: 過去8週の最低値を下限
- **システム対応**: N（アラート連携）

### C-25 2段階予測（室数と単価）
- **種別**: 計算式
- **内容**: 稼働（室数）予測とADR予測は分けて行う。ADR予測 = 推奨ランクの価格 × 想定ミックス（人数構成・部屋タイプ構成）。売上予測 = 室数 × ADR。
- **システム対応**: AiPriceRecommendation.predictedAdr

### C-26 ミックス予測
- **種別**: 計算式
- **内容**: 利用人数構成（1名/2名/3名以上）の比率を曜日・季節別に持ち、ADR・DOR予測に使う。週末は2名以上比率が上がり、平日は1名比率が上がるのが都市型の典型。
- **推奨パラメータ（初期値）**: 曜日×月の構成比テーブル
- **システム対応**: F-ANA-01 / DailyRoomData

### C-27 モデル差し替えの原則
- **種別**: 注意
- **内容**: ルールベース→ML移行時も、出力インターフェース（予測稼働・需要レベル・推奨ランク・確信度・寄与内訳）は変えない。モデルバージョンを保存し、精度比較ができる状態を維持する。
- **推奨パラメータ（初期値）**: modelVersion を必須保存
- **システム対応**: AiPriceRecommendation.modelVersion / DemandForecaster IF

### C-28 バックテスト
- **種別**: 判定ルール
- **内容**: 予測ロジックの変更は、過去12か月に対するバックテスト（MAPE・Biasの改善）を確認してから本番適用する。1か月分の目視確認だけで採用しない。
- **推奨パラメータ（初期値）**: 12か月バックテスト
- **システム対応**: F-DP-05

### C-29 予測値の丸め
- **種別**: 注意
- **内容**: 表示上の稼働は整数%、内部計算は小数で保持する。丸めた値で需要レベル判定をすると境界付近で不安定になる。
- **推奨パラメータ（初期値）**: 内部は小数3桁
- **システム対応**: computePredictedOccupancy（3桁丸め）

### C-30 予測と実績の並列表示
- **種別**: 説明ルール
- **内容**: カレンダー・グラフでは予測と実績を同じ軸で連続表示し、実績確定後は「予測との差」を残す。差の履歴が精度改善とレビュアーの信頼を生む。
- **システム対応**: F-DASH-03 / F-DP-01

### C-31 複数日程の相互作用
- **種別**: 判定ルール
- **内容**: 連泊需要が多い日は前後日の予測を連動させる（片方が満室なら連泊需要が隣日にも来ない）。イベント前後泊もこの一種。独立予測だけでは連休の谷を過大に読む。
- **システム対応**: F-DP-05

### C-32 予測凍結（Freeze）
- **種別**: 注意
- **内容**: 当日・翌日の予測は当日朝以降更新を止め、実績との比較用に凍結値を残す。動き続ける予測は精度評価ができない。
- **推奨パラメータ（初期値）**: 前日18時で凍結
- **システム対応**: AiPriceRecommendation.computedAt


## D. 需要レベル判定

関連機能・データ: DemandLevel A〜E

### D-01 需要レベルの定義
- **種別**: 定義
- **内容**: A〜Eの5段階。A = 売り切れが確実で強気最大、B = 強い、C = 標準、D = 弱い、E = 非常に弱い。価格推奨・アラート・説明文のトーンはこのレベルに連動する。
- **推奨パラメータ（初期値）**: 5段階固定
- **システム対応**: DemandLevel enum

### D-02 レベル判定の入力
- **種別**: 判定ルール
- **内容**: レベルは予測稼働だけで決めず、①予測稼働 ②ペース（STLY比） ③残需要 vs 残在庫 の3要素で決める。予測が70%でもペースが+30%なら1段上げる。
- **推奨パラメータ（初期値）**: 3要素合成
- **システム対応**: F-DP-05

### D-03 稼働閾値（初期値）
- **種別**: 判定ルール
- **内容**: 予測稼働ベースの初期閾値: A > 90%、B > 80%、C > 65%、D > 50%、E ≤ 50%。ホテルの平均稼働に応じて調整する（平均85%のホテルはA閾値を95%に）。
- **推奨パラメータ（初期値）**: 90/80/65/50（平均稼働で調整）
- **システム対応**: mapOccupancyToDemandLevel

### D-04 ペースによる補正
- **種別**: 判定ルール
- **内容**: 同リードタイムSTLY比で +20%以上速い → 1段上げ、−20%以上遅い → 1段下げ。ただし前年が異常期の場合はペース補正を無効化する。
- **推奨パラメータ（初期値）**: ±20%で±1段
- **システム対応**: F-DP-05

### D-05 残需要による補正
- **種別**: 判定ルール
- **内容**: 残需要 ÷ 残在庫 ≥ 1.2 なら1段上げ（売り切れ確実）、≤ 0.5 なら1段下げ。リードタイム7日以内で特に重視する。
- **推奨パラメータ（初期値）**: ≥1.2 / ≤0.5
- **システム対応**: F-DP-05

### D-06 ヒステリシス（ばたつき防止）
- **種別**: 判定ルール
- **内容**: レベルの上下は閾値を跨いだだけで変えず、境界から±3pt以上離れたときに変更する。日々AとBを往復すると価格も往復し、現場の信頼を失う。
- **推奨パラメータ（初期値）**: 境界 ±3pt
- **システム対応**: F-DP-05

### D-07 レベルの手動上書き
- **種別**: 判定ルール
- **内容**: MANAGER はレベルを手動で上書きでき、理由とともに監査ログに残す。上書きは有効期限（例: 7日）を持ち、期限後は自動判定に戻る。上書きと自動値の差は精度評価に使う。
- **推奨パラメータ（初期値）**: 上書き有効期限 7日
- **システム対応**: F-DP-03 / AuditLog

### D-08 レベルと推奨ランクの関係
- **種別**: 判定ルール
- **内容**: 需要レベルは「方向と強さ」、推奨ランクは「具体の価格」。同じレベルでもリードタイム・残在庫でランクは変わる。レベル→ランクの固定対応表にしない。
- **システム対応**: F-DP-01

### D-09 イベント日のレベル
- **種別**: 判定ルール
- **内容**: 影響度「高」のイベント日は、予測稼働が閾値未満でも最低Bとする（イベントは直前に急伸するため早期の弱気を防ぐ）。
- **推奨パラメータ（初期値）**: 高影響 → 最低B
- **システム対応**: Event.expectedImpact

### D-10 レベルの説明文
- **種別**: 説明ルール
- **内容**: 各レベルには根拠を1文添える。例「B: 予測稼働84%、前年同曜日より予約が18%速く、近隣で展示会（中）」。レベルだけの表示は現場が納得しない。
- **システム対応**: F-DASH-06 / F-DP-05

### D-11 レベル分布の健全性
- **種別**: 判定ルール
- **内容**: 月内のレベル分布が極端（全日Aや全日E）になったら閾値のキャリブレーション不良を疑う。目安は年間でA 10〜15%、B 20%、C 30〜40%、D 20%、E 10%程度。
- **推奨パラメータ（初期値）**: 年間分布の目安
- **システム対応**: F-DP-05

### D-12 レベルの遷移ログ
- **種別**: 注意
- **内容**: レベルが変わった日時・理由（どの入力が動いたか）をログに残す。「なぜ昨日Bだったのが今日Cなのか」に即答できる状態を保つ。
- **システム対応**: AiPriceRecommendation（履歴）


## E. 価格決定

関連機能・データ: F-DP-01 / F-DP-02 / F-DP-03 / PricingStrategyConfig

### E-01 価格決定の目的関数
- **種別**: 定義
- **内容**: 目的は当日のRevPAR最大化ではなく、残在庫を使った「残期間の売上最大化」。今日1室を安く売ることで失う直前の高単価需要（機会費用）を常に勘定に入れる。
- **システム対応**: F-DP-01

### E-02 重み付けの意味
- **種別**: 定義
- **内容**: 稼働率重視 = 埋めることを優先し弱い日は下げやすい。ADR重視 = 単価維持を優先し下げ渋り上げ早め。競合追従度 = 競合価格の参照度。3つの合計は100%。重みは「方針」を数値化したものでアルゴリズムの直接の係数ではない。
- **推奨パラメータ（初期値）**: 初期値 40/40/20
- **システム対応**: F-DP-02 / PricingStrategyConfig

### E-03 重みの反映方法
- **種別**: 計算式
- **内容**: 推奨価格 = 需要ベース価格 × (w_occ + w_adr) ＋ 競合参照価格 × w_comp。需要ベース価格内では、w_occ > w_adr なら弱い日の下げ幅を大きく・強い日の上げ幅を小さく、w_adr > w_occ なら逆にする。
- **システム対応**: F-DP-02

### E-04 需要ベース価格
- **種別**: 計算式
- **内容**: 需要ベース価格 = その日の需要レベル・予測稼働・残在庫・リードタイムから決まる基準ランクの価格。基準ランクの算出は E-05〜E-08 に従う。
- **システム対応**: F-DP-01 / PriceRank

### E-05 基準ランクの初期マッピング
- **種別**: 計算式
- **内容**: 基準ランク = 予測稼働（制約なし）× 最大ランク数、を最低1・最大40にクリップ。ただしホテルの平均稼働で正規化する（平均稼働のときに中央ランク付近になるよう調整）。
- **推奨パラメータ（初期値）**: rank = clip(round(occ_norm × 40), 1, 40)
- **システム対応**: mapOccupancyToRank

### E-06 残在庫による調整
- **種別**: 判定ルール
- **内容**: 残在庫率（残室 ÷ 総室）が低いほどランクを上げる。目安: 残在庫 ≤10% → +3ランク、≤20% → +2、≤30% → +1。逆に残在庫 ≥60% で残り14日以内 → −2。
- **推奨パラメータ（初期値）**: 10/20/30% で +3/+2/+1
- **システム対応**: F-DP-01

### E-07 リードタイムによる調整
- **種別**: 判定ルール
- **内容**: 同じ予測稼働でも、リードタイムが長いほど「まだ伸びる」ため強気に、短いほどOTB重視で現実的に。60日超は基準ランク+1、7日以内は残在庫ルール優先。
- **推奨パラメータ（初期値）**: 60日超 +1
- **システム対応**: F-DP-01

### E-08 最終ランクの合成
- **種別**: 計算式
- **内容**: 最終ランク = 基準ランク ＋ 残在庫調整 ＋ リードタイム調整 ＋ ペース調整 ＋ 競合調整 ＋ イベント調整、を上限・下限ランクでクリップし、変更幅制限（E-13）を適用する。各調整値を保存して説明に使う。
- **推奨パラメータ（初期値）**: 調整値を項目別に保存
- **システム対応**: AiPriceRecommendation.recommendedRank

### E-09 上限・下限ランク
- **種別**: 判定ルール
- **内容**: ホテルごとに下限ランク（ブランド毀損防止）と上限ランク（機会損失・クレーム防止）を設定し、推奨は必ずこの範囲内。曜日・季節で上下限を変えられるようにする。
- **推奨パラメータ（初期値）**: 下限 R05、上限 R38 を初期値
- **システム対応**: F-SET-02 / PriceRank.isActive

### E-10 競合参照価格
- **種別**: 計算式
- **内容**: 競合参照価格 = コンプセット価格の中央値（平均ではなく中央値。1社の極端値に引かれない）× 自館のポジション係数。ポジション係数は過去のARI実績から（自館が市場より10%高く売れていれば1.10）。
- **推奨パラメータ（初期値）**: 中央値 × ポジション係数
- **システム対応**: F-DP-06（「平均」表現を使わない）

### E-11 競合追従の非対称
- **種別**: 判定ルール
- **内容**: 競合が値上げ → 追従は早く（需要が強いシグナル）。競合が値下げ → 自館の需要レベルがC以上なら追従しない。追従度20%は「参照度」であり、値下げ合戦への自動参加ではない。
- **推奨パラメータ（初期値）**: 値下げ追従は需要D以下のみ
- **システム対応**: F-DP-02 / F-DP-06

### E-12 競合売止めのシグナル
- **種別**: 判定ルール
- **内容**: コンプセットの半数以上が売止め（満室）なら、自館の推奨ランクを+2し、需要レベルを1段上げる。市場在庫が消えた日は自館に流入する。
- **推奨パラメータ（初期値）**: 半数以上売止め → +2
- **システム対応**: CompetitorPriceData（soldout）

### E-13 1日あたりの変更幅制限
- **種別**: 判定ルール
- **内容**: 推奨ランクの1日の変更は ±3ランク以内（確信度が低い日は ±1）。大きな変更が必要なら数日に分けて段階的に動かし、都度売れ行きを確認する。
- **推奨パラメータ（初期値）**: ±3（低確信度 ±1）
- **システム対応**: F-DP-01

### E-14 上げと下げの非対称
- **種別**: 判定ルール
- **内容**: 値上げは小刻みに何度でも（+1〜2ランク/日）。値下げは慎重に（−1ランク/日を上限、理由必須）。下げは戻しにくく、ゲストの学習効果があるため。
- **推奨パラメータ（初期値）**: 上げ +2/日、下げ −1/日
- **システム対応**: F-DP-01

### E-15 最小変更単位
- **種別**: 判定ルール
- **内容**: 価格差が1ランク分（数百円）しかない変更は推奨として出さない（変更コスト＞効果）。表示上は「維持」とし、2ランク以上動くときに推奨変更とする。
- **推奨パラメータ（初期値）**: 変更推奨は ≥2ランク差
- **システム対応**: F-DP-01

### E-16 繁忙日の段階値上げ
- **種別**: アクション
- **内容**: 需要レベルA/Bの日は、OTBが目標カーブの節目（例: 50%・70%・85%）を超えるごとに+1〜2ランク上げる。一度に上限まで上げず、売れ行きで確認しながら上げる。
- **推奨パラメータ（初期値）**: 節目 50/70/85%
- **システム対応**: F-DP-01 / F-DAILY-01

### E-17 最終在庫の価値（Last Room Value）
- **種別**: 判定ルール
- **内容**: 残り数室（残在庫 ≤5%）は最も価値が高い在庫。上限ランク付近を維持し、直前でも下げない。「空室で終わるより安く売る」は、残室が10%以上あるときの判断。
- **推奨パラメータ（初期値）**: 残 ≤5% は上限維持
- **システム対応**: F-DP-01

### E-18 閑散日の下げ順序
- **種別**: アクション
- **内容**: 需要レベルD/Eの日は、価格を下げる前に①露出（OTA掲載順位・写真・プラン名）②条件（早割・連泊・朝食付き）③チャネル追加 を提案し、それでもピックアップが改善しなければ値下げ。推奨文にこの順序を示す。
- **推奨パラメータ（初期値）**: 露出→条件→価格
- **システム対応**: F-DP-01 / F-DASH-06

### E-19 直前値下げの制限
- **種別**: 判定ルール
- **内容**: 宿泊3日前以内の値下げは、残在庫が20%以上ある場合のみ、かつ−2ランク以内。常態化を防ぐため、月内の直前値下げ回数をアラートで可視化する。
- **推奨パラメータ（初期値）**: 3日前以内: 残≥20%・−2以内
- **システム対応**: N（アラート）

### E-20 価格弾力性の推定
- **種別**: 計算式
- **内容**: 弾力性 = ピックアップ変化率 ÷ 価格変化率（同リードタイム・同需要レベルの過去事例から）。|弾力性| > 1 なら値下げで売上増、< 1 なら値上げで売上増。曜日・季節・セグメント別に持つ。
- **推奨パラメータ（初期値）**: 初期仮定 −0.8（都市型平日）、−1.3（レジャー週末）
- **システム対応**: F-DP-05（学習）

### E-21 弾力性を使った推奨
- **種別**: 判定ルール
- **内容**: |弾力性| < 1 の日（需要が価格に鈍感）では、レベルC以下でも値下げ推奨を出さず維持または微増。弾力性の高い日で在庫過多のときだけ値下げが売上に効く。
- **システム対応**: F-DP-01

### E-22 曜日別ベース価格
- **種別**: 判定ルール
- **内容**: 曜日ごとの基準ランクを持つ（例: 金土 = 中央+4、日 = 中央−3、月〜木 = 中央）。需要予測はこのベースからの差分として働く。曜日ベースがないと毎日ゼロから計算して不安定になる。
- **推奨パラメータ（初期値）**: 曜日ベースランク表
- **システム対応**: F-SET-02 / Hotel.weekendDays

### E-23 価格の心理的節目
- **種別**: 注意
- **内容**: ランク表の価格は節目（10,000円、15,000円、20,000円）を跨ぐときに予約率が段差的に落ちる。節目直下（9,800／14,800）にランクを置き、節目直上のランクは避けるか幅を広げる。高級帯はキリの良い価格が好まれる。
- **推奨パラメータ（初期値）**: 節目直下にランク配置
- **システム対応**: F-SET-02 / PriceRank

### E-24 人数別価格の整合
- **種別**: 判定ルール
- **内容**: 同一ランク内で 1P < 2P < 3P < 4P、かつ1人あたり単価は人数が増えるほど下がる（2P ÷ 2 < 1P）。逆転があると2名客が1名×2で予約する等の抜け道が生まれる。
- **推奨パラメータ（初期値）**: 2P/2 ≤ 0.85 × 1P
- **システム対応**: PriceRank.price1P〜4P

### E-25 部屋タイプ間の価格差
- **種別**: 判定ルール
- **内容**: 上位タイプとの価格差は需要に応じて可変にする。繁忙日は差を縮めて上位タイプへ誘導（アップセル）、閑散日は差を広げて下位タイプの値ごろ感を出す。
- **推奨パラメータ（初期値）**: 繁忙日: 差 −20%
- **システム対応**: RoomType / DailyRoomData

### E-26 プラン別の価格差
- **種別**: 判定ルール
- **内容**: 返金不可は返金可の −8〜12%、早割（30日前）は −10〜15%、朝食付きは原価 + 適正利益。差が大きすぎると全員が安い方に流れ、小さすぎると条件の意味がない。
- **推奨パラメータ（初期値）**: 返金不可 −10%、早割 −12%
- **システム対応**: Campaign

### E-27 AI推奨と手動の関係
- **種別**: 判定ルール
- **内容**: 手動で価格を変更した日は、AI推奨を上書きした事実・理由・差分を記録し、着地後に「AI推奨に従った場合との差」を検証する。リセット（F-DP-03）でAI値に戻せる。
- **推奨パラメータ（初期値）**: 上書き記録必須
- **システム対応**: F-DP-03 / AuditLog

### E-28 推奨の有効期限
- **種別**: 注意
- **内容**: 推奨価格は算出時刻を持ち、24時間以上更新されていない推奨は「要再計算」として表示する。古い推奨に従うのは無推奨より悪い。
- **推奨パラメータ（初期値）**: 24時間
- **システム対応**: AiPriceRecommendation.computedAt

### E-29 推奨の根拠表示
- **種別**: 説明ルール
- **内容**: 推奨ランクには必ず内訳を添える: 基準ランク（予測稼働）、残在庫調整、ペース調整、競合調整、イベント調整、変更幅制限の有無。数値付きで1〜2行に収める。
- **システム対応**: F-DP-01 / F-DASH-06

### E-30 価格変更のログと検証
- **種別**: 注意
- **内容**: 全ての価格変更（AI・手動）を宿泊日・変更日時・前後価格・理由・その時点のOTBとともに記録する。月次で「変更後7日のピックアップ変化」を集計し、ルールの効果を検証する。
- **システム対応**: AuditLog / AiPriceRecommendation

### E-31 変更頻度の上限
- **種別**: 判定ルール
- **内容**: 同一宿泊日の価格変更は1日1回を基本とし、直前7日のみ2回まで。頻繁な変更はチャネル反映遅延・レートパリティ崩れ・ゲスト不信を招く。
- **推奨パラメータ（初期値）**: 1回/日、直前7日は2回
- **システム対応**: F-DP-01

### E-32 凍結日（Blackout）
- **種別**: 判定ルール
- **内容**: 契約上価格を動かせない日（法人固定料金・団体確定・パッケージ販売）は凍結フラグを持ち、推奨は出すが「変更不可」を明示する。
- **推奨パラメータ（初期値）**: frozen フラグ
- **システム対応**: F-DP-01（拡張）

### E-33 長期滞在・連泊の価格
- **種別**: 判定ルール
- **内容**: 連泊は1泊ごとの日別価格の合算を基本とし、閑散日を含む連泊に限り割引率を設定する。繁忙日だけを含む連泊に割引は不要。
- **推奨パラメータ（初期値）**: 閑散日含む連泊のみ割引
- **システム対応**: Campaign

### E-34 価格の下限根拠
- **種別**: 計算式
- **内容**: 下限価格 ≥ 変動費（清掃・アメニティ・リネン・OTA手数料）÷ (1 − 目標変動費率)。変動費を割る価格は稼働を上げても利益を減らす。
- **推奨パラメータ（初期値）**: 変動費の1.5倍を下限目安
- **システム対応**: F-SET-02

### E-35 価格の上限根拠
- **種別**: 計算式
- **内容**: 上限価格 = 過去に実際に売れた最高ADR × 1.2、またはコンプセット最高値 × 1.1 のいずれか低い方を初期上限とし、実績に応じて更新。売れたことのない価格帯は徐々に試す。
- **推奨パラメータ（初期値）**: 実績最高 × 1.2
- **システム対応**: F-SET-02

### E-36 実験（A/B）の考え方
- **種別**: 注意
- **内容**: 新しい価格ルールは、同条件の日を2群に分けて比較するか、導入前後の同曜日比較で効果を測る。全日に一斉適用して「良くなった気がする」で終わらせない。
- **システム対応**: F-DP-05

### E-37 推奨の粒度
- **種別**: 定義
- **内容**: 推奨は「ホテル全体（代表部屋タイプ）」を基本に、部屋タイプ別推奨を追加する。部屋タイプ別データが無い間は全体推奨＋タイプ別差額ルールで運用する。
- **推奨パラメータ（初期値）**: roomTypeId = null が全体
- **システム対応**: AiPriceRecommendation.roomTypeId

### E-38 需要レベルと価格の整合チェック
- **種別**: 判定ルール
- **内容**: 需要レベルAで前日比値下げ、Eで値上げのような矛盾推奨は出力前に検出し、理由（凍結・上限・手動）を添えるか抑止する。
- **推奨パラメータ（初期値）**: 矛盾検出ルール
- **システム対応**: F-DP-01

### E-39 推奨の受容率
- **種別**: 計算式
- **内容**: 受容率 = AI推奨どおりに設定された日数 ÷ 推奨日数。受容率が低い期間は推奨の妥当性か説明の不足を疑い、上書き理由を分析する。
- **推奨パラメータ（初期値）**: 目標 ≥70%
- **システム対応**: F-DP-03 / AuditLog


## F. 料金ランク運用

関連機能・データ: F-SET-02 / PriceRank（40段階・1P/2P/3P/4P）

### F-01 ランク表の構造
- **種別**: 定義
- **内容**: 40段階のランク（R01〜R40）ごとに 1P/2P/3P/4P の価格を持つマスタ。価格を直接動かすのではなくランクを動かすことで、判断の速さと一貫性、記録性を得る。
- **推奨パラメータ（初期値）**: 40段階
- **システム対応**: F-SET-02 / PriceRank

### F-02 刻み幅の設計
- **種別**: 判定ルール
- **内容**: 隣接ランクの価格差は基準価格の3〜5%を目安に。等差ではなく等比（下位は数百円、上位は千円超）にすると、上位帯でも1段の変更が意味を持つ。
- **推奨パラメータ（初期値）**: 等比 3〜5%/段
- **システム対応**: PriceRank

### F-03 有効ランクの範囲
- **種別**: 判定ルール
- **内容**: 実際に使うのは上下限内の20〜30段。全40段を常用しない。使わない段は isActive=false にし、推奨アルゴリズムの探索範囲から外す。
- **推奨パラメータ（初期値）**: 常用 20〜30段
- **システム対応**: PriceRank.isActive

### F-04 中央ランクの意味
- **種別**: 定義
- **内容**: 平均稼働・平常需要時の価格を中央付近（R18〜R22）に置く。中央からの距離が「平常比でどれだけ強気/弱気か」を直感的に示す。
- **推奨パラメータ（初期値）**: 中央 = R20
- **システム対応**: F-SET-02

### F-05 ランク表の改定
- **種別**: 判定ルール
- **内容**: ランク表の価格改定は年1〜2回（市場水準・コスト変動時）。期中に頻繁に改定すると過去ランクとの比較ができなくなる。改定履歴はバージョン管理する。
- **推奨パラメータ（初期値）**: 年1〜2回
- **システム対応**: AuditLog / PriceRank.updatedAt

### F-06 ランク表と季節
- **種別**: 判定ルール
- **内容**: 季節で価格水準が大きく変わるホテルは、ランク表を季節別に持つより「季節ベースランク」をずらす方が運用しやすい（同じR20でも夏はR24相当として扱う）。
- **推奨パラメータ（初期値）**: 季節オフセット
- **システム対応**: F-SET-02

### F-07 ラベルの表示
- **種別**: 注意
- **内容**: 現場向けには「R24（¥14,800）」のようにランクと代表価格（2P）を併記する。ランクだけでは価格感が伝わらず、価格だけではランク運用の意味が消える。
- **推奨パラメータ（初期値）**: R + 2P価格
- **システム対応**: F-DP-01 UI

### F-08 人数別価格の生成ルール
- **種別**: 計算式
- **内容**: 2P = 1P × 1.6〜1.8、3P = 2P × 1.3〜1.4、4P = 3P × 1.2〜1.25 を初期生成ルールとし、部屋定員・ベッド構成で個別調整。人数が増えるほど1人単価が下がる形を保つ。
- **推奨パラメータ（初期値）**: 1.7 / 1.35 / 1.2
- **システム対応**: PriceRank.price2P/3P/4P

### F-09 ランク運用の検証
- **種別**: 計算式
- **内容**: ランク別の実績（そのランクで売った日の平均ピックアップ・着地ADR）を月次で集計し、「上げても売れた」「下げても売れなかった」ランク帯を特定して弾力性推定に使う。
- **推奨パラメータ（初期値）**: 月次集計
- **システム対応**: F-DP-05

### F-10 ランク表の欠落
- **種別**: 注意
- **内容**: 推奨ランクに対応する価格が未設定（null）の場合、推奨価格は出さず「ランク表を確認」と表示する。近傍ランクの価格で代用しない。
- **推奨パラメータ（初期値）**: null は補完しない
- **システム対応**: pricingService（rankByNumber）

### F-11 複数部屋タイプのランク
- **種別**: 判定ルール
- **内容**: 部屋タイプ別にランク表を持つか、代表タイプのランクに「タイプ差額」を足すかを選ぶ。タイプ数が5以下なら差額方式が運用しやすい。
- **推奨パラメータ（初期値）**: 5タイプ以下は差額方式
- **システム対応**: RoomType

### F-12 ランクの初期設定手順
- **種別**: アクション
- **内容**: ①過去12か月のADR分布（5〜95パーセンタイル）を確認 ②その範囲をR05〜R35に等比で割付 ③上下に余白5段ずつ ④曜日別ベースランクを設定 ⑤上下限を設定。この順で行う。
- **システム対応**: F-SET-02


## G. 在庫・販売制限

関連機能・データ: （推奨提示のみ。書き戻しはスコープ外）

### G-01 Min LOS（最低泊数）
- **種別**: アクション
- **内容**: イベント日・連休中日など「その日だけ埋まって前後が空く」日に、2泊以上を条件にする。前後日の予測稼働が当日より30pt以上低いときが適用の目安。
- **推奨パラメータ（初期値）**: 前後差 ≥30pt で Min LOS 2
- **システム対応**: 推奨提示

### G-02 CTA（到着日クローズ）
- **種別**: アクション
- **内容**: 超繁忙日（レベルA・残在庫≤10%）は到着日としての受付を止め、前日からの連泊のみ受ける。前日の稼働を引き上げつつ当日は確実に埋まる。
- **推奨パラメータ（初期値）**: A かつ残 ≤10%
- **システム対応**: 推奨提示

### G-03 CTD（出発日クローズ）
- **種別**: アクション
- **内容**: 翌日が超繁忙日のとき、翌日出発の予約を止めて連泊を促す。清掃集中の緩和にも効く。
- **システム対応**: 推奨提示

### G-04 チャネル売止め
- **種別**: アクション
- **内容**: 残在庫 ≤15% になったら、実効手数料の高いチャネルから順に売止めし、直販・低手数料チャネルに在庫を集約する。
- **推奨パラメータ（初期値）**: 残 ≤15% で高手数料チャネル停止
- **システム対応**: OtaChannelData

### G-05 安値プランの停止
- **種別**: アクション
- **内容**: 需要レベルB以上の日は早割・クーポン対象・キャンペーンプランを停止する。同じ部屋を安い条件で売る理由がない。
- **推奨パラメータ（初期値）**: B以上でプラン停止
- **システム対応**: Campaign

### G-06 部屋タイプの出し分け
- **種別**: アクション
- **内容**: 安いタイプが先に売れるため、繁忙日は下位タイプの在庫を絞って上位タイプへ誘導する。下位タイプの残在庫 ≤20% で上位との価格差を縮める。
- **推奨パラメータ（初期値）**: 下位残 ≤20%
- **システム対応**: RoomType

### G-07 オーバーブッキング上限
- **種別**: 計算式
- **内容**: OB上限 = 期待ノーショー室数 − 安全余裕。期待ノーショー = 到着予定 × ノーショー率（曜日・チャネル別）。安全余裕は振替コストとの兼ね合いで決める。初期は控えめに。
- **推奨パラメータ（初期値）**: ノーショー率実績の70%まで
- **システム対応**: GroupBooking / 将来拡張

### G-08 オーバーブッキング実施条件
- **種別**: 判定ルール
- **内容**: 近隣の振替先・差額負担・謝罪対応の手順が整備されているときのみ実施する。体制なしのOBはブランド毀損リスクが利益を上回る。
- **推奨パラメータ（初期値）**: 手順書必須

### G-09 団体ブロックの期限
- **種別**: 判定ルール
- **内容**: 団体ブロックには確定期限（カットオフ）を設け、期限を過ぎた未確定分は個人販売に戻す。繁忙日は期限を早く（60日前）、閑散日は遅く（14日前）。
- **推奨パラメータ（初期値）**: 繁忙60日前 / 閑散14日前
- **システム対応**: GroupBooking.cutoffDate（拡張）

### G-10 在庫の隠し持ち
- **種別**: アクション
- **内容**: OTA各社に全在庫を出さず、直販に一定数を確保する。ただし売れ残りリスクがあるため、直前7日で残っていればOTAに開放する。
- **推奨パラメータ（初期値）**: 直販確保 5〜10%、7日前に開放
- **システム対応**: OtaChannelData

### G-11 制限の解除タイミング
- **種別**: 判定ルール
- **内容**: Min LOS・CTAは需要が想定より弱ければ即解除する。制限が残ったまま空室で終わるのが最悪。直前7日で残在庫 ≥20% なら全制限を解除。
- **推奨パラメータ（初期値）**: 7日前・残 ≥20% で解除
- **システム対応**: 推奨提示

### G-12 制限の推奨表示
- **種別**: 説明ルール
- **内容**: システムは制限を自動反映せず「推奨」として表示する（書き戻しはスコープ外）。推奨文には条件・理由・解除条件を添える。
- **システム対応**: F-DP-01

### G-13 在庫と価格の連携
- **種別**: 判定ルール
- **内容**: 価格を上げても売れ続ける日は制限（Min LOS・CTA）を追加し、制限してもピックアップが止まらない日はさらに価格を上げる。価格と在庫は交互に使う。
- **システム対応**: F-DP-01

### G-14 キャンセル期限後の戻り
- **種別**: アクション
- **内容**: 無料キャンセル期限（前日・3日前等）直後に戻る在庫を見込み、期限翌日の朝に価格・制限を見直す。この在庫を投げ売りしないよう、当日販売チャネルの価格も上限寄りに。
- **推奨パラメータ（初期値）**: 期限翌朝に再評価
- **システム対応**: 推奨提示


## H. イベント・外部要因

関連機能・データ: F-DP-07 / Event / DailyData.isHoliday

### H-01 イベントの分類
- **種別**: 定義
- **内容**: 種別（concert / sports / conference / festival / exhibition / intl_holiday / local）と影響度（高・中・低）で分類する。影響度は「商圏の宿泊需要をどれだけ増やすか」で決め、イベントの知名度では決めない。
- **推奨パラメータ（初期値）**: type × impact
- **システム対応**: Event.type / expectedImpact

### H-02 影響度の判定基準
- **種別**: 判定ルール
- **内容**: 高 = 来場者数が商圏客室数の50%超、または過去の同イベント日が満室。中 = 来場者数が商圏客室数の20〜50%。低 = それ未満だが需要増が観測される。判定根拠を description に残す。
- **推奨パラメータ（初期値）**: 50% / 20% の比率
- **システム対応**: Event.expectedImpact / description

### H-03 影響度の初期加算値
- **種別**: 計算式
- **内容**: 予測稼働への加算は 高 +15pt / 中 +8pt / 低 +3pt を初期値とし、同イベントの過去実績（イベント日の稼働 − 同曜日平均）で上書きする。2回目以降は実績値が優先。
- **推奨パラメータ（初期値）**: 15/8/3pt → 実績で上書き
- **システム対応**: computeEventImpact

### H-04 波及日の設定
- **種別**: 計算式
- **内容**: イベントの前日・翌日にも影響を設定する。夜公演のライブは前泊型（前日+50%）、朝開始のスポーツ・マラソンは前泊型、複数日の学会・展示会は会期中フラット＋前日+30%。
- **推奨パラメータ（初期値）**: 前日 0.5 / 翌日 0.3
- **システム対応**: Event.startDate/endDate

### H-05 繰り返しイベント
- **種別**: 判定ルール
- **内容**: 毎年開催のイベントは前年登録から自動で翌年候補を生成し、日程確定時にオペレーターが確認する。登録漏れが最大の機会損失要因。
- **推奨パラメータ（初期値）**: 翌年候補を自動生成
- **システム対応**: F-DP-07

### H-06 イベントの登録期限
- **種別**: 判定ルール
- **内容**: イベントは開催90日前までに登録する（早期予約が入り始める前）。直前登録は予測に反映されるが、既に安値で売れた在庫は戻らない。
- **推奨パラメータ（初期値）**: 90日前まで
- **システム対応**: F-DP-07（OPERATOR登録）

### H-07 イベント日の価格挙動
- **種別**: 判定ルール
- **内容**: イベント日は通常より早期（60〜90日前）から強気にし、段階値上げの節目を前倒しする。イベント日のブッキングカーブは通常日より前倒しで立ち上がる。
- **推奨パラメータ（初期値）**: 節目を30日前倒し
- **システム対応**: F-DP-01

### H-08 イベント中止・延期
- **種別**: アクション
- **内容**: 中止・延期が判明したら即時イベントを無効化し予測を再計算、キャンセル急増をアラートで通知する。空いた在庫は通常日ルールで販促。
- **推奨パラメータ（初期値）**: 即時再計算
- **システム対応**: F-DP-07 / N

### H-09 祝日・連休の扱い
- **種別**: 定義
- **内容**: 祝日・連休はイベントとは別に祝日マスタで扱う。連休の並び（3連休・飛び石・GW10連休等）による需要パターンの違いは、連休種別として補正する。
- **推奨パラメータ（初期値）**: 祝日マスタ + 連休種別
- **システム対応**: DailyData.isHoliday / holidayName

### H-10 GW・お盆・年末年始
- **種別**: 判定ルール
- **内容**: GWは中日（平日）の谷、お盆は都市型のビジネス需要消失、年末年始は12/31〜1/2の観光地ピークと1/3以降の急落、を個別パターンとして持つ。一般の祝日補正では捉えられない。
- **推奨パラメータ（初期値）**: 個別パターン3種
- **システム対応**: F-DP-05

### H-11 海外の連休
- **種別**: 判定ルール
- **内容**: 春節（1〜2月）、国慶節（10月初）、タイ正月（4月中）、欧米のクリスマス休暇等を intl_holiday として登録し、インバウンド比率の高いホテルでは需要要因に加える。
- **推奨パラメータ（初期値）**: 主要5連休を初期登録
- **システム対応**: Event.type = intl_holiday

### H-12 競合施設の変化
- **種別**: 判定ルール
- **内容**: 近隣の新規開業・閉館・改装は「供給イベント」として登録する。開業直後3〜6か月は市場価格が下押しされ、閉館は自館への流入増となる。
- **推奨パラメータ（初期値）**: 供給イベント種別
- **システム対応**: Event.type = supply

### H-13 ネガティブ要因
- **種別**: 判定ルール
- **内容**: 近隣工事・交通規制・大規模な悪天候予報・感染症流行は負の外部要因として登録し、予測稼働から減算する（低 −3pt / 中 −8pt / 高 −15pt）。
- **推奨パラメータ（初期値）**: 負の影響度
- **システム対応**: DailyData.externalFactors / Event（負値）

### H-14 イベント情報の出典
- **種別**: 注意
- **内容**: イベント登録には出典（公式サイト・会場発表）と登録者を残す。未確認情報で強気にして外すと現場の信頼を失う。
- **推奨パラメータ（初期値）**: 出典URL必須
- **システム対応**: Event.description / createdByUserId

### H-15 イベント効果の検証
- **種別**: 計算式
- **内容**: イベント日の着地稼働 − 同曜日ベースライン = 実測影響。登録時の影響度と比較し、翌年の初期値を更新する。3回分の実績があれば実測値の中央値を採用。
- **推奨パラメータ（初期値）**: 3回で中央値採用
- **システム対応**: F-DP-05（学習）

### H-16 イベントカレンダーの表示
- **種別**: 説明ルール
- **内容**: 価格カレンダーにイベント名・影響度・波及日を重ねて表示し、推奨価格の根拠として「近隣で○○（高）」を明示する。
- **システム対応**: F-DP-01 / F-DP-07


## I. 競合分析

関連機能・データ: F-DP-06 / F-DAILY-03 / F-ANA-02 / CompetitorPriceData

### I-01 コンプセットの選定
- **種別**: 判定ルール
- **内容**: 自館の予約検討者が同時に比較する施設を4〜6社。基準: 立地（徒歩圏・同駅）、価格帯（ADR ±30%）、客層・グレード。知名度で選ばない。半年ごとに見直す。
- **推奨パラメータ（初期値）**: 4〜6社、ADR ±30%
- **システム対応**: F-SET-03 / Competitor

### I-02 価格取得の条件
- **種別**: 定義
- **内容**: 1名・2名・3名以上の利用人数別に、スタンダードクラス・食事なし・キャンセル可を標準条件として毎日同時刻に取得する。プラン最安値ではなく標準条件価格を比べる。
- **推奨パラメータ（初期値）**: 標準条件固定
- **システム対応**: F-DAILY-03 / CompetitorPriceData.price1P/2P/3P

### I-03 "平均"を使わない
- **種別**: 説明ルール
- **内容**: 競合価格は中央値・最安・最高・自館の位置（何番目か）で示し、「平均」という表現・指標を使わない（1社の外れ値で意味が変わるため。仕様で確定）。
- **推奨パラメータ（初期値）**: 中央値・レンジ・順位
- **システム対応**: F-DP-06 / F-ANA-02（仕様）

### I-04 価格ポジション指数
- **種別**: 計算式
- **内容**: ポジション指数 = 自館価格 ÷ コンプセット中央値。過去のARI実績（自館が高く売れてきた度合い）と比べ、指数が実力より高ければ売れ行き鈍化、低ければ安売りの疑い。
- **推奨パラメータ（初期値）**: ARI実績 ±5% 以内が適正
- **システム対応**: F-DP-06

### I-05 競合の「動き」検知
- **種別**: 判定ルール
- **内容**: コンプセットの中央値が前日比 ±8% 以上動いた日、または半数以上が同方向に動いた日を「市場の動き」として検知しアラート。1社だけの動きは無視する。
- **推奨パラメータ（初期値）**: ±8% or 過半数同方向
- **システム対応**: N / CompetitorPriceData

### I-06 追従する動き・しない動き
- **種別**: 判定ルール
- **内容**: 追従する: 過半数の一斉値上げ（需要シグナル）。追従しない: 1社の値下げ、自館の需要レベルC以上での市場値下げ。追従度の重みは参照度であり自動追従ではない。
- **システム対応**: F-DP-02

### I-07 競合売止めの活用
- **種別**: 判定ルール
- **内容**: コンプセットの売止め社数を日別に記録し、過半数売止めで自館ランク+2・レベル+1。全社売止めなら上限ランク。市場の在庫消失は最強の需要シグナル。
- **推奨パラメータ（初期値）**: 過半数 +2、全社 上限
- **システム対応**: CompetitorPriceData（soldout）

### I-08 価格差の許容範囲
- **種別**: 判定ルール
- **内容**: 自館が中央値より20%以上高く、かつペースがSTLY比−15%以下なら「価格が理由で負けている」可能性。逆に20%以上安くペースが速いなら「安売り」。両条件が揃ったときだけ価格要因と判断する。
- **推奨パラメータ（初期値）**: ±20% × ペース ∓15%
- **システム対応**: F-DP-06 / F-DAILY-01

### I-09 競合の値上げ余地シグナル
- **種別**: 判定ルール
- **内容**: 自館が売止めまたは残在庫 ≤10% で、競合がまだ販売中かつ自館より高いなら、自館は安すぎる。即時+2ランク以上。
- **システム対応**: F-DP-01

### I-10 市場データとの切り分け
- **種別**: 判定ルール
- **内容**: 自館のRGIが低下したとき、市場（コンプセット）のRevPARが伸びているなら自館固有の問題、市場も落ちているなら外部要因。打ち手が全く異なるため必ず切り分ける。
- **システム対応**: F-ANA-02

### I-11 レートパリティ監視
- **種別**: 判定ルール
- **内容**: 自館の同一条件価格がチャネル間で ±3% 以上ずれていたらアラート。パリティ崩れはOTA掲載順位低下・ベストレート保証違反・ゲスト不信を招く。
- **推奨パラメータ（初期値）**: ±3%
- **システム対応**: OtaChannelData / N

### I-12 競合の口コミ評点
- **種別**: 判定ルール
- **内容**: 同価格帯で自館の評点がコンプセットより0.3以上低ければ、価格ではなく商品・サービス起因の弱さと判断し、値下げで補わない。評点差はポジション係数に反映する。
- **推奨パラメータ（初期値）**: 評点差 0.3
- **システム対応**: F-ANA-04 / ReviewScore

### I-13 競合分析の頻度
- **種別**: 判定ルール
- **内容**: 価格は日次、コンプセット構成は半年、評点は月次で見直す。競合分析は週次RM会議の固定議題。
- **推奨パラメータ（初期値）**: 日次/半年/月次
- **システム対応**: P（業務サイクル）

### I-14 競合データの限界
- **種別**: 注意
- **内容**: OTA表示価格は競合の「売りたい価格」であり実際の成約ADRではない。市場のADR実績は業界ベンチマーク（STR等）や自治体統計で補完する。
- **システム対応**: F-ANA-02

### I-15 競合価格の表示
- **種別**: 説明ルール
- **内容**: 日別カレンダーでは自館推奨価格と競合中央値・レンジを同じ人数条件で並べる。人数条件の異なる比較（自館2P vs 競合1P）を画面上で起こさない。
- **推奨パラメータ（初期値）**: 同人数条件で表示
- **システム対応**: F-DAILY-03

### I-16 新規競合の観測期間
- **種別**: 判定ルール
- **内容**: 新規開業ホテルはコンプセットに入れる前に3か月観測し、開業特価が終わってから価格帯を判定する。開業直後の価格でコンプセットの中央値を歪めない。
- **推奨パラメータ（初期値）**: 3か月観測
- **システム対応**: F-SET-03


## J. 販売チャネル

関連機能・データ: OtaChannelData / Campaign

### J-01 チャネルの分類
- **種別**: 定義
- **内容**: 直販（公式サイト・電話）、国内OTA（楽天トラベル・じゃらん・一休等）、海外OTA（Booking.com・Agoda・Expedia等）、リアルエージェント、法人契約、ウォークイン。チャネル別にネット実績を持つ。
- **システム対応**: OtaChannelData

### J-02 実効手数料の定義
- **種別**: 計算式
- **内容**: 実効手数料率 = (基本手数料 ＋ ポイント原資 ＋ 事前決済手数料 ＋ 広告・クーポン負担) ÷ 販売額。表面手数料だけで比較しない。チャネルごとに月次で実測する。
- **推奨パラメータ（初期値）**: 国内OTA 10〜13%、海外OTA 15〜18% を初期値
- **システム対応**: OtaChannelData.commission

### J-03 チャネル別ネットRevPAR
- **種別**: 計算式
- **内容**: チャネル評価はネットRevPAR（手数料控除後）で行う。表面ADRが高くても実効手数料が高ければ手残りは低い。
- **システム対応**: OtaChannelData

### J-04 チャネル×客層
- **種別**: 定義
- **内容**: 楽天・じゃらん = 国内レジャー・ファミリー、Booking.com = 欧米個人、Agoda = アジア圏、一休・Relux = 高単価・記念日、直販 = リピーター。自館ターゲットに合わせて注力配分を決める。
- **システム対応**: OtaChannelData.channel

### J-05 直販比率の目標
- **種別**: 判定ルール
- **内容**: 直販比率（室数ベース）の初期目標20%、リピーター多いホテルは30%以上。直販が伸びない月はOTA依存度上昇として月次レビュー議題にする。
- **推奨パラメータ（初期値）**: 20%（初期）
- **システム対応**: OtaChannelData / F-ANA

### J-06 レートパリティと直販優位
- **種別**: 判定ルール
- **内容**: 表示価格はチャネル間で揃え、直販には会員価格・特典（レイトチェックアウト・朝食）・ベストレート保証で実質優位を作る。表示価格でOTAより安くしない（OTA側のペナルティ回避）。
- **システム対応**: Campaign

### J-07 繁忙日のチャネル配分
- **種別**: アクション
- **内容**: 需要レベルA/Bの日は、実効手数料の高いチャネルから在庫を絞り、直販・低手数料チャネルに集約。どうせ埋まる日に高コストで売らない。
- **推奨パラメータ（初期値）**: A/Bで高手数料チャネル絞り
- **システム対応**: OtaChannelData

### J-08 閑散日のチャネル活用
- **種別**: アクション
- **内容**: 需要レベルD/Eの日は、OTA内広告・タイムセール・クーポン等のチャネル施策を価格引き下げより先に使う。露出施策のコストは値下げより回収しやすい。
- **推奨パラメータ（初期値）**: 露出施策を先行
- **システム対応**: Campaign

### J-09 OTA掲載順位
- **種別**: 判定ルール
- **内容**: OTA内の検索順位はコンバージョン・評点・パリティ・在庫充足で決まる。順位低下時は価格より先に写真・プラン名・評点対応・在庫開放を確認する。
- **システム対応**: OtaChannelData

### J-10 キャンペーンの評価
- **種別**: 計算式
- **内容**: キャンペーン効果 = 期間中のネットRevPAR − 同曜日ベースラインのネットRevPAR。表面売上の増加ではなく、手数料・割引後の増分で判断する。
- **推奨パラメータ（初期値）**: ネット増分で評価
- **システム対応**: Campaign

### J-11 サイトコントローラー点検
- **種別**: アクション
- **内容**: 在庫・料金連動の設定（プラン紐付け・在庫割当・停止条件）を月1回点検する。設定ミスは売り逃し・過剰販売・パリティ崩れに直結する。
- **推奨パラメータ（初期値）**: 月1回
- **システム対応**: F-SET-03（連携先確定後）

### J-12 チャネル別リードタイム
- **種別**: 判定ルール
- **内容**: チャネルごとのリードタイム分布を持つ（海外OTAは長い、国内OTAは中、直販・電話は短い）。予測の残ピックアップはチャネルミックスで補正する。
- **システム対応**: OtaChannelData / F-DP-05

### J-13 チャネル別キャンセル率
- **種別**: 判定ルール
- **内容**: 海外OTAのキャンセル可プランはキャンセル率が高い傾向。チャネル別キャンセル率をOTBの実需換算とオーバーブッキング判断に使う。
- **推奨パラメータ（初期値）**: チャネル別に実測
- **システム対応**: OtaChannelData

### J-14 チャネル戦略の説明
- **種別**: 説明ルール
- **内容**: AIコメントで「○チャネルの比率が高い」と言うときは、必ずネット単価への影響（手残り）を数字で添える。比率だけの指摘は行動につながらない。
- **システム対応**: F-DASH-06


## K. セグメント・団体

関連機能・データ: F-SET-05 / GroupBooking

### K-01 セグメントの定義
- **種別**: 定義
- **内容**: ビジネス個人 / 国内レジャー / インバウンド / 団体・グループ / 法人契約 / その他。セグメント（客層）とチャネル（販売経路）は別軸で管理する。
- **システム対応**: GroupBooking / 将来拡張

### K-02 セグメント別の行動特性
- **種別**: 定義
- **内容**: ビジネス: 平日・直前・価格感度中。国内レジャー: 週末連休・2〜8週前・価格感度高。インバウンド: 長期リード・連泊・為替影響。団体: 大口・ウォッシュあり。法人: 固定価格・平日安定。
- **システム対応**: F-DP-05

### K-03 ディスプレイスメント分析
- **種別**: 計算式
- **内容**: 団体受入の判断: 団体売上 − 押し出される個人需要の売上（＝押し出し室数 × 個人の予測ADR）＋ 団体の付帯売上（宴会・料飲）。正なら受入、負なら断るか価格を上げる。
- **システム対応**: F-SET-05 / GroupBooking

### K-04 押し出し室数の推定
- **種別**: 計算式
- **内容**: 押し出し室数 = max(0, 個人の予測需要 − (総在庫 − 団体室数))。個人需要が総在庫を下回る日なら押し出しはゼロ（団体はほぼ純増）。
- **システム対応**: F-SET-05

### K-05 団体の最低受入価格
- **種別**: 計算式
- **内容**: 団体最低価格 = 押し出される個人需要の売上 ÷ 団体室数（＝ハードルレート）。繁忙日はこの値が個人価格に近づき、閑散日はゼロに近づく。年間一律の団体料金を使わない。
- **推奨パラメータ（初期値）**: 日別ハードルレート
- **システム対応**: F-SET-05

### K-06 ウォッシュ率の適用
- **種別**: 判定ルール
- **内容**: 団体ブロックの実需 = ブロック室数 × (1 − ウォッシュ率)。ウォッシュ率は団体種別（旅行会社・学校・企業）別の過去実績。ブロック全量を需要として予測に入れない。
- **推奨パラメータ（初期値）**: 初期 25%
- **システム対応**: GroupBooking / F-DP-05

### K-07 団体の受入判断フロー
- **種別**: アクション
- **内容**: ①その日の個人予測需要とレベル確認 ②押し出し室数計算 ③ハードルレートと提示価格を比較 ④付帯売上・将来リピートを加味 ⑤受入可否と条件（室数上限・カットオフ・キャンセル料）を提示。
- **システム対応**: F-SET-05

### K-08 団体の室数上限
- **種別**: 判定ルール
- **内容**: 1団体で総在庫の30%超、または複数団体で50%超のブロックは、繁忙日には原則受けない（個人需要の取り込み余地を残す）。閑散日は上限を緩める。
- **推奨パラメータ（初期値）**: 繁忙 30%/50%
- **システム対応**: F-SET-05

### K-09 団体キャンセル条件
- **種別**: 判定ルール
- **内容**: 団体には室数確定期限と段階的キャンセル料（30日前50%・14日前80%・7日前100%等）を設定し、ウォッシュリスクを価格・条件に転嫁する。
- **推奨パラメータ（初期値）**: 段階キャンセル料
- **システム対応**: GroupBooking

### K-10 法人契約（LRA/NLRA）
- **種別**: 定義
- **内容**: LRA = 最終1室まで契約価格で販売する義務あり、NLRA = 満室近くで契約価格の販売を止められる。LRAは繁忙日の機会損失要因のため、契約時に対象日除外か価格差を設ける。
- **システム対応**: 将来拡張

### K-11 法人契約の年次見直し
- **種別**: アクション
- **内容**: 契約更改時に、契約価格の実績（利用室数・繁忙日利用比率・機会損失額）を提示し、繁忙日除外・季節別価格・利用室数コミットを交渉する。
- **推奨パラメータ（初期値）**: 年1回
- **システム対応**: F-SET-05

### K-12 インバウンドの早売り防止
- **種別**: 判定ルール
- **内容**: インバウンドは長期リードで安値プランに入りやすい。90日超のOTBがベースラインより速く、その大半が低価格帯なら、遠い日の早割・安値プランを停止する。
- **推奨パラメータ（初期値）**: 90日超で早割停止
- **システム対応**: F-DP-01 / Campaign

### K-13 セグメントミックスの計画
- **種別**: 判定ルール
- **内容**: 月・季節ごとに「セグメント別の目標室数比率」を持ち、閑散期は団体・法人でベースを厚く、繁忙期は個人・高単価比率を上げる。実績との差を月次レビュー。
- **推奨パラメータ（初期値）**: 月別ミックス目標
- **システム対応**: F-SET-05

### K-14 団体の影響表示
- **種別**: 説明ルール
- **内容**: 団体が入った日は価格カレンダー・ブッキングカーブ上で団体分を色分けし、個人需要の見え方を分離する。団体込みの稼働で「好調」と誤読させない。
- **推奨パラメータ（初期値）**: 団体を別色
- **システム対応**: F-DP-01 / F-DAILY-01 / GroupBooking

### K-15 団体ルールの未確定事項
- **種別**: 注意
- **内容**: 団体客レベニュー影響ルール（F-SET-05）はクライアント協議中。本カテゴリの数値は汎用初期値であり、協議結果で上書きする。
- **システム対応**: F-SET-05（課題No.53）

### K-16 セグメント別予測の分離
- **種別**: 判定ルール
- **内容**: データが揃えば、セグメント別にブッキングカーブと予測を持ち合算する。混合カーブでは「レジャーが先に作るベース」と「直前に乗るビジネス」が区別できず、直前の伸びを過小評価する。
- **システム対応**: F-DP-05


## L. 利用人数別・部屋タイプ

関連機能・データ: F-ANA-01 / DailyRoomData / DOR

### L-01 利用人数別の分析軸
- **種別**: 定義
- **内容**: 1名・2名・3名以上の3区分で構成比・客単価・ADRを見る。稼働率は人数別には出さない（仕様）。
- **推奨パラメータ（初期値）**: 3区分
- **システム対応**: F-ANA-01

### L-02 人数構成と売上
- **種別**: 計算式
- **内容**: 客室売上 = Σ(人数区分別室数 × 区分別価格)。同じ稼働でも2名以上比率が上がれば売上が増える。DORの変化はRevPARの説明要因に含める。
- **システム対応**: DOR / F-ANA-01

### L-03 平日1名・週末2名の典型
- **種別**: 判定ルール
- **内容**: 都市型は平日1名比率60〜80%、週末2名以上比率60%以上が典型。曜日別の構成比が崩れたら（週末に1名が増える等）需要の質の変化として要因確認。
- **システム対応**: F-ANA-01

### L-04 人数別価格の推奨
- **種別**: 判定ルール
- **内容**: 推奨ランクは共通で、1P/2P/3Pの価格差はランク表の比率に従う。ただし週末に1名需要が強いホテルは、1Pの比率を高めに（2P ÷ 1P を1.5に近づける）設定してもよい。
- **システム対応**: PriceRank / F-DP-01

### L-05 人数別競合比較
- **種別**: 判定ルール
- **内容**: 競合比較は同じ人数条件で行う。自館の2P価格と競合の1P価格を並べない。3名以上は部屋タイプが変わるため、比較可能な施設だけで見る。
- **推奨パラメータ（初期値）**: 同人数条件
- **システム対応**: F-DAILY-03

### L-06 部屋タイプ別の稼働偏り
- **種別**: 判定ルール
- **内容**: 下位タイプの稼働が上位より20pt以上高い状態が続くなら、価格差が大きすぎる。差を縮めるか下位タイプの価格を上げる。
- **推奨パラメータ（初期値）**: 稼働差 20pt
- **システム対応**: DailyRoomData / RoomType

### L-07 アップセル導線
- **種別**: アクション
- **内容**: 下位タイプ完売時の上位への誘導（差額提示）と、チェックイン時アップセルの標準単価を持つ。繁忙日は差額を小さく、閑散日は上位を割安に見せる。
- **システム対応**: RoomType

### L-08 客単価の推移
- **種別**: 判定ルール
- **内容**: 客単価（人単価）が下がり続けるときは、多人数利用の増加（構成変化）か値下げ（価格変化）かを分解する。構成変化なら健全な場合もある。
- **システム対応**: F-DASH-01 客単価

### L-09 定員超過・添い寝
- **種別**: 注意
- **内容**: 添い寝・幼児無料の扱いは人数集計ルールを明示し、DOR・客単価の前年比較で定義変更による段差を作らない。
- **システム対応**: DailyData.guests

### L-10 部屋タイプ別データの段階導入
- **種別**: 注意
- **内容**: 部屋タイプ別実績（DailyRoomData）が揃うまでは全体推奨＋差額ルールで運用し、揃った時点でタイプ別推奨に切り替える。切替時点を記録する。
- **システム対応**: DailyRoomData / AiPriceRecommendation.roomTypeId


## M. フォーキャスト・予算・着地

関連機能・データ: F-DP-04 / F-DASH-02 / MonthlyBudget / MonthlyLandingSimulation

### M-01 月間着地の定義
- **種別**: 計算式
- **内容**: 月間着地 = Σ日別（実績確定日は実績、未来日は予測）。売上・室数・ADR・OCC・RevPARを併記する。ADRとRevPARは必ず併記（仕様）。
- **システム対応**: F-DP-04 / MonthlyLandingSimulation

### M-02 着地の3シナリオ
- **種別**: 計算式
- **内容**: 基準（予測どおり）、弱気（残ピックアップ −20%）、強気（＋20%）の3本を出し、予算達成に必要なシナリオを明示する。単一値の着地は外れたときに議論にならない。
- **推奨パラメータ（初期値）**: ±20%
- **システム対応**: F-DP-04

### M-03 予算差の分解
- **種別**: 計算式
- **内容**: 売上差 = (実績室数 − 予算室数) × 予算ADR ＋ (実績ADR − 予算ADR) × 実績室数。数量要因と価格要因に分けて打ち手を決める。
- **システム対応**: F-DASH-02

### M-04 再フォーキャストの頻度
- **種別**: 判定ルール
- **内容**: 月間着地は日次で自動更新、週次で人が確認・コメント。月の前半に予算未達が見えたら15日までに対策を決める（残り半月で打てる手は限られる）。
- **推奨パラメータ（初期値）**: 日次自動・週次確認・15日判断
- **システム対応**: P

### M-05 フォーキャスト精度の目標
- **種別**: 判定ルール
- **内容**: 月初時点の月間売上予測の誤差 ±5%以内、15日時点 ±3%以内を目標。外れ幅が目標を超えた月は要因（イベント・団体・予測癖）を記録する。
- **推奨パラメータ（初期値）**: 月初 ±5% / 15日 ±3%
- **システム対応**: F-DP-04

### M-06 予算の設定原則
- **種別**: 判定ルール
- **内容**: 予算は前年実績 × 市場成長率 × 自館施策効果で日別（少なくとも曜日別）に配賦する。月合計だけの予算では日別の進捗管理ができない。
- **推奨パラメータ（初期値）**: 日別配賦
- **システム対応**: F-SET-04 / MonthlyBudget

### M-07 前年実績の補正
- **種別**: 判定ルール
- **内容**: 予算・前年比の前年実績は、曜日ずれ（364日）、前年の異常日（イベント・断絶）を補正した「比較可能前年」を別に持つ。生の前年と補正前年を切り替えて表示できるようにする。
- **推奨パラメータ（初期値）**: 補正前年を別保持
- **システム対応**: MonthlyBudget（前年実績）

### M-08 年度累計の扱い
- **種別**: 定義
- **内容**: 年度は4月始まり。年度累計の達成率は「年度予算に対する累計実績＋当月着地」で示し、月次の達成率と混同しない。
- **推奨パラメータ（初期値）**: 4月始まり
- **システム対応**: F-DASH-02

### M-09 着地未達時の打ち手
- **種別**: アクション
- **内容**: 残リードタイムが長い（15日以上）: プラン・露出・チャネル施策。短い（15日未満）: 直前需要の取り込み・法人/団体の追加受入・当日販売。値下げは最後。打ち手ごとの期待効果を着地シナリオに反映する。
- **推奨パラメータ（初期値）**: 15日で切替
- **システム対応**: F-DP-04 / F-DASH-06

### M-10 着地超過時の打ち手
- **種別**: アクション
- **内容**: 予算超過見込みの月は、残日程の価格を上げて単価を取る（稼働を追わない）。超過分を翌月の弱い日に回す施策（連泊・翌月早割）も検討。
- **システム対応**: F-DP-04

### M-11 KPIスナップショット
- **種別**: 定義
- **内容**: 月初・毎週月曜・15日時点のKPI（OTB・予測着地・予算比）を凍結保存し、月初比較・日付比較に使う。動く数値だけでは「いつ・何が変わったか」が追えない。
- **推奨パラメータ（初期値）**: 月初・週次・15日
- **システム対応**: F-DASH-04 / KpiSnapshot

### M-12 予算比の表示ルール
- **種別**: 説明ルール
- **内容**: 予算比・前年比は必ず同じ軸（本日まで／累計進捗／年度累計）で売上・ADR・OCCを揃えて表示する。軸の異なる数字を並べない（仕様）。
- **システム対応**: F-DASH-02

### M-13 翌月・翌四半期の見通し
- **種別**: 判定ルール
- **内容**: 当月だけでなく翌月〜3か月先の着地見込み（ベースライン主体）を持ち、早期に弱い月を特定して販促・団体営業に着手する。
- **推奨パラメータ（初期値）**: 3か月先まで
- **システム対応**: F-DP-04 / F-ANA-03

### M-14 フォーキャストの他部門共有
- **種別**: アクション
- **内容**: 週次フォーキャスト（日別予測稼働・人数）を料飲・清掃・フロントの人員計画に共有する。予測精度は客室以外のコストにも効く。
- **推奨パラメータ（初期値）**: 週次共有
- **システム対応**: F-REP-01

### M-15 予測着地と実績のギャップ記録
- **種別**: 注意
- **内容**: 月末に「月初予測・15日予測・実績」の3値を保存し、精度推移をグラフ化する。予測が信用されるのはこの記録があるとき。
- **システム対応**: F-DP-04 / KpiSnapshot

### M-16 着地の説明文
- **種別**: 説明ルール
- **内容**: 着地見込みの説明は「予算比○%、主因は○（数量/価格）、残○日で必要な日次ピックアップ○室」の形で、必要ピックアップを必ず含める。
- **システム対応**: F-DASH-06


## N. アラート・例外検知

関連機能・データ: F-DASH-05 / Alert（Level 1〜5）

### N-01 アラート重要度の定義
- **種別**: 定義
- **内容**: Level 5 = 即日対応（機会損失・大量キャンセル・データ断）、4 = 当日中対応、3 = 週次会議で確認、2 = 参考、1 = 情報。ダッシュボードには5・4のみ表示し、該当画面へリンク。
- **推奨パラメータ（初期値）**: 5段階、表示は4以上
- **システム対応**: F-DASH-05 / Alert.level

### N-02 ペース異常（速い）
- **種別**: 判定ルール
- **内容**: 同リードタイムSTLY比 +30%以上、または目標カーブを15pt以上上回る日 → Level 4「値上げ検討」。残在庫 ≤10% なら Level 5。
- **推奨パラメータ（初期値）**: +30% / 15pt
- **システム対応**: F-DAILY-01

### N-03 ペース異常（遅い）
- **種別**: 判定ルール
- **内容**: STLY比 −30%以下、または目標カーブを15pt以上下回る日が7日以内にある → Level 4「原因確認・販促」。30日以内なら Level 3。
- **推奨パラメータ（初期値）**: −30% / 15pt
- **システム対応**: F-DAILY-01

### N-04 ピックアップ急増
- **種別**: 判定ルール
- **内容**: 日次ピックアップが同曜日平均の3倍以上 → Level 4。イベント・団体・競合売止めの発生を疑い、価格見直しを促す。
- **推奨パラメータ（初期値）**: 3倍
- **システム対応**: BookingCurveData

### N-05 キャンセル急増
- **種別**: 判定ルール
- **内容**: 日次キャンセルが総在庫の5%以上、または同曜日平均の3倍 → Level 5。イベント中止・天候・団体キャンセルを確認し、戻り在庫の販売方針を即決。
- **推奨パラメータ（初期値）**: 5% or 3倍
- **システム対応**: BookingCurveData

### N-06 競合の大きな動き
- **種別**: 判定ルール
- **内容**: コンプセット中央値の前日比 ±8%以上、または過半数の同方向変動 → Level 3。過半数売止め → Level 4（値上げ余地）。
- **推奨パラメータ（初期値）**: ±8% / 過半数
- **システム対応**: CompetitorPriceData

### N-07 レートパリティ崩れ
- **種別**: 判定ルール
- **内容**: 自館の同条件価格がチャネル間で ±3%以上ずれ → Level 4。ベストレート保証違反・OTA順位低下のリスク。
- **推奨パラメータ（初期値）**: ±3%
- **システム対応**: OtaChannelData

### N-08 予測と実績の乖離
- **種別**: 判定ルール
- **内容**: 前日予測と当日実績の稼働差が ±10pt以上の日が週3日以上 → Level 3「予測キャリブレーション」。
- **推奨パラメータ（初期値）**: ±10pt × 3日/週
- **システム対応**: F-DP-05

### N-09 予算進捗の遅れ
- **種別**: 判定ルール
- **内容**: 月の15日時点で累計進捗（実績＋OTB）が予算の85%未満 → Level 4。月初時点で前年同時点比 −15%以下 → Level 3。
- **推奨パラメータ（初期値）**: 85% / −15%
- **システム対応**: F-DASH-02

### N-10 推奨の未反映
- **種別**: 判定ルール
- **内容**: AI推奨と現在価格の差が3ランク以上の日が7日以内に3日以上 → Level 3「推奨確認」。上書き理由が未記録なら Level 4。
- **推奨パラメータ（初期値）**: 3ランク × 3日
- **システム対応**: F-DP-01 / F-DP-03

### N-11 データ断
- **種別**: 判定ルール
- **内容**: 日別実績・OTBスナップショット・競合価格のいずれかが2日以上更新されていない → Level 5。予測・推奨は古いデータで動き続けるため最優先。
- **推奨パラメータ（初期値）**: 2日
- **システム対応**: DailyData / BookingCurveData / CompetitorPriceData

### N-12 イベント未登録の疑い
- **種別**: 判定ルール
- **内容**: 予測稼働が同曜日平均より20pt以上高くイベント登録がない日 → Level 3「イベント登録確認」。過去の同時期にイベントがあった場合は Level 4。
- **推奨パラメータ（初期値）**: 20pt
- **システム対応**: Event / F-DP-07

### N-13 直前値下げの常態化
- **種別**: 判定ルール
- **内容**: 月内の3日前以内値下げ回数が5回以上 → Level 3。翌月も続けば Level 4。ゲストの学習効果を防ぐ。
- **推奨パラメータ（初期値）**: 5回/月
- **システム対応**: AuditLog

### N-14 満室日の残需要
- **種別**: 判定ルール
- **内容**: 残在庫0で7日以上前 → Level 4「早期満室: 価格が安かった可能性」。翌年の同日・類似日の初期価格を上げる学習材料にする。
- **推奨パラメータ（初期値）**: 7日以上前の満室
- **システム対応**: F-DP-05

### N-15 団体ブロック期限
- **種別**: 判定ルール
- **内容**: カットオフ3日前で未確定率50%以上の団体 → Level 4「確定催促・在庫戻し判断」。
- **推奨パラメータ（初期値）**: 3日前・50%
- **システム対応**: GroupBooking

### N-16 アラートの抑止・重複排除
- **種別**: 注意
- **内容**: 同一事象のアラートは24時間内に1回。対応済み・確認済みはステータスで閉じ、同条件が続いても再通知は週1回に抑える。アラート疲れは全てを無視させる。
- **推奨パラメータ（初期値）**: 24h重複排除
- **システム対応**: Alert.status

### N-17 アラートの文面
- **種別**: 説明ルール
- **内容**: 文面は「何が（事象）・どの日に・どれくらい（数値）・何をすべきか（1アクション）・リンク」の順。例「9/21(土) 予約ペースが前年比+42%。残12室。価格見直しを推奨 → プライシング」。
- **システム対応**: Alert.message / linkTo

### N-18 アラート効果の検証
- **種別**: 計算式
- **内容**: アラート後72時間以内に対応（価格変更・設定変更）された比率と、対応した場合の着地改善を月次で集計。反応されないアラートは閾値か文面を見直す。
- **推奨パラメータ（初期値）**: 対応率目標 ≥60%
- **システム対応**: Alert / AuditLog


## O. AIコメント・説明生成

関連機能・データ: F-DASH-06 / AiComment

### O-01 AIコメントの役割
- **種別**: 定義
- **内容**: 数値の羅列ではなく、「今どういう状況で、なぜそう判断し、次に何をすべきか」を現場の言葉で示す。レベニュー担当者が朝5分で状況把握できる文章を目指す。
- **システム対応**: F-DASH-06 / AiComment

### O-02 構成の順序
- **種別**: 説明ルール
- **内容**: 結論（状況の一言）→ 根拠（数値2〜3個、比較対象付き）→ 推奨アクション（1〜2個、具体的）→ 注意点・不確実性。この順を崩さない。
- **推奨パラメータ（初期値）**: 結論→根拠→アクション→注意
- **システム対応**: AiComment

### O-03 数値の表現
- **種別**: 説明ルール
- **内容**: 数値には必ず比較対象を添える（前年同曜日比・予算比・目標カーブ比・コンプセット比のいずれか）。「稼働78%」だけでなく「稼働78%（前年同曜日72%、予算75%）」。
- **推奨パラメータ（初期値）**: 比較対象必須
- **システム対応**: AiComment

### O-04 用語の補足
- **種別**: 説明ルール
- **内容**: 専門用語（RevPAR・ピックアップ・OTB等）は初出で一言補足する。「RevPAR（客室あたり収益）」。オーナー・支配人向けは補足必須、レベニュー担当者向けは省略可（ロールで切替）。
- **推奨パラメータ（初期値）**: ロールで切替
- **システム対応**: AiComment / UserRole

### O-05 推奨アクションの具体性
- **種別**: 説明ルール
- **内容**: 「価格を見直してください」ではなく「9/21(土)を R24→R27（¥14,800→¥16,800）へ。残12室・前年比+42%のため」。日付・ランク・金額・理由を含める。
- **推奨パラメータ（初期値）**: 日付・ランク・金額・理由
- **システム対応**: AiComment / F-DP-01

### O-06 不確実性の明示
- **種別**: 説明ルール
- **内容**: 確信度が0.6未満の予測に基づく推奨は「データが少なく確度は中程度」等の限定を付け、変更幅を抑えた推奨にする。断定調で外すと信頼を失う。
- **推奨パラメータ（初期値）**: conf<0.6 で限定表現
- **システム対応**: AiPriceRecommendation.confidence

### O-07 しないこと
- **種別**: 説明ルール
- **内容**: 「平均」という表現（競合分析）、未実装機能の言及、根拠のない断定、値下げの安易な推奨、他社の実名批判、ゲスト個人情報の記載はしない。
- **システム対応**: F-DP-06 仕様 / Phase 4

### O-08 トーン
- **種別**: 説明ルール
- **内容**: 敬体・簡潔・事実ベース。煽らない（「危険」「大チャンス」等は使わない）。良い結果も過度に称賛せず、次の判断材料を示す。
- **システム対応**: AiComment

### O-09 長さ
- **種別**: 説明ルール
- **内容**: ダッシュボードのAIまとめは3〜5文（200字前後）。日別のコメントは1〜2文。長文は読まれない。詳細は該当画面へのリンクで補う。
- **推奨パラメータ（初期値）**: 200字前後
- **システム対応**: F-DASH-06

### O-10 優先順位付け
- **種別**: 説明ルール
- **内容**: 複数の論点があるときは、金額インパクト（機会損失・未達額）の大きい順に述べる。Level 5・4アラート対象日を先頭に置く。
- **推奨パラメータ（初期値）**: 金額インパクト順
- **システム対応**: Alert.level

### O-11 質問への回答
- **種別**: 説明ルール
- **内容**: ユーザーの質問には、①システム内の該当データ（数値・日付）を根拠に、②本知識ベースの原則を引いて、③次のアクションを示す。データがない場合は「データがない」と明言する。
- **システム対応**: AiComment / 将来Q&A

### O-12 知識ベースと実装値の関係
- **種別**: 説明ルール
- **内容**: 閾値・重み・補正値の具体値を説明するときはシステムの現在設定値を参照して述べる。本知識ベースの初期値をそのまま「システムの値」として語らない。
- **推奨パラメータ（初期値）**: 実装値が正
- **システム対応**: PricingStrategyConfig / 設定

### O-13 週次サマリーの型
- **種別**: 説明ルール
- **内容**: 週次: ①先週の実績 vs 予算・前年（RevPAR分解） ②今後4週の要注意日（強い日・弱い日 各上位3日） ③競合・市場の動き ④推奨アクション3つ。
- **推奨パラメータ（初期値）**: 4項目固定
- **システム対応**: F-REP-01 / AiComment

### O-14 月次サマリーの型
- **種別**: 説明ルール
- **内容**: 月次: ①着地 vs 予算・前年（分解） ②要因（イベント・団体・チャネル・価格施策） ③予測精度の振り返り ④翌月の見通しと重点日 ⑤ルール・設定の見直し提案。
- **推奨パラメータ（初期値）**: 5項目固定
- **システム対応**: F-REP-01

### O-15 日別コメントの型
- **種別**: 説明ルール
- **内容**: 日別: 「需要レベル○（予測稼働○%、前年比○%）。推奨R○（¥○）。理由: ○」。イベント・団体・競合売止めがあれば1語で添える。
- **システム対応**: F-DP-01

### O-16 コメントの再生成条件
- **種別**: 判定ルール
- **内容**: コメントは元データが変わったとき（予測再計算・実績更新・イベント登録）に再生成し、生成時刻と参照データの時点を表示する。古いコメントを新しい数値の横に置かない。
- **推奨パラメータ（初期値）**: データ更新時に再生成
- **システム対応**: AiComment.generatedAt

### O-17 ハルシネーション防止
- **種別**: 注意
- **内容**: 生成時に参照した数値はシステムから取得した値のみとし、生成文中の数値は参照データと突合してから表示する。突合できない数値を含む文は表示しない。
- **推奨パラメータ（初期値）**: 数値突合必須
- **システム対応**: AiComment（Phase 4 実装時）

### O-18 説明の一貫性
- **種別**: 注意
- **内容**: 同じ事実に対して画面ごとに異なる表現・数値が出ないよう、指標の定義（A章）と比較軸（M章）を共通ライブラリで統一する。
- **システム対応**: utils / shared


## P. 業務サイクル

関連機能・データ: 運用全般

### P-01 日次: 実績確認
- **種別**: アクション
- **内容**: 前日実績（OCC・ADR・RevPAR・人数）を予算・前年同曜日・前日予測と比較。予測との差が±10pt以上なら原因を1行メモ。
- **推奨パラメータ（初期値）**: 10分
- **システム対応**: F-DASH-01 / F-DASH-02

### P-02 日次: ピックアップ確認
- **種別**: アクション
- **内容**: 今後90日の日次・週次ピックアップ（ネット）を確認。Level 4以上のアラート日を先に処理し、次に目標カーブとの乖離が大きい日。
- **推奨パラメータ（初期値）**: 15分
- **システム対応**: F-DAILY-01 / F-DASH-05

### P-03 日次: 価格・制限の決定
- **種別**: アクション
- **内容**: AI推奨を確認し、採用/上書きを決定。上書き時は理由を記録。変更は1日1回にまとめる。
- **推奨パラメータ（初期値）**: 15分
- **システム対応**: F-DP-01 / F-DP-03

### P-04 日次: 現場共有
- **種別**: アクション
- **内容**: 当日〜3日の方針（残室の売り方・ウォークイン価格・アップセル目標）をフロント・予約に共有。
- **推奨パラメータ（初期値）**: 5分

### P-05 週次: RM会議アジェンダ
- **種別**: アクション
- **内容**: ①先週実績と月間着地更新 ②今後90日の要注意日と対策 ③競合・市場・イベント情報 ④チャネル別ネット実績 ⑤団体・法人案件のディスプレイスメント判断 ⑥アラート対応状況。60分以内。
- **推奨パラメータ（初期値）**: 60分
- **システム対応**: F-DP-04 / F-ANA-02 / F-SET-05

### P-06 週次: 予測精度チェック
- **種別**: アクション
- **内容**: 先週の予測（7日前・前日）と実績のMAPE・Biasを確認。Biasが同方向に3週続いたら補正係数を見直す。
- **システム対応**: F-DP-05

### P-07 月次: 着地確定と要因分析
- **種別**: アクション
- **内容**: 着地を予算・前年と比較しRevPARを分解、セグメント・チャネル・曜日別に要因を特定。月次サマリー（O章の型）を作成。
- **システム対応**: F-REP-01

### P-08 月次: 設定の見直し
- **種別**: アクション
- **内容**: 重み付け、上下限ランク、需要レベル閾値、イベント影響度、コンプセットの妥当性を月1回点検。変更は監査ログに理由付きで。
- **推奨パラメータ（初期値）**: 月1回
- **システム対応**: F-DP-02 / F-SET-02 / AuditLog

### P-09 月次: 翌月〜3か月の計画
- **種別**: アクション
- **内容**: 翌月の弱い日・強い日を特定し、販促計画・団体営業方針・イベント登録漏れ確認を行う。
- **システム対応**: F-DP-04 / F-DP-07

### P-10 四半期: ランク表・弾力性の見直し
- **種別**: アクション
- **内容**: ランク別実績から弾力性を再推定し、ランク表の刻み・上下限を見直す。年1〜2回の価格改定判断もここで。
- **推奨パラメータ（初期値）**: 四半期
- **システム対応**: F-SET-02

### P-11 年次: 予算とカレンダー
- **種別**: アクション
- **内容**: 翌年度予算の日別配賦、祝日・連休マスタの更新、繰り返しイベントの翌年登録、法人契約の見直しを年度末（1〜3月）に行う。
- **推奨パラメータ（初期値）**: 1〜3月
- **システム対応**: F-SET-04 / Event

### P-12 引き継ぎと記録
- **種別**: 注意
- **内容**: 全ての判断は「日付・事象・判断・理由・結果」で記録し、担当交代時に判断の再現ができる状態を保つ。記録のないRMは属人化して崩れる。
- **システム対応**: AuditLog / notes


## Q. 判断の経験則

関連機能・データ: 運用全般

### Q-01 値上げ余地の典型形
- **種別**: 判定ルール
- **内容**: 予測稼働が高く（≥85%）ADRが同曜日平均以下の日は、値上げ余地が最も大きい。+2ランクから始めて反応を見る。
- **推奨パラメータ（初期値）**: OCC≥85% & ADR≤平均
- **システム対応**: F-DP-01

### Q-02 速いピックアップは原因を先に
- **種別**: 判定ルール
- **内容**: ピックアップが急伸したら値上げの前に原因（イベント・団体・競合売止め・OTAセール）を1分で確認。原因が構造的（イベント）なら大きく、一時的（セール）なら小さく上げる。
- **システム対応**: N / F-DP-07

### Q-03 値下げの評価軸
- **種別**: 判定ルール
- **内容**: 値下げの成否は「予約が入ったか」ではなく「RevPAR（ネット）が上がったか」。稼働+10ptで単価−15%は失敗。
- **システム対応**: A / F-DP-01

### Q-04 直前値下げは自分のカーブを壊す
- **種別**: 注意
- **内容**: 直前値下げが続くとゲストが待つようになり、早期予約が減ってカーブ全体が後ろ倒しになる。3か月単位で早期予約比率の推移を見る。
- **推奨パラメータ（初期値）**: 早期予約比率を監視
- **システム対応**: F-DAILY-01

### Q-05 残り数室は最も高い在庫
- **種別**: 判定ルール
- **内容**: 残在庫5%以下は最後まで上限維持。直前に空室で終わるリスクより、安く売って直前需要を逃す損失の方が大きい（弾力性が低い局面）。
- **推奨パラメータ（初期値）**: 残 ≤5%
- **システム対応**: F-DP-01

### Q-06 キャンセル期限の見かけの動き
- **種別**: 注意
- **内容**: 無料キャンセル期限の直前は予約が増え、直後にキャンセルが出る。期限前後3日のピックアップはネットで見るまで判断しない。
- **推奨パラメータ（初期値）**: 期限 ±3日
- **システム対応**: BookingCurveData

### Q-07 満室の翌年は強気に
- **種別**: 判定ルール
- **内容**: 満室で断った需要は記録に残らない。前年満室日は「前年実績＋10〜30%」の需要として翌年の初期価格を1〜2ランク上げてスタートする。
- **推奨パラメータ（初期値）**: +1〜2ランク
- **システム対応**: C（制約なし需要）

### Q-08 団体価格は日替わり
- **種別**: 判定ルール
- **内容**: 団体の相場は「その日の個人需要の強さ」で決まる。年間一律の団体料金は繁忙日で大きく損をする。ハードルレートを日別に出す。
- **システム対応**: K / F-SET-05

### Q-09 イベントは周辺に波及する
- **種別**: 判定ルール
- **内容**: 自館に直接来ないイベントでも、商圏全体の在庫が減れば流入が来る。半径3〜5kmの大型施設の日程は全て登録対象。
- **推奨パラメータ（初期値）**: 半径3〜5km
- **システム対応**: H / F-DP-07

### Q-10 閑散日は露出→条件→価格
- **種別**: 判定ルール
- **内容**: 弱い日の手当ては露出（順位・写真・プラン名）→条件（早割・連泊・朝食）→価格の順。価格から始めると単価もブランドも戻らない。
- **システム対応**: E / J

### Q-11 日曜泊の境目
- **種別**: 判定ルール
- **内容**: 週末が強い施設ほど日曜泊（週末価格から平日価格への境目）の設定で収益差が出る。日曜を平日と同一視せず「日曜専用ベースランク」を持つ。
- **推奨パラメータ（初期値）**: 日曜ベースランク
- **システム対応**: F / Hotel.weekendDays

### Q-12 平均は嘘をつく
- **種別**: 注意
- **内容**: 月平均が予算どおりでも、火・水が崩れて金・土で補っている等の偏りがある。必ず曜日別・日別に割って見る。
- **システム対応**: A / F-ANA

### Q-13 競合は鏡ではなく風向計
- **種別**: 注意
- **内容**: 競合価格は「自館がいくらで売るべきか」ではなく「市場の需要がどちらに向いているか」を示す。追従ではなく読解に使う。
- **システム対応**: I

### Q-14 予測は当てるものではなく直すもの
- **種別**: 注意
- **内容**: 予測の価値は精度そのものより「毎日更新され、外れた理由が記録され、次に活かされる」こと。外れを隠さず記録する文化が精度を上げる。
- **システム対応**: C / M

### Q-15 小さく速く何度でも
- **種別**: 判定ルール
- **内容**: 価格変更は大きく1回より小さく何度も。1日1回・±1〜2ランクの積み重ねが、大幅変更1回より取りこぼしが少なくリスクも小さい。
- **推奨パラメータ（初期値）**: ±1〜2ランク/日
- **システム対応**: E

### Q-16 上げるのは早く、下げるのは遅く
- **種別**: 判定ルール
- **内容**: 上振れの兆候（ペース+、競合売止め）には即日反応し、下振れの兆候には原因確認を挟んで1〜2日待つ。非対称に動くのが正しい。
- **システム対応**: E


## R. アンチパターン

関連機能・データ: 運用全般

### R-01 早売りしすぎ
- **種別**: アンチパターン
- **内容**: 繁忙日を早期の安値で埋め、直前の高単価需要を逃す。→ 繁忙日ほど段階的に値上げし、早割・安値プランを早期に停止。90日超の低価格OTBを監視。
- **システム対応**: E / K

### R-02 直前の投げ売り
- **種別**: アンチパターン
- **内容**: 直前に大きく値下げして稼働を買う。→ 3日前以内の値下げは残在庫≥20%かつ−2ランク以内に制限。常態化をアラートで可視化。
- **システム対応**: E / N

### R-03 競合追従の値下げ合戦
- **種別**: アンチパターン
- **内容**: 1社の値下げに全員が追従し市場単価が崩れる。→ 需要レベルC以上なら追従しない。追従度は参照度であり自動追従ではない。
- **システム対応**: I / E

### R-04 平均値の罠
- **種別**: アンチパターン
- **内容**: 月平均で判断し曜日・日別の崩れを見逃す。→ 日別・曜日別・セグメント別に分解して見る。
- **システム対応**: A

### R-05 イベント登録漏れ
- **種別**: アンチパターン
- **内容**: 大型イベント日を通常価格で売り切る。→ 繰り返しイベントの自動候補生成、90日前登録期限、未登録疑いアラート。
- **システム対応**: H / N

### R-06 レートパリティ崩れ
- **種別**: アンチパターン
- **内容**: チャネル間で価格がずれ、OTA順位低下・ベストレート違反。→ ±3%監視アラート、サイトコントローラー月次点検。
- **システム対応**: J / N

### R-07 部屋タイプ放置
- **種別**: アンチパターン
- **内容**: 下位タイプだけ完売し上位が余る。→ 繁忙日はタイプ間価格差を縮めアップセル、稼働差20ptで価格差見直し。
- **システム対応**: L

### R-08 記録なしの価格変更
- **種別**: アンチパターン
- **内容**: 理由のない変更が積み重なり検証も引き継ぎもできない。→ 全変更に理由を必須化し監査ログに残す。
- **システム対応**: P / AuditLog

### R-09 予測の過信
- **種別**: アンチパターン
- **内容**: 低確信度の予測で大きく動かして外す。→ 確信度と変更幅を連動（conf<0.6 は ±1ランク）、限定表現を付ける。
- **システム対応**: C / O

### R-10 団体の年間一律料金
- **種別**: アンチパターン
- **内容**: 繁忙日も閑散日も同じ団体料金で受け、繁忙日の個人需要を押し出す。→ 日別ハードルレートとディスプレイスメント分析。
- **システム対応**: K

### R-11 グロスOTBでの判断
- **種別**: アンチパターン
- **内容**: キャンセル前の予約数でピックアップを見て、直前の在庫戻りに驚く。→ OTBはネット保存、キャンセル期限前後はネットで判断。
- **システム対応**: B

### R-12 前年同日付の比較
- **種別**: アンチパターン
- **内容**: 365日前の同日付と比べて曜日ずれで誤読する。→ 364日前の同曜日、祝日は暦位置で対応付け。
- **システム対応**: A / C

### R-13 アラートの氾濫
- **種別**: アンチパターン
- **内容**: 重要度の低い通知が多すぎて全部無視される。→ 表示はLevel 4以上、24時間重複排除、対応率で閾値を見直す。
- **システム対応**: N

### R-14 ブラックボックスの推奨
- **種別**: アンチパターン
- **内容**: 理由のない推奨価格は現場に採用されず、上書きが常態化する。→ 推奨に内訳（基準・残在庫・ペース・競合・イベント）を必ず添える。
- **システム対応**: E / O


## 用語集

| 用語 | 意味 |
|---|---|
| OCC（稼働率） | 販売客室数 ÷ 販売可能客室数（OOO除外） |
| ADR | 平均客室単価。客室売上 ÷ 販売客室数（税・付帯除外） |
| RevPAR / REV-Per | 販売可能客室1室あたり売上 = OCC × ADR |
| TRevPAR | 総売上（料飲等含む）÷ 販売可能客室数 |
| GOPPAR | 営業総利益 ÷ 販売可能客室数 |
| DOR | 1室あたり利用人数 = 宿泊人数 ÷ 販売室数 |
| 客単価（人単価） | 客室売上 ÷ 宿泊人数 = ADR ÷ DOR |
| ネットADR / ネットRevPAR | チャネル手数料控除後のADR / RevPAR |
| OTB（On The Books） | 現時点で確定している予約（キャンセル控除後） |
| ピックアップ | 一定期間に積み上がった予約の増分（ネット） |
| ペース | 同リードタイム時点の前年（STLY）とのOTB差 |
| STLY / STLW | Same Time Last Year / Last Week。同リードタイム時点の前年・前週比較 |
| ブッキングカーブ | 宿泊日に向けたOTBの積み上がり曲線（リードタイム軸） |
| 目標カーブ | 過去同等日・予算から作る基準のブッキングカーブ |
| リードタイム | 予約日から宿泊日までの日数 |
| 残需要 | 予測最終需要 − 現在OTB |
| 制約なし需要（Unconstrained Demand） | 満室・売止めがなかった場合の本当の需要 |
| フォーキャスト | 着地見込みの予測（日別・月別） |
| MAPE / Bias | 平均絶対誤差率 / 平均符号付き誤差（予測の精度と癖） |
| 需要レベル | A〜Eの5段階の需要強度区分 |
| 料金ランク | 40段階の価格帯区分（R01〜R40）。1P〜4Pの価格を持つ |
| BAR（Best Available Rate） | その時点で誰でも予約できる最良価格。変動価格の基準 |
| レートフェンス | 返金不可・早期予約など条件による料金の仕切り |
| レートパリティ | チャネル間で同条件の価格を揃えること |
| 価格弾力性 | 価格変化率に対する需要変化率。|値|>1で値下げが売上増 |
| Last Room Value（LRV） | 残り最後の1室の価値。直前需要の期待単価 |
| ハードルレート | 団体・大口を受け入れるための最低価格（押し出す個人需要の単価） |
| ディスプレイスメント | 大口予約が押し出す他の需要（機会損失） |
| ウォッシュ | 団体ブロックのうち消化されない割合 |
| カットオフ | 団体ブロックの室数確定期限 |
| LRA / NLRA | 法人契約で最終1室まで契約価格販売の義務あり / なし |
| Min LOS | 最低泊数制限 |
| CTA / CTD | 到着日クローズ / 出発日クローズ |
| クローズアウト | 特定チャネル・プランの販売停止 |
| オーバーブッキング | ノーショーを見込み販売可能数を超えて受けること |
| ノーショー | 予約したまま連絡なく現れないこと |
| OOO（Out of Order） | 故障・改装で販売不能の客室 |
| コンプセット | 比較対象とする競合ホテル群（4〜6社） |
| MPI / ARI / RGI | コンプセット対比の稼働・単価・RevPARインデックス（100=市場並み） |
| ポジション指数 | 自館価格 ÷ コンプセット中央値 |
| 実効手数料 | 基本手数料＋ポイント原資＋決済手数料＋広告費の合計率 |
| OTA | オンライン旅行会社（楽天トラベル、じゃらん、Booking.com等） |
| サイトコントローラー | 複数OTAの在庫・料金を一元管理するツール |
| PMS / RMS | ホテル管理システム / レベニューマネジメントシステム |
| セグメント | 客層の区分（ビジネス・レジャー・インバウンド・団体・法人）。チャネルとは別軸 |
| アップセル | 上位部屋タイプ・付帯への誘導販売 |
| ウォークイン | 予約なしの当日来館客 |
| インバウンド | 訪日外国人需要 |
| KPIスナップショット | 月初・週次等の時点でKPIを凍結保存したもの |
| 確信度 | 予測の信頼度（0〜1）。データ充足・過去精度・異常要因で算出 |
