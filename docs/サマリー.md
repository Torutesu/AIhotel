## 1. 要約

ホテル向けの収益管理・価格最適化SaaSである。要件定義工程では業務要件82件・機能要件50件・業務フロー10件が整理された。現在の実装は、単一ホテルのデータをもとにダッシュボード表示、需要予測（ルールベース）、価格カレンダー、各種分析を提供する段階にある。

**要件全体に対する実装の到達度は2〜3割程度である。** 機能要件50件のうち、画面から利用できる状態まで到達しているのは10件前後にとどまる（部分実装を含めた数え方により幅がある）。未達の中心は外部システム連携（PMS・サイトコントローラー・OTA）と競合価格収集であり、いずれも要件定義工程で仕様が確定しておらず、着手できる状態にない。

1stリリース予定日（2026/10/01）まで約2か月であるが、後述する3つの論点が未解決のままである。スケジュールの再確認を要する。

## 4. 対応を要する論点

設計文書の作成過程で、判断を要する事項が3件見つかった。いずれも実装の欠陥ではなく、要件・仕様の未確定に起因する。

### 4.1 価格戦略の重み付けが価格算出に接続されていない（最重要）

価格戦略の重み（稼働率・ADR・競合、合計100%）は、保存・監査・入力検証まで実装されているが、**価格を算出するロジックから参照されていない**。需要予測は予測稼働率のみから推奨ランクと推奨価格を導出しており、利用者が重みを変更しても結果は変わらない。

これは本プロダクトの中核価値である「価格最適化」（BR-004、FR-025）の実質的な未達を意味する。設定画面が存在し値を保存できるため、外形上は機能しているように見える点に注意を要する。

対応には、ADR実績と競合価格をそれぞれ料金ランクへ写像する方式の決定が必要であり、要件側の確認事項である。

### 4.2 権限体系が要件と実装で食い違っている

機能要件 FR-003 / FR-005 は「本部管理・管理者・オペレーター・閲覧のみ」の4権限を前提としている。一方、確定済みのロールは ADMIN / MANAGER / OPERATOR の3種であり、「本部管理」と「閲覧のみ」に対応するものがない。

加えて、現在の ADMIN はテナントを越えて全ホテルへアクセスできる実装である（`requireHotelAccess` のバイパス）。これはシステム提供側の運用を想定した仕様だが、「本部管理」を ADMIN で代用する場合、顧客企業の本部が他社データにも到達しうる構造となる。権限体系の確定は、デモ配布（FR-040〜044）の設計にも影響する。

### 4.3 テナント分離と認可のテストが存在しない

マルチテナントSaaSにおいて最も事故コストが高い領域であるにもかかわらず、テナント分離（`requireHotelAccess`）とロール別認可（`requireRole`）を検証するテストが1件もない。現状のテスト43件はすべて純粋関数・検証スキーマ・認証ユーティリティを対象とした単体テストであり、API結合テストの基盤自体が未整備である。

現在の実装が正しいかどうかではなく、**今後の変更で壊れても気付けない**ことが問題である。テスト仕様書 §5.2 に TC-T（8ケース）および TC-R（10ケース）として仕様を定義した。

## 5. 要件面の指摘

### 5.1 機能要件から参照されていない業務要件が10件ある

業務要件82件のうち、機能要件から参照されているのは72件である。未参照の10件には優先度「高」が3件含まれる。

| BR-ID | 内容 |
| --- | --- |
| BR-006 | 団体客影響を加味した販売配分 |
| BR-013 | 施設側のデータ取得手順を標準化する |
| BR-067 | 団体管理の画面を追加する |

BR-067 は画面追加の要求でありながら、対応する機能要件が存在しない。団体管理はプロジェクトスコープに明記された追加項目であるため、要件定義工程への差し戻しが妥当である。

### 5.2 「※要確認」が広範に残っている

業務要件・機能要件の大半に「※要確認」が付記されている。特に外部連携（連携先製品、方式、頻度、データ粒度、テスト環境の提供可否）と競合価格収集（対象サイト、公式APIの有無、スクレイピング可否）は、確定しなければ設計に着手できない。

外部連携と競合価格収集は機能要件50件のうち13件を占める。ここが未確定である限り、実装到達度は現状から大きく前進しない。

### 5.3 文書間の不整合

`AGENTS.md` は PDF/Excel 出力を「未実装（Phase 4）」に分類しているが、実際にはバックエンドに実装が存在する（ExcelJS / pdfkit、日本語フォント同梱）。ただしフロントエンドのレポート画面はAPIを呼んでおらず、利用者からは到達できない。同様に、KPI比較・月間着地シミュレーション・需要予測再計算・レビュースコアなど、バックエンドにあってフロントエンドから呼ばれていないエンドポイントが複数ある。

「実装済み」の定義を、バックエンド単体ではなく画面から利用可能な状態に統一することを推奨する。

## 6. 推奨する進め方

優先順位は、事故コストと、後戻りの大きさで決めた。

**第1優先: テナント分離・認可のテスト整備**
API結合テストの基盤を用意し、TC-T と TC-R を実装する。機能追加より先に行う。テストがない状態で機能を積むほど、後の検証コストが上がる。

**第2優先: 未確定事項の確定**
特に §4.1（価格算出への重み組み込み）と §4.2（権限体系）。いずれも実装の前提であり、確定しないまま進めると作り直しになる。外部連携（Q-02、Q-03）と競合価格（Q-04）は、施設側・外部サービス側の回答待ちとなるためリードタイムが長い。確認の着手を早めることが必要である。

**第3優先: 画面から到達できない機能の接続**
バックエンド実装済みの機能をフロントエンドへ接続する。新規開発より工数が小さく、提供機能を増やせる。

**第4優先: 未実装機能の実装**
団体管理、デモ配布管理は仕様確定後に着手可能。外部連携・競合価格収集は仕様確定待ち。

### スケジュールについて

1stリリース 2026/10/01 まで約2か月である。外部連携と競合価格収集の仕様が未確定であることを踏まえると、これらを含めた1stリリースは現実的でない。リリース範囲を、現在稼働している収益管理・分析機能に限定し、外部連携をフルローンチ（2026/12）へ送る前提で再調整することを推奨する。その場合も、データ投入手段（現状は seed のみ）の確保が別途必要となる。
