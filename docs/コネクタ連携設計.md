## 1. 前提・制約

- **公式API・CSV連携は使えない想定**。読み書きはすべて画面操作（ブラウザ自動化 / Windows UIオートメーション）で行う。
- リンカーンには **IP制限** がかかっており、操作はクライアントのPC内からのみ可能。
- したがってクラウド側（backend）から対象システムへ直接アクセスする構成は成立しない。
- 扱う主データは **料金ランク**（`PriceRank`: hotelIdごとに rank 1〜40、1〜4名料金）。
  - リンカーン: 読み取り＋書き込み
  - ねほっぷす: 書き込み（読み取りは書き込み後の反映確認に必要な最小限のみ）

## 2. 全体アーキテクチャ

**クライアントPC常駐の「コネクタエージェント」＋ クラウド側ジョブキュー（Pull型）**

```
[SaaS backend]                          [クライアントPC]
 SyncJob キュー  <-- 外向きHTTPSポーリング --  コネクタエージェント(常駐)
   |  結果POST(zod検証→upsert→AuditLog)        |- Playwright ……… リンカーン(Web)
   v                                           |- FlaUI CLI ……… ねほっぷす(UIA)
 PriceRank / Alert / AuditLog
```

- エージェント→backend の**外向きHTTPSのみ**。クライアント側FWにインバウンド開放は不要。
- リンカーンへのアクセスはクライアントPCのIPから行われるため、IP制限を自然に満たす。
- Web（リンカーン）もネイティブ（ねほっぷす）も、同一PC上の同一エージェントが担当する。

### 実行方式の原則

**決定的スクリプト（Playwright / UIA）を主経路、AI（computer use）は例外処理のフォールバック**とする。
料金の書き込みは金額を扱う不可逆操作であり、再現性と監査可能性を最優先する。AIの用途は:

- セレクタ失敗時のスクリーンショット/DOM診断（「画面の何が変わったか」の特定と修正案の生成）
- 初期構築時の操作手順の洗い出し補助

定常同期をAIに直接操作させることはしない（コスト・速度・再現性で不利）。

### 自律運転の原則

本連携は**無人運転が既定**。READもWRITEも人の承認を挟まず自動で回し、安全はガードレール（§15）と
読み戻し検証（§10.4）が担う。人間が関与するのは自動で安全に進められない例外時のみで、
その通知先は原則**開発側（SaaS運営）**とする（§14）。ホテルスタッフに日常運用の負担を求めない。

人間の関与が残る場面は次の3つだけ:
1. 開発側の例外対応（認証失敗・検証不一致・自己修復失敗などの通知を受けての対処）
2. クライアントPC上の物理作業（初回セットアップ、資格情報の再入力、PC交換時のペアリング）
3. 長期停止インシデント時の手動反映モード発動判断（§13.5 — デフォルト無効）

dry-run・WRITE凍結は導入初期と障害対応時の一時的な運転モードであり、定常はフル自動。

### 既製RPA製品を採用しない理由

UiPath / Power Automate Desktop / WinActor 等は1〜2施設の社内利用なら成立するが、
SaaSとして複数クライアントに配布する場合、フローの配布・更新・バージョン管理・SaaS側との
連携がすべて製品外の運用になる。自前エージェントに自動化ロジックを同梱し、
バックエンドから定義・更新を配信する方式を採る。

## 3. 対象システム別方式

### 3.1 リンカーン（Web）— Playwright

- headed Chromium を**永続プロファイル**（`launchPersistentContext`）で起動しログインセッションを維持。
  2段階認証・画像認証がある場合は初回のみ人がログインし、以後セッション維持で運用。
- **読み取り**: 料金ランク画面のDOMを構造化JSONに正規化 → backendへPOST →
  `validators.ts` のzodスキーマで検証 → `PriceRank` へupsert（tenantId/hotelId必須）→ 差分を `AuditLog`。
- **書き込み**: フォーム入力 → 送信 → **同一画面を読み戻して意図値と一致するか検証**（write-after-write verify）
  してからジョブをDONEにする。検証NGは FAILED＋スクリーンショット添付 → `Alert`。
- 画面が裏で叩くXHR（隠しAPI）が観測できる場合は将来の高速化候補とするが、
  まずHAR採取で観測のみ行い、採用判断は別途（認証トークンの扱い・規約リスクがあるため）。

### 3.2 ねほっぷす（ネイティブWindows）— UIオートメーション

- 最初に **UIAツリーが取得できるかの調査**を行う（Accessibility Insights for Windows / FlaUInspect）。
  - 標準的なWinForms/WPFアプリ → FlaUI で確実に自動化可能
  - 独自描画のレガシー画面 → 座標クリック＋OCR / computer use となり難易度が一段上がる
  - **この調査結果が工数を最も左右する**ため、他の実装より先に確定させる
- 実装は **FlaUIベースの小さなC# CLI** をエージェントに同梱し、子プロセスとして呼ぶ
  （例: `nehopps-writer.exe --job job.json`）。
- 書き込み後は書き込み画面の表示値を読み返す最小限の反映確認のみ実装する。

  hotel        Hotel           @relation(fields: [hotelId], references: [id], onDelete: Cascade)

  updatedAt    DateTime        @updatedAt

  @@index([tenantId])
  @@index([hotelId])
}

enum SyncDirection { READ WRITE }

model SyncJob {
  id             String        @id @default(cuid())
  tenantId       String
  tenant         Tenant        @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  hotelId        String
  hotel          Hotel         @relation(fields: [hotelId], references: [id], onDelete: Cascade)
  target         SyncTarget
  direction      SyncDirection
  idempotencyKey String        @unique // 再実行安全のための冪等キー
  payload        Json          // WRITE: 書き込む料金ランク差分 / READ: 取得範囲

// 生スナップショット（バックアップと復旧の基盤 — §13）

model SyncSnapshot {

  storageKey  String       // オブジェクトストレージのキー

  sanitized   Boolean      @default(false) // Cookie等マスク済みか（未サニタイズは閲覧不可）

## 5. API契約案（`/api/v1/connector/*`）

レスポンス形式は既存どおり `{success: true, data}` / `{success: false, error}`。
エージェント認証は既存ユーザーJWTとは**別系統のデバイストークン**（`Authorization: Bearer <deviceToken>`、
DBにはハッシュのみ）。スコープはhotel単位。

| メソッド/パス | 認証 | 用途 |
| --- | --- | --- |
| `POST /connector/devices/pair` | ワンタイムコード | デバイス登録（ADMIN/MANAGERがUIで発行したコードと交換でトークン払い出し） |
| `GET  /connector/jobs/next` | device | PENDINGジョブを1件クレーム（リース付きでRUNNINGへ。ロングポーリング可） |
| `POST /connector/jobs/:id/lease` | device | 実行中ジョブのリース延長（長時間ジョブ用） |
| `POST /connector/jobs/:id/result` | device | 実行結果報告（READデータ / 検証結果 / item単位の成否 / 失敗証跡） |
| `POST /connector/jobs/:id/artifacts` | device | スクリーンショット・DOM/HARスナップショット添付（サニタイズ済みのみ受理） |
| `GET  /connector/definitions` | device | セレクタ・操作手順定義の取得（バージョン＋署名付き） |
| `POST /connector/heartbeat` | device | 死活監視（lastSeenAt更新。途絶は `Alert`＋standbyフェイルオーバー） |
| `POST /hotels/:hotelId/sync-jobs` | user (ADMIN/MANAGER) | 手動ジョブ作成・再実行（定常のジョブはbackendのスケジューラと価格確定ロジックが自動生成）＋ `writeAuditLog()` |
| `POST /hotels/:hotelId/devices/:id/revoke` | user (ADMIN) | デバイス即時失効（kill switch）＋ `writeAuditLog()` |
| `POST /hotels/:hotelId/sync/freeze` | user (ADMIN/MANAGER) | 凍結スイッチ（自動WRITE停止/再開）＋ `writeAuditLog()` |

## 6. 壊れにくくするための運用設計

1. **セレクタ・操作手順はコードに埋め込まず、サーバー配信の定義ファイル**にする。
   画面変更時は定義のみ更新して即配信（エージェント再配布不要）。
2. **失敗時の証跡**: スクリーンショット＋DOMスナップショット（UIAはツリーダンプ）を添えてFAILED報告。
   AIによる画面差分診断の入力にもなる。
3. **dry-runモード**: 入力まで行い送信せず、入力後画面のスクショを記録・確認できるようにする。導入初期の信頼構築用。
4. **冪等・排他**: ジョブは冪等キー付き、エージェントは同時1ジョブ実行。
   書き込みは「現在値を読む→差分があるときだけ書く」で再実行安全にする。
5. **自動更新**: エージェントは起動時にbackendへバージョン確認して自己更新する（署名検証つき — §12）。
6. **認証情報の保管**: リンカーンのID/PWはクライアントPCのWindows資格情報マネージャー（DPAPI）に
   保存し、クラウドに預けない。

継続稼働・障害対応・バックアップの詳細設計は §10〜§15 を参照。

## 10. 信頼性設計 — 「取得し続け、反映し続ける」ための多層防御

### 10.1 基本原則: 単一経路で「絶対」は作れない

画面操作ベースの連携は、画面変更・認証・PC障害のどれか一つで必ず止まり得る。
したがって「絶対に取得・反映できる」は**単一経路の頑健化ではなく、フォールバックの階層**で保証する。
最下層に人間経路を組み込むことで、技術がすべて失敗しても業務としての反映は止まらない。

| 層 | 経路 | 発動条件 |
| --- | --- | --- |
| L1 | 定義ベース自動化（Playwright / FlaUI） | 通常運用 |
| L2 | 代替経路（別画面ルート・観測済みXHR） | L1のセレクタ失敗が定義切替で解決しない |
| L3 | AI自己修復: computer useで失敗時スクショ/DOMを診断 → セレクタ定義の修正案を生成 → **自動検証を通れば自動採用・配信** → L1で自動復旧 | 画面変更の検知時 |
| L4 | **手動反映モード**（§13.5）: 書き込み内容をSaaS UIにチェックリスト表示し、スタッフが手入力して完了記録。最終手段であり通常運用では発動しない（発動自体が開発側対応のインシデント） | L1〜L3が長期停止し、開発側が発動を判断したとき |

L3の要点は2つ。①「AIに画面を直接操作させて書き込む」のではなく「AIは定義を直す係、書き込みは常に
決定的スクリプト」という分離を守ること。②無人運転のため修正定義の採用も自動化するが、無条件では
採用しない: 修正定義でREADを試行し、抽出結果がzodスキーマ・妥当性チェック（件数・値域・前回取得値
との乖離）を通ったものだけを自動採用する。**WRITEへの適用はさらに保守的に、新定義でのREAD連続成功
（例: 3回）を条件とする。** 自動採用の成否はいずれも開発側へ通知し（§14）、失敗時は該当経路を保留
して開発側対応に切り替える。

### 10.2 デバイス冗長（PC障害対策）

- 1ホテルに PRIMARY / STANDBY の2台構成を推奨（STANDBYは事務PCへの同居インストールで可）。
- ジョブのクレームは常に1台のみ（リース方式により二重実行は構造的に起きない）。
- PRIMARYのheartbeatが5分途絶したらサーバーがSTANDBYへの割当に切替え、`Alert` を発報。
  復帰したPRIMARYは自動でSTANDBYに降格（スプリットブレイン防止: 割当の正はサーバー側のみが持つ）。
- 1台しか置けない施設では、PC障害＝L4（手動反映モード）へ直行し、`Alert` で明示する。

### 10.3 接続の安定化

**エージェント ⇔ backend**
- ポーリングは指数バックオフ＋ジッタ。ネット断で暴れない・復帰後に殺到しない。
- 実行結果・証跡は**まずローカルスプール（ファイル/SQLite）に永続化してから送信**。
  送信失敗は再送キューで面倒を見る。ネット断・プロセス再起動でも結果は消えない。
- 時刻はサーバー基準（エージェントのPC時計を信用しない）。

**エージェント ⇔ リンカーン**
- 各ジョブ実行前にログイン状態を確認。セッション切れは自動再ログイン（§11の認証ルールに従う）。
- アクセス頻度は人間の操作速度に律速（画面遷移に最低ウェイト）。不正検知・負荷起因のブロックを予防する。
- メンテナンス時間帯は設定で静止（定義ファイルにメンテ窓を持たせる）。

**クライアントPCの運用要件（導入時チェックリスト化する）**
- スリープ/休止無効、電源接続、Windows Update の再起動時間帯を指定。
- エージェントはWindowsサービス＋クラッシュ時自動再起動（サービス回復設定）。再起動後は自動復帰。
- 別プロセスの軽量watchdogが本体を監視し、応答停止時に再起動。
- **UIA（ねほっぷす）はロック解除されたデスクトップセッションが必須**。専用アカウントの自動ログオン＋
  物理的に安全な設置、が許容されない場合は、ねほっぷすWRITEを営業時間内（人がログイン中）の実行に限定する。

### 10.4 リトライポリシー（方向で非対称にする）

- **READ**: 冪等なのでリトライは自由。自動3回（バックオフ）→ 以降は次の定期周期へ。連続失敗は閾値で `Alert`。
- **WRITE**: 「現在値を読む → 差分確認 → 書く → 読み戻して検証」を1原子単位とする。
  - 書き込み操作の自動再実行は**検証込みで最大1回**。それ以上は `NEEDS_REVIEW` にし、当該ホテルの
    WRITEを自動凍結して開発側へ即時通知（§14）。
    二重反映・誤反映が最悪事故であり、「書けないこと」より「間違って書くこと」を恐れる。
  - **不明状態の扱い**: 送信後に応答が取れず「書けたか分からない」場合は、再実行せず必ずREADで実際の値を
    確認してから判断する。確認できるまでそのホテルのWRITEはブロック。
  - 部分失敗（40ランク中30件成功等）: `result` にitem単位の成否を記録し、再開ジョブは未完了itemのみ実行。
- ジョブは**リース方式**: クレーム時に `leaseExpiresAt` を設定し、期限までに延長も結果報告もなければ
  サーバーが回収する。READはPENDINGへ戻して自動再割当、WRITEは上記の不明状態手順を経てから戻す。

### 10.5 データ鮮度SLO（古いデータで意思決定させないガード）

`HotelSyncState.lastSuccessfulReadAt` を基準に:

| 経過 | 挙動 |
| --- | --- |
| 〜6時間 | 正常。UIに最終同期時刻を常時表示 |
| 6時間超 | UIで「stale」表示（バッジ） |
| 12時間超 | `Alert`（警告） |
| 24時間超 | AI価格推奨の入力から除外し、推奨画面に「実勢データ未取得」を明示（古いランクを前提に推奨を出さない） |

## 11. エラー分類と対応マトリクス

表中の `Alert` はテナントUIへの表示に加えて、深刻度に応じた開発側通知（§14）を必ず伴う。

| 事象 | 検知 | 自動対応 | エスカレーション |
| --- | --- | --- | --- |
| ネットワーク断 | ポーリング/送信失敗 | バックオフ再試行＋ローカルスプール温存 | 30分継続で `Alert` |
| セッション切れ | ジョブ前チェック | 自動再ログイン（**1回だけ**） | 失敗で即停止＋ `Alert` |
| 認証失敗（PW変更・ロック疑い） | ログインエラー画面判定 | **即停止。2回目を試さない**（アカウントロックを絶対に自分で起こさない） | `Alert`＋資格情報再設定フロー（PC側で再入力） |
| CAPTCHA・不正アクセス検知 | 画面判定 | 停止＋スクショ保全 | `Alert`。人が解除し、アクセス頻度設定を見直す |
| 画面変更（セレクタ不一致） | 要素未検出＋画面構造ハッシュの差分 | 該当ジョブ保留＋L3自己修復を自動実行（自動検証を通れば自動復旧） | 自己修復の成否を開発側へ通知。失敗・長期化は開発側対応、必要ならL4 |
| 対象システムのメンテ/障害 | エラー/メンテ画面判定・メンテ窓設定 | 静止して窓明けに自動再開 | 想定外の長期化で `Alert` |
| PC電源断・再起動 | heartbeat途絶（5分） | STANDBYへフェイルオーバー（§10.2）／復帰時に自動レジューム | STANDBY無し構成は `Alert`＋L4 |
| エージェントクラッシュ | watchdog／リース期限切れ | サービス自動再起動。RUNNINGジョブはリース回収 | 頻発（1日3回超）で `Alert` |
| 書き込み検証不一致 | 読み戻し比較 | 自動リトライ1回 → `NEEDS_REVIEW`＋当該ホテルWRITE自動凍結 | 開発側へ即時通知＋PRE_WRITEスナップショットからロールバック提案（§13.2） |
| スタッフの同時操作競合 | 書き込み直前の現在値がジョブ生成時点の前提値と不一致 | 書き込み中断（勝手に上書きしない）→ 最新値を再READし価格ロジックに再入力してジョブを自動再生成（ガードレール内なら自動続行） | ガードレール外になった場合のみ凍結＋開発側通知 |
| 定義配信の不整合 | 定義バージョン/署名検証NG | 旧定義で継続 or 停止 | `Alert` |

## 12. セキュリティ設計（脅威モデルと対策）

**守る資産**: ①リンカーン/ねほっぷすの資格情報 ②デバイストークン ③料金データ ④証跡（スクショ/HAR/DOM）

| 脅威 | 対策 |
| --- | --- |
| クライアントPCの盗難・マルウェア | 資格情報はDPAPI（ユーザー/マシン束縛）でクラウドに置かない。トークンはhotel単位スコープのみで、漏れても他テナントに波及しない。`revoke` APIで即時失効（kill switch） |
| デバイストークン漏洩・なりすまし | DBはSHA-256ハッシュのみ（`hashToken()` 踏襲）。90日ローテーション。デバイス単位rate limit。ジョブ結果のzod検証＋ホテルスコープ外データは拒否。異常頻度・異常IPで `Alert`＋自動失効 |
| 証跡に含まれる秘密情報 | エージェント側でアップロード前にサニタイズ（Cookie / Authorization / Set-Cookie / 既知の資格情報文字列をマスク）。未サニタイズはbackendが受理しない。スクショは個人情報が写り得る前提で、閲覧は当該hotelのADMIN/MANAGERのみ・保持期限で自動削除（§4 `deleteAfter`） |
| backend侵害 | 最大の防御は「資格情報をクラウドに保管しない」設計そのもの。SyncJob payloadに含まれるのは料金データのみ |
| 中間者攻撃 | TLS必須。エージェントに配布するbackendのCA/証明書ピンニングを検討 |
| エージェント自動更新の乗っ取り（供給網） | 更新パッケージとセレクタ定義に署名を付け、エージェントは**署名検証してから適用**。検証NGは現行版で継続＋ `Alert` |
| 内部不正・誤操作 | 手動操作（手動ジョブ・凍結解除・ロールバック・デバイス失効）は `requireRole('ADMIN','MANAGER')`＋`writeAuditLog()`。自動生成ジョブもガードレール検査（§15）を通り、全WRITEにPRE/POSTスナップショットが残るため事後検証可能。ペアリングコードは10分有効・1回限り |

## 13. バックアップと復旧

「経路」「データ」「デバイス」「業務」の4面でバックアップを持つ。

1. **データ（re-ingest可能性）**: READは正規化前の生HTML＋抽出JSONを `SyncSnapshot(READ_RAW)` として
   オブジェクトストレージに保管する。パーサー不具合や正規化ロジックの改修時に、**過去分を再パースして
   `PriceRank` を復元できる**。DBデータが壊れてもソースから再構築可能。
2. **書き込みのロールバック**: WRITE実行前に必ず現在値を `PRE_WRITE` スナップショットとして保存。
   誤反映が起きたら「前値に戻すWRITEジョブ」をワンクリック生成できる（新規入力ではなく記録からの復元
   なので、ロールバック自体も安全）。`POST_WRITE` と合わせて反映の前後が常に証跡として残る。
3. **経路**: §10.1 の L1→L4 フォールバック階層。
4. **デバイス**: STANDBY機（§10.2）。エージェントの正となる状態（定義・ジョブ・スコープ）はすべて
   サーバー側にあるため、PC交換時は再インストール＋ペアリングのみで完全復旧する。PC側に失って困る
   状態を持たせない（資格情報のみ再入力が必要 — これは設計上クラウドに置かないため）。
5. **手動反映モード（最終バックアップ = 業務継続）**: 自動反映の長期停止時に、システムが確定した
   WRITE内容をSaaS UIにチェックリスト表示し、スタッフが手入力して完了チェック → `AuditLog` 記録。
   自動化復旧後は必ずREADを実行し、手入力結果とシステム上の期待値の差分を検出して整合を確認する。
   無人運転の原則（§2）により**デフォルト無効**とし、発動は開発側の判断（インシデント対応）とする。
6. **凍結スイッチ**: hotel単位で自動WRITEを一時停止（繁忙期・障害対応時）。READは止めない。

## 14. 監視と開発側通知（Ops Alerting）

無人運転の成立条件は「取得・反映が止まったことを**開発側が確実に・すぐ知れる**こと」。
通知の一次宛先は開発側（SaaS運営）であり、テナントUIの既存 `Alert`／連携ステータスウィジェットは
補助的な可視化と位置づける。

### 14.1 検知は二系統（イベント駆動＋デッドマン方式）

1. **イベント駆動**: エージェントが報告してくる失敗（ジョブFAILED、検証不一致、認証失敗など）。
2. **サーバー側の定期スイープ（デッドマン方式）**: heartbeat途絶・鮮度SLO超過・PENDINGジョブ滞留は
   「**報告が来ないこと自体が異常**」なので、エージェントからのイベントでは検知できない。
   backendの定期スイープ（5分間隔）が `HotelSyncState` / `AgentDevice.lastSeenAt` / ジョブキューを
   走査して検知する。**「取得ができなくなった」の検知はこのスイープが本体**であり、
   エージェントの生存に依存しない。

### 14.2 通知チャネルと深刻度ルーティング

チャネルは Slack Incoming Webhook（主）＋メール（副）。宛先・トークンは `src/lib/config.ts` 経由で
設定する（例: `OPS_SLACK_WEBHOOK_URL` / `OPS_ALERT_EMAIL`。`process.env` 直接参照禁止の規約どおり）。

| 深刻度 | 通知タイミング | 対象事象 |
| --- | --- | --- |
| SEV1（即時通知） | 検知した瞬間 | 認証失敗（自動停止済み）/ CAPTCHA・不正検知ブロック / 書き込み検証不一致（自動凍結済み）/ 全デバイスheartbeat途絶 / 鮮度24時間超 / 定義・更新の署名検証NG |
| SEV2（1時間以内に集約通知） | 集約ウィンドウごと | 鮮度12時間超 / READ連続失敗が閾値超過 / L3自己修復の失敗 / フェイルオーバー発生 / スプール滞留 |
| SEV3（日次ダイジェスト） | 毎朝1通 | 単発の失敗と自動回復 / L3自己修復の成功報告 / リトライ統計 / トークンローテーション期限予告 |

### 14.3 通知の中身（通知だけで一次判断がつくこと）

テナント名・ホテル名 / 対象システム（LINCOLN/NEHOPPS）/ 事象と深刻度 / 最終成功時刻と経過 /
自動対応の実施内容（凍結した・フェイルオーバーした等）/ 失敗証跡（スクショ・ジョブID）への管理画面リンク /
対応runbookへのリンク。開発側が通知を開いた時点で「何が起き、システムが何をどこまで自動対応済みで、
人は何をすべきか」が判る形にする。

### 14.4 通知の抑制と解決通知

- 事象単位のdedupeキー（hotel × 事象種別）でクールダウン管理。同一事象の再通知は
  **状態が変化したとき**（悪化＝深刻度昇格、または回復）のみ。鳴りっぱなしで麻痺させない。
- 回復時は必ず解決通知（resolved）を送る。「直ったかどうか分からない」を残さない。
- 通知送信自体の失敗はログ＋次回スイープで再送（通知経路も単一障害点にしない。SEV1はSlack＋メール両送）。

### 14.5 メトリクスとSLO

**メトリクス（hotel単位）**: `lastSuccessfulReadAt` 経過時間 / ジョブ成功率 / 連続失敗数 /
実行時間中央値 / heartbeat / 画面変更検知回数 / L3自己修復の成功率と所要時間

**SLO（初期目標。運用実績で調整）**
- 料金ランク鮮度: 6時間以内（§10.5）
- WRITE反映: 価格確定から30分以内（手動反映モード時を除く）
- READ成功率: 月間99%以上（L4期間は分母から除外して別掲）
- 「取得停止から開発側SEV1通知まで」: 10分以内（スイープ間隔5分＋通知処理）

**改善ループ**: 週次で成功率・画面変更検知・L3修復の所要時間をレポート（SEV3ダイジェストに同梱）し、
頻発する失敗パターンを定義・ガードレールに還元する。「静かに壊れている」を作らないことが
無人運転と鮮度SLOの実効性を支える。

## 15. 書き込みガードレール（誤反映の影響最小化）

無人運転では人の承認という防波堤がないため、**ガードレールが安全装置の主役**になる。
エージェント側とbackend側の両方で同じ制約を検査する（片側のバグ・改ざんへの防御）:

- 価格変動幅の上限: 現在値から±一定%（既定30%、hotel単位で設定）を超える書き込みはブロックし、`NEEDS_REVIEW`＋開発側通知（価格ロジックの異常出力を疑うシグナルとして扱う）
- 値域: rank 1〜40・正の整数価格・`Hotel.weekendDays` 等の既存ドメインルールとの整合
- 一括書き込みの件数上限（既定: 1ジョブ100項目）
- 対象日付が過去日でないこと・設定された先付け上限内であること
- 凍結スイッチON中のWRITEはbackendがジョブ作成自体を拒否する
