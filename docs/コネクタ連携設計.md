# コネクタ連携設計 — サイトコントローラー/PMSへの画面操作ベース読み書き

対象: TL-リンカーン（Web）・ねほっぷす（ネイティブWindowsアプリ）
ステータス: 設計確定・実装準備中（Phase 4 の「PMS/サイトコントローラー連携」に対応）

## 1. 前提・制約

- **公式API・CSV連携は使えない想定**。読み書きはすべて画面操作（ブラウザ自動化 / Windows UIオートメーション）で行う。
- リンカーンには **IP制限** がかかっており、操作はクライアントのPC内からのみ可能。
- したがってクラウド側（backend）から対象システムへ直接アクセスする構成は成立しない。
- 扱う主データは **料金ランク**（`PriceRank`: hotelIdごとに rank 1〜40、1〜4名料金）。
  - リンカーン: 読み取り＋書き込み
  - ねほっぷす: 書き込み（読み取りは書き込み後の反映確認に必要な最小限のみ）

## 2. 全体アーキテクチャ

**クライアントPC常駐の「コネクタエージェント」＋ クラウド側ジョブキュー（Pull型）**

```
[SaaS backend]                          [クライアントPC]
 SyncJob キュー  <-- 外向きHTTPSポーリング --  コネクタエージェント(常駐)
   |  結果POST(zod検証→upsert→AuditLog)        |- Playwright ……… リンカーン(Web)
   v                                           |- FlaUI CLI ……… ねほっぷす(UIA)
 PriceRank / Alert / AuditLog
```

- エージェント→backend の**外向きHTTPSのみ**。クライアント側FWにインバウンド開放は不要。
- リンカーンへのアクセスはクライアントPCのIPから行われるため、IP制限を自然に満たす。
- Web（リンカーン）もネイティブ（ねほっぷす）も、同一PC上の同一エージェントが担当する。

### 実行方式の原則

**決定的スクリプト（Playwright / UIA）を主経路、AI（computer use）は例外処理のフォールバック**とする。
料金の書き込みは金額を扱う不可逆操作であり、再現性と監査可能性を最優先する。AIの用途は:

- セレクタ失敗時のスクリーンショット/DOM診断（「画面の何が変わったか」の特定と修正案の生成）
- 初期構築時の操作手順の洗い出し補助

定常同期をAIに直接操作させることはしない（コスト・速度・再現性で不利）。

### 既製RPA製品を採用しない理由

UiPath / Power Automate Desktop / WinActor 等は1〜2施設の社内利用なら成立するが、
SaaSとして複数クライアントに配布する場合、フローの配布・更新・バージョン管理・SaaS側との
連携がすべて製品外の運用になる。自前エージェントに自動化ロジックを同梱し、
バックエンドから定義・更新を配信する方式を採る。

## 3. 対象システム別方式

### 3.1 リンカーン（Web）— Playwright

- headed Chromium を**永続プロファイル**（`launchPersistentContext`）で起動しログインセッションを維持。
  2段階認証・画像認証がある場合は初回のみ人がログインし、以後セッション維持で運用。
- **読み取り**: 料金ランク画面のDOMを構造化JSONに正規化 → backendへPOST →
  `validators.ts` のzodスキーマで検証 → `PriceRank` へupsert（tenantId/hotelId必須）→ 差分を `AuditLog`。
- **書き込み**: フォーム入力 → 送信 → **同一画面を読み戻して意図値と一致するか検証**（write-after-write verify）
  してからジョブをDONEにする。検証NGは FAILED＋スクリーンショット添付 → `Alert`。
- 画面が裏で叩くXHR（隠しAPI）が観測できる場合は将来の高速化候補とするが、
  まずHAR採取で観測のみ行い、採用判断は別途（認証トークンの扱い・規約リスクがあるため）。

### 3.2 ねほっぷす（ネイティブWindows）— UIオートメーション

- 最初に **UIAツリーが取得できるかの調査**を行う（Accessibility Insights for Windows / FlaUInspect）。
  - 標準的なWinForms/WPFアプリ → FlaUI で確実に自動化可能
  - 独自描画のレガシー画面 → 座標クリック＋OCR / computer use となり難易度が一段上がる
  - **この調査結果が工数を最も左右する**ため、他の実装より先に確定させる
- 実装は **FlaUIベースの小さなC# CLI** をエージェントに同梱し、子プロセスとして呼ぶ
  （例: `nehopps-writer.exe --job job.json`）。
- 書き込み後は書き込み画面の表示値を読み返す最小限の反映確認のみ実装する。

## 4. DBスキーマ案（未マイグレーション — 実装時に `prisma migrate dev` で生成）

```prisma
// エージェントのデバイス登録（ワンタイムコードでペアリング）
model AgentDevice {
  id           String    @id @default(cuid())
  tenantId     String
  tenant       Tenant    @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  hotelId      String
  hotel        Hotel     @relation(fields: [hotelId], references: [id], onDelete: Cascade)
  name         String    // 例: フロントPC1
  tokenHash    String    @unique // デバイストークンはSHA-256ハッシュのみ保存（hashToken()踏襲）
  lastSeenAt   DateTime?
  isActive     Boolean   @default(true)
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt

  @@index([tenantId])
  @@index([hotelId])
}

enum SyncTarget { LINCOLN NEHOPPS }
enum SyncDirection { READ WRITE }
enum SyncJobStatus { PENDING RUNNING DONE FAILED CANCELLED }

model SyncJob {
  id             String        @id @default(cuid())
  tenantId       String
  tenant         Tenant        @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  hotelId        String
  hotel          Hotel         @relation(fields: [hotelId], references: [id], onDelete: Cascade)
  target         SyncTarget
  direction      SyncDirection
  idempotencyKey String        @unique // 再実行安全のための冪等キー
  payload        Json          // WRITE: 書き込む料金ランク差分 / READ: 取得範囲
  dryRun         Boolean       @default(false) // 入力まで行い送信しない（承認UIでスクショ確認）
  status         SyncJobStatus @default(PENDING)
  result         Json?         // READ結果 / 検証結果 / 失敗時の証跡参照
  errorMessage   String?
  requestedById  String?       // 承認したユーザー（WRITEは承認必須）
  deviceId       String?
  startedAt      DateTime?
  finishedAt     DateTime?
  createdAt      DateTime      @default(now())
  updatedAt      DateTime      @updatedAt

  @@index([tenantId])
  @@index([hotelId, status])
}
```

## 5. API契約案（`/api/v1/connector/*`）

レスポンス形式は既存どおり `{success: true, data}` / `{success: false, error}`。
エージェント認証は既存ユーザーJWTとは**別系統のデバイストークン**（`Authorization: Bearer <deviceToken>`、
DBにはハッシュのみ）。スコープはhotel単位。

| メソッド/パス | 認証 | 用途 |
| --- | --- | --- |
| `POST /connector/devices/pair` | ワンタイムコード | デバイス登録（ADMIN/MANAGERがUIで発行したコードと交換でトークン払い出し） |
| `GET  /connector/jobs/next` | device | PENDINGジョブを1件クレーム（RUNNINGへ。ロングポーリング可） |
| `POST /connector/jobs/:id/result` | device | 実行結果報告（READデータ / 検証結果 / 失敗証跡） |
| `POST /connector/jobs/:id/artifacts` | device | 失敗時スクリーンショット・DOMスナップショット添付 |
| `GET  /connector/definitions` | device | セレクタ・操作手順定義の取得（バージョン付き） |
| `POST /connector/heartbeat` | device | 死活監視（lastSeenAt更新。途絶は `Alert`） |
| `POST /hotels/:hotelId/sync-jobs` | user (ADMIN/MANAGER) | ジョブ作成（WRITEは承認フロー経由のみ）＋ `writeAuditLog()` |

## 6. 壊れにくくするための運用設計

1. **セレクタ・操作手順はコードに埋め込まず、サーバー配信の定義ファイル**にする。
   画面変更時は定義のみ更新して即配信（エージェント再配布不要）。
2. **失敗時の証跡**: スクリーンショット＋DOMスナップショット（UIAはツリーダンプ）を添えてFAILED報告。
   AIによる画面差分診断の入力にもなる。
3. **dry-runモード**: 入力まで行い送信せず、入力後画面のスクショを承認UIに表示。導入初期の信頼構築用。
4. **冪等・排他**: ジョブは冪等キー付き、エージェントは同時1ジョブ実行。
   書き込みは「現在値を読む→差分があるときだけ書く」で再実行安全にする。
5. **自動更新**: エージェントは起動時にbackendへバージョン確認して自己更新する。
6. **認証情報の保管**: リンカーンのID/PWはクライアントPCのWindows資格情報マネージャー（DPAPI）に
   保存し、クラウドに預けない。

## 7. エージェント実装スタック

- 本体: **Node.js (TypeScript)**。モノレポと言語を揃え、Playwrightをそのまま搭載。
  単体exe化してWindowsサービス or タスクトレイ常駐。
- ねほっぷす操作: **FlaUI (C#) 製CLI** を同梱し子プロセス呼び出し。
- リポジトリ上は `connector-agent/` ワークスペースで管理（現状は調査ツールのみ。以降ここで育てる）。
