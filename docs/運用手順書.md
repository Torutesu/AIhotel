# 運用手順書（本番）

本番環境のデプロイ・バックアップ・監視・障害対応の手順（#86）。
クラウド（AWS / GCP など）は未確定（#21）のため、どの基盤でも同じ手順になるよう、
コンテナとマネージド PostgreSQL だけを前提に書く。基盤が決まったら、各節に基盤別の設定を書き足す。

## 1. 構成

| 要素 | 実体 | 備考 |
|---|---|---|
| frontend | `ghcr.io/<owner>/hotel-revenue-frontend`（Next.js）または Vercel | `/api/*` を backend へ中継する。前段にロードバランサ／リバースプロキシを置く |
| backend | `ghcr.io/<owner>/hotel-revenue-backend`（Express） | 複数レプリカ可。インターネットに直接公開しない |
| DB | マネージド PostgreSQL 16 | 自動バックアップと PITR を有効にする（§4） |
| 日次ジョブ | backend と同じイメージを `job daily` で起動 | スケジューラから1日1回（README「バッチ」） |
| 競合価格の取得 | backend と同じイメージを `job competitor-prices` で起動 | 変動の監視のため1日4回（JST 3:00・9:00・15:00・21:00）。3:00 の回は日次ジョブより前に終わらせる。楽天トラベルは `RAKUTEN_APPLICATION_ID` を設定したときだけ取得する（#9） |
| マイグレーション | backend と同じイメージを `migrate` で起動 | リリースのたびに1回だけ（§3） |
| ファイル保存 | S3 互換のオブジェクトストレージ（`STORAGE_DRIVER=s3`） | 月次レポートのキャッシュ。複数レプリカで共有するため本番は s3。単一レプリカの検証環境は local でよい |
| メール送信 | SMTP サーバー（`MAIL_DRIVER=smtp`） | 招待と一時パスワードの再発行を本人に届ける（#89）。未設定（none）なら管理者の画面に1回だけ表示するので、無くても運用はできる。送信ドメインの SPF / DKIM を設定しておく |

環境変数は `backend/.env.example` と `frontend/.env.example` を正とする。クライアント IP の扱い
（`TRUST_PROXY` / `TRUSTED_PROXY_HOPS`）は README「クライアント IP の扱い」を参照。

## 2. ヘルスチェック

| パス | 見ているもの | 用途 |
|---|---|---|
| `/livez` | プロセスが応答できるか（DB を見ない） | コンテナの HEALTHCHECK・liveness probe。失敗したら再起動してよい |
| `/readyz` | DB への `SELECT 1` を含む | ロードバランサの振り分け・readiness probe。失敗したら流入を止めるだけで、再起動はしない |
| `/health` | `/readyz` と同じ（互換のため） | 既存の監視設定向け |

DB が一時的に止まっても `/livez` は成功するので、コンテナの入れ替えが連鎖しない。

## 3. リリース

1. `main` にマージし、CI（型チェック・lint・テスト・マイグレーションのドリフト検出・E2E・Docker のスモークテスト）がすべて通っていることを確かめる
2. タグを打つ: `git tag v1.2.3 && git push origin v1.2.3`。`Release images` ワークフローが両イメージを GHCR に push する
3. **マイグレーションを先に、1回だけ実行する**（アプリのロールアウトより前）:
   ```sh
   docker run --rm --env-file backend.env ghcr.io/<owner>/hotel-revenue-backend:1.2.3 migrate
   ```
   - 起動時に自動で適用する `MIGRATE_ON_START=true` は、単一レプリカの検証環境だけで使う（複数レプリカが同時に適用しようとするため）
   - マイグレーションは後方互換にする（列の追加 → アプリのリリース → 旧列の削除、の順に分ける）。これで §5 のロールバックでも DB を戻さずに済む
4. backend をロールアウトする（ローリング更新。`/readyz` が成功したレプリカから流入させる）
5. frontend をロールアウトする
6. 確認: ログイン → ダッシュボードの表示 → 設定タブの表示。`/readyz` と 5xx 率を 15 分見る

## 4. バックアップとリストア

| 項目 | 要件（案。確定は #21） |
|---|---|
| 自動バックアップ | 毎日。保持 14 日以上 |
| PITR（任意の時点への復元） | 有効。保持 7 日以上 |
| RPO（失ってよいデータの時間） | 5 分（PITR の WAL 保持で満たす） |
| RTO（復旧までの時間） | 4 時間 |
| リストア訓練 | 四半期に1回。検証用 DB へ復元し、件数と最新の更新日時を確かめる |
| 暗号化 | 保存時の暗号化を有効にする（マネージド DB の設定） |

リストアの手順（どの基盤でも同じ流れ）:

1. 影響範囲と復元する時点を決める（監査ログ・アプリのログで誤操作や障害の時刻を特定する）
2. 本番とは**別の** DB インスタンスへ、その時点で PITR 復元する
3. 復元した DB で `prisma migrate status` を実行し、アプリのバージョンとマイグレーションが揃っていることを確かめる
4. 件数・最新データを確認したら、backend の `DATABASE_URL` を切り替えてローリング再起動する
5. 切り替え前の DB は調査のため一定期間残す

## 5. ロールバック

- アプリ: 1つ前のタグのイメージで backend → frontend の順にロールアウトし直す。§3 のとおりマイグレーションを後方互換にしていれば DB は戻さない
- マイグレーションそのものに問題があった場合は、修正のマイグレーションを新しく作って進める。DB を初期化する操作や手作業の DDL は行わない（AGENTS.md の禁止事項）。データを失った場合は §4 のリストア

## 6. 日次ジョブの監視

- 1ホテルでも失敗すると終了コード 1 で終わる。スケジューラの失敗通知を運用担当に届くようにする
- 翌朝に確認すること: 失敗したホテル（ログの `日次バッチに失敗しました`）、アラートの生成件数、期限切れトークンの削除件数
- 失敗したら、原因を直してから手動で `job daily` を再実行してよい（冪等）

## 6.1 外部要因ジョブ（D-13）

- `job external-signals` を1日1回、競合価格の取得（`job competitor-prices`）と日次ジョブ（`job daily`）より前に動かす（02:30 JST 目安）。
  その日の予測に新しい天気・イベントが入る
- 中身は3段で、1つの失敗で他を止めない。失敗が1つでもあれば終了コード 1
  1. 祝日: 内閣府の CSV を取り、ストレージ（`reference/jp-holidays.csv`）に保存する。サーバー・ジョブは起動時にこれを読み、同梱の一覧より新しい年を足す。
     内閣府は例年2月ごろに翌年分を出すので、出たら `node scripts/update-jp-holidays.mjs` を流して同梱の一覧（バックエンドとフロント）もコミットする
  2. 天気: 気象庁の予報（7日先まで）。ホテルの予報区（`weatherAreaCode`、無ければ都道府県から）ごとに1回取る。画面に出すときは「出典：気象庁ホームページ」を添える
  3. 外部要因エージェント: `ANTHROPIC_API_KEY` を設定したときだけ。ホテルごとに7日に1回（`EXTERNAL_AGENT_INTERVAL_DAYS`）、
     Claude が Web 検索で周辺のイベント・新規ホテル・市場の動き・過去30日の台風や災害を集めて登録する
- エージェントが登録した行は `source = agent` と根拠の URL を持つ。人が登録した行は上書きしない。誤りは画面で消してよい（次の集め直しで同じ行が戻ることがある）
- 費用の確認: `ExternalAgentRun` に検索回数・トークン数が残る。月の費用 ≒ ホテル数 × 4回 × 1回あたり（検索8回まで）
- 外へのアクセス: www.jma.go.jp・www8.cao.go.jp・api.anthropic.com に出られるようにする
- AI 解説（D-13）: `ANTHROPIC_API_KEY` を設定すると、日次ジョブ（`job daily`）がホテルごとに毎朝1回、ダッシュボードの AI 解説・
  価格の提案・外部需要の総合コメントを作る（材料は DB の事実だけで、Web 検索はしない）。失敗しても前日の解説が残り、
  ジョブは失敗にしない（ログの「AI 解説を作れませんでした」で気づく）。30日より古い解説は消す。
  分析タブのインサイト（当月の集計から）も別の呼び出しで毎朝作る（ログは「分析インサイトを作れませんでした」）
- AI チャット（D-13 — 画面右下）: `ANTHROPIC_API_KEY` を設定すると使える（未設定なら「使えません」と表示）。質問のたびにそのホテルの事実の束を
  材料に Claude API を1回呼ぶ。会話はサーバーに保存しない。費用の上限として1ユーザー・15分あたり `CHAT_RATE_LIMIT_MAX`（既定30）回まで

## 7. 監視とアラート（最低限）

収集基盤は #21 で決める（#49-6）。決まるまでも、次の条件で通知が飛ぶようにしておく。

| 条件 | 目安 |
|---|---|
| `/readyz` の失敗 | 3 回連続 |
| backend の 5xx 率 | 5 分間で 1% 超 |
| 日次ジョブの失敗 | 1 回でも |
| 競合価格の取得の「連続失敗」ログ | 1 回でも（サイトの画面・API が変わった可能性。取得処理の修正が必要。設定タブの「競合価格の取得状況」に理由が出る） |
| 「一時パスワードのメール送信に失敗しました」の警告ログ | 1 回でも（SMTP の設定・認証情報の期限切れを確認。利用者への伝達は画面表示に切り替わっているので業務は止まらない） |
| 外部要因ジョブの失敗 | 2 日続けて（天気・祝日の取得先の障害か形式の変更。エージェントの失敗は `ExternalAgentRun.errorMessage`） |
| 監査ログの `TOKEN_REUSE_DETECTED` / `ACCOUNT_LOCKED` の急増 | 1 時間で 10 件超（不正アクセスの兆候。設定タブの監査ログで確認できる） |

## 7.1 トライアル（デモ）アカウントの運用

- 発行・延長・停止・パスワード再発行・削除は、運営アカウントの設定タブ「トライアル管理（運営）」から行う
- ログイン ID は `trial-xxxxxxxx@<TRIAL_LOGIN_DOMAIN>` で自動発行する（発行時に任意の ID も指定できる）。本番では運営のドメインを設定する
- 期限（既定30日、最長90日）を過ぎると使えなくなる。期限から30日たったものは日次ジョブが自動で削除する
- デモデータは発行した日を基準に作る（過去90日の実績・今後90日の予測）。日次ジョブが予測を毎日更新するので、期限まで画面が古くならない

## 7.2 IP 制限（#12）

- テナントの管理者が設定タブ「IP アドレス制限」で、会社ごとに許可するアドレス・範囲を登録して有効にする。許可リスト外からはログイン・利用中の操作・トークン更新がすべて止まる（運営アカウントは対象外）
- 照合するのはリクエストのアクセス元 IP（`req.ip`）。ロードバランサ・リバースプロキシの内側で動かすときは `TRUST_PROXY` を正しく設定する。
  設定しないとプロキシの IP で照合され、全員が止まるか、全員が通る（README「クライアント IP の扱い」）
- 締め出し防止: 自分のアクセス元が入っていない許可リストでは有効にできない
- それでも締め出された（回線の変更でアクセス元が変わった等）ときは、運営アカウントの設定タブ「テナント管理（運営）」で「IP 制限を解除」を押す。
  許可リストは残るので、テナントの管理者が直してから有効にし直す。操作は監査ログに `IpRestriction` として残る
- ログイン失敗の監査ログの理由 `IP_NOT_ALLOWED` が急に増えたら、アクセス元の変更か、プロキシ設定の誤りを疑う

## 7.3 監査ログの保持（#49-5）

- `AUDIT_LOG_RETENTION_DAYS`（30以上）を設定すると、日次ジョブがそれより古い監査ログを削除する。未設定なら削除しない
- 保持期間はクライアント確認中（#21 D2-2。推奨は1年 = 365）。決まるまでは設定しない

## 7.4 新しいテナント・ホテルの立ち上げ（D-13）

運営と先方（テナントの管理者）の分担。目安は契約から2週間で「参考値で使い始め」、過去データの取り込みが済めば本番の判断に使う。

| 順 | 誰が | 何を | どこで |
|---|---|---|---|
| 1 | 運営 | テナント・最初のホテル・管理者を1回で作る。ホテルタイプ・都道府県・開業日（開業1年未満なら）・販売開始・週末をこの時に入れる | `POST /api/v1/platform/tenants/provision`（途中で失敗したら何も残らない） |
| 2 | 管理者 | 初回ログインでパスワードを変える。ホテルに所属する利用者（マネージャー・オペレーター）を招待する | 設定タブ「ユーザー管理」 |
| 3 | 管理者 | 初期設定シート（Excel）に、部屋タイプ・料金ランク・競合（OTA の URL）・月次予算を入れて取り込む。基本情報のシートで開業日・販売開始・週末・予報区も直せる | 設定タブ「初期設定を速くする」 |
| 4 | 管理者・運営 | 過去の日次実績（できれば2年）、過去の予約の推移、日別の予算（持っていれば）を取り込む。予約の推移は、予約明細（予約日・チェックイン日・泊数・室数・取消日）を2年分もらって作るのが一番よい（月ごとに送る） | `POST /imports/daily-data`・`/imports/reservations`（明細）か `/imports/booking-curve`（OTB のスナップショット）・`PUT /settings/daily-budgets` |
| 5 | 運営 | 毎日の予約（OTB）と実績の取り込みを自動にする（PMS・サイトコントローラーの出力を定時で受ける） | `POST /imports/otb`・`/imports/daily-data` |
| 6 | 管理者 | 価格戦略（重み・ランクの幅）を保存する | プライシングタブ |
| 7 | 運営 | 準備状況を確かめる。チェックリストの必須がそろい、予測の準備状況が learning 以上なら使い始めてよい | `GET /hotels/:id/setup-status`・`/hotels/:id/forecast-readiness` |

- 過去の予約の推移（4）が一番効く。無いと、ピックアップ型・前年ペース・似た日の予測が、毎日の取り込みを始めてから季節をひと回りするまで働かない
- 開業1年未満のホテルは、実績の基準が開業からの日数の8割になる。実績が28日に満たないうちは、ホテルタイプの典型的な予約の入り方で予測を補う（参考値）
- 天気は立ち上げの直後に取る。外部要因エージェントは次の日の外部要因ジョブで初めて動く

## 7.5 競合サイトの巡回（D-13）

| サイト | 取り方 | 状態 |
|---|---|---|
| 楽天トラベル | 公式 API（`RAKUTEN_APPLICATION_ID`） | 実装済み（実際のアプリ ID での確認待ち） |
| じゃらん | プラン一覧のページを読む（手書きの読み取り） | 2026-11-12 に実際のページで確認済み。`CRAWL_ENABLED_SOURCES=jalan` で動く |
| Booking.com・Agoda | ブラウザで描画し、AI（Claude）で料金を読む | 実際のページは未確認（Playwright 入りのイメージと `ANTHROPIC_API_KEY` が要る）。検証環境で数件試してから有効にする |
| 一休 | — | robots.txt から 403 で拒否されるため取らない |
| Expedia・Trip.com | — | robots.txt が料金のページ・料金の API を禁止しているため取らない |

止められないための決まり（共通の基盤 `crawler/` が守る。サイトごとに書かない）:
- robots.txt を毎日確かめ、禁止のパスには行かない。robots.txt が 401・403・5xx ならそのサイトはすべて禁止とみなす
- 同じホストへの間隔は 5秒＋ゆらぎ（最大1.5倍）。Crawl-delay が長ければそちら
- 宿泊日は 0〜30日先は毎日、31〜60日先は2日おき、61〜90日先は4日おき。人数は既定で2名だけ
- 1回のジョブで1サイトに 300 リクエストまで。超えた分は次の回（近い日から取るので近い日が優先）
- 403・続く 429・CAPTCHA・アクセス制限の画面を見たら、その回は止め、24時間そのサイトを休ませる（実行記録の理由が `BLOCKED:`）。
  休止が繰り返すなら量を減らすか、そのサイトは公式 API・レートショッピング業者に切り替える。ブロックをすり抜ける工夫（IP の付け替え・
  ブラウザの偽装・CAPTCHA の突破）はしない
- 名乗る User-Agent に運営の連絡先を入れる（`EXTERNAL_FETCH_USER_AGENT`）。定期実行は深夜（03:00 JST 目安）に寄せる

サイトを足すとき: `crawler/sites/<key>.ts` に URL の作り方と読み取りを書き、実際のページを `__fixtures__` に保存して単体テストで固定する。
手書きが難しいサイトは `createLlmSiteScript`（AI で読む）で URL の作り方だけを書く。`sources.ts` に登録し、`CRAWL_ENABLED_SOURCES` に足す。

## 8. 障害時の初動

1. `/livez` と `/readyz` を確認する（プロセスの問題か、DB の問題か切り分ける）
2. backend のログをリクエスト ID（`x-request-id`）で追う
3. DB の問題なら、マネージド DB の状態・接続数・ストレージを確認する
4. 直近のリリースが原因なら §5 でロールバックする
5. 顧客影響があった場合は、影響範囲（テナント・期間）を監査ログで確認して報告する
