# レベニュー運用仕様（汎用）

全施設に共通して適用する仕様。**施設ごとに変わる値はここに書かない** — それらは
`docs/ホテル個別設定_テンプレート.md` を複製した施設別MDに書く。

| | |
|---|---|
| 版 | v1.0（2026-09） |
| 適用範囲 | 全契約施設 |
| 対になる文書 | 個別: `docs/ホテル個別設定_テンプレート.md` ／ 未決: `docs/協議アジェンダ.md` |
| 根拠 | `要件定義書.md` §6、`AGENTS.md`、レビューシート v3.0（311ルール／回答275件） |

## 0. 二層構成の原則

```
汎用MD（このファイル）        … 全施設共通の定義・計算式・処理手順
   ↓ 既定値を提供
個別MD（施設ごとに1枚）       … 施設固有の値・方針・PMS都合による例外
   ↑ ヒアリングシートで収集
協議アジェンダ                … まだ決まっていない共通仕様
```

3つのルール:

1. **汎用MDには「既定値」だけを書き、施設で上書きされる前提で書く。** 既定値は
   「大半の施設で無難」であって「正しい」ではない。
2. **個別MDに書いてよいのは、汎用MDに項目が存在するものだけ。** 個別MDが新しい概念を
   持ち込んだら、それは汎用MD側の不足なので汎用MDに項目を足す。
3. **どちらとも決められないものは協議アジェンダに置き、実装しない。** 暫定値で実装して
   後から直すより、未決のまま止めるほうが安い。

レビューシート v3.0 の回答では、311ルール中 **38件が「施設ごとの初期設定にすべき」**、
**36件が「協議事項」** と判定された。この文書の構成はその判定に従っている。

## 1. 予約データ取込の標準仕様

### 1.1 なぜ予約明細を取り込むのか

現行DBは `DailyData`（日別の集計結果）が入口で、中身はseedデータ。ここに **PMSの予約明細**
を入れると、集計をシステム側で生成できるようになる。さらに、**毎日取り込むこと自体が
「その日時点の予約残」のスナップショットになる**ため、ブッキングカーブ（`BookingCurveData`）と
ピックアップが特別な仕組みなしで実データ化する。

> 取込を後回しにすると、その期間のカーブは**後から作れない**。仕様が固まらなくても
> 「生データを溜めるだけ」は先に始めること。

### 1.2 データモデル（3層＋ロット）

```
ImportBatch（取込ロット）              いつ・誰が・どのファイルを・何行
  └ Reservation（予約明細 = 元データ1行）   PMS出力の1レコードをそのまま保持
       └ ReservationNight（日別展開）        1泊 = 1行。派生データ
            → DailyData / DailyRoomData      既存の集計テーブル（導出結果として再計算）
```

設計上の要点:

- **元データは加工せず保持する。** 按分ルールを変えたときに再生成できる。
- **日別展開は派生。** 何度でも作り直せる。Excelマクロで一度きり展開する方式を取らない。
- **`DailyData` は消さない。** 役割を「入力テーブル」から「導出テーブル」に変えるだけで、
  既存のダッシュボード・レポート・PDF出力はそのまま動く。
- 全テーブルに `tenantId` ＋ tenantリレーション ＋ `@@index([tenantId])` を付与する
  （`AGENTS.md` 必須ルール）。クエリは hotelId / tenantId で絞る。

### 1.3 日別展開の標準ルール

| ルール | 内容 |
|---|---|
| 展開単位 | 予約明細1行 × 泊数 = 泊数分の行 |
| 宿泊日 | `チェックイン日 + (泊目 − 1)`。**チェックアウト日当日の行は作らない** |
| 泊数の検証 | `泊数 = チェックアウト日 − チェックイン日` を全行で検算し、不一致は取込エラー |
| 金額の按分 | `合計 ÷ 泊数` の均等割。**端数は最終泊に寄せる**（円単位の整数で保持） |
| 人数の按分 | 同上。延べ人数を泊数で均等割し、端数は最終泊 |
| 按分の検算 | 明細単位で「日別の合計 = 元の合計」を必ず検証する |
| 型 | 宿泊日・チェックイン/アウト日・予約登録日/変更日は**日付型**。泊目は**整数** |
| 一意キー | `元行番号 + 泊目`。予約番号は一意ではない（下記 1.5 参照） |
| ステータス | RSV/CXL をそのまま保持し、**集計側で必ず絞る**。行を捨てない |

**端数を最終泊に寄せる理由**: 日別画面の数字を足せば総額に一致するため、現場が電卓で
検算しても合う。「内部は小数、表示だけ丸め」にすると画面の合計が合わず問い合わせになる。

**按分値は推定値である。** 延べ人数を泊数で割った日別人数は、実際には日ごとに人数が
変わる予約を均した値。UI上で実測と区別できるようにする（`AGENTS.md` の
「サンプル表示を実データのように見せない」と同じ思想）。

### 1.4 日別展開データの標準カラム（38列）

新宿ワシントン（NEHOPS）のサンプルで実装・検証済みの標準形。PMSが変わっても
この列構成に正規化する。

| # | 列名 | 型 | 備考 |
|---|---|---|---|
| 1 | 行ID | 文字列 | `元行番号-泊目`。一意 |
| 2 | 元行番号 | 整数 | 元データへのトレース用 |
| 3 | 予約番号 | 整数 | **一意ではない** |
| 4 | ステータス | 文字列 | RSV / CXL |
| 5 | 有効フラグ | 整数 | RSV=1 / CXL=0。合計するだけで有効分が出る |
| 6 | 個人団体 | 文字列 | 個人 / 団体 |
| 7 | 宿泊日 | 日付 | 分析の主軸 |
| 8 | 年月 | 文字列 | `YYYY-MM` |
| 9 | 曜日 | 文字列 | 月〜日 |
| 10 | 休前日区分 | 文字列 | 休前日 / 通常。**AG-03 決定までは「週末区分（金土）」で暫定運用**（サンプル実装はこの暫定版） |
| 11 | 泊目No | 整数 | 1始まり |
| 12 | 泊数 | 整数 | |
| 13-14 | チェックイン日 / チェックアウト日 | 日付 | |
| 15 | 予約タイプ | 文字列 | PMS原コード |
| 16-17 | タイプ区分 / ベースタイプ | 文字列 | PMSコード体系の正規化（施設別マッピング） |
| 18-21 | Market / 支払 / エージェント / 地域コード | 文字列 | コード表は個別MD |
| 22-23 | 会社名カナ / 団体名カナ | 文字列 | 個人情報。連携要否は個別MDで判断 |
| 24-26 | 人数 / 男 / 女（1日分・按分） | 整数 | 推定値 |
| 27-29 | 室料 / 朝食 / 売上計（1日分・按分） | 整数 | 円 |
| 30 | 1人単価（按分） | 整数 | 売上計 ÷ 人数 |
| 31-32 | 予約登録日 / 予約変更日 | 日付 | |
| 33 | リードタイム日数 | 整数 | 宿泊日 − 予約登録日 |
| 34 | 按分注意 | 文字列 | 人数端数 / 人数0の泊あり |
| 35-38 | 各種「延べ・合計（元）」 | 整数 | 検算用に元値を保持 |

> **室数の列が無い。** サンプルPMSの出力に販売室数が含まれておらず、これが無いと
> **OCC・ADR（1室単価）・RevPAR が計算できない**。室数の取得可否は施設ごとの最重要確認事項
> （個別MD §7 / ヒアリングシート D-01）。取得できるまで該当KPIは「未連携」と表示し、
> 0や空欄で誤魔化さない。

### 1.5 取込時に必ず検出する異常

サンプル500件の実データで実際に発生したもの。取込処理は以下を**警告として人に見せ、
黙って捨てたり丸めたりしない**。

| 検出項目 | 実例 | 既定の扱い |
|---|---|---|
| 予約番号が一意でない | 同一「予約番号×ステータス×部屋タイプ」が5組10行 | 元行番号で区別して取り込む |
| 1予約で宿泊期間が分かれる | 1予約番号が3区間（RSV/CXL混在）に分割 | チェックイン日等を「予約共通項目」として扱わない |
| 延べ人数が泊数で割り切れない | 15泊・延べ16名 → 1日1.07名 | 按分注意フラグを立てて取り込む |
| 未知の部屋タイプコード | 17種中1件のみのコード（打ち間違いの疑い） | **取込を止めて確認を求める** |
| キャンセルの比率が高い | CXL 322 / 500行（64%） | 集計は必ずステータスで絞る |
| 同一ファイルの再取込 | — | ファイルハッシュで検知し二重計上を防ぐ |

### 1.6 取込UIの要件

3ステップに分け、**②で止められること**を必須とする。

1. **アップロード** — ファイルを置く（将来は定時フォルダ監視）
2. **プレビューと検証** — 対象日レンジ／元行数→展開行数／RSV・CXL内訳／警告一覧／前回との差分を表示。
   ここで取り込まずに離脱できる（dry-run）
3. **確定** — バッチ単位で記録。**バッチ単位でロールバックできる**

補助要件:

- ダッシュボード最上部に1行で最終取込状態を表示（例: `最終取込 9/18 07:39 ／ 対象 10/1〜11/17 ／ 500件`）
- 取込が既定日数以上停止したら `Alert`（Level 4〜5）を発火
- 取込・取消は `writeAuditLog()` で監査ログに残す

## 2. 指標定義

### 2.1 共通定義（変更しない）

| 指標 | 定義 |
|---|---|
| OCC（稼働率） | 販売客室数 ÷ 販売可能客室数 |
| ADR | 客室売上 ÷ 販売客室数 |
| RevPAR / REV-Per | 客室売上 ÷ 販売可能客室数 = OCC × ADR |
| DOR | 宿泊人数 ÷ 販売室数 |
| 客単価（人単価） | 客室売上 ÷ 宿泊人数 = ADR ÷ DOR |
| RevPARの分解 | RevPAR変化率 ≒ OCC変化率 ＋ ADR変化率（小変化での加法近似） |

### 2.2 施設ごとに決める部分（個別MDへ）

計算式は共通でも、**分子・分母に何を入れるかはPMSと施設の考え方で変わる**。
レビューで「PMSの仕様による」「都度ヒアリングにより初期設定」と指摘された箇所。

| 項目 | 汎用の既定値 | 施設で変わる理由 | 個別MD |
|---|---|---|---|
| OOO（故障部屋）の除外 | 長期（工事等）は除外／単発（1泊〜1週間）は含む | PMSの持ち方と施設の考え方 | §2 |
| コンプ（無料）ルーム | 販売室数から除外 | 施設の考え方 | §2 |
| ADRに食事を含むか | 含まない（純客室料金） | 1泊2食の旅館・小規模リゾートは含めることがある | §2 |
| ADRの税・サービス料 | 税抜・サービス料除外 | PMSの出力仕様 | §2 |
| TRevPAR / GOPPAR | 対象外（将来拡張） | 室料以外の売上部門がPMSにあるか。宴会は別システムのことが多い | §2 |
| ネットADR（手数料控除後） | 対象外 | PMSにコスト設定がない。本システム側にマスタが要る | §2 |
| 会計年度の開始月 | 4月 | 施設の会計年度に準ずる | §2 |
| 休前日の定義 | 金・土 | 「週末」ではなく**休前日**で持つべき（→協議 AG-03） | §3 |

## 3. 需要予測・価格決定の共通枠組み

### 3.1 枠組み（共通）

```
実績・予約積上
   ↓ ベースライン生成（移動平均 × 前年同曜日の加重）
   ↓ ペース補正（ブッキングカーブ上の位置）
   ↓ イベント・外部要因の加算
需要レベル A〜E
   ↓ 基準ランクへのマッピング
   ↓ 施設ポリシーによる制約（上下限・変更幅・変更頻度）
推奨料金ランク ＋ 確信度 ＋ 根拠
```

- 需要レベルは **A〜E の5段階**（`DemandLevel`）
- 価格戦略の重みは **稼働率 / ADR / 競合 の合計100%必須**（`PricingStrategyConfig`）
- 推奨は**提示のみ**。サイトコントローラーへの書き戻しは現時点でスコープ外
- 推奨には必ず**根拠（寄与の内訳）**を保存し、AIコメントから参照できるようにする

> **この枠組み自体に未決の大論点がある。** レビュー回答は「カレンダー比較ではなく
> **パターン比較**を基礎にすべき」と11箇所で繰り返し指摘している（AG-01）。
> 採否が決まるまで、予測ロジックの実装は保留する。

### 3.2 汎用の既定パラメータ（個別MDで上書き可）

施設固有値が未収集の間に使う初期値。**「正しい値」ではなく「置きにいく値」**。

| 分類 | パラメータ | 汎用既定値 |
|---|---|---|
| 予測 | ベースライン加重（移動平均:前年） | 0.6 : 0.4 |
| 予測 | 学習期間の下限 | 移動平均 ≥4週 / 前年 ≥1年 |
| 予測 | 確信度 | 両データ有 0.85 / 移動平均のみ 0.7 / 前年のみ 0.6 / なし 0.4 |
| 予測 | 天候の反映 | 7日以内のみ |
| 価格 | 戦略の重み（稼働/ADR/競合） | 40 / 40 / 20 |
| 価格 | ランク段階数 | 40（→協議 AG-02） |
| 価格 | 刻み幅 | 等比 3〜5%/段 |
| 価格 | 上限・下限ランク | 下限 R05 / 上限 R38 |
| 価格 | 1日あたり変更幅 | ±3（低確信度 ±1） |
| 価格 | 上げ下げの非対称 | 上げ +2/日 / 下げ −1/日 |
| 価格 | 最小変更単位 | 1ランク |
| 価格 | 変更頻度上限 | 1回/日（直前7日は2回） |
| 在庫 | オーバーブッキング | 実施しない |
| 在庫 | 直販確保枠 | 5〜10%（7日前に開放） |
| 団体 | ウォッシュ率 | 25% |
| チャネル | レートパリティ許容幅 | ±3% |
| チャネル | 直販比率目標 | 20% |
| 運用 | スナップショット取得 | 日次固定時刻（直前7日は朝夕2回） |
| 運用 | 再フォーキャスト | 日次自動・週次人手確認 |

## 4. 品質・表示の共通ルール

- **推定値と実測値を区別して表示する。** 按分値・ルールベースのダミー値は
  その旨をUIに明示する
- **未連携の指標は「未連携」と表示する。** 0や空欄で埋めない
- **モックへのサイレントフォールバック禁止。** ローディング／エラー／再試行を出す
- **「平均」という表現を競合分析で使わない**（要件定義書 F-DP-06 / F-ANA-02）
- 金額は円単位の整数で保持し、日別の合計が総額に一致すること
- UIは日本語。ロール表示名の唯一の出所は `shared/types/index.ts` の `ROLE_LABELS`

## 6. 用語

| 用語 | 意味 |
|---|---|
| OOO | Out Of Order。故障・改装で販売不能な客室 |
| コンプ | 無料提供室 |
| ウォッシュ | 団体ブロックのうち実際には使われず戻る分 |
| ブロック | 団体向けに確保した在庫枠 |
| STLY | Same Time Last Year。前年同時期 |
| ピックアップ | 一定期間での予約の積み上がり |
| CTA / CTD | Closed To Arrival / Departure。到着日・出発日クローズ |
| LRV | Last Room Value。最終在庫の機会費用 |
| レートパリティ | チャネル間の料金一致 |
| SC | サイトコントローラー |
| RSV / CXL | 予約 / 取消（PMSの予約ステータス） |
