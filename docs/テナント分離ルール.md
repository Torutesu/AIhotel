## 0. 本書の位置づけ

本システムは複数のホテル運営企業が同一基盤を共有するマルチテナントSaaSである。テナント分離の欠陥は、他社の売上・稼働・価格戦略といった競争上の機微情報の漏洩に直結する。**分離違反は本番事故として扱い、例外を認めない。**

本書は「何を守るか」だけでなく「どう書けば守れるか」「どう検証するか」を定義する。判断に迷った場合は、より制限の強い側を選ぶこと。

---

## 1. 用語と階層

| 用語 | 定義 |
| --- | --- |
| テナント（`Tenant`） | 契約単位。通常はホテル運営企業1社 |
| ホテル（`Hotel`） | テナントに属する施設。1テナントが複数ホテルを持ちうる |
| 利用者（`User`） | テナントに属する。原則として単一ホテルに紐づく |

```
Tenant (契約企業)
 └── Hotel (施設)        ← 業務データはすべてこの配下
      └── 業務データ (DailyData, PriceRank, Event, ...)
```

分離の境界は**テナント**である。ホテル単位のアクセス制御は、テナント境界を越えないことを保証したうえでの、さらに内側の制御と位置づける。

---

## 2. データモデルのルール

### R-1. 業務データモデルは必ずテナントに属する

新規の業務データモデルには、以下を**すべて**付与する。1つでも欠けたらマージしない。

```prisma
model NewModel {
  id       String @id @default(cuid())
  tenantId String
  tenant   Tenant @relation(fields: [tenantId], references: [id], onDelete: Cascade)
  hotelId  String
  hotel    Hotel  @relation(fields: [hotelId], references: [id], onDelete: Cascade)

  // ... 業務フィールド

  @@index([tenantId])
  @@index([hotelId])
}
```

| 要素 | 必須 | 理由 |
| --- | --- | --- |
| `tenantId String` | ✅ | 絞り込みの基準。アプリ側のバグでホテル指定が漏れても最後の砦になる |
| `tenant` リレーション | ✅ | 参照整合性 |
| `onDelete: Cascade` | ✅ | テナント解約時にデータを残さない |
| `@@index([tenantId])` | ✅ | 絞り込みが常に走るため、無いと全件走査になる |
| `hotelId` + `@@index([hotelId])` | 原則✅ | ホテル単位で扱わないデータのみ省略可 |

### R-2. `tenantId` を NULL 許容にしてよいのは3モデルのみ

| モデル | NULL を許す理由 |
| --- | --- |
| `User` | テナント横断の ADMIN（システム提供側）を表現するため |
| `RefreshToken` | `User` に従属するため |
| `AuditLog` | テナント削除後も監査証跡を残すため |

**上記以外で `tenantId String?` としてはならない。** 新規モデルで NULL 許容が必要と判断した場合は、設計判断としてレビューを要する。

### R-3. 間接的に属するモデルも例外ではない

親モデル経由でテナントが判明する場合（例: `CompetitorPriceData` → `Competitor` → `Hotel`）でも、自身に `tenantId` を持たせる。JOIN を経ずに絞り込めることが、クエリ漏れに対する防御になる。

## 3. クエリのルール

### R-4. 業務データの検索は必ずテナントまたはホテルで絞る

```ts
// ✅ 正しい
await prisma.dailyData.findMany({ where: { hotelId, date: { gte: from } } })

// ❌ 禁止 — 全テナントを走査する
await prisma.dailyData.findMany({ where: { date: { gte: from } } })
```

`findMany` / `findFirst` / `count` / `aggregate` / `groupBy` のいずれも対象である。

### R-5. ID 直指定の取得でも所属を検証する

主キーは推測困難（cuid）だが、推測困難性を分離の根拠にしてはならない。

```ts
// ❌ 危険 — 他テナントのIDでも取れてしまう
await prisma.event.findUnique({ where: { id } })

// ✅ 正しい — hotelId を条件に含める
await prisma.event.findFirst({ where: { id, hotelId } })
```

更新・削除も同様に、`updateMany` / `deleteMany` へ `hotelId` を含めるか、取得時に所属を検証してから実行する。

```ts
// ✅ 正しい
const result = await prisma.event.updateMany({ where: { id, hotelId }, data })
if (result.count === 0) throw new NotFoundError('イベント')
```

### R-6. 親経由の絞り込みは親のホテルを条件に含める

```ts
// ✅ 正しい — 自ホテル配下の競合に限定する
await prisma.competitorPriceData.findMany({
  where: { competitor: { hotelId, isActive: true }, date: { gte: from, lte: to } },
})
```

### R-7. 書き込み時の `tenantId` はリクエストから受け取らない

作成対象の `tenantId` は、必ずサーバ側で確定した値（対象ホテルの `tenantId`、または認証済みユーザーの `tenantId`）を用いる。リクエストボディの `tenantId` を信頼してはならない。

```ts
// ✅ 正しい — ホテルから導出する
const hotel = await prisma.hotel.findUnique({ where: { id: hotelId } })
if (!hotel) throw new NotFoundError('ホテル')
await prisma.priceRank.create({ data: { hotelId, tenantId: hotel.tenantId, ...input } })
```

`registerSchema` を用いたユーザー登録でも、テナントは指定された `hotelId` から導出する実装としている（`authService.registerService`）。

### R-8. Prisma を import してよいのは `services/` と `lib/` のみ

controllers / routes からの直接アクセスを禁じる。分離ロジックをサービス層に集約し、検証対象を限定するためである。ESLint が違反をエラーとする。

## 4. APIのルール

### R-9. 認証なしで公開してよいのは3経路のみ

`POST /api/v1/auth/login`、`POST /api/v1/auth/refresh`、ヘルスチェック。**それ以外のすべてのルートに `authenticate` を適用する。**

### R-10. hotelId を受け取るルートには `requireHotelAccess` を適用する

抽出元を明示して適用する。抽出元とバリデーション対象がずれると検証が素通りするため、両者を必ず一致させる。

```ts
// クエリから受け取る場合
router.use(requireHotelAccess((req) => req.query.hotelId as string | undefined))

// ボディから受け取る場合
router.post('/', requireHotelAccess((req) => req.body?.hotelId), validate(createSchema), handler)

// パスパラメータから受け取る場合
router.put('/:id', requireHotelAccess((req) => req.params.id), validate(updateSchema), handler)
```

| 受け取り方 | 抽出関数 |
| --- | --- |
| `?hotelId=` | `(req) => req.query.hotelId as string \| undefined` |
| ボディ | `(req) => req.body?.hotelId` |
| パス | `(req) => req.params.id` |

ルータ全体で同一の抽出元を使えるならば `router.use(...)` でまとめて適用する。エンドポイントごとに受け取り方が異なる場合は、**個別に適用する**（`pricing.ts` / `settings.ts` が該当）。

### R-11. `requireHotelAccess` の挙動を理解して使う

| 条件 | 結果 |
| --- | --- |
| `req.user` が ADMIN | **すべて通過（バイパス）** |
| hotelId が抽出できない | 400 |
| `req.user.hotelId` と不一致 | 403 |
| 一致 | 通過 |

**ADMIN はテナントを越えて全ホテルにアクセスできる。** これはシステム提供側の運用を想定した現行仕様である。顧客企業の「本部管理」権限を ADMIN で代用してはならない。代用すると、その企業が他社データに到達しうる。本部管理の実現方式は未確定事項（基本設計書 Q-01）であり、確定するまで顧客に ADMIN を付与しない。

### R-12. 変更系にはロール制限と監査を併用する

```ts
router.put(
  '/:id',
  requireRole('ADMIN', 'MANAGER'),
  requireHotelAccess((req) => req.params.id),
  validate(updateSchema),
  handler
)
```

コントローラ側で `writeAuditLog()` を呼び、`oldValue` / `newValue` を記録する。

**例外**: `POST /api/v1/events` は `requireRole` を適用していない。現場オペレーターによるイベント登録を許容する設計判断（F-DP-07）である。テナント分離（`requireHotelAccess`）は適用済みであり、この例外は**ロール制限のみ**の緩和である。テナント分離の緩和は、いかなる理由でも認めない。

### R-13. 入力は必ず zod で検証する

`validators.ts` のスキーマと `validate()` を用いる。生の `req.body` / `req.query` を参照しない。hotelId は `entityIdSchema` で形式検証したうえで `requireHotelAccess` に渡す。

## 5. 応答のルール

### R-14. 他テナントの存在を推測させない

他テナントのリソースIDを指定された場合、403（`requireHotelAccess` による）を返す。エラーメッセージにリソース名や所有者情報を含めない。

「存在しない」と「アクセス権がない」を区別できるメッセージは、IDの総当たりによる存在推測を許す。`errorHandler` の既定メッセージを使い、独自の詳細メッセージを足さない。

### R-15. 集計・一覧のスコープを明示する

一覧取得（例: `GET /api/v1/hotels`）では、ADMIN は全件、それ以外は自テナントのみを返す。この分岐はサービス層に置き、コントローラで再実装しない。

## 6. テストのルール

### R-16. hotelId を受け取る新規エンドポイントにはテナント分離テストを必須とする

テスト仕様書 §5.2 の TC-T に準じ、最低限以下を追加する。

| 観点 | 期待 |
| --- | --- |
| 他テナントのホテルIDを指定 | 403 |
| hotelId 未指定 | 400 |
| 自テナントのホテルIDを指定 | 200 |

### R-17. 変更系にはロール別テストを必須とする

TC-R に準じ、許可されないロールで 403 になることを確認する。意図的に緩和した経路（`POST /events`）については、緩和が維持されていることを確認するテストを置く（誤って `requireRole` を追加した際に気付けるようにするため）。

### R-18. 分離テストは実装より先に壊れることを確認する

テスト追加時は、`requireHotelAccess` を一時的に外すと当該テストが失敗することを確認する。素通りするテストは分離を保証しない。

## 7. レビューチェックリスト

新規・変更のプルリクエストで、以下をすべて確認する。

**Prisma スキーマ**
- [ ] 新規モデルに `tenantId` とテナントリレーションがある
- [ ] `onDelete: Cascade` が設定されている
- [ ] `@@index([tenantId])` がある
- [ ] `tenantId` を NULL 許容にしていない（R-2 の3モデルを除く）
- [ ] `prisma migrate dev` でマイグレーションを生成しコミットした

**クエリ**
- [ ] 全ての検索が tenantId または hotelId で絞られている
- [ ] `findUnique({ where: { id } })` で業務データを直接引いていない
- [ ] 更新・削除が所属検証を経ている
- [ ] 作成時の `tenantId` をリクエストから受け取っていない

**ルート**
- [ ] `authenticate` が適用されている
- [ ] hotelId を受け取るなら `requireHotelAccess` が適用され、抽出元が実際の受け取り方と一致している
- [ ] 変更系に `requireRole` と `writeAuditLog()` がある
- [ ] 入力が zod スキーマで検証されている
- [ ] Prisma を controllers/routes から import していない

**テスト**
- [ ] TC-T 相当のテナント分離テストを追加した
- [ ] TC-R 相当のロール別テストを追加した

## 8. 違反を見つけた場合

1. 影響範囲（どのデータが、どの条件で、誰に露出しうるか）を特定する
2. 修正を最優先で行う。他の作業に先行させる
3. 同じ型の違反が他にないか、同一パターンで横断的に確認する
4. 再発を防ぐテストを追加する。テストなしの修正で完了としない
