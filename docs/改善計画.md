# 改善計画（総点検 2026-09-11 の所見に基づく）

総点検で洗い出した所見を、実装順・担当領域・受け入れ条件つきのタスクに落としたもの。
各タスクの ID はコミット件名の末尾に付ける（例 `fix(backend): アクセストークンに type クレームを追加 (S-1)`）。

- 前提: AGENTS.md の必須ルール（認証／テナント分離／zod／監査ログ／`config` 経由の環境変数／マイグレーションのコミット）は全タスクに適用する。
- 検証: 各 Wave の終わりに `pnpm --filter './*' type-check` → `pnpm --filter './*' lint` → `pnpm --filter backend test` → 両ビルド → ローカル PostgreSQL での migrate/seed/API 疎通 → ブラウザ操作を通す。
- 方針の変更点（要確認）: **デモモードを opt-in（`NEXT_PUBLIC_DEMO_MODE=true` のときだけ有効）に変える**。既存のデモ環境（hotel-price.vercel.app）を維持するには Vercel の環境変数に `NEXT_PUBLIC_DEMO_MODE=true` を設定する必要がある。

## 依存関係の既知の残課題

`pnpm audit --prod` の high / critical は 0 件（CI の audit ジョブはこの水準をゲートにしている）。
残る 1 件は以下の理由で保留する。

| 深刻度 | パッケージ | 経路 | 保留理由 |
|---|---|---|---|
| moderate | `uuid` < 11.1.1 | `backend > exceljs > uuid@8` | 該当脆弱性は `v3/v5/v6` に `buf` を渡した場合のみ。exceljs は `v4()` しか呼ばないため影響しない。exceljs 4.4.0 が最新で上流の更新待ち |

`brace-expansion` / `deepmerge-ts` / `qs` / `body-parser` / `sharp` / `postcss` / `nanoid` は
ルート `package.json` の `pnpm.overrides` でパッチ版に固定している。上流が追随したら override を削除する。

### 実装中に追加で見つかり修正したもの

| 内容 | 影響 |
|---|---|
| `next.config.mjs` の `rewrites()` は転送先を `next build` 時に `routes-manifest.json` へ焼き込むため、実行時の `BACKEND_URL` が反映されない。コンテナを一度ビルドして環境ごとに差し替える運用（`docker/frontend.Dockerfile` の想定）では常にビルド時の値へ転送され、本番で500になる | `app/api/[...path]/route.ts` のルートハンドラに置き換え、毎リクエストで解決。PDF/Excel等のバイナリも中継 |
| フロントの未使用ファイル整理で `frontend/public/` が空になり、Dockerイメージの `COPY frontend/public` が失敗する状態だった | `.gitkeep` を置いてディレクトリを維持 |
| 開発環境で Prisma が全SQLをログ出力し他のログが埋もれる | `LOG_LEVEL=debug` 指定時のみに限定 |
| `express` 経由の `qs` / `body-parser`、`exceljs` 経由の `brace-expansion`、`prisma` 経由の `deepmerge-ts` に脆弱性 | `express` を 4.22.2 に更新し、残りは `pnpm.overrides` でパッチ版へ固定 |

### ロール体系の変更（#62 — 最重要）

ADMIN がテナントを越えてデータを読めていた点について、**権限そのものを分離**した。

| ロール | 日本語表示 | tenantId | テナント越え | 想定利用者 |
|---|---|---|---|---|
| `PLATFORM_ADMIN` | 運営 | null | **可（唯一）** | サービス提供側。顧客には渡さない |
| `ADMIN` | 管理者 | 必須 | 不可 | 顧客テナントの管理者（テナント内で最上位） |
| `MANAGER` | マネージャー | 必須 | 不可 | 支配人・レベニューマネージャー |
| `OPERATOR` | オペレーター | 必須 | 不可 | 現場フロント |

- `requireHotelAccess` のロール早期 return は `PLATFORM_ADMIN` のみ。`ADMIN` は必ずテナント判定を通る
- `requireRole` は `PLATFORM_ADMIN` を全ロールの上位集合として扱う
- ユーザー登録の `tenantId` は**作成者のテナント**から導出する。他テナントのホテルIDを送っても
  「指定されたホテルが見つかりません」（400）で、そのホテルの存在は判別できない（#52）
- 併せて `PUT` / `DELETE /hotels/:id` に `requireHotelAccess` が無かった不備を修正（テナント管理者が
  他テナントのホテルを改名・論理削除できた）
- 日本語表示名の唯一の出所は `shared/types/index.ts` の `ROLE_LABELS`

**#49-4 の実装内容**

### D-1 データの誤り・権限の穴

#### #76 価格戦略の重みを推奨ランクへ反映する

- 未マージブランチ `claude/plugin-dir-config-p9ahd0` の `strategyWeighting.ts`（28b4cf2）を移植し、`MODEL_VERSION` を `rule-based-v2` にする
- 3観点をそれぞれ料金ランクへ写像し、`PricingStrategyConfig` の重みで加重平均する
  - 稼働率: 予測稼働率 → ランク（従来どおり）
  - ADR: 直近28日の同曜日ADR実績の平均 → 最も近い `price1P` のランク（同曜日が無ければ窓内全日）
  - 競合: 対象日の**有効な**競合（`isActive`）の `price1P` の**中央値** → 最も近いランク（C-9 の「平均を使わない」に合わせ、移植元の平均から変更）
- データが無い観点・重み0の観点は合成から外し、残りの重みで按分する（競合価格が無い日にランクが下がらない）
- 設定が無いホテルは稼働率100%（従来と同じ結果）
- 需要レベル（A〜E）は価格戦略と独立させ、予測稼働率だけで決める
- 受け入れ: 重みを変えると推奨ランクが変わることをユニットテストで固定。要件定義書 §6 の F-DP-02 は実態どおり「実装済み（初版の写像方式。#17 で確定後に見直し）」

#### #77 predictedAdr の算出と、リセット時の着地予測の再計算

- forecaster が `predictedAdr` を返す。算出式:
  - 基準ADR = 直近28日の同曜日ADR実績の平均（無ければ窓内全日の平均）
  - 基準ADRに対応するランク（ADR観点と同じ写像）と推奨ランクの両方の `price1P` があれば、
    `predictedAdr = 基準ADR × price1P(推奨ランク) / price1P(基準ランク)`（推奨ランクへの価格変更を実績ADRに比例で反映）
  - 料金ランクが無ければ基準ADRそのまま。ADR実績が無ければ `null`
- 着地計算の「predictedAdr が無ければ推奨価格」の代替は、ADR実績がまだ無い新規ホテルのためだけに残す
- フロント: 「AI予測値へリセット」は `POST /pricing/recompute` の後に、表示中の年月について `POST /pricing/simulation/recompute` を呼ぶ（`api.recomputeSimulation()` を追加）。案内文を実際の動きに合わせる
- 受け入れ: 再計算後も predictedAdr が入っている（統合テスト）。リセット後に着地予測が更新される（RTL）

#### #78 無効化・降格・契約停止を即時に反映し、アカウント単位でロックアウトする

- `authenticate` はトークン検証後に `User`（`isActive`・`role`・`tenantId`・`hotelId`）と `Tenant.isActive` を DB から読み、
  - ユーザーが無効／存在しない、またはテナントが停止されていれば 401
  - `req.user` のロール・テナント・ホテルは DB の値で上書きする（降格が次のリクエストから効く）
- ログインもテナント停止中は失敗させる（メッセージは既存の失敗と同一）
- `JWT_EXPIRES_IN` の既定値を `15m` にする（フロントはリフレッシュを single-flight で行うため影響なし）
- ロックアウト: `User.failedLoginCount` / `User.lockedUntil` を追加（マイグレーション）
  - 連続5回失敗で15分ロック。ロック中は正しいパスワードでも失敗させ、メッセージは既存と同一（アカウントの存在・ロック状態を漏らさない）
  - 成功でカウンタを0に戻す。ロック発生時に監査ログ `ACCOUNT_LOCKED` を残す
- `/auth/refresh` に専用のレート制限（IP 単位、15分に60回）
- 受け入れ: 無効化・降格・テナント停止の直後のリクエストが 401／降格後の権限になる（統合テスト）。6回目のログインが正しいパスワードでも失敗する（統合テスト）

#### #80 保存されない操作・権限外のボタン・サイレントフォールバック

- イベント一覧の編集・削除ボタンを `canManage(role)` で出し分ける（登録は OPERATOR にも残す）
- 日別詳細ダイアログ: その日にかかる登録済みイベント（`/events`）を表示する。独自の「メモ保存」は廃止し、イベント登録は既存のイベント登録フォームに一本化する。カレンダーのイベント表示も `/events` から作る
- 部屋タイプのセレクタは撤去する（部屋タイプのマスタは #81 で扱う）
- 複数月KPIの取得失敗時は ErrorState と再試行を出す
- サンプル画面（セグメント別クロス分析設定・OTA販促参画）の成功トーストを「サンプル表示のため保存されません」に変える
- 受け入れ: OPERATOR でイベントの編集・削除ボタンが出ない（RTL）。複数月KPIの失敗時にエラーが出る（RTL）

#### #90-1 削除済み競合を価格カレンダーの代表値から除く

- `pricingService` の競合価格の抽出条件に `competitor.isActive = true` を加える
- 受け入れ: 論理削除した競合の価格がカレンダーの中央値・最小・最大に含まれない（統合テスト）

- `middleware.ts` でリクエストごとに nonce を作り、CSP を付ける:

### R-2 リリース前に必須（インフラと設定）

1. **R-2-1 DB と実行環境**: マネージド PostgreSQL 16（PITR・保存時暗号化・`DATABASE_URL` に `sslmode=require`）、GHCR の非公開イメージを
   取得できるコンテナ実行環境。リリース前に一度リストアを試す（`docs/運用手順書.md`）
2. **R-2-2 バックエンドの環境変数**
   - `FRONTEND_URL` は本番でも必須になっておらず、未設定だと黙って `http://localhost:3000` になる（`lib/config.ts:22-31`）。
     CORS とメール内のリンクに使われるので、本番のドメインを必ず設定する。起動時に本番で未設定なら落とす検証を足す
   - `.env.example` は `NODE_ENV=development`（:11）。これを写した env ファイルを `--env-file` で渡すと、イメージの `NODE_ENV=production` を
     上書きし、helmet の CSP が外れ、CORS に localhost が加わる（`app.ts:88,94-96`）。手順書に明記するか、本番用の例を分ける
   - `JWT_SECRET`（32文字以上）、`MAIL_DRIVER=smtp` と SPF/DKIM（無いと一時パスワードが画面に1回表示されるだけになる）
3. **R-2-3 バックエンドの公開範囲と `TRUST_PROXY`**: Vercel のサーバー関数からバックエンドへはインターネット経由になり、
   手順書の「直接公開しない」と食い違う。直接叩かれると `X-Forwarded-For` を偽装でき、ログイン回数の制限と監査ログの IP が
   ずれる。受け付けを Vercel からに絞る（許可リスト・Secure Compute）か、中継とバックエンドの間に共有の秘密ヘッダーを足す。
   前段に ALB / Cloud Run が入るなら `TRUST_PROXY` の段数を合わせる（`README.md` の `TRUST_PROXY=1` は前段が無い前提）
4. **R-2-4 Vercel の本番**: デモとは別のプロジェクトにする（デモはログイン情報を公開しているため）。`BACKEND_URL` を https で設定し、
   `NEXT_PUBLIC_DEMO_MODE` は置かない。デモ無効の検証（`verify-demo-mode.mjs --expect-disabled`）は CI にしか無いので、
   本番プロジェクトのビルドコマンドにも入れる。デモ用プロジェクトにあるバックエンドの変数（`DATABASE_URL`・`JWT_SECRET` など）は消し、
   実際の値だったなら取り替える
5. **R-2-5 最初の運営（PLATFORM_ADMIN）を作る手段**: 運営を作れるのは運営だけ（`authService.ts:285`）で、
   今は seed の `platform@example.com` / `Admin1234`（README・AGENTS.md に記載）しか無い。`job create-platform-admin` のような1回限りのジョブを作り、
   `mustChangePassword` を立てて作る
6. **R-2-6 seed を本番で走らせない**: `prisma/seed.ts` は `NODE_ENV` も接続先も確かめず、本番イメージに入っている（`Dockerfile:80`）。
   本番では拒否するガードを入れる。デモ用アカウント（パスワード共通）が本番 DB に入る経路を塞ぐ
7. **R-2-7 定期実行**: `job daily`（毎日早朝 JST）と `job competitor-prices`（1日4回）をスケジューラに登録し、終了コード1で通知する
8. **R-2-8 最低限の監視**: `/readyz` の外形監視、5xx の割合、ジョブの失敗、`ACCOUNT_LOCKED` / `TOKEN_REUSE_DETECTED` の急増。
   エラー追跡・メトリクスのライブラリはまだ入っていない
9. **R-2-9 利用規約・プライバシーポリシー**: 画面もリンクも無い（`frontend/app` はログインとエラー画面だけ）。Vercel Analytics の利用も記載する

### R-3 テナント周り

中程度（リリース前に直す）:

- **R-3-1 契約停止したテナントもバッチが処理し続ける**: `listActiveHotelsForJobService`（`services/hotelsService.ts:70-78`）がホテルの
  `isActive` しか見ていない。停止中のテナントにも予測・アラート・スナップショット・競合サイトへの取得が走る。`tenant.isActive` も条件に入れる
- **R-3-2 テナントの解約（オフボーディング）が無い**: 削除・データの書き出し・保持期間と消去の手順が無い。`User`・`RefreshToken`・`AuditLog` の
  テナント外部キーは `ON DELETE SET NULL` なので、テナント行を消すとユーザーがテナント無しの有効なアカウントとして残る。
  当面は「消さずに停止する」運用と、データ書き出し・消去の手順を決める（R-1-1 の保持期間と合わせる）
- **R-3-3 メールアドレスがテナントをまたいで一意**（`schema.prisma:66`）: ログインがメールだけなので必要な制約だが、
  招待で 409 が返るため、テナントの管理者が「そのアドレスが他社や運営に存在するか」を確かめられる。1人が2テナントに属することもできない。
  409 の文言を他テナントの存在が分からないものにするか、仕様として受け入れるかを決める

低（早めに直す）:

- **R-3-4** `RefreshToken` に `@@index([tenantId])` が無い（AGENTS.md の規約違反。停止時の一括削除で使う）。`CompetitorFetchRun.hotelId` に外部キーが無い
- **R-3-5** 「運営 ⇔ tenantId が null」を強制していない。運営ロールで `hotelId` 付きの登録をするとテナント付きの運営ができ、
  運営がテナントのユーザーを運営に昇格させると tenantId が残る（`services/authService.ts:329-348`、`services/usersService.ts:104-114`）
- **R-3-6** ホテルに所属するユーザーでも、`GET /hotels` と `GET /audit-logs` はテナント全体を返す（`services/hotelsService.ts:14-32`、`services/auditService.ts:76-95`）。方針（#79）に合わせるか決める
- **R-3-7** 停止中のテナントにも運営がユーザーを登録できる（`services/authService.ts:318-324` がテナントの `isActive` を見ていない）

足りない仕組み（v1 の後でもよいが、顧客が増える前に）:

- **R-3-8** テナント立ち上げが3回の別々の呼び出し（テナント作成 → 管理者登録 → ホテル作成）で、途中で失敗すると半端な状態が残る。1つの手続きにまとめる
- **R-3-9** テナントごとの上限（ホテル数・ユーザー数）とプラン・契約の情報が無い（`Tenant` モデル）
- **R-3-10** 監査ログ: テナントに属さない記録（運営のログイン、存在しないメールでのログイン失敗）を見る手段が無い。ホテルが無いテナントは自分の記録を見られない。
  運営が顧客データを読んだことは記録されない
- **R-3-11** 多層防御: 運営の多要素認証、Postgres の行レベルセキュリティ、「レコードの tenantId＝ホテルの tenantId」の DB 制約は無い
- **R-3-12** テストの穴: 「自ホテルの hotelId＋他テナントのレコード ID」の組み合わせをイベント・競合・料金ランク・価格固定期間で確かめていない。
  バッチが停止テナントを飛ばすテストも無い

### R-4 実データで回すための前提

- **R-4-1 毎日の手作業が多い**: 前日の実績 CSV、OTB の CSV、楽天以外の競合価格の CSV を毎日手で取り込み、推奨ランクはサイトコントローラーに手で転記する。
  OTB は取りこぼした日を後から埋められない（ブッキングカーブが欠ける）。機械からの取り込み用の認証（API キー・サービスアカウント）が無く、
  取り込みはユーザーの JWT でしかできない。R-1-3 の回答に合わせて、定時のファイル受け渡しか API キーでの取り込みを作る
- **R-4-2 需要予測が OTB を見ていない**: `rule-based-v3`（`ruleBasedForecaster.ts`）は過去の実績・イベント・料金ランク・戦略・競合だけを使い、
  予約の入り方（`BookingCurveData`）は画面のグラフにしか使っていない。予約ペースに推奨が反応しない
- **R-4-3 競合価格**: 楽天トラベルは実際のアプリ ID で未確認（D-8）。ほかのサイトは CSV で、48時間より古い価格は推奨に使わないため、
  取り込みが止まると競合の観点が推奨から外れる
- **R-4-4 seed でしか入らないテーブル**: `OtaChannelData`（チャネル別）・`DailyRoomData`（部屋タイプ別）・`ReviewScore`（口コミ）・`AiComment`（AI解説）は
  取り込み経路が無く、実顧客では常に空になる。取り込みを作るか、画面で「データ未取り込み」と分かるようにする
