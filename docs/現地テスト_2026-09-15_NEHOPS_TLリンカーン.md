# 現地テスト 手順・記録（2026-09-15 / NEHOPS × TL-リンカーン）

**目的: 一度取るのではなく「無人で取り続けられる」ことの実証。**
1サイクルを手で通したうえで、スケジューラから人の操作なしで同じことが起きるところまで確認する。

対象Issue: #6（連携方式・取得端末）、#18（A1〜A12 提供仕様）、#24 E2（OTBスナップショット）、#9（競合価格は別ルート）

## 0. 構成の選択肢

| | 構成 | ホテル側に置くもの | 成立条件 |
|---|------|-----------------|---------|
| A | **クラウドから TL-リンカーン API を定期取得** | なし | APIで予約明細が取れること（シーナッツ社へ要確認） |
| B | **ホテル端末から定期送信**（TLの自動出力 → 端末 → 取込API） | Windows端末1台に送信スクリプトとタスク登録 | TLに出力のスケジュール機能があること（A11） |
| C | B の変種（TLに自動出力が無い場合） | 端末に画面操作の自動化（RPA）も必要 | 規約・MFA・画面変更に耐えられること |

Aが本命。ただし明日その場で確かめられるのはBの経路なので、**Bを実証しつつAの可否を確認する**のが今回の狙い。

明日の送信先は次のどちらかを事前に決める:

- **持参PCをサーバ役にする**（同一LANの `http://<持参PCのIP>:3001`）— 準備が軽い。ホテルのネットワークに持参PCを繋げることと、端末から持参PCへ通信できることが条件
- **クラウドに置いたバックエンドへ送る** — 本番に近いが、インフラ確定（Issue #21 D1）とHTTPSの用意が必要

## 1. 前日までの準備

### 1-1. 送信先（サーバ側）

```bash
docker compose -f docker/docker-compose.dev.yml up -d
pnpm --filter backend db:generate
pnpm --filter backend db:migrate && pnpm --filter backend db:seed
pnpm --filter backend dev     # 0.0.0.0:3001 で待ち受ける
```

- 取込端末用のアカウントを1つ払い出す（**MANAGER 以上が必要**。ホテル担当者の個人アカウントは使わない）。
  端末に置く資格情報の権限を絞るのは Issue #12（IP制限）とあわせた次の課題。
- 持参PCのファイアウォールで 3001 への受信を許可し、端末から `http://<IP>:3001/health` が 200 を返すことを確認しておく。

### 1-2. ホテル端末（Windows）

USBから次の2ファイルを端末のフォルダ（例 `C:\hotel-import`）へコピーする。**インストールは不要**。

- `tools/field-test/Send-ReservationCsv.ps1`（送信）
- `tools/field-test/Inspect-ReservationCsv.ps1`（列の確認・個人情報列の除去。任意）

パスワードは平文で置かず、DPAPIで暗号化して保存する（同じ端末・同じユーザーでしか復号できない）:

```powershell
powershell -ExecutionPolicy Bypass -File C:\hotel-import\Send-ReservationCsv.ps1 `
  -SavePassword -CredentialPath C:\hotel-import\cred.txt
```

## 2. 当日の順序

### フェーズ1: 1サイクルを手で通す

1. 自分のPCのブラウザで TL-リンカーンにログイン（ASP型なのでどこからでも入れる。**正規URLから**入る）。
2. 予約検索画面から直近1か月をCSV出力（**A1**）。
3. 列を確認（**A2** 予約受付日 / **A3** 取消日・ステータス / **A4** 団体区分 / **A6** 販売先 / 室タイプ）。
4. 列マッピングをサーバに登録する（以降、端末はファイルを送るだけになる）:

   ```bash
   curl -X PUT http://localhost:3001/api/v1/import/mapping \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"hotelId":"<hotelId>","source":"tl-lincoln","encoding":"cp932","delimiter":",",
          "mapping":{"checkInDate":"チェックイン","nights":"泊数","rooms":"室数","guests":"人数",
                     "revenue":"合計金額","revenueScope":"per-stay","bookedAt":"予約受付日",
                     "cancelledAt":"取消日","status":"ステータス","cancelStatusValues":["取消"],
                     "channel":"販売先","roomTypeCode":"室タイプコード"}}'
   ```

   手元で列を確かめるだけなら DB 不要のCLIも使える: `pnpm --filter backend import:reservations -- --file ./予約明細.csv --inspect`

5. 端末から **dry-run** で送る（書き込まない疎通確認）:

   ```powershell
   powershell -ExecutionPolicy Bypass -File C:\hotel-import\Send-ReservationCsv.ps1 `
     -Endpoint http://<サーバIP>:3001 -Email import@example.com -CredentialPath C:\hotel-import\cred.txt `
     -HotelId <hotelId> -CsvPath C:\hotel-import\in\予約明細.csv -DryRun
   ```

6. `-DryRun` を外して本番送信。画面でダッシュボード・日別実績・ブッキングカーブが実データになることを確認。

### フェーズ2: 無人で1回動かす（ここが本題）

7. TL-リンカーンの**出力スケジュール機能**の有無を確認（**A11**）。
   - ある場合: 出力先フォルダを `C:\hotel-import\in` に向ける
   - ない場合: 当面は人が出力する運用とし、自動化は構成A（API）かCの判断へ回す
8. 送信をタスクスケジューラに登録する（フォルダ内の最新CSVを送り、成功したら処理済みへ移動）:

   ```
   schtasks /Create /TN "HotelImport" /SC DAILY /ST 06:30 /RL LIMITED /F ^
     /TR "powershell -NoProfile -ExecutionPolicy Bypass -File C:\hotel-import\Send-ReservationCsv.ps1 -Endpoint http://<サーバIP>:3001 -Email import@example.com -CredentialPath C:\hotel-import\cred.txt -HotelId <hotelId> -WatchFolder C:\hotel-import\in -MoveToFolder C:\hotel-import\done"
   ```

9. **その場で1回走らせる**（`schtasks /Run /TN "HotelImport"`）。人が触らずに取込まで届くことを確認する。
   確認するのは3点: タスクの「前回の実行結果」が 0、`logs\send-*.log` に成功行、`GET /api/v1/import/runs?hotelId=` に履歴。
10. 耐性を確認する（無人運用で落ちるのはここ）:
    - 画面ロック／サインアウト状態でも動くか（「ユーザーがログオンしているかどうかに関わらず実行する」の設定可否）
    - スリープ・電源設定（夜間にスリープすると走らない）
    - 端末の再起動後もタスクが残るか
    - プロキシ環境でも `Invoke-RestMethod` が通るか
11. 翌日以降も動く状態にして終わる（タスクを有効のまま残す）。翌朝、`import/runs` と欠損アラートを見て**2日連続で入ったか**を確認する。

### フェーズ3: データの中身を確定（従来のA項目）

12. キャンセルを含む条件で再出力し、取消行が残るか（**A3**）。
13. 出力項目設定で氏名・連絡先を外せるか（**A12**）。外せたらそれを定常の出力とする。
14. 最古の期間を指定して遡及限界（**A5**）。統計データも1種類だけ形を見る。
15. NEHOPS 側で実績・部屋タイプ別・予算の出力範囲と締め時刻（**A9・A10・A11**）。
16. NEHOPS↔TL の連携形態（在庫と料金はどちらが正か、2WAYか片方向か）。価格書き戻しの前提。

## 3. ホテル側に許可をもらう項目

- 業務用PCへのファイル配置とタスクスケジューラ登録（インストールは不要だが、**設定変更にあたる**）
- 端末をスリープさせない設定、または夜間に起きている時間帯の指定
- 端末から送信先（持参PC or クラウド）への通信許可
- 取込用アカウントの発行と、パスワードの受け渡し方法

**許可が取れない場合**: フェーズ1（手動1サイクル）までで切り上げ、常駐は次回に回す。その場合も
「何があれば無人化できるか」を上の10項目の形で持ち帰る。

## 4. 取り扱い

- 操作は**参照とエクスポートに限る**。在庫・料金・プランの更新系は触らない（TL-リンカーンは販売中の在庫と料金を握っている）。
- 認証情報は現地メモやスクリーンショットに残さない。端末のパスワードはDPAPIで暗号化して保存する。
- 個人情報は受領しない設計が最も安全（A12）。氏名・連絡先は出力から外す。
